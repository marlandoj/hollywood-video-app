# HV-032-01 — Give the queue a dead-letter terminus, and bound the two lists that had none

epic: HV-032
spend_usd: 0

## Goal

Stop a job whose worker keeps dying from occupying a project's only concurrency slot for ever, and put a bound on the two unbounded lists inside a stored job body.

**The defect.** `requeueExpired` returned every lapsed-lease job to `queued`, incremented `resumedCount`, appended a notification, and bounded none of it. The retry budget beside it — `retriesUsed` against `retryPolicy.maxRetries` — is consumed **only** by `fail()`, which needs a worker alive enough to report a failure. A job whose worker is OOM-killed, whose host is lost, or which crashes the process reports nothing at all: it stays `running` with a lapsed lease, is recovered, is claimed again, dies again. `resumedCount` was incremented and then read by exactly one place — a graphic-job view that displays it — and compared against nothing.

`TIERS.free.maxConcurrent` is **1**. So the consequence is not untidiness: a single poison job holds a free-tier project's only slot, and every honest job behind it waits for the life of the deployment. No dead-letter state existed anywhere in the codebase; the token appears nowhere in FULL-SCOPE §P15's implementation.

**How this increment was found.** The program-wide re-verification of the pre-loop credit ran one auditor per epic across all 22 epics that had never had the pass `docs/loop/STATUS.md` says the first planner is supposed to run. HV-032 came back `partially-delivered`, with a correction to the board in the *understating* direction — the three-slot fleet, leases with version fences, enqueue-time idempotency and abandoned-lease recovery are all real and tested — and with this as its recommended first increment: *"bound `requeueExpired` so a job whose lease has lapsed more than N times stops at a terminal `failed` state with an explicit dead-letter reason instead of being re-claimed for ever, and bound the `notifications` array the way `recordRouteDecision` already bounds `routeDecisions`."* Verified against the source before any code was written.

## The shape of the repair

**Two budgets, kept separate on purpose.** `MAX_LEASE_RECOVERIES = 5` counts times a job was returned to the queue because its *worker* died. `retryPolicy.maxRetries` counts failures a worker *reported*. Conflating them would mean a job admitted with `maxRetries: 0` — every audio take and every audition, by construction — could never survive a single host restart, and a job with `maxRetries: 2` would get three host restarts for reasons unrelated to the host. They are different failure modes with different operational meanings, and the constant's doc comment says so where an editor will meet it.

**The terminus is a real terminal state, not a skip.** A job past the budget becomes `failed` with `failureKind: "dead_letter"` — an additive second member of a closed set whose only prior value was `"policy_refusal"` — an explicit `failureReason` naming the count, `completedAt` set, `nextEligibleAt` cleared, and no lease or claim. `TERMINAL` already contains `failed`, so `eligibleToStart` refuses it, `requeueExpired` no longer sees it, and `complete()` cannot be called on it. Skipping the job instead would have left it `running` for ever and *still* counted against its project's concurrency.

**`recoverAbandoned` now returns what it touched, not what it resumed.** The PostgreSQL store persists whatever that call returns, so a dead-lettered job that was not returned would have been computed and thrown away, leaving the row `running` in the database and the terminus purely local. The return value is every touched job and the caller reads the status: `job.dead_lettered` or `job.resumed` on the outbox.

**One notify, seven writers.** `notifications` lives inside the stored job body and had seven append sites across two packages, none bounded, while `routeDecisions` beside it has been bounded at 8192 since it was written. There is now one `notify(job, message)` that appends and trims to `MAX_JOB_NOTIFICATIONS = 256`. The oldest entries are dropped rather than the write refused, because these are messages to a person and not evidence — `routeDecisions` throws because it *is* evidence, and that asymmetry is deliberate.

**The seventh writer was a second copy of a whole rule.** `packages/storage/src/ledger.ts` cancels a job for exceeding its cost cap inside its own transaction, and spelled the user-facing sentence out a second time — identical text, in a second file, with nothing holding them equal. `costCapCancelNotice()` is now declared once beside `notify`, and a test scans `packages/*/src/**/*.ts` for the sentence and requires exactly one file to contain it. This is the eighth instance in this program of one rule stated in more than one place.

## Acceptance criteria

1. **A job whose worker keeps dying stops at a dead letter.** Five lapsed leases return it to `queued` with `resumedCount` incrementing, a notification each time, no `failureKind`, and `retriesUsed` untouched. The sixth makes it `failed` with `failureKind: "dead_letter"`, the reason naming the count, `completedAt` set and `nextEligibleAt`, `claimedBy` and `leaseExpiresAt` all null. A later `claimNext` returns nothing and a later `recoverAbandoned` returns nothing. Satisfies FULL-SCOPE §P15 (the "dead-letter" clause, previously absent from the codebase) and ADR-0020 fail-closed.

2. **The terminus releases the project's only concurrency slot.** With a poison job and an honest job queued for the same free-tier project, every pass hands the slot back to the poison job until the terminus; the next claim is the honest job. Before this change that assertion was the poison job for ever. Satisfies FULL-SCOPE §10 "Free and anonymous for every end user" read with AC-025's fair-share intent.

3. **The two budgets are independent.** A job admitted with `maxRetries: 0` still receives the full recovery budget, and a *reported* failure consumes `retriesUsed` while leaving `resumedCount` and `failureKind` alone. Satisfies CLAUDE.md "Every criterion gets a real test."

4. **The notification list is bounded, in one place, for every writer.** A job carrying 300 notifications — a record written before this bound existed — is trimmed to 256 by its next write, keeping the newest and dropping the oldest contiguously.

5. **The cost-cap cancellation notice is declared once.** A scan of every `packages/*/src/**/*.ts` finds the sentence in exactly one file, and `packages/storage/src/ledger.ts` reaches it through the module and no longer appends to `notifications` directly.

6. **Nothing frozen is touched, and no new dependency, vendor, key, route, account, tier, payment path, budget default or migration appears.** `failureKind` gains a member, which is additive on a field no persisted record is validated against outside the queue. `docs/loop/STATUS.md` and `docs/PROGRAM-EXECUTION.md` are not in the diff; RECORD owns both.

## Demonstrated, not asserted

Six perturbations, each applied on this branch, measured against the final test file, and reverted:

| perturbation | result |
|---|---|
| P1 — unbounded requeue, exactly as it shipped | `3 pass / 2 fail` |
| P2 — the terminus sets `failureKind` but not `failed`, so it skips rather than terminates | `4 pass / 1 fail` |
| P3 — the recovery budget is taken from `retryPolicy.maxRetries` | `2 pass / 3 fail` |
| P4 — `notify` appends without trimming | `4 pass / 1 fail` |
| P5 — the PostgreSQL ledger spells the cancel notice out again | `4 pass / 1 fail` |
| P6 — `requeueExpired` returns only resumed jobs, so the PostgreSQL recovery never persists a dead letter | `4 pass / 1 fail` |

P3 is the one worth reading: conflating the two budgets takes three tests down, because a job admitted with `maxRetries: 0` is then dead-lettered on its first host restart. P6 is the shape that would have made the terminus purely local — computed in memory and thrown away, leaving the row `running` in the database for ever.

## What this increment does **not** do

- **It does not fix HV-032's other MAJOR: fair-share weight never decays.** `packages/operator/src/index.ts:89` weights a project by lifetime-cumulative GPU seconds, so an established project is starved indefinitely — the exact opposite of AC-025. That needs a decay window and a decision about its length, and it is HV-032-02.
- **It does not give HV-032 the gap register its two sibling epics have.** HV-038 and HV-040 both wrote down what their pillar does not cover and pointed the remainder at HV-032; HV-032 has never written its own. The audit's fuller recommendation is that it should, and this increment is not that.
- **It delivers no kill switch, no operator lever, no GPU worker, no real job classes, no webhook or polling reconciliation, no network- or session-level fairness, no graded reduced-capacity mode and no public capacity page.** P15 remains largely absent under this epic's own name, and the three clauses that *are* substantially delivered are delivered by HV-038 and HV-040.
- **It does not make `hv_workers.classes` mean anything.** Three advertised job classes are honoured by no worker and consumed by no reader while thirteen job stages are actually claimed. Separate defect, not touched.
- **It chooses 5 rather than deriving the recovery budget from anything.** There is no operational evidence in this repository about how often a worker dies, so 5 is a judgement, stated as one, and exported so a later increment with evidence can move it in one place.
