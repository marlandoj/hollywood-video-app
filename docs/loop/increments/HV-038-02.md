# HV-038-02 — Operator reliability panel (read-only): latency percentiles, failure-rate breakdown, provider circuit health and cost burn
epic: HV-038
spend_usd: 0

## Goal
Close the read-only half of the P15 operator console that HV-038 owns. Today `/api/operator/status` shows queue counts, worker liveness, a 30-day budget line and backup freshness; `/api/operator/metrics` evaluates one fixed PromQL rate expression (`OPERATIONS_QUERY`, `packages/observability/src/explorer.ts`); the `hv.operation.duration` histogram is exported but never read; the router's circuit breaker (`ProviderHealth`, `packages/generator/src/router.ts`) is worker-process state nobody outside the worker can see; failure codes are on spans but not on the counter (`METRIC_KEYS` omits `hv.failure_code`); cost readings have no per-provider or trend view although both ledgers already implement `rollup(period)` with `byProvider`. This increment adds, behind the existing diagnostics token and with no new caller-supplied parameters: (1) a fixed bundle of three additional instant PromQL queries inside `TelemetryExplorer.metrics()` — p50/p95/p99 per operation from the histogram, success/error rate per operation × failure code from the counter, and `provider.attempt` success/error rate per provider category; (2) `hv.failure_code` as a bounded counter/histogram label and wider histogram buckets (top finite bucket 600 s instead of 10 s) so worker-side percentiles are real numbers; (3) a per-provider circuit-health summary written by each worker in its existing 5-second `hv_workers` heartbeat body and read by the API's isolated read-only diagnostics query (the API process never holds router state; the heartbeat is the simplest truthful source and needs no migration); (4) 24 h / 7 d / 30 d cost by provider with totals, daily average and last-day-vs-average from the same diagnostics transaction (PostgreSQL) or `CostLedger.rollup` (JSON); (5) a "Reliability" section in the operator console rendering all of the above next to the existing queue depth/running counts, with `not_configured`, `unavailable` and `available` shown distinctly. No route is added; the two operator data routes gain additive fields. No migration, dependency, budget default, provider, frozen path or `.github/**` change; spend is 0 and providers stay `mock`.

## Acceptance criteria
1. **Latency percentiles per operation come from the existing histogram through a fixed query.** `packages/observability/src/explorer.ts` exports `LATENCY_QUERY`, a single instant PromQL expression that unions `histogram_quantile(0.5|0.95|0.99, sum by (le, hv_operation) (rate(hv_operation_duration_milliseconds_bucket{http_route!~"/api/operator/.*"}[5m])))` under a static `quantile` label (`p50|p95|p99`) via `label_replace`. `metrics()` evaluates it at the same minute-floored `end` as the range query with `timeout=1s` and `limit=30`, and returns `reliability.latency: {operation, p50Ms, p95Ms, p99Ms, capped}[]` where an operation outside `OPERATIONS` or a quantile label outside the three fixed values makes the whole reading `unavailable`, `NaN`/`±Inf` become `null`, duplicate `(operation, quantile)` rows fail closed, and `capped` is true when any quantile is at or above the histogram's top finite boundary. Caller-supplied PromQL, hosts, ranges and limits remain rejected (any query parameter on `/api/operator/metrics` is still 400). Satisfies FULL-SCOPE §3 P15 "Operator console: budgets, provider health, queue depth, failure rates, latency, cost variance …" (latency) and "Observability: … metrics".
2. **Histogram buckets cover real job and provider durations.** `StudioTelemetry` replaces the single `hv.*` view with two views: `hv.operations` (unchanged allow-list processor and 256 cardinality limit) and `hv.operation.duration` with the same processor/limit plus `AggregationType.EXPLICIT_BUCKET_HISTOGRAM` boundaries `[5, 10, 25, 50, 100, 250, 500, 1000, 2500, 5000, 10000, 30000, 60000, 120000, 300000, 600000]` ms. The explorer's `ceilingMs` constant equals 600000 and `docs/OBSERVABILITY.md` states that a quantile at the ceiling is a floor, not a measurement. Satisfies §3 P15 "latency" read with §10 "Evidence before promotion" (a p95 pinned at the 10 s default top bucket is not evidence).
3. **Failure rates are broken down by operation × failure code from the counter, with bounded cardinality.** `METRIC_KEYS` gains `hv.failure_code` (values are the closed `FAILURES` set of eight; it is set only on failed spans, so it multiplies error series only). `FAILURES_QUERY` = `sum by (hv_operation, hv_outcome, hv_failure_code) (rate(hv_operations_total{http_route!~"/api/operator/.*"}[5m])) * 60`, `limit=128`; the parser returns `reliability.failures: {operation, successPerMinute, errorPerMinute, errorRatio, codes}[]` where `codes` maps each `FailureCode` or `"unknown"` (an absent/empty label, i.e. series exported before this release) to a per-minute rate, any other code value fails closed, `errorRatio` is `error / (success + error)` or `null` when the total is 0, and more than 128 rows (or a Prometheus truncation warning) makes the reading `unavailable` rather than partial. `PROVIDER_ATTEMPTS_QUERY` = `sum by (hv_provider, hv_outcome) (rate(hv_operations_total{hv_operation="provider.attempt"}[5m])) * 60`, `limit=8`, returns `reliability.providers: {provider ∈ mock|fal|rich-animatic|other, successPerMinute, errorPerMinute, errorRatio}[]`. `docs/OBSERVABILITY.md` lists `failure code` among the bounded metric labels. Satisfies §3 P15 "failure rates" and "metric labels exclude identifiers" (OBSERVABILITY.md) under ADR-0018 "privacy-preserving abuse controls".
4. **The bundle keeps the one-pending, one-deadline, one-cache rule.** `Backend.read` accepts a list of URLs fetched sequentially under one `AbortController`, one 2-second deadline and one cache entry keyed `"metrics"`; a hang or invalid response in any of the four queries yields `{state: "unavailable", value: null}` with no partial value, a busy slot still fails a different key promptly, a late aborted reply cannot populate the cache, and no second `Backend` instance is created for Prometheus. `/api/operator/metrics` keeps schema `hv-operator-metrics/1` with the additive `reliability` object (`evaluatedAt`, `windowSeconds: 300`, `ceilingMs`, `latency`, `failures`, `providers`). Satisfies OBSERVABILITY.md "Each backend allows one pending request, with a two-second response deadline" and §3 P15 "Observability: … metrics".
5. **Provider circuit health is recorded by the worker that owns it and read without a migration.** `ProviderHealth.summary(entries)` (new method; `observation()` and therefore `RouteRanking`/`RouteDecision` content hashes are unchanged) returns at most 24 rows `{stage, provider, id, state ∈ unknown|closed|open|half-open, consecutiveFailures, samples, latencyMs (null below 3 samples, as today), lastOutcome ∈ success|error|null, observedAt}` using the same 600 s expiry as `observation()`. `runWorker` passes `summary()` over the configured `final`, `animatic` and `character-sheet` pools (keyed by capability revision, `provider = providerKind(snapshot.adapter)`, `id = spec` only when it matches `^[A-Za-z0-9_.:/-]{1,80}$` and contains no `://`, else `null`) to `PostgresWorkerRegistry.heartbeat(state, activeJobId, providers?)`, which stores it as `body.providers` only when its JSON is ≤ 8 KiB. `storageDiagnostics` reads `body->'providers'` of the latest incarnation per name with a heartbeat in the last 45 s (`idle|busy|draining`, ≤ 64 workers) in the same read-only transaction and validates every entry with closed validators in `packages/observability/src/diagnostics.ts` (`providerHealthReadings`), dropping and counting malformed entries instead of blanking the reading. The API process reads nothing from `hv_provider_attempts` (project-scoped RLS). Satisfies §3 P15 "provider health" and "Render farm: … job classes with leases, retries" read with `docs/WORKER-FLEET.md` "A stale heartbeat is not evidence that a process is still alive" (stale rows never contribute).
6. **Cost readings show burn by provider and trend, from the same ledger admission uses.** `DatabaseStatus` gains `costs: {byProvider: {provider, dayUsd, weekUsd, monthUsd, events}[], totals: {dayUsd, weekUsd, monthUsd}, dailyAverageUsd, lastDayVsAverage}` — PostgreSQL: one grouped query over `hv_cost_events` for the trailing 24 h / 7 d / 30 d inside the existing diagnostics transaction (`limit 64` rows, sorted by `monthUsd` descending, at most 16 named providers, the remainder folded into `"other"`, provider names must match `^[a-z0-9][a-z0-9._:-]{0,39}$` or fold into `"other"`); JSON: `CostLedger.rollup("day"|"week"|"month")`. `monthUsd` totals equal `budget.recordedMonthUsd` (same trailing-30-day window). `lastDayVsAverage = dayUsd / (monthUsd / 30)` or `null` when the average is 0. The reading carries no project, job, attempt or request id. Satisfies §3 P15 "cost variance" and "Observability: … cost dashboards" and ADR-0018 "Hosted inference costs remain operator-visible".
7. **`/api/operator/status` exposes the new observations with distinct states.** `OperatorDiagnostics.collect()` adds two top-level observations derived from the single database probe (no new probe, no new pending slot): `providerHealth: {state, observedAt, value}` where `state` is `not_configured` on the `json` backend (no worker registry), otherwise the database probe's state, and `value` is `database.value.providers ?? null`; and `costs: {state, observedAt, value}` from `database.value.costs`. Under an `unavailable` database the last verified values are retained with the old `observedAt`, exactly as `budget` behaves today. The overall `status` derivation is unchanged. Schema stays `hv-operator-status/1` (additive). Satisfies §3 P15 "queue depth" (unchanged reading reused by the panel) and OBSERVABILITY.md "Empty available results and an unconfigured backend are distinct states".
8. **The console renders a read-only Reliability section and states staleness honestly.** `packages/frontend/src/operator.html/.js/.css` add one section with four fixed tables (latency by operation; failure rates by operation with the top codes; provider health per worker/provider with circuit state, consecutive failures, samples, EWMA latency, last outcome, plus attempt rates from metrics; cost by provider with the three windows, totals, daily average and last-day-vs-average) and the queue depth/running figures already loaded. `refresh()` loads `/api/operator/status` then `/api/operator/metrics` sequentially and `refreshAll` awaits `refresh()` before the explorer refresh, so the single Prometheus slot is not raced by the page itself; `not_configured`, `unavailable` (with "previous readings are stale") and `available` are rendered distinctly; no new network destination, cookie, storage or script origin; the CSP is unchanged. Satisfies §3 P15 "Operator console: …" and ADR-0018 (cookie-free, identity-free) and ADR-0020 (private surface only; `/api/operator/*` is not linked from any public page).
9. **The real-backend contract job exercises the new queries.** `scripts/telemetry-explorer-smoke.ts` (not on the frozen list; invoked by the frozen `ci.yml` step as `bun scripts/telemetry-explorer-smoke.ts "$RUNNER_TEMP/telemetry-binaries"`, which is unchanged) gains, inside its existing `until` predicate, the additional conditions that `reading.value.reliability.latency` contains `job.process` with a non-null `p95Ms` and that `reliability.failures` contains `job.process` with `codes.provider > 0`, and prints `latencyOperations` and `failureCodes` in its final JSON line. Because `metrics()` fails closed as a bundle, the job also proves that Prometheus 3.14.0 accepts all three new expressions and the `limit` parameter on instant queries. The `.github/workflows/ci.yml` file is untouched. Satisfies §10 "Evidence before promotion: tests, benchmarks, post-flight evals, gap audits" and the EXECUTION-LOOP frozen list.
10. **No frozen path, dependency, budget default, account, vendor, migration, route or public-surface change.** The diff touches nothing under `docs/legal/**`, `docs/adr/**`, `.github/workflows/**`, `packages/safety/**` or `infra/drizzle/**`; no `package.json`/lockfile entry; no new HTTP route or query parameter; no cookie, storage, tracking or identifier (worker names and pool specs are operator configuration; no project/job/attempt/request ids appear in any new field); `packages/observability/src/logs.ts` is not modified; the diagnostics token is required before any probe or explorer is initialized (existing tests re-run against the new fields). Satisfies §10 "Free and anonymous for every end user; no billing code reachable.", CLAUDE.md "Never add keys, accounts, or vendors" and ADR-0020 fail-closed launch.
