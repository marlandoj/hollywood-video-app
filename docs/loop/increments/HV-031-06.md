# HV-031-06 — Refuse at the mint what the import refuses

epic: HV-031
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

This is a regression **this loop introduced today**, in HV-031-05, found by a critic pass over the
planner the same evening.

`createActorShare` carries a rule in its own comment:

> Refuse at the mint what the import would refuse. A share is immutable and lives seven days; one
> that cannot be imported is not a share, and the owner is the only person who can do anything
> about it.

And four lines below it, another:

> Counting is not validating. The name is safe because this module builds it; the *description* is
> copied straight from the wardrobe entry and was checked by nobody until the import — the same
> permanent, collective failure one field over.

HV-031-05 taught `importedActor` to read every free-text field of the record it saves, **costume
preset names included** (`castRecordText`). It did not teach the mint the same question. So the
name — which "is safe because this module builds it" — stopped being safe, because this module
builds it out of a screenplay scene heading:

```ts
name: costumePresetName(value.sceneNumber!, character.sceneBindings.find(…)?.heading)
```

Scene headings are written verbatim from the screenplay, `PUT /script` gates nothing about them,
and a cast record's own save never reads `sceneBindings` — so an owner whose screenplay has a scene
headed `INT. TAYLOR SWIFT'S DRESSING ROOM - NIGHT`, with a wardrobe entry for that scene, could:

1. save the cast record — accepted, and correctly, because the record is clean;
2. mint a share — **201**, with a link they send out;
3. watch every recipient get **400, "This cast record names a public figure"** — about a record that
   is clean, for the whole seven-day immutable life of the share, with nothing they can do to it.

Exhibited end to end through the real server:

```
script PUT:  200
cast save:   200
share mint:  201
import:      400 {"error":"This cast record names a public figure. …"}
preset name the share carries: "Scene 2 — INT. TAYLOR SWIFT'S DRESSING ROOM - NIGHT"
```

The safety refusal itself is right. What was wrong is *where* it lands: on a stranger, about
something the owner could have fixed, after the only moment at which fixing it was possible.

## What this increment does

- **The mint asks what the import asks**, over everything the mint contributes: the record's own
  twelve text fields and aliases, the wardrobe it carries, and the presets it derives from the scene
  bindings. It is the same function — `castRecordText` — so the two cannot disagree about which
  fields count. Only the importer's chosen `name` and `aliases` cannot be known here, and
  `importedActor` still reads the whole record at the border.
- **The refusal says what to do about it**, and says it to the person who can: rename the scene or
  remove that scene's wardrobe, then share again.
- **The import's own check stays**, and its test now builds a share the way `createActorShare`
  builds one *minus the checks it did not yet have* — which is exactly what a share minted before
  the public-figure list grew looks like. A share already in the world cannot be re-minted, so the
  import is what stands between it and a new project. That is the case the border check exists for,
  and it is the case it is now tested on.

## Acceptance criteria

1. **A scene heading naming a public figure is refused at the mint**, and the message tells the
   owner to rename the scene.
2. **A wardrobe description is refused the same way**, which is the same question one field over.
3. **The record itself still saves**, because it is clean — a scene binding is none of the fields a
   record's own save reads, and this increment does not change that.
4. **A clean actor still shares, and what it shares still imports**, with its presets and their
   heading-derived names intact.
5. **Whatever the mint accepts, the import takes** — asserted over the pair rather than over one
   example, so a future field that one reads and the other does not fails here.
6. **A share minted before the list grew is still refused at import**, with the refusal naming the
   record, which is all the import can say about a share it cannot re-mint.
7. Reverting `actor-library.ts` makes 1, 2 and 5 fail.

- Tests: `packages/planner/test/consented-casting.test.ts`.

## Known gaps this leaves

- **Nothing re-checks a share that is already live.** A share minted before this increment, or
  before the list grew, still refuses at every import for the rest of its seven days and the owner
  is still not told. Revoking it is possible; knowing to is not. A listing that showed an owner
  which of their shares can no longer be imported would close that, and it is a route and a view
  rather than a validator.
- **The screenplay is still not gated on scene headings**, and should not be: a heading is the
  writer's text, and refusing a screenplay because of one would refuse the film rather than the
  share. What this increment establishes is that the *derived* text is checked where it is derived.
- **`costumePresetName` still truncates**, and a heading long enough to be clamped could in
  principle be clamped *into* or *out of* a listed name. The clamp is at 1,100 characters and the
  longest reachable name is 1,013, so it cannot fire today — which is what the comment beside it
  already says, and it is why this is a note rather than a change.
- **This was a regression one increment old.** It was found by a critic pass on the same evening,
  which is the argument for running them; it was not found by the increment's own tests, which is
  the argument against trusting those alone when a change adds a check on one side of a pair.
