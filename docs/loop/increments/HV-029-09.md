# HV-029-09 — Retention removed the film and kept the review link

epic: HV-029
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

`sweepExpired` and `takedown` each emptied one map:

```ts
for (const [id, project] of this.projects) {
  if (new Date(project.deleteAfter).getTime() <= now) { this.projects.delete(id); removed.push(id); }
}
```

`reviewLinks` is the only other map this state keys by project, and nothing in the file ever removed
an entry from it — `grep reviewLinks packages/api/src/index.ts` gives `set`, `get`, and a `clear` on
reload. `snapshot()` then wrote every dead project's links back on the next `persist()`.

So after day thirty the project record and `artifacts/<projectId>/` were gone and
`state/projects.json` still held, indefinitely, every `ReviewLink` that film had ever minted: the
review **token**, a bearer capability valid for up to seven more days; `decisionNote`, up to 2,000
characters the reviewer typed; the `outputBinding`; and the viewer hashes. The same was true of a
takedown, where the operator's intent is that the content is gone.

`scripts/sweep-expired.ts` is the retention loop for this backend, and its own comment says
*"Retention is only real if both halves expire."* FR-057's promise that anonymous project data
auto-deletes after thirty days was kept on PostgreSQL —
`PostgresRetention.purgeProject` runs `delete from hv_reviews where project_id = …`, alongside
`hv_operator_reviews`, `hv_outbox`, `hv_artifacts` and `hv_archives` — and not on the default
backend. That divergence is exactly why it went unseen: retention is tested where it works.

Nothing caught it because `api.test.ts`'s only sweep case asserts the returned id array and nothing
else and never mints a link, and `review-views.test.ts` reads links out of the state file but never
sweeps or takes down.

## What this increment does

- **One `forget(projectId)` removes everything this state holds about a project**, and both callers
  go through it. `projects` and `reviewLinks` are the two collections keyed by a project;
  `takenDown` and `takedownLog` are the record of the removal and stay.
- **Asserted on disk, not only in memory**: the tests read `state/projects.json` back and open the
  swept film's token with a fresh `ProjectService`, because the defect was in what was persisted.

## Acceptance criteria

1. **A swept project takes its review links with it**, in the file and in a service that reloads it:
   the dead film's token opens nothing, and another film's link — still inside its own seven days —
   still does.
2. **So does a taken-down one**, and the tombstone and the operator's log survive it, because they
   are the record of the removal rather than the thing removed.
3. **Nothing this state keys by project outlives the project**: `PersistedState`'s collections are
   enumerated by name, one place removes a project, and both callers go through it.
4. Reverting `packages/api/src/index.ts` fails all three.

- Tests: `packages/api/test/retention-review-links.test.ts`. Verified: all three fail on the
  unchanged source.

## Known gaps this leaves

- **Retention on this backend is still a single sweep with no audit of what it removed.**
  `sweepExpired` returns the project ids and says nothing about the links; the PostgreSQL path
  records a purge. An operator has no way to check afterwards that a specific link is gone other than
  by reading the file.
- **A link minted after a takedown is still possible in principle.** `createReviewLink` authorizes
  through `authorize`, which fails for a removed project, so it cannot happen today — but nothing
  asserts that, and the tombstone is not consulted at mint.
- **The two backends still say retention differently.** One deletes five tables in a transaction and
  keeps financial receipts; the other deletes two maps and rewrites a file. Nothing compares them, and
  this increment closed one difference of what may be several.
- **Nothing expires `takedownLog`.** It is meant to be permanent, and it holds a project id and the
  operator's reason for ever; whether that is the right retention for an operator's own record is a
  question nobody has asked here.
