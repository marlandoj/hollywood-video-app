# HV-029-08 — A review link that could not be withdrawn, handing out URLs that outlived it

epic: HV-029
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

A critic pass over the API's anonymous surface.

A review link is this studio's whole answer to *"show someone my film without making them an
account"*. It lives seven days (`REVIEW_TOKEN_TTL_MS`) and admits a named number of viewers
(`maxViews`, default 3). Three things were wrong with what that promise actually bought.

### It could not be revoked

`ProjectService.revokeReviewLink` (`index.ts:1037`) and `PostgresProjectService.revokeReviewLink`
(`storage/src/projects.ts:282`) have both existed, and been unit-tested, since review links did —
`api.test.ts`, `review-binding.test.ts` and `postgres.test.ts` all call them. Neither had a route.
`server.ts` had exactly three: create, open, decide. `studio.js` only creates.

```
owner tries to revoke the link (DELETE)   -> 404
owner tries POST .../revoke               -> 400
owner tries to LIST their links (GET)     -> 404
```

Every refusal string in the read path says *"invalid, expired, revoked, or fully used"* — naming a
state no caller could reach.

### The viewer's media URLs outlived the link by twenty-three days

`signedOutput` mints them with `artifactLinkExpiry`, which clamps to the job's own thirty days
(FR-040) and the project's `deleteAfter`. It knew nothing about the review token's seven.

```
link minted with maxViews=1; review token expires in 7.00 days
the ONE admitted viewer received: mp4Url, hlsUrl, captionsUrl, manifestUrl
   its artifact token expires in: 30.00 days
a 2nd viewer on the spent link -> 403 {"error":"...fully used"}
but the URL viewer #1 can paste anywhere, fetched with NO review token
and NO viewer header -> 200   ...and again, x5: 200,200,200,200,200
```

So "three viewers" bought three *first* views. What each of them walked away with was an
unauthenticated media URL good for the rest of the month — and, with no revoke route, nothing the
owner could do about it even in principle.

### And the one anonymous route was the one route with no cache directive

About thirty owner routes send `"cache-control": "private, no-store"`. The review GET sent none.
Observed headers: `access-control-allow-origin`, `access-control-expose-headers`, `content-length`,
`content-type`, `date`, `vary: Origin`. A shared cache therefore applies heuristic freshness to a
body carrying the signed media URLs and the `projectId` — and replays it **without reaching the
origin**, so **without counting a view**, which is the bound the whole link is built on. The two
responses that mint tokens — the project's own bearer token and the review token — were bare too.

## What this increment does

- **`DELETE /api/projects/:id/reviews/:token`** wires the route that was missing to the method that
  was already there. The owner's token authorizes it, another project's owner gets a 401, and a
  token this project never issued gets a 404 rather than a silent success.
- **`artifactLinkExpiry` takes a further cap**, and the review route passes the link's own
  expiry — which `openReviewLink` now returns, from the payload it already verifies. The owner's own
  URLs are untouched: the cap applies where the link is what granted the access.
- **Three responses say `private, no-store`**: the review GET, the review-link mint, and the project
  creation. A response that carries a token or a signed URL is never a cacheable one.

## Acceptance criteria

1. **An owner can withdraw a link they have shared, and only their own**: a 200 and `{revoked:
   true}`, the link refused afterwards, another owner's attempt refused with 401 and their link
   still working, an unknown token a 404, and revoking twice still leaving it revoked.
2. **The media URLs a viewer is given last as long as the link, not as long as the film**: seven
   days rather than thirty, fetched and served while they last, and the owner's own view of the same
   cut still thirty.
3. **No response that carries a token or a signed URL invites a shared cache to keep it** — the two
   mints and the anonymous read, all `private, no-store`.
4. Reverting `server.ts` and `index.ts` makes all three fail.

- Tests: `packages/api/test/review-link-life.test.ts`.

## Known gaps this leaves

- **Revoking does not reach a URL already handed out.** It stops the link; the media token a viewer
  already holds is signed against the project and the job, not against the link, so it keeps working
  until it expires — now in days rather than weeks, which is the whole improvement. Making
  revocation reach it means binding the artifact token to the review link and checking that link on
  every `/artifacts/` fetch, which is a second read on the hottest anonymous route and belongs with
  the cost work in HV-038-07's gap list, not here.
- **There is still no way to list a project's links.** An owner can revoke one they have in hand and
  cannot see what they have issued. That is a route and a view, and the frontend has neither.
- **The frontend does not offer it.** `studio.js` creates a link and shows the URL; nothing draws a
  revoke control. This increment makes it possible, not visible.
- **`/artifacts/` media still carries no `nosniff` and no CSP**, unlike the graphic and delivery
  routes. `CONTENT_TYPES` holds no executable type and unknown extensions fall back to
  `application/octet-stream`, so the same pass could not construct an execution — hygiene, recorded
  rather than fixed.
- **Nothing was swept for other bare responses.** Three were fixed because they carry a token or a
  signed URL; the rest of the route table was not audited, and a guard that asserted every response
  carrying either says `no-store` would be the structural version of this.
