# HV-034-01 — a share that no one could ever import

epic: HV-034
spend_usd: 0

## Goal

Stop one screenplay scene heading making an actor share permanently unimportable for everyone, and stop a share being minted whose presets the import would refuse. Build the preset name in one place, used by both sides, so the share and the import cannot disagree about what a name is.

## The defect

`importedActor` built each imported scene-bound costume preset's name by concatenating a screenplay heading straight in:

```ts
name:"Scene "+value.sceneNumber+" — "+(share.character.sceneBindings.find(b=>b.sceneNumber===value.sceneNumber)?.heading??"Shared costume")
```

A heading is validated on the way in only for being a string of at most 1000 characters — `characterRecord` checks nothing about its content. The preset name is validated on the way back out by `text(preset.name,"Costume preset",1100,true)`, which refuses control characters and, because the clause is `text(...)!==preset.name`, also requires the value to equal its own trim.

A **forced Fountain heading** — one starting with `.`, the route any heading takes that is not a recognised `INT.`/`EXT.` form — carries whatever it contains through the parser into `sceneBindings`, control characters included. Measured, not assumed: a script containing a forced heading whose text is `BELL` + U+0007 + ` RINGS` produces `sceneBindings: [{sceneNumber: 2, heading: "BELL\u0007 RINGS"}]`.

**The failure is permanent and collective.** `createActorShare` never runs the import-side construction, so the share mints cleanly; it is revision-hashed and immutable (`"The saved actor share changed."`), so no one can repair it; and every import attempt by every recipient fails identically for its whole seven-day life. The owner's only recourse is to mint a new share — which the message does not say, because it blames the one thing that was never wrong:

> Costume preset must be text up to 1100 characters.

**The length was never reachable.** `"Scene "` (6) + a scene number (≤4) + `" — "` (3) + a heading (≤1000) = at most **1013**, comfortably inside 1100. The audit's account of this defect named a growing `"Copy of "` prefix and a length overflow; neither exists. The mechanism is the charset, and a second one below is the count.

**The count cap had the same shape.** `if(unique.length>48)` was checked only by the import, so a character carrying more presets than a share can hand over was shared anyway and refused on arrival — with a message addressed to the one person who cannot act on it, since the owner is not the importer. A character reaches that many only by carrying imported presets of its own (wardrobe alone caps at 24), which is exactly what re-sharing an imported actor does.

## The shape of the repair

**One builder, used by both sides.** `sharedCostumePresets(character)` is the preset list an import derives from a share. `createActorShare` calls it to refuse a share whose presets could not be imported; `importedActor` calls it to build them. A share that mints is importable by construction, rather than by two pieces of code agreeing — which is this program's recurring defect, and here it had already cost a permanently broken artefact.

**And the mint asks the validator rather than counting.** `assertCostumePresets` is the clause `characterRecord` already enforced, lifted out of it and exported, so the side that *builds* presets can ask the side that reads them back. Counting was not enough: the name is safe because this module builds it, but the **description** is copied straight from the wardrobe entry and was checked by nobody until the import — the same permanent, collective failure one field over, which the first draft of this increment left open. Today the two limits happen to agree (`text(entry.description,"Wardrobe",600,true)` in, 600 out), so it is not reachable through the service; widen either number and it is.

**`costumePresetName(sceneNumber, heading)` builds the name so the validator that reads it back can accept it:** DEL and every code point below 32 removed **except tab, newline and carriage return, which become a space**. Those three are what `text()` allows, so a heading of `HALL<TAB>DAY` imported fine before this increment and must not silently become `HALLDAY`. Then trimmed, and clamped to `COSTUME_PRESET_NAME_LIMIT` by code point so a clamp can never cut an astral character in half. A heading with no readable text left falls back to `Shared costume`, the same label an unbound wardrobe entry already got, rather than producing `Scene 2 — `.

**The refusal moved to the mint and says what to do.** "This actor has *n* costume presets, more than the 48 a share carries. Remove unused presets before sharing." — addressed to the owner, who is the person holding the tool.

## Declared changes beyond the defect

- **Imported preset names change for headings that contained control characters.** There is no migration: names already stored in an imported character are untouched, and a share carrying such a heading was never importable, so no existing imported name can have come from one.
- **`COSTUME_PRESET_LIMIT` and `COSTUME_PRESET_NAME_LIMIT` are new exports.** The numbers are unchanged; a case reads both back out of `casting.ts`'s validator rather than restating them.

## What this increment does not do

- **It does not validate scene headings themselves.** `characterRecord` still accepts any 1000-character string as a `sceneBindings` heading, and the parser still passes a forced heading through unchanged. Sanitising at the source would be the deeper fix and would touch every consumer of a heading — the direction panel, the sheet labels, the performance memory's staleness check, which compares headings for equality. This increment makes the *preset name* safe to build from any heading; it leaves the heading alone.
- **It does not repair shares already minted.** A share created before this change with a control-character heading is still unimportable, because it is immutable by design and its revision covers the character. Its seven-day life expires on its own; the owner can mint a new one, and now that one works.
- **The length clamp is unreachable today and is kept anyway.** A heading caps at 1000 and a scene number at 1000, so the longest name is 1013 of 1100; the clamp's only exercise is a direct call. It stays because it is what makes that arithmetic not need to be true.
- **It does not address the audit's account of this defect, which was wrong in its mechanism.** No `"Copy of "` prefix exists, no suffix grows, and the length cap is unreachable. That is recorded here rather than quietly corrected, because the next person reading the audit will find the same sentence. The audit's "or one ending in a space" is wrong too: the parser trims a heading before storing it, so no parser-produced heading ends in whitespace.
- **It does not examine the other paths that concatenate untrusted text into a validated field.** The scan in case 6 is scoped to this name's shape in `packages/planner/src`. The pattern — build a value in one place, validate it more strictly in another — is the family, and nothing here looks for it elsewhere.
- **`importedActor`'s own count refusal is now unreachable for shares minted after this change**, and is kept for the ones minted before it. Nothing tests that path, because reaching it means constructing a share this build will not mint.

## Acceptance criteria

1. A share whose scene heading carries a control character mints and imports, the preset name carries the heading's readable text with the control character gone, and the imported character round-trips through the validator that used to refuse it. — `packages/planner/test/actor-share-presets.test.ts` case 1; Z1, Z3.
2. Seven heading shapes — a control character, several, a DEL, nothing but control characters, a thousand characters, non-latin text, an ordinary heading — all produce a name that is trimmed, control-free, within the limit, and accepted by `characterRecord`; and an empty label still names the scene. — case 2; Z1, Z2, Z3, Z4, Z5.
3. A character with more presets than a share carries is refused at the **mint**, with a message naming the count and addressed to the owner; one fewer mints, imports and lands inside the cap. — case 3; Z6, Z10.
4. The sanitiser is the validator's charset rather than samples of it: every code point below 32 and DEL is exercised, tab/newline/carriage return become a space because the validator allows them, and every result satisfies the clause that reads it back. — case 4; Z9.
5. A preset the import would refuse does not mint either — an over-long wardrobe description and an over-long carried preset both refused, one exactly at the limit accepted. — case 5; Z8, Z11.
6. The name is built in one place, in any spelling: `costumePresetName` is the only site in `packages/planner/src` matching `Scene … —`, `importedActor` builds no name of its own, the mint goes through the same builder, and the three limits are the validator's own constants rather than literals restated beside them. — case 6; Z7, Z10, Z11.

## The critic's findings

An adversarial read found four green defects and three claims the code did not support.

1. **Z8 — the mint counted and called it validating.** "Importable by construction" was false: `createActorShare` compared a length and never ran the clause the import would. The name was safe only because this module builds it; the description is copied verbatim from the wardrobe entry, and the two limits agreeing today is a coincidence of two literals, not a rule. `assertCostumePresets` is now exported from `casting.ts` and asked by both sides, and case 5 constructs the disagreement a future edit to either number would create.
2. **Z9 — the sanitiser's charset was pinned by four samples.** `![1,7,31,127].includes(code)` passed the whole suite, and a heading carrying U+0008 reintroduced the defect byte for byte. Case 4 now exercises every code point below 32 plus DEL, and asserts the result against the validator rather than against an expected string alone.
3. **Z10 — only the import side of "one builder" was scanned.** The mint could stop calling `sharedCostumePresets` and count a list of its own with everything green. Case 6 now reads the mint's body too.
4. **The scan matched one spelling of the em dash** — and broke the moment the builder was written with a `\u2014` escape, which is how it was found. It now matches any spelling and is exercised against a template literal, single quotes and an array join.

Three claims were corrected rather than argued: **tab, newline and carriage return were being deleted**, which silently turned `HALL<TAB>DAY` into `HALLDAY` for a share that used to import fine — they become a space now, and the doc no longer says every affected name was one that could never be imported; the JSDoc's **"or one ending in a space"** is unreachable, because the parser trims a heading before storing it; and the **length clamp is dead code** on every real path, kept deliberately and now labelled as such.
