# HV-031-12 — Expiry is recorded as expiry, not as a takedown

epic: HV-031
release: 2 "Voice and crew depth"
gate: G4 (migration), approved by Kevin 2026-09-30, recorded as G15 in docs/loop/HUMAN-GATES.md
spend_usd: 0

## Why

The PostgreSQL retention sweeper purged a project whose 30-day retention had ended by setting
`taken_down_at` to the sweep time and `takedown_reason` to "content removed". Nobody took the
project down: `taken_down_at` was simply the only "this project is gone" marker the schema had, and
26 queries used it that way. So the record said a project was taken down when it had only expired,
and every rollback export repeated it (HV-031-03 pinned this as a failing expectation to change).
Two things kept it that way: an empty purged row with no marker would read as a live project, and
the billing records that outlive a purge must point at a project or a tombstone in a snapshot.

## What this increment does

- **Migration 0019** adds `hv_projects.expired_at`. Additive only; no existing row is changed.
- **The sweeper** sets `expired_at` and `purged_at` for an expiry, and leaves the takedown columns
  empty. A takedown's purge is unchanged, including HV-031-03's preserved date and reason.
- **"Gone" means taken down or expired** in every storage query (26 SQL guards), the generation
  ledger's permission checks, the actor-share import and `scripts/storage-owner-link.ts`.
- **`PostgresProjectService`** reads an expired row as no project and never writes to it — the
  write-back would otherwise have deleted the row that records the expiry.
- **Whole-state snapshots, schema 17:** `projects.expired: [{projectId, at}]`, validated (shape,
  uniqueness, not live, not taken down, not in the future). Audio and lip-sync attempts may name an
  expired project. Export and restore carry it; a state with no expiry record keeps its schema.
  Every schema list that accepted /16 accepts /17; `hv-state/18` is now the unsupported probe.
- **Archives** refuse /17 in both packagers: a one-project archive never carries an expiry record.
- **The file store** (`ProjectService.sweepExpired`) records `expired` the same way.
- **Existing mislabelled rows are flagged, not rewritten:** `scripts/report-expiry-takedowns.ts`
  lists them read-only (`findSweeperStampedTakedowns`). The rule is the old sweeper's signature:
  `takedown_reason = 'content removed' and purged_at = taken_down_at and expired_at is null`.
  Correcting them rewrites the record and is a separate operator decision (G8-class).

## Acceptance criteria

1. An expired project's purge leaves `taken_down_at` and `takedown_reason` null and sets
   `expired_at`; the export reports it in `projects.expired` at schema 17, not as a takedown.
2. A restore of an expiry record writes a purged row with no takedown; the next export matches.
3. After expiry the owner's token authorizes nothing, and a write leaves the row in place.
   Removing the new guard in `PostgresProjectService` fails this (checked).
4. The validator refuses an expiry record below schema 17, a malformed or future-dated one, a
   duplicate, and one naming a live or taken-down project.
5. The file store records a sweep as expired, never taken down, and omits the field when empty.
6. The report lists only the old sweeper's stamp, not a real takedown with the same reason, and
   changes no row.

- Tests: `packages/storage/test/project-expiry.test.ts` (new),
  `packages/storage/test/takedown-record.test.ts` (the pinned case flipped), and the /17 → /18
  probes in `archive-schema.test.ts`, `snapshots.test.ts`, the golden `rejections.json` and
  `scripts/test_archive_package.py`.
- Run locally against a disposable PostgreSQL 15 (port 55433, CI fixture credentials), never the
  staging cluster.

## Known gaps this leaves

- **Staging's existing stamped rows stay as they are** until an operator decides to correct them.
  Run the report after the deploy to see how many there are.
- **No audio or lip-sync fixture test for an expired project's attempt:** the validator change is
  one clause beside the takedown clause, and is covered by review, not by a fixture.
- **The migration is applied by the next deploy** (`deploy-storage-staging.py` runs migrations).
