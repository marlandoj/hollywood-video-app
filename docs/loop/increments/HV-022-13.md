# HV-022-13 — The two warnings on the voice vendor's line that nothing could raise

epic: HV-022
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

A critic pass over `packages/operator`.

HV-022-08 gave ElevenLabs its own budget line, at the operator's gate G14-202609210000: a ceiling of
**$25** and alerts at **$5 and $15**. The module says so in its first paragraph, the constant is
frozen, and both halves are implemented:

```ts
export const VOICE_VENDOR_ALERTS_USD: readonly number[] = Object.freeze([5, 15]);
export function assertVoiceVendorBudget(spend: VoiceVendorSpend, requestUsd: number): void { … }
/** The alerts this take crosses, given what was already committed. The caller raises them. */
export function voiceVendorAlerts(committedUsd: number, requestUsd: number): number[] { … }
```

"The caller raises them." There was no caller:

```
$ grep -rn "voiceVendorAlerts" --include=*.ts . \
    | grep -v operator/src/voice-vendor-budget.ts | grep -v operator/test/
(no output)
```

`admitAudio` is the one place a take is charged against that line, and at `audio-ledger.ts:104` it
already holds **both operands**: `await this.voiceVendorSpend(policy.provider, tx)` — the committed
total — and `policy.heldUsd` — the request. It passes them to `assertVoiceVendorBudget` and stops.
So the only signal the operator ever got from this line was the hard refusal at $25, which is
exactly the thing the two warnings exist to arrive before. The function was written, exported,
documented, unit-tested against six cases, and dead.

The crew's line, one epic over, does it properly: `runReadThrough` returns `crewSpend.alerts` and
the route raises each one as `logger.warn("crew.budget_alert", …)` (`server.ts:1588`, `:1637`).

## What this increment does

- **The alerts are computed where the ceiling is checked**, from the same figures, inside the same
  transaction and the same row set — so the total an alert names is the total a refusal would have
  named, and the two cannot disagree.
- **They are raised after the admission commits**, never inside it. A transaction that rolls back
  raises nothing, and an alert is therefore always about money the studio has actually committed.
  An idempotent replay returns before the vendor block is reached, so it raises nothing either.
- **`PostgresAudioLedger.onVendorAlert`** is the seam. The studio sets it to
  `logger.warn("voice.budget_alert", …)`, beside the crew's, and `voice.budget_alert` joins the
  log's closed event set — which is the set that decides what an operator's console can show.
- **A guard sits in the file the dead function lived in.** Every assertion in
  `voice-vendor-budget.test.ts` passed on the day these alerts were written and every day since,
  while nothing read them. The new one asserts that something does: that `audio-ledger.ts` calls
  `voiceVendorAlerts` and exposes `onVendorAlert`, that `server.ts` raises the event, that the event
  name is admitted by the log's own set, and that the thresholds are still the two the operator
  approved.

Nothing about what is refused changes. The ceiling, the operands and the epsilon are untouched, and
no new spend is possible: this increment only adds a warning to a line that already had a wall.

## Acceptance criteria

1. **The warnings reach the operator, once each, for money actually committed** — takes admitted
   $0.25 at a time until the line passes $15, with `raised.map(a => a.thresholdUsd)` equal to
   `[5, 15]` exactly, each naming the vendor, and each naming a total that is at its threshold and
   within one take of it, so it is the take that crossed rather than one some way past.
2. **An idempotent replay is not a second commitment**, so not a second alert.
3. **A refused take crosses nothing**, because the ceiling is checked before the alert is computed
   and the alert is raised only after the admission commits.
4. **Something reads what this line computes**: `voiceVendorAlerts` is called from the ledger,
   `onVendorAlert` is set by the studio, the event is in the log's closed set, and the thresholds
   are `[5, 15]`.
5. Reverting the three source files makes 4 fail, and 1–3 unreachable.

- Tests: `packages/storage/test/audio-jobs.test.ts` (1–3, PostgreSQL),
  `packages/operator/test/voice-vendor-budget.test.ts` (4).

## Known gaps this leaves

- **1–3 run only in CI.** They need PostgreSQL and the S3 fleet bucket, so they skip in this
  container and CI's run on the exact head is what says they pass. Criterion 4 is the part that can
  be run anywhere, and it is the part that would have caught the original defect.
- **The alert is a log line, not a stop.** An operator who is not reading the logs learns nothing
  until the refusal, exactly as with the crew's. Whether $5 and $15 should also reach the operator
  console's diagnostics — which is a surface, not a threshold — is a decision for the operator.
- **`admitLipSync` has no vendor line at all.** Lip-sync has its own policy and its own hold, and
  nothing in `voice-vendor-budget.ts` is asked about it. That is a gap in HV-022-08's scope rather
  than in its wiring, and it needs the operator to say what that line is before code can hold it to
  it.
- **The same dead-code shape is not swept for.** This was found by reading; nothing asserts in
  general that an exported guard has a caller. A lint rule for unexported-but-unused would not have
  caught it, because the function is exported and is used — by its own test.
