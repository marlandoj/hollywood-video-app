# HV-039-21 — The accessibility audit, and the checkboxes and focus rings it found below the bar

epic: HV-039
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

HV-039 promises WCAG 2.2 AA across the whole app. Twenty increments fixed what critics found one at
a time, and nothing yet said, criterion by criterion and panel by panel, where the app stands. This
increment adds that audit, `docs/ACCESSIBILITY-AUDIT.md`: 15 criteria across 15 panels, each cell
pass, fail or not verifiable from code, with file and line. It also fixes the two findings that live
in the creator UI's one stylesheet.

**Checkboxes at 13 pixels (2.5.8).** Seven panels size their checkboxes at 44px, one rule each:

    .dialogue-workbench input[type=checkbox] { width: 44px; height: 44px; }   // index.html:105, and six more

Everywhere else a checkbox is the browser's own 13×13 square. That covers:

- the Advanced switch in the page header and the screenplay rights box;
- the studio front door's rights and cast consent boxes;
- every consent, grant and view box on the cast desk;
- shot direction's coverage flags and frame-anchor attestations;
- the shared-actor import.

A target under 24px passes only through the spacing exception. Whether the exception holds depends
on the layout around each box, and nobody has measured it.

**Selects and headings with the browser's focus ring (2.4.7).** The product's ring (3px `--accent`,
offset 3px) was on `textarea`, `button`, `a`, `input` and `summary`. For `select` it was declared
only inside the cast, direction and dialogue panels and the dialogue-revision studio:

    textarea:focus-visible, button:focus-visible, a:focus-visible, input:focus-visible { ... }   // index.html:46

A `select` in the sound session, picture editorial, the assembly studio or the graphics desk fell
back to the browser's default ring. So did every heading that HV-039-04 to -17 move focus to
(`tabIndex = -1` in nine modules). That ring differs by browser, and nothing holds it to 3:1 on this
dark palette.

## What this increment does

- **Adds the audit.** `docs/ACCESSIBILITY-AUDIT.md` records how each cell was decided: computed
  contrast, a cascade resolver, a label check over the 3,933 controls the test suite mounts, and a
  handler scan. It lists the failures and the cells no code check can settle (first audit: 6 and
  21; re-checked after HV-039-22, HV-039-23 and HV-029-15 merged: 3 and 24), which increments fix
  which cells, and what still needs a person with a screen reader. The re-check covers HV-029-15's
  review comments.
- **No checkbox or radio renders under 24×24.** One rule,
  `input[type=checkbox], input[type=radio] { min-width: 24px; min-height: 24px; }`. A minimum only
  raises a size, so the panels that draw 44px keep 44px.
- **`select`, `video`, `audio` and `[tabindex]` get the product's focus ring** in every panel. The
  selectors join the existing rule, so there is still one declaration of the ring. `video` is the
  export player a review comment's timecode focuses (HV-029-15).
- `contrast.test.ts` counts one more operable rule (79, after HV-029-15's two). The new rule is one
  it checks.

## Acceptance criteria

1. **Every checkbox is at least 24×24.** Resolving the cascade for a checkbox where each panel draws
   one (the header, the screenplay form, the studio, the cast desk, shot direction, frame anchors,
   scene cuts, performances, the shared-actor import, and the seven sized panels) gives at least 24
   by 24. A radio outside a sized panel is also 24. The sound session's checkbox stays 44.
2. **The size is measured, not agreed.** A later, more specific rule that draws a checkbox at 16px
   is still raised to 24. Without the minimum, the studio's rights box resolves to the browser's 13.
3. **The ring is everywhere.** Every focusable kind in the creator UI draws a solid ring of at least
   2px in keyboard focus, in a token of at least 3:1 on `--bg` and `--surface`. That includes a
   `select` in each of nine panels, the focus-return headings of the studio and the cast desk, the
   mask viewport, the review comment box's textarea and button, a comment's timecode button, the
   export player it focuses, and a sound preview's `audio`.
4. **The ring shows focus.** None of those elements draws an outline when not focused.
5. **The operator console is unchanged.** It still draws a 3px solid ring on every element it makes
   focusable.
6. The resolver follows specificity, source order and `!important`, checked against rules whose
   outcome is known.
7. Reverting `index.html` fails criteria 1, 2, 3 and 6. Criterion 6 fails because it reads the new
   minimum.

- Tests: `packages/frontend/test/focus-target.test.ts`. It parses both stylesheets, `@media` blocks
  included, matches selectors against elements described as the modules build them, and takes the
  winner by specificity and order. An unknown selector fails the test rather than being skipped.
  `packages/frontend/test/contrast.test.ts` has its count updated.

## Known gaps this leaves

- **Sizes are resolved, not laid out.** The test knows the browsers' 13px default and treats a
  width of 100% as wide enough. It does not render, so a checkbox squeezed by a flex container, or
  clipped, would not show up. The audit keeps that as needing a browser.
- **A heading with `tabindex="-1"` now draws the ring whenever the browser treats its programmatic
  focus as keyboard focus.** That is the point, but it is new on those headings. Chromium and
  Firefox show `:focus-visible` after `focus()` only when the last input was from the keyboard.
- **The other open cells are unchanged here: 3 failures and 11 not verifiable.** The audit lists
  them. HV-039-24 takes the preview canvases and sound cues. HV-039-22 and -23 (merged) took the mask
  viewport's keyboard instructions and the graphics credit rows. The review list's identical
  Resolve and Reopen buttons (2.4.6) are left open.
