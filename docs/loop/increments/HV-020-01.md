# HV-020-01 — A camera path goes to the provider as its own camera control, where one is declared (Release 3 step 12, part one)

epic: HV-020
release: 3 "Features"
gate: none new (cites G20-202610031349: Release 3's build order is agreed, and this is part one of its step 12)
spend_usd: 0

## Why

Release 3's part `HV-020.native-camera` is exercised when "a camera move reaches the provider as its
own camera control, not as a local crop". HV-030-27 found that a camera path today is only a local
crop. `docs/CAMERA-PATHS.md` said: "No camera-path fields are added to vendor requests."
`FailoverGenerator.attempt` cropped every path with ffmpeg after the render, and nothing in a
capability could say a model takes a camera move.

Build step 12 says: native camera control only where a provider in the pool takes it. So this
increment does two things. It builds the path from a direction's camera path to a provider's own
control, and it records, per model, whether the pool has one. It does not invent the vendor's
parameters. The adapter code and the vendor sources the repository cites
(`docs/REFERENCE-PROVIDERS.md`, `docs/CAMERA-PATHS.md`) document no camera-control input for Kling
2.5 Turbo Pro or Kling O3 (reference or keyframes). Each is therefore `camera: none` and keeps the
local crop. The report now records that, and why.

## What

- **A path is read as moves** (`cameraPathMoves`, `packages/planner/src/camera-path.ts`). There is one
  move per axis: the crop's centre right or left is `pan-right` or `pan-left`, down or up is
  `tilt-down` or `tilt-up`, and the crop shrinking or growing is `zoom-in` or `zoom-out`. A
  screen-space crop can't tell a dolly from a zoom, so it is a zoom. A net change under 1% of the
  frame on an axis isn't a move. A path that turns back on any axis (`path-reverses`) or doesn't
  move (`path-has-no-move`) has no moves. A provider's camera control takes a move, not keyframe
  times or easing.
- **A capability field, `nativeCamera: {moves}`** (`packages/generator/src/capabilities.ts`). It
  must be a non-empty set of known moves. Absent is `camera: none`. It is absent rather than `[]` so
  every revision admitted before this field exists is unchanged; a test pins the four fal revisions
  to `main`'s. Declaring moves changes the revision, so a pinned route meets it as
  `capability-changed`, like any other capability change.
- **`cameraControlPlan(snapshot, path)`** decides native or local crop and why: native only when the
  provider declares every move the path makes. `matchCapability` uses it for the route's adaptation
  ("native camera control: pan-right" instead of the local-framing note). Eligibility, the estimate
  and the requirements are untouched.
- **The fal adapter sends it** (`packages/generator/src/fal.ts`). A `FalModelSpec` may carry
  `cameraControl: {moves, input}`. That is the vendor's own fields, to be set only from a cited
  vendor schema. When the plan is native, those fields go in the request body. A field that would
  replace one the adapter already sends is refused before dispatch. The clip reports
  `applied: "native"` and its `moves`. No spec in `FAL_MODELS` sets `cameraControl`.
- **The local crop runs only when the move wasn't sent** (`FailoverGenerator.attempt`,
  `packages/generator/src/index.ts`). If the capability and the clip disagree, the attempt stops
  with a `FramingError`: either the provider declared a native move but didn't confirm sending it,
  or it reported one it doesn't declare. The completed render's cost is kept once, and failover
  doesn't run (the existing local-framing failure rule).
- **Provenance says which path was used.** Every new `cameraPathControl` report carries
  `applied: "native"` with `moves`, or `applied: "local-crop"` with a `reason`. The reasons are
  `provider-has-no-native-camera`, `move-not-supported`, `path-reverses` and `path-has-no-move`.
  That covers the storyboard (`animatic.ts`) and the video crop (`framing.ts`). The report already
  flows to the job's `cameraPathRenders`, take manifests, per-shot export manifests and portable
  archives. `assertCameraPathApplied` checks it in snapshot validation (`snapshots.ts`) and for
  mixed current-film rows: a native claim must carry exactly the path's own moves, and a crop must
  carry a known reason. Reports without `applied` (all written before this increment, all crops)
  still validate.
- **Routing order is unchanged, and this is documented.** Native support doesn't make a provider
  eligible or ineligible, and it isn't a preference. `configured` is the operator's order. `cost`,
  `latency` and `quality` break their ties by that same order, so no existing strategy has room for a
  camera preference without changing what it means. A preference would also have to be mirrored in
  the shot-execution capture's ranking check. It is left as a routing decision for later.
- Docs: `docs/CAMERA-PATHS.md` (a "Native camera control" section with the per-model table, and
  dispatch and verification updated), and one sentence in `docs/PROVIDER-ROUTING.md`.

## Acceptance criteria

1. **The request body carries the camera control for a supporting model.** A fixture fal model that
   declares `pan-left`, `pan-right` and `zoom-in` is routed a pan-right path over the fake fal
   transport. The submitted body is exactly `{prompt, duration, aspect_ratio,
   fixture_camera_moves: ["pan-right"]}`. The clip's report is
   `{applied: "native", moves: ["pan-right"]}`. Both the route and the decision say "native camera
   control: pan-right". The first frame is the provider's whole frame, both halves of a red/blue
   clip, so no local crop ran.
2. **An unsupported model falls back to the local crop, with a recorded reason.** Kling 2.5 Turbo
   Pro's body keeps exactly its four fields, with nothing added. The report is
   `{applied: "local-crop", reason: "provider-has-no-native-camera"}`, the route keeps the
   local-framing adaptation, and the first frame is the cropped red half. If a supporting model
   lacks one of the path's moves, nothing is sent and the reason is `move-not-supported`. A path
   that turns back is `path-reverses`.
3. **Provenance records native or crop, and can't be altered.** Moves are read one per axis, with
   the 1% threshold, reversal and a still camera all covered (2 tests). A report must match its path
   (1 test). A snapshot whose crop report is changed to claim a native move it doesn't make is
   refused ("camera path"). So is a mixed current-film row with a crop report that has no reason, or
   a native report with the wrong moves.
4. **Capability revision changes are handled like other capability changes.** Every fal model in the
   pool is `camera: none`, with its revision byte-identical to `main`'s. A capability with an empty,
   unknown, duplicated or extra-keyed `nativeCamera` is refused. Declaring moves changes the revision
   but not the price version. A snapshot altered to add them fails integrity. A route pinned to the
   old revision refuses with `capability-changed`, without dispatch.
5. **Spend and eligibility are unchanged.** For the same request, a native and a `none` capability
   give the same eligibility, reasons, estimate and billed duration. Their non-camera adaptations
   are equal too, and the requirements carry nothing new.
6. **A mismatch fails closed.** A provider that declares a move and doesn't confirm it stops with a
   `FramingError`. It is dispatched once, never failed over, and its cost is drained once and carried
   on the error. A clip claiming a move its capability doesn't declare is refused too.
7. Reverting the request wiring in `fal.ts` fails criterion 1. Making the attempt crop
   unconditionally fails criteria 1 and 6. Removing the snapshot check fails criterion 3's snapshot
   case. All three were checked.

## Known gaps

- **No model in the pool takes native camera control, so `HV-020.native-camera` can't yet be
  exercised.** Build step 12 says the part is then deferred to a gate entry. This increment doesn't
  write that entry, because a gate entry is the operator's record. The part stays unexercised until a
  model whose camera-control input is cited from its vendor schema joins the pool (a new endpoint on
  fal is a model addition, not a new vendor), or until the operator records the deferral.
- **No paid render has verified that a provider honours a camera control.** The native path is
  proven only against a fixture model. Its `fixture_camera_moves` field is not a vendor parameter.
  The fixture shows the plumbing (capability, request, crop skipped, report). It does not show that
  any vendor moves the camera, how far, or with what timing.
- **A native move is coarser than the path.** The control carries the move, not the keyframes,
  easing or extent. The report keeps the authored keyframes beside `moves`, but the picture won't
  follow them exactly. A creator who needs the exact curve has no way to ask for the crop when a
  provider could move natively. That would be a direction setting, like frame anchors' `native`,
  `storyboard` and `prefer-native`.
- **Routing doesn't prefer a native provider.** This is deliberate (see What), and it is a routing
  decision for later.
- **A screen-space path can't express a dolly, a truck, a roll or an orbit.** It is a 2D crop, so it
  reads as pan, tilt and zoom only. Moves a vendor names beyond these would need a direction field
  that says them.
- **Checked on fixtures and the fake transport, not in a browser or against a live vendor.** The
  shot editor doesn't yet show whether a path will be native or cropped. The route's adaptation and
  the manifest's report are the only places it appears.
