# HV-031-09 — A manifest that had lost its shots killed the job with a TypeError instead of refusing

epic: HV-031
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

Four verifiers compare a retained export's render records with the ones the film actually recorded,
and each wrote the extraction out inline. Two spellings:

```ts
contentHash(provenance.shots?.map((s:{renderRecord?:unknown})=>s.renderRecord))        // sound-media, dialogue-replacement
contentHash(provenance.shots?.map((s:{renderRecord?:unknown})=>s.renderRecord)??null)  // edit-source-media, twice
```

Two left the `?? null` off, and that is not a cosmetic difference. `contentHash(undefined)` is not a
hash of nothing: `canonical(undefined)` is `JSON.stringify(undefined)`, which is `undefined`, and
`createHash("sha256").update(undefined)` throws. Verified under this repo's Bun:

```
TypeError: The "data" argument must be of type string or an instance of Buffer, TypedArray, or DataView. Received undefined
```

So a manifest that **satisfied `provenanceMatches`** — right spec, right project, a valid
`assembledAt`, a claim bound to the file's own sha256, so the `||` does not short-circuit — and had
lost its `shots` key did not produce *"The picture's original provenance changed."* It killed the
sound-mix or dialogue-replacement job with that TypeError as its `failureReason`. A tamper signal
became an internal type error, and the creator was told nothing about their film.

`provenance.ts` exists for exactly this. Its own header says the spec and the claim were each written
in five places and that a change would have broken every retained export *"with each verifier
reporting a different failure"*. The identity check moved into it. This comparison stayed behind, in
four copies, and the copies disagreed.

Nothing caught it because `provenance.test.ts`'s fixture always carries `shots: [{…}]`, and its
whole-map guard asserts that the four files *call* `provenanceMatches` — it pins the function, not
the expression beside it.

## What this increment does

- **`provenanceShotRecords(manifest)`** returns the records a manifest carries, in comparison order,
  or `null` when it carries none — for an absent `shots`, a non-array one, and a manifest that is not
  an object at all. The extraction is a function, so the `?? null` cannot be left off: there is
  nowhere left to leave it.
- **All four call sites go through it**, beside the identity check they already went through.
- **The whole-map guard is extended** to the expression as well as the function: no file outside
  `provenance.ts` reaches into a manifest's `shots` any more.

## Acceptance criteria

1. **A manifest with no shots has no records**, for an absent, null, string, number and non-object
   `shots`; hashing that answer does not throw, and it does not collide with a manifest that has
   records.
2. **A manifest that has them hands them over in its own order**, and a shot carrying no record keeps
   its place, because position is what is being compared.
3. **The identity of the manifest is unchanged**: a manifest with no shots still matches, which is
   exactly why the comparison below it had to be reached rather than thrown past.
4. **No file outside `provenance.ts` extracts the records for itself**, and each of the three
   verifiers reaches for both the identity check and the extraction.
5. Reverting `packages/planner/src/provenance.ts` fails all four; restoring the old spelling in one
   verifier alone fails criterion 4.

- Tests: `packages/planner/test/provenance-shot-records.test.ts`. Verified both ways.

## Known gaps this leaves

- **`contentHash(undefined)` still throws.** This increment stopped four callers from handing it
  `undefined`; it did not make `canonical` refuse by name, and the next caller that does will get the
  same TypeError. Making `contentHash` refuse is a change to a function every package uses.
- **No test drives a verifier end to end with a broken manifest.** The refusal message each verifier
  writes is asserted nowhere; this asserts what is handed to the comparison, not what the job says
  when it fails. Reaching `verifySoundMedia` needs a rendered film.
- **A manifest with the wrong *number* of shots is caught only by the hash.** The refusal says the
  provenance changed and not how, which is correct for a tamper signal and unhelpful for a truncated
  file.
- **`renderRecord` is still not in `ProvenanceManifest`'s declared shape.** The extraction casts for
  it, as the four call sites did; declaring it would make the cast unnecessary and is a change to the
  manifest type that the assembler and every reader would have to agree to.
