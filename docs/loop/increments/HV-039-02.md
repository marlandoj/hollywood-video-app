# HV-039-02 — Stop suppressing every status announcement in the creator UI

epic: HV-039
spend_usd: 0

## Goal

Move `aria-busy` off the element that carries each panel's live region, so that the messages these panels already write are actually announced; collapse the eleven hand-written copies of that wrapper into one helper, so the fix cannot land in one panel and miss ten; and make the shared module the helper introduces provably reachable by the browser, because the route table that decides what is served was seven hand-written path arrays and two single-path checks with nothing holding them equal to what the modules import.

## The defect, as a user meets it

Every workbench panel in the creator UI holds its own status element — `role="status"`, and in two of the eleven (`audio-studio.js:9`, `performances.js:52`) with `aria-live="polite"` as well; `edit-script.js:14` writes `aria-live="off"` — **inside** the panel, and each one set `aria-busy="true"` on that panel around its own async work. `aria-busy="true"` tells assistive technology that the element is mid-change and that it may wait before exposing what changed, so:

- the success message, written inside the awaited action, is written under `aria-busy`;
- the error message, written in the `catch`, is also written under `aria-busy`, because `catch` runs before the `finally` that clears it;
- and in the five synchronous `sync()`-shaped call sites, `status.textContent = …` and `setAttribute('aria-busy', …)` are adjacent statements in the same pass.

So a screen-reader user presses **Generate audition**, the request fails, the visible red text says the draft was retained — and nothing is announced. The control appears to hang. This is the silent-wrong-answer shape rather than a refusal: the failure is shown and never surfaced.

**Where it was.** Eleven `aria-busy` call sites across **eleven** modules — one each. An earlier draft of this doc said ten, which was simply miscounted; `git grep -l aria-busy origin/main -- packages/frontend/src` returns eleven files. The audit named six of them (`audio-studio.js:56`, `editorial.js:78`, `graphic-studio.js:13`, `dialogue-replacement.js:19`, `edit-assemblies.js:16`, `edit-assemblies-render.js:52`). Four more have the same defect and were not named: `sound-studio.js:24`, `lipsync.js:8`, `living-script.js:20`, `edit-script.js:29`.

**One that is not a defect, stated because a blanket fix would have broken it.** `performances.js:56` sets `aria-busy` on a play *button*, and the status element beside it is a sibling, not a descendant — so nothing is suppressed there. It is routed through the same helper for uniformity, and the helper is written so that a subtree containing no live region still marks the element itself. Without that branch the conversion would have silently removed a working affordance; perturbation P6 measures it.

**Nothing caught any of it.** There is no `aria-busy` assertion in any test in any of the twelve packages on `main`, and the only `aria` references in the frontend tests are three `aria-label` values used as element selectors. `HV-039-01` left the program its first accessibility assertion, about colour; this is the second, and the first about ARIA semantics.

## The shape of the repair

**One helper, eleven callers.** `packages/frontend/src/busy.js` owns the rule: mark the busy subtrees, never a subtree that carries a live region. `busyRegions(root)` returns `root` itself when nothing under it is live — which is exactly what the eleven copies did, so the button case and the controls-only panels are unchanged — and otherwise the shallowest descendants that carry no live region, so the whole of the panel except its live regions is marked. `whileBusy(root, action)` runs the action with the marks set and clears them however it ends, for the six `try/finally` panels; `applyBusy(root, busy)` is the form the four `sync()` panels and the one button need.

**The marks are reference-counted, which the first draft of this helper got wrong.** `editorial.js` marks its own panel, and the `edit-assemblies` panel mounted inside it marks its own subtree, so one element can be claimed by two roots. With a plain `removeAttribute` the inner panel finishing first stripped a mark the container still held, leaving a busy container with an unmarked child. The test in this increment caught that before the code was committed; perturbation P3 measures the version without the count.

**A live region is left alone entirely, children included.** The first draft descended into any element that *held* a live region, which meant the children of the live region itself got marked — so `<p role="status">Saved <strong>3</strong> takes</p>` had its own `<strong>` marked busy. Every case in the suite built a childless live region, so nothing saw it until a case with markup inside the status was added. P13 measures the descent; P16 measures the converse mistake, a helper that stops recognising any live region that has children, which passed all eight of the original cases.

**The helper takes the action rather than returning a release call, because the critic found the release could be dropped invisibly.** With `markBusy(root)` returning the clear, `markBusy(panel); const idle = () => {};` in any one module left that panel marked for the rest of the session — every later message silenced, worse than `main` — while the whole suite stayed green: the source guard sees the helper being called, and five of these panels are mounted by no test. `whileBusy(root, action)` puts the clear in a `finally` inside the helper, so it cannot be forgotten by accident. What remains expressible is a deliberate `applyBusy(panel, true)` with no matching clear, and a source guard refuses a constant second argument to `applyBusy` in any importer; P19 measures it. Beyond that — a module computing an always-true expression — nothing short of mounting all eleven panels would catch it, and that gap is the unexercised-module gap recorded under Verification.

**It is the same code in the browser and in the tests.** `busyRegions` walks `children` and reads attributes through `getAttribute`, both of which the browser DOM and this repository's hand-rolled test element expose, so nothing is stubbed and no DOM library is added.

**The helper has to be served, and that is a second rule written in six places.** The API returns the creator UI's modules two ways: most as the raw file with their `import` statements intact, ten bundled by `previewBrowserModule` with imports inlined. Which module goes which way was decided, on `origin/main`, by nine route sites: seven hand-written path arrays contiguous at `server.ts:610-617`, and two single-path checks, one at `:616` and one at `:995` — about 380 lines below the block. An earlier draft of this doc said "six arrays, one of them a thousand lines below the other five"; both halves of that were wrong and the corrected figures are above. Nothing held any of them equal to what the modules import. A shared module added to a raw-served panel makes the browser request a path no array names; it 404s, and the whole panel fails to load. Every existing check named one such path by hand, so none of them would have noticed.

`packages/api/test/frontend-modules.test.ts` now walks the graph the way the browser walks it: the entries come out of the two served HTML pages, and every further edge comes out of **the bytes the server returned**, not the source on disk. That distinction is the whole point — a bundled module's response has no imports left to follow while its source has three, so a walk over sources would demand routes the browser never asks for. Perturbation P12 measures exactly that mistake.

**The edges are parsed, not matched, and the reached set is pinned exactly.** The first draft of that test used three regular expressions and a floor of `seen.size >= 25` against a real closure of 42. The critic built a green defect out of the slack: write one import without spaces — `import{x}from"./audio-phrases.js"` — and delete that module's route, and the browser loses the whole voice studio while the test reports nothing, because the edge is invisible to the pattern and seventeen edges can vanish before the floor notices. P18 reproduces it against the first draft and measures `3 pass / 0 fail`. The scan is now `Bun.Transpiler().scanImports`, which is in the runtime already, is not fooled by a string that looks like an import, and handles spaceless, multi-line and bare re-export forms; and the 42 reached paths are pinned deep-equal, so any change to what the browser fetches has to be written down on purpose. P11 and P17 measure both halves.

The three route lines for modules shared across prefixes are replaced by one derived from two exported constants, `BROWSER_MODULE_PREFIXES` and `SHARED_BROWSER_MODULES`, and `busy.js` joins that list. Four arrays and the two single-path checks are left alone; see the deferral below.

## Declared changes beyond the defect

- **`/api/speech-player.js` now answers.** It was served at `/api/cast/` and `/api/direction/` only; folding it into the shared-module list serves it at all three prefixes. It is the same already-public client module at a third path, with the same headers; no new file becomes reachable.
- **A duplicated import walk was deleted, not added to.** `packages/api/test/editorial.test.ts` already walked `/api/editorial.js`'s imports, capped at `expect(visited.size).toBeLessThanOrEqual(9)`. That cap was an assertion about the module count wearing a recursion guard's clothes: adding one shared import to a panel made it 10 and failed the test. The walk is removed with a pointer to the new test, which starts from all thirteen entries rather than one, handles the bundled modules correctly, and needs no hand-updated bound.
- **Four test element stubs gained `getAttribute` and `removeAttribute`.** They had `setAttribute` and an `attributes` bag only. A first draft added them to a fifth, `editorial-assembly-guards.test.js`, which already had both — two dead duplicate class members that `bun run lint` reported as `no-dupe-class-members` warnings while an exit-code-only check called the run clean. Both the duplicates and that claim are corrected. **Six separate `class Element` stubs exist** across `packages/frontend/test` (`edit-assemblies-fixture.js`, `edit-assembly-preview.test.js`, `edit-script.test.js`, `editorial-assembly-guards.test.js`, `living-script-comparison.test.js`, and an inline one in `mask-viewport.test.js`) — the same duplication family this increment is about, one level down. Consolidating them is not attempted here: it would touch every frontend test in the same change as a behaviour fix, and it is recorded so the next reader does not have to rediscover it. `busy.test.js` imports the existing fixture rather than adding a seventh.
- **The literal `aria-busy="false"` becomes an absent attribute in the five `applyBusy` call sites.** `setAttribute('aria-busy', String(x))` wrote the literal string on every pass; `applyBusy(root, false)` removes the attribute. The two are semantically identical — an absent `aria-busy` is `false` — and nothing in the repository reads the attribute outside `busy.js` and its test (no CSS, HTML or other test matches it), but it is a DOM-observable change in five files and belongs here rather than being noticed later. The same conversion also removed a latent `aria-busy="undefined"`: `edit-assemblies.js` wrote `String(s.busy||renderPanel?.locked)`, which is the string `"undefined"` when both operands are, and `Boolean(...)` at the call site now settles it.
- **Collapsing the remaining four route arrays into one directory-backed route is deliberately deferred.** Serving any `*.js` that exists in `packages/frontend/src` would remove the arrays entirely, but it changes what is *reachable* — `operator.js`, today served only as `/api/operator/app.js` with the console's own `content-security-policy`, would answer at `/api/operator.js` without it. That is a change to the API's static surface and deserves its own increment and its own reasoning, not a paragraph inside an accessibility fix. The new test makes the remaining arrays unable to drift silently, which is the failure mode; the arrays themselves are cosmetic by comparison.

## What this increment does not do

- **It does not audit the rest of WCAG 2.2 AA.** It fixes 4.1.3 Status Messages for these eleven sites and nothing else. `mask-viewport.js:6` still declares `role="img"` on a focusable, arrow-key-operated canvas — a live 4.1.2 failure the audit named, untouched here.
- **It does not cover content created during the busy window.** `applyBusy` marks the tree as it stands when it is called, so an element appended while the panel is busy is unmarked. The four `sync()` panels and the one button re-apply on every pass and self-correct; the six `try/finally` panels mark once and may redraw inside the action. Marking the panel instead would cover that case and silence the announcement, which is the defect. The controls in every one of these panels are disabled for the duration, which is the affordance a sighted user actually reads, so the residual is a missing "wait" hint on newly-created content, not a missing state.
- **It does not give a busy state to the panels that never had one.** `direction.js:108` and `:118`, `scene-cuts.js:15`, `subject-motion.js:82`, `takes.js:13` and `casting.js:201` have the same `run(action)` shape — disable the controls, await, restore — and set no `aria-busy` at all. That is a different gap from this one (a missing state rather than a misplaced one) and is left for whoever takes the next slice of this epic.
- **It does not verify announcement with a screen reader.** These are DOM-structure assertions: they prove the message is not written inside an `aria-busy` subtree. Whether a given screen reader then speaks it is a manual check, and V-020 — which still names WCAG 2.1 AA while this epic is defined as 2.2 AA — remains the open gate.

## Acceptance criteria

1. No live region in the creator UI has an ancestor marked `aria-busy` while its panel is busy. — `packages/frontend/test/busy.test.js`, cases 1, 2 and 11; case 11 drives a real `edit-assemblies` panel into a held request and pins its status element's whole ancestor chain by tag and by value.
2. Everything in a busy panel other than its live regions is marked, and nothing inside a live region is. — case 1 (`['h2','div']`), case 2 (`['header','button','a']`) and case 5, whose live region has element children. P1, P2, P13 and P16.
3. A subtree with no live region marks the element itself, preserving the button and controls-only behaviour. — case 3; P6.
4. A nested panel and its container cannot clear each other's marks, in either completion order. — case 4; P3.
5. Only real live regions are excluded: `role` by its first token, case-insensitively, and `aria-live` overriding the role in both directions. — case 7, a twelve-row truth table; P4, P5, P14.
6. The busy state is always cleared: `whileBusy` clears on throw as well as on return, and no module marks with a constant. — cases 8 and 9; P15 and P19.
7. `aria-busy` is written in exactly one file, and every module that used to write it imports and calls the helper. — case 9; P7 and P8.
8. Every module path the browser will request, following the served responses from the entries in both pages, is served with a JavaScript content type — and the reached set is exactly the 42 paths pinned in the test. — `packages/api/test/frontend-modules.test.ts`, case 1; P9, P10, P17, and P18 which shows the first draft failing this criterion.
9. The edges are parsed rather than pattern-matched, so a spaceless, multi-line or bare re-export import is still an edge. — the `Bun.Transpiler` scan, exercised by case 2 and measured by P11 and P17.
10. A name that is not a module is refused at every prefix, so a 200 means something. — case 3 of the API test.
11. The walk follows a raw response's imports and does not invent requirements from a bundled module's source. — case 2 of the API test; P12.
