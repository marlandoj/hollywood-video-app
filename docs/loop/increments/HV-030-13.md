# HV-030-13 — A crew plan with a control character was paid for, then refused with a false reason

epic: HV-030
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

HV-030-12 gated every shot field at the direction's own length limit. An over-long field is now
refused inside `validateCrewPlan`, where `runPlan` falls back to the stand-in plan.

Length isn't the only rule the later validators apply. `directionSettings` and `characterRecord`
both refuse C0 control characters, except tab, line feed and carriage return, and `characterRecord`
also refuses DEL. The crew's gate didn't. So a plan whose light read "Soft\fwindow light", or whose
wardrobe read "Blue\fapron":

- passed `validateCrewPlan`, was returned as `source: "anthropic"`, and was recorded against the
  crew's budget;
- then threw from `crewChanges` with *"keyLight must be text of at most 240 characters."* or
  *"Wardrobe must be text up to 600 characters."* The plan route does not catch this error.

That is the same failure as before: the plan is paid for and then refused. This time the reason
given isn't even true.

## What this increment does

- **The crew's gate refuses the characters the direction and cast validators refuse.** That is C0
  controls other than tab, line feed and carriage return, plus DEL, as `characterRecord` does. A
  plan containing them is one the studio cannot use, so the step falls back to the stand-in plan,
  and the model call is recorded once.
- **The same gate reads the creator's answers and tone.** Those now refuse the same characters,
  where before they carried them into the prompt.

## Acceptance criteria

1. **Each shot text field and each cast text field is refused at the gate** when it contains a
   control character, and the unmodified plan is accepted.
2. **Tab, line feed and carriage return are still text.** A plan using them passes the gate and
   `crewChanges`.
3. **A paid plan with a control character falls back to the stand-in plan**, with
   `fallbackReason: "model_unusable"` and its cost recorded once, and `crewChanges` accepts the
   stand-in plan.
4. Reverting `production-plan.ts` fails criteria 1 and 3.

- Tests: `packages/planner/test/crew-plan-controls.test.ts`. The crew planner suites and the plan
  route pass.

## Known gaps this leaves

- **The crew's gate still runs its own copy of each validator's rules.** Length (HV-030-12) and
  characters (here) now match, but a new rule added to `directionSettings` would need adding here
  too. Calling `crewChanges` inside the gate would remove the copy. It would also make the gate
  depend on the current cast and direction, which it does not see today.
