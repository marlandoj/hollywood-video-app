# HV-024-03 — The Composer's tests say how long their own work takes

epic: HV-024
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

PR #168's CI failed on a test that has nothing to do with what it changed:

```
(fail) the score is the same bytes every time, a 48 kHz 16-bit stereo WAV of eight bars [5272.52ms]
  ^ this test timed out after 5000ms.
1952 pass, 10 skip, 1 fail
```

The test renders **eight bars of 48 kHz stereo audio, sample by sample, in JavaScript — three times**
(two renders to prove the bytes are identical, and a third in a different mode to prove they differ).
Measured, that is about 1.2 s on a build machine and 5.27 s on a loaded CI runner, against bun's 5 s
default. It passed until now because the runner happened to be fast enough.

A test that encodes "the machine running me is fast" fails on a change that touched nothing near it,
and costs a full CI cycle — which for this repository's `quality` job is about eighty minutes. That
is a worse failure than a slow test: it teaches whoever sees it that a red build might mean nothing,
which is the habit that lets a real failure through.

## What this increment does

- **The two render-heavy score tests carry an explicit 60-second budget**, and a comment above them
  says what the work is, what it measures, and why the budget is for the slowest machine that runs
  the suite rather than the fastest.
- Nothing about the Composer, the score, the recipe or the rights record changes. The tests assert
  exactly what they asserted.

## Acceptance criteria

1. **The score suite passes** with the two audio-rendering tests given a budget that a loaded runner
   can meet, and the two arithmetic-only tests left on the default.
2. **The assertions are unchanged** — the same bytes, the same header fields, the same frame count,
   the same seam and the same peak.
3. **Nothing else changes.**

- Tests: `packages/frontend/test/score.test.js` itself.

## Known gaps this leaves

- **This does not make the render faster.** Eight bars of stereo at 48 kHz is 1.5 million samples per
  channel per render, and the Composer writes them one at a time. If the score ever needs to be
  rendered inside a request rather than in a test, that cost becomes a real one and wants measuring.
- **No other slow test was audited.** This one failed, so this one was fixed; a sweep for other tests
  sitting near the default budget would be its own piece of work.
