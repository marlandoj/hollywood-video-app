# HV-040-03 — Row-level capability coverage for the accounting tables
epic: HV-040
spend_usd: 0

## Goal
Close the "row-level capability checks" half of the data pillar. Seven project-scoped tables already carry `ENABLE` + `FORCE ROW LEVEL SECURITY` with an `hv_api` policy bound to the transaction-local `hv.project_id` setting and an unconditional `hv_worker` policy (`infra/drizzle/0001_project_capabilities.sql`, `0002_runtime_privileges.sql`, `scopePolicies` in `packages/storage/src/schema.ts`). The five accounting and operations tables are outside that regime: `hv_budget_accounts` and `hv_reservations` are granted `SELECT, INSERT, UPDATE, DELETE` to `hv_api` with no row security at all, so a compromised or buggy API session can rewrite any job's hold or delete the operator budget row; `hv_cost_events` and `hv_workers` are readable by `hv_api` and `hv_operator_reviews` by nobody but `hv_worker`, all without a declared policy. The API in fact performs exactly two writes to these tables, both inside a validated capability scope: the `'operator'` budget-account upsert/lowering and the reservation INSERT during admission (`packages/storage/src/ledger.ts`); it never updates or deletes a reservation on PostgreSQL. This increment adds one additive migration that gives every `hv_*` table forced row security with a policy per role and command that the code actually uses, narrows the `hv_api` grants to those commands, records the admitting project on new reservations so the write policy can be row-level rather than a blanket, and adds a guard test in the CI storage lane that fails whenever a future migration grants `hv_api` a command on any table without a matching policy. No user-facing route, budget default, provider or object-store behaviour changes.

## Acceptance criteria
1. **Every `hv_*` table forces row-level security.** After `StudioDatabase.migrate()`, `pg_class.relrowsecurity` and `relforcerowsecurity` are true for all twelve `public.hv_*` tables, including `hv_budget_accounts`, `hv_reservations`, `hv_cost_events`, `hv_workers` and `hv_operator_reviews`, and `hv_api` and `hv_worker` remain `NOSUPERUSER NOBYPASSRLS` (`scripts/storage-ci-roles.ts`, `scripts/prepare-postgres.py`). Satisfies FULL-SCOPE §3 P15 Full scope "Data: PostgreSQL as system of record and job coordinator; Drizzle migrations; row-level capability checks." and the §9 epic register row "HV-040 | Storage and Archive at Scale (PostgreSQL, S3, lifecycle, portable archive)".
2. **No command `hv_api` can execute on any table is unpoliced, and its accounting privileges are the minimum the API uses.** For every (table, command) pair in which `has_table_privilege('hv_api', table, command)` is true, at least one row in `pg_policies` names `hv_api` with `cmd` equal to that command or `ALL`. Concretely, migration `0015` revokes `UPDATE, DELETE` on `hv_reservations` and `DELETE` on `hv_budget_accounts` from `hv_api` (the API never issues them on PostgreSQL: every `ledger.release`/`ledger.reserve` call in `packages/api/src` is in the JSON-ledger `else` branch) and leaves `SELECT` on `hv_cost_events` and `hv_workers`, no privilege on `hv_operator_reviews`, `SELECT, INSERT, UPDATE` on `hv_budget_accounts`, and `SELECT, INSERT` on `hv_reservations`. Satisfies §3 P15 "row-level capability checks" and §8 "Security: capability isolation, signed URL scope, IDOR, …".
3. **Budget-account writes require a validated capability scope; the row is the singleton.** `hv_api` policies on `hv_budget_accounts`: `SELECT USING (id = 'operator')`; `INSERT WITH CHECK (id = 'operator' AND coalesce(current_setting('hv.project_id', true), '') <> '')`; `UPDATE USING (id = 'operator') WITH CHECK (same predicate)`. Inside `forProject`, the existing upsert (checked before the conflict path), `SELECT … FOR UPDATE` and cap lowering succeed unchanged; outside any scope, including on a pooled connection whose previous transaction was scoped (where the setting reads `''`, not `NULL`), the same statements raise SQLSTATE `42501`. `scripts/storage-readiness.ts` and `packages/storage/src/diagnostics.ts` keep reading the cap with no scope. Satisfies §3 P15 "row-level capability checks", §10 "Free and anonymous for every end user; no billing code reachable." (the operator-funded cap is only ever lowered by the API, never raised, and the frozen "budget defaults upward" rule is unaffected) and ADR-0018 "Revocable capability tokens … replace accounts and billing."
4. **Reservation inserts are bound to the admitting project; reads stay global by design.** `hv_reservations` gains a nullable `project_id text` column (additive, no default, no backfill). `PostgresCostLedger.reserveWithin` and `reserve` take the project id and write it; every admission call site in `ledger.ts`, `audio-ledger.ts` and `lipsync-ledger.ts` passes the scoped `projectId`. `hv_api` policies: `SELECT USING (true)` (the monthly-cap check sums every open hold; rows carry no project content) and `INSERT WITH CHECK (project_id = current_setting('hv.project_id', true))`. An insert for another project id, a `NULL` project id, or an insert outside a scope is refused with `42501`; an insert inside `forProject(A)` with `project_id = A` succeeds; `UPDATE`/`DELETE` by `hv_api` fail with `42501` (privilege revoked). Pre-existing rows with `NULL project_id` are touched only by `hv_worker` and `hv_admin`. Satisfies §3 P15 "row-level capability checks" and §3 P15 "Reliability: … near-zero loss for approved media" read together with the §9 Wave A exit "Staging runs on PostgreSQL + S3 with the existing E2E passing" (the budget invariant that admission depends on is preserved, not narrowed).
5. **Worker, sweeper and admin paths are unchanged.** `hv_worker` gets `FOR ALL USING (true) WITH CHECK (true)` on all five tables, matching the seven existing `*_worker` policies; `hv_admin` is the cluster superuser and bypasses row security. `ledger.test.ts`, `retention.test.ts`, `diagnostics.test.ts`, `direction.test.ts` (admission as `hv_api`), `audio-jobs.test.ts`, `lipsync.test.ts`, `backups.test.ts`, the snapshot import/export suites and `scripts/storage-fleet-smoke.ts` pass without modification, which is the proof that no live write path broke. Satisfies §9 Wave A exit "Staging runs on PostgreSQL + S3 with the existing E2E passing" and §10 "Evidence before promotion: tests, benchmarks, post-flight evals, gap audits."
6. **A repo guard test makes the invariant permanent.** `packages/storage/test/capability-coverage.test.ts` runs in the CI storage lane (real PostgreSQL, `hv_api`/`hv_worker` roles from `scripts/storage-ci-roles.ts`) and asserts, for every `public.hv_*` relation of kind `r`: RLS enabled and forced; for each role in `{hv_api, hv_worker}` and each command in `{SELECT, INSERT, UPDATE, DELETE}` that `has_table_privilege` grants, a covering `pg_policies` row exists; `PUBLIC` holds no privilege on any `hv_*` table; the exact per-table privilege map for `hv_api` equals the table in the test (so a widened grant is a deliberate edit); and the policy names in `pg_policies` equal the `pgPolicy` names declared by `getTableConfig` on every export of `packages/storage/src/schema.ts`, with `enableRLS` true on each, so `schema.ts` and the hand-written migrations cannot drift apart. An offline companion case (always runs) checks the `schema.ts` half alone. Satisfies §3 P15 "Drizzle migrations; row-level capability checks." and §10 "Evidence before promotion: tests, benchmarks, post-flight evals, gap audits."
7. **The migration is additive and cutover-safe.** `infra/drizzle/0015_accounting_capabilities.sql` contains only `ALTER TABLE … ADD COLUMN` (nullable, catalog-only), `REVOKE`, `ENABLE`/`FORCE ROW LEVEL SECURITY` and `CREATE POLICY`; no `DROP`, `DELETE`, `UPDATE` or data rewrite. `deploy-storage-staging.py --release-sha` stops the edge and API before draining and runs `scripts/migrate-storage.ts` as `hv_admin` only after the worker and sweeper are stopped and a backup exists, so the `REVOKE` never reaches a running API and the readiness probe (`hv_api`, no scope) passes on restart. The journal entry uses `idx 15`, `version "7"`, a `when` greater than the previous entry, and existing migration files are byte-identical (the migrator hashes them). Satisfies EXECUTION-LOOP frozen list "Destructive migrations against the staging database or object store" (not triggered) and §3 P15 "Drizzle migrations".
8. **No frozen path, dependency, budget default, account, vendor or user-facing surface change.** The diff touches nothing under `docs/legal/**`, `docs/adr/**`, `.github/workflows/**` or `packages/safety/**`, adds no `package.json` or lockfile entry, no key, account, tier, cookie or tracking, does not change `HV_MONTHLY_BUDGET_USD` or `HV_COST_CAP_PER_SHOT_USD` defaults, and changes no HTTP route or response. Satisfies §10 "Free and anonymous for every end user; no billing code reachable." and "Safety refusals expand only."

## Out of scope
- Backfilling `project_id` on existing `hv_reservations` rows (a data rewrite; those rows are worker-owned and transient), and any change to the per-project snapshot export filter in `packages/storage/src/snapshots.ts`.
- Narrowing `hv_api` reads of `hv_cost_events`, `hv_reservations` or `hv_workers` to a project scope: admission and diagnostics depend on whole-table aggregates; per-project cost is already delivered through `hv_jobs.body.costUsd`.
- Policies for `hv_admin` (superuser today) or a non-superuser migration role; certificate identities; `HV_DATABASE_TLS_DIR` handling.
- Enforcing "cap may only be lowered" in the database (needs a trigger, not RLS); `HV_MONTHLY_BUDGET_USD` semantics.
- Down-migrations or editing `0001`/`0002` (the migrator hashes them; rollback is a documented manual reversal if ever needed).
- Applying migration 0015 to private staging by hand; `.github/workflows/ci.yml`; `scripts/storage-ci-roles.ts`.
- Column-level grants, `SECURITY DEFINER` helpers, or changes to `hv_queue_counts()`.
- Any new npm or pip dependency, vendor, account or key.
