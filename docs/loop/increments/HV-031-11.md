# HV-031-11 — The retention sweep deleted a project, and its queued render still ran

epic: HV-031
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

On the JSON backend, `scripts/sweep-expired.ts` is the retention loop. `sweepExpiredProjects`
removed an expired project's record and its media folder, but never touched its jobs. By contrast,
a takedown revokes a project's jobs, and the PostgreSQL purge deletes them. The worker does not look
up the project before an ordinary render (`assertPendingContext` returns early for one). So a render
queued before the sweep was claimed and rendered after it:

- With a paid provider, money was spent on a project that retention had already erased.
- `artifacts/<projectId>/` was written back. With the project gone from the state file, only the
  folder-age sweep would ever remove it.

## What this increment does

- **The sweep now stops a swept project's unfinished jobs**, as a takedown does, before it deletes
  the media. The jobs' cancel reason says why: *"…reached the end of its 30-day retention and was
  deleted."*

## Acceptance criteria

1. **Swept projects.** A project the sweep removes has its queued render cancelled with the
   retention notice. The worker then renders nothing for it and writes no media.
2. **Kept projects.** A project the sweep keeps keeps its queued render.
3. Reverting `scripts/sweep-expired.ts` fails criterion 1.

- Tests: `packages/api/test/retention-sweep-jobs.test.ts`.

## Known gaps this leaves

- **The cancelled job records remain in `jobs.json`**, and with them the script text, as a taken-down
  project's do. The JSON store has no way to delete a project's jobs; the PostgreSQL purge does.
- **No worker backstop.** The worker still does not check that an ordinary render's project exists.
  A job admitted in the moment between the sweep's read and its revocation would still run.
