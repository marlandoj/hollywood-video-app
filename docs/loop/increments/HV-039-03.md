# HV-039-03 — the mask viewport told assistive technology it was a picture

epic: HV-039
spend_usd: 0

## Goal

Stop the mask editor's viewport declaring `role="img"` on an element that is focusable, arrow-key operated and continuously changing, and give it the value channel it never had. Then refuse the shape, not just the instance, so the same contradiction cannot be authored again elsewhere in the frontend.

## The defect

`packages/frontend/src/mask-viewport.js` built its canvas like this:

```js
canvas.className='mask-viewport';canvas.tabIndex=0;
canvas.setAttribute('aria-label','Mask shape editor. Select a handle and use arrow keys to move it; Shift moves ten pixels.');
canvas.setAttribute('role','img');
```

Three lines that contradict each other. `tabIndex=0` makes it focusable; a `keydown` listener eleven lines later implements `ArrowLeft/Right/Up/Down` with Shift and Alt modifiers, plus `Escape` and `Enter`; `pointerdown`/`pointermove`/`pointerup` implement direct manipulation with pointer capture. And then the element declares itself a static image.

This is a **WCAG 4.1.2 (Name, Role, Value)** failure on two of its three counts:

- **Role.** `img` says "static graphic". The element is a shape editor. Assistive technology prunes an `img`'s subtree and presents it as one opaque graphic with a name, so nothing inside it could ever be reported even if there had been something to report.
- **Value.** There was nothing to report. `selectedVertex`, `selectedHandle`, `mode`, `frame` and the Q16 geometry all live in the closure. The `<p class="mask-view-caption">` beneath the canvas is rewritten on every `paint()` with a live description, but it had no `id`, nothing referred to it, and it was not a live region — so it was visible text that no screen reader had reason to read. The only live region nearby is the mask editor's own `role="status"` node, which carries save and error messages, not handle state.

Name was fine: the `aria-label` is present and descriptive.

There is a second effect that is not a conformance failure but is why the widget was unusable rather than merely mislabelled. Screen readers run in browse mode by default and consume the arrow keys for reading navigation. An element the reader believes is an image gets no reason to leave browse mode, so the arrow keys the label invites the user to press never reach the handler.

## The shape of the repair

**`role="application"`, not nothing.** Dropping the role would leave a focusable, named canvas whose arrow keys are still eaten by browse mode. `application` is the one role that hands keystrokes to the widget, and its cost — content inside it is not browsable — is zero here, because a `<canvas>` has no accessible children. It is applied to the single canvas element, which is the narrowest scope available, and the live region is placed **outside** it so announcements are not pruned along with everything else.

**Description.** The caption gets a generated `id` and the canvas an `aria-describedby` pointing at it, so the sentence that was already being written for sighted users becomes the element's description.

**Value, on a separate element.** A new `aria-live="polite"` paragraph reports the selected handle and where it now sits, in the source pixels the coordinate fields use: *"Bottom-right corner at source pixel 240, 135."*, or *"Vertex 1 of 3 at source pixel 90, 45."* for polygons.

It cannot be the caption, and this is the part worth getting right. `paint()` runs on every `pointermove` during a drag; a live caption would announce continuously while the user drags. So the announcement is a distinct element, written only at discrete moments — a keyboard move, a selection change, the **end** of a drag, and a `set()` from the editor — and never with text it has just said. `changed()`, which is what `pointermove` calls, does not announce.

**The step rule, declared once.** The old label promised "Shift moves ten pixels"; the keydown handler spelled `event.shiftKey?10:event.altKey ? .1 : 1`; the mask editor's instructions paragraph said "Arrow keys move one pixel; Shift moves ten; Alt moves a tenth." One rule, three statements, nothing holding them equal — the defect family this program keeps finding, sitting right beside the one being fixed, and the reason the label was already wrong (it never mentioned Alt). All three now read `MASK_STEP_PIXELS`, and a case pins the sentence to the numbers **and** the numbers to the handler's measured behaviour.

## Declared changes beyond the defect

- **The mask editor's instructions paragraph is now derived**, so `mask-editor.js` imports `MASK_STEP_SENTENCE`. Its visible wording changes slightly: "Arrow keys move 1 pixel; Shift moves 10 pixels; Alt moves 0.1 pixels." replaces the spelled-out version.
- **The accessible name changes** and now names the Alt step, which it never did.
- **`mountMaskViewport` returns `caption` and `announcement`** alongside `canvas`, so the test can assert against the elements rather than against a re-implementation of how they are found.
- **`packages/frontend/test/mask-viewport.test.js`'s stub gained `setAttribute`/`append` for non-canvas elements.** It returned `{}` for anything but the canvas, which is why adding a second paragraph broke it.

## What this increment does not do

- **It does not audit the rest of WCAG 2.2 AA for this panel.** HV-039-01 covered contrast (1.4.3, 1.4.11) and HV-039-02 covered status messages (4.1.3); this covers one 4.1.2 failure and the 2.1.1 consequence behind it. The mask editor has forty-odd controls whose labelling, focus order and error identification are unexamined here.
- **It does not give the shape itself a traversable structure.** A thorough repair would expose each handle as a focusable `role="slider"` child with `aria-valuemin/max/now/text`, so a screen-reader user could tab between vertices and hear each one's value. That is a rewrite of focus management in this file. What is here reports the *selected* handle's identity and position; it does not let the user enumerate handles without clicking. The mask editor's coordinate fields remain the accessible route to precise values.
- **It does not verify against a real screen reader.** Every assertion is structural: which attributes exist, on which element, and which text is written when. Whether NVDA, JAWS and VoiceOver each announce this as intended is unverified, and `role="application"` is precisely the area where their behaviour differs most.
- **It does not touch the other four divergent DOM stubs** in `packages/frontend/test` (`edit-assemblies-fixture.js`, `edit-assembly-preview.test.js`, `edit-script.test.js`, `editorial-assembly-guards.test.js`, `living-script-comparison.test.js` — five, not the six the audit claims, and they differ substantially in method sets, so folding them is its own increment).
- **The family guard is a source scan.** It is per element, covers both `setAttribute('role', ...)` and the reflected `el.role =` property, and self-exercises in both languages — but it reads text. A role set through a variable or a template string, or on an *aliased* receiver (`const el=canvas;el.setAttribute('role','img')`), passes the per-element check. The lower bound on how many static roles the scan finds is what stands under an alias, and it is a weak net: it notices the role appearing, not what it lands on.
- **`role="application"` is not free, and the doc no longer says it is.** A canvas's fallback content *is* its accessible subtree, and that is the standard route to the per-handle `role="slider"` tree described above. `application` forecloses that route for as long as it is there. It is accepted because that tree does not exist yet and the arrow keys have to work today — not because a canvas has no children, which is what an earlier draft of this document and of the source comment claimed, and which is false.

## Acceptance criteria

1. The canvas declares `application`, never `img`; is focusable; carries the shared label; is described by the caption's real `id`; and the live region is a different element, outside the canvas, marked `aria-live="polite"` while the caption is marked neither live nor a status. — `packages/frontend/test/mask-viewport-a11y.test.js` case 1; W1, W2, W3, W10.
2. The step rule is stated once: the sentence is **derived** from `MASK_STEP_PIXELS` (asserted from source, not only by its value), the editor's paragraph is concatenated from that export rather than copying its text, no other frontend source restates the rule in numbers-in-context, and the handler's measured movement for plain, Shift and Alt equals those three distinct numbers. — case 2; W7, W8, W9, W13, W14.
3. A keyboard move announces the handle by name and its position in source pixels; an unchanged repaint announces nothing; a new selection names the new handle. — case 3; W4, W6.
4. A polygon vertex is announced by its position in the ring. — case 4.
5. A change arriving through the editor — `set()` — announces as well, both when the geometry moved and when only the selected vertex changed. — case 5; W12.
6. A pointer drag writes nothing to the live region while it runs and exactly one announcement when it ends, while the caption keeps being rewritten throughout. — case 6; W4, W5.
7. No element anywhere in `packages/frontend/src` carries a static role together with `tabIndex=0`, a `tabindex="0"` attribute, a `keydown` listener or an `onkeydown` handler — in either the `setAttribute` or the reflected `el.role` spelling; the scan is per element, strips comments first, finds at least the two legitimate static roles that remain, and is exercised against passing and failing snippets in both languages. — case 7; W1, W10, W15.

## The critic's findings

An adversarial read of the diff found four green defects and two claims the code did not support. W12–W15 are the four, each now failing.

1. **W12 — `set()` was a declared announce site with no test on it.** Deleting `announce()` from `set()` left all nine cases green, and `set()` is not a corner: `mask-editor.js`'s `paint()` is `viewport.set({...})`, the terminus of the coordinate and vertex number fields, the vertex select, mask switching, a frame change on an animated mask and `finishPolygon`. Removing it would have left the live region asserting the previous handle at the previous position after every one of those. With `role="application"` exposing no value of its own, the live region is the entire value channel, so this was most of it. The only `set()` assertion in the suite was the *negative* one — that an unchanged repaint says nothing — which a `set()` that never announces satisfies more easily. Case 5 now covers both a geometry-moving `set()` and a selection-only `set()`.
2. **W13 — the sentence's *derivation* was untested.** Case 2 pinned `MASK_STEP_SENTENCE` against a hard-coded string, so freezing the sentence as its own literal passed; moving `MASK_STEP_PIXELS` would then have changed the handler while the label kept promising the old numbers. The derivation is now asserted from source: the sentence expression must name all three `MASK_STEP_PIXELS` keys and must contain none of the numbers as literals.
3. **W14 — the prose scan matched only the wording this increment deleted.** `/Shift moves ten|moves a tenth|move one pixel/` cannot match any future restatement written in the new wording, and `expect(editor).toContain('MASK_STEP_SENTENCE')` was satisfied by the import line alone, so the editor could copy the sentence's text and stay green. The scan is now on the numbers in context, self-exercised against both wordings, and the editor's paragraph is asserted to be *concatenated* with the export.
4. **W15 — the family scan knew only one way to set a role.** `el.role='img'` — the reflected ARIA property, supported everywhere and the form a modern author reaches for — matched neither half of the scan, so the shipped defect authored that way passed. Also missed: `setAttribute('tabindex','0')`, `el.onkeydown=`, unquoted and upper-case HTML attributes. All are covered now, and each is exercised.

Two further findings were not green defects but claims the code did not support, and both are corrected rather than argued:

- **`expect(canvas.children).toEqual([])` could not fail.** Nothing in the file ever appends to the canvas, so it proved nothing about the live region being outside the application element. Replaced with the positive assertion that `parent`'s children are exactly the canvas, the caption and the announcement, in that order.
- **The rationale for `role="application"` was wrong.** Both the doc and the source comment said the cost was zero "because a canvas has no accessible children". A canvas's fallback content *is* its accessible subtree, and it is the standard route to the per-handle slider tree this increment declines to build — so `application` forecloses that route rather than costing nothing. The comment and the "does not do" section now say that. The placement itself was checked and is right: `aria-describedby` and `aria-live` both resolve from outside the application element.

The critic also confirmed, read-only, that `announce()` cannot throw on any path (null geometry, a polygon with no vertices, a null `selectedVertex` and an unknown handle id all reach the clear-and-return branch); that the dedupe suppresses only genuinely identical state, since moving a handle away and back passes through different strings; that no caller spreads or enumerates `mountMaskViewport`'s return, so the two new keys are inert; and that the `hit.d>22` miss, `draw()`, `cancelDrawing()` and the drawMode vertex click all leave the announced state true rather than stale.
