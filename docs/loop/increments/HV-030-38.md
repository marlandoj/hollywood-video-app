# HV-030-38 — An upload to the object store is verified and never hangs (Release 3's live run)

epic: HV-030
release: 3 "Features"
gate: none new
spend_usd: 0

## Why

Release 3's live run stalled again on the object store. This was on staging, at release 67aca2c, with
rustfs S3 and Bun 1.4.0:

- Sequence 1's `dialogue-replacement` job a4cb95e3 started on worker-2 at 14:35:08 UTC.
- By 14:35:25 it had rendered its whole output into the worker cache: export.mp4 (46 MB),
  dialogue.wav (5.5 MB), 16 HLS segments, provenance.json, the C2PA sidecar and the captions.
- Then nothing happened for 40 minutes and more. The worker was idle (0% CPU). It had no connection open
  to the object store, only 3 PostgreSQL connections with no active query. The job stayed `running`
  with its lease renewed, and no dialogue checkpoint was saved.

The step after the render is `checkpointDialogue`, which uploads each file through
`PostgresArtifactStore.upload`:

1. `checksum(source.stream())`
2. `object.exists()`
3. `object.write(new Response(source.stream()), {partSize: 8 MiB, queueSize: 2, retry: 2})`
4. `checksum(object.stream())`, reading the whole object back

None of these awaits had a bound. Every checkpoint and publish uses `upload` (17 call sites). The
sequence's final, a similar 46 MB export, had uploaded fine minutes earlier. The mock rehearsals'
files are under 8 MiB, so they go up in a single PUT, and they never hung.

**The measured cause.** This was reproduced against an S3-compatible stand-in on loopback (create,
upload part, complete, HEAD, GET), with Bun's own `S3Client`, 8 MiB parts and a queue of 2:

| Upload form | 5 MiB | 9 MiB | 17 MiB | 20 MiB | 46 MiB |
|---|---|---|---|---|---|
| `write(new Response(Bun.file(path).stream()))` | 3/3 done | 3/3 done | 3/3 pending | 1/3 pending | 3/3 pending |
| `S3File.writer()`, fed the file's chunks | | | 3/3 done | | 3/3 done (90 MiB: 3/3) |

When it hangs, the store has seen "create, part 1, part 2" and then nothing: no third part and no
open request. That is the staging picture: an idle worker with no connection to the store. It is
intermittent. With the file read once first (as `upload` does for its checksum), the same 17 MiB
upload sometimes completes, and in the test runner, `main`'s upload of a 46 MiB export completed in 2
of 4 runs. A part that never answers, an existence check that never answers and a read back that stops
sending each wait forever too, because Bun's client has no timeout of its own.

## What this increment does

- **`upload` writes through the client's writer.** `S3File.writer({partSize: 8 MiB, queueSize: 2,
  retry: 2})` is fed the file chunk by chunk (`write`, then `flush`), then `end`. It no longer uses
  `write(new Response(stream))`.
- **Every call on the store is bounded** (`packages/storage/src/bounded.ts`). The existence check, each
  write and flush, the end, and each chunk of the read back wait no longer than the job's signal and
  120 s without progress (`OBJECT_STALL_MS`). The job's abort stops the upload at once.
- **A stall is tried again, then fails the job.** A stalled attempt is abandoned and the whole upload
  starts again from the existence check, three attempts in all (`UPLOAD_ATTEMPTS`). After the third,
  the job fails: "The object store stalled on `<key>` in all 3 attempts; the upload was abandoned. The
  object store made no progress uploading `<key>` for 120 s." Any other error fails at once, as before.
- **Nothing is recorded unverified.** Every attempt ends by reading the whole object back and checking
  its size and sha256, as before. The database step comes only after that.
- The limits can be given to `PostgresArtifactStore` (`ObjectTransferLimits`); the API and workers use
  the defaults. HV-030-34's `copyStoredArtifact` now uses the same bounded wait, with its own messages.
- The mixed current film's artifact test fakes the client's `writer`. Its upload failure is still
  injected once per attempt.
- docs/STORAGE-RETENTION.md says so beside the incomplete-upload sweep, which aborts what an abandoned
  attempt leaves.

## Acceptance criteria

1. **A multipart export uploads and is checked.** Through `publishExport` and Bun's S3 client, a 46 MiB
   export goes up in six parts and its captions in one PUT. Each is read back once, the stored bytes
   are the file's, and only then is the database step reached.
2. **A stall is tried again.** A part that hangs once is abandoned at the stall limit. The upload starts
   again (two multipart creations), and the second attempt is verified and recorded.
3. **A store that never answers fails the upload.** A part that never answers, an existence check that
   never answers, and a read back that stops sending each fail the upload after three attempts, within
   seconds, with the message naming the key and what stalled. Nothing is recorded.
4. **The job's abort stops a hung upload at once**, with the default two-minute stall limit.
5. **Reverting the change fails the new tests.** Restoring `packages/storage/src/artifacts.ts` and
   `packages/queue/src/stored-artifact.ts` from `main` (and removing `bounded.ts`) fails the last three
   tests in `object-upload.test.ts`: each upload is still pending at its bound (checked). The first
   test hangs on `main` intermittently (2 of 4 runs here).

- Tests: `packages/storage/test/object-upload.test.ts` (1–4; 4 pass, 3 runs). Unchanged and passing:
  `packages/queue/test/stored-artifact.test.ts` and `packages/queue/test/feature-film-object-store.test.ts`
  (5 pass), `packages/storage/test/archive-schema.test.ts` and `incomplete-uploads.test.ts` (11 pass,
  1 skip), and `current-film-mixed-artifacts.test.ts`'s first five cases, including its failed partial
  upload (5 pass).

## Known gaps

- **The stand-in is not rustfs.** Bun's client and `upload` are real; the store answers from memory.
  The live run's rerun will show it on rustfs. The PostgreSQL-backed artifact suites
  (`artifacts.test.ts` and the others gated on `HV_S3_ENDPOINT`) didn't run here: no PostgreSQL or object
  store was running. CI runs them.
- **The whole of `current-film-mixed-artifacts.test.ts` takes about 23 minutes** (CI's measure), more
  than this machine's 590 s limit per run. Only its first five ordered cases ran here.
- **`upload` doesn't know the job's deadline.** Its 17 callers pass the job's signal, and the worker
  doesn't abort that signal at the deadline. So a stall that keeps recurring is bounded by three
  attempts at the stall limit (about 6 minutes per file), not by the deadline.
- **An abandoned attempt isn't cancelled.** Bun's writer has no abort. Its request is left to the
  connection, and its incomplete multipart upload is left to the hourly sweep.
- **Other reads of the store are still unbounded.** `restoreCheckpoint`'s download loop, and the
  shot-reuse and final-dialogue copies, check the signal only between chunks.
- **The cause is Bun's.** It was not reported upstream from here.
