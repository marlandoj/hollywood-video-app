# HV-016-36 — CI runs the test suite in four parallel shards, not one 3.5-hour step

epic: HV-016
release: 2 "Voice and crew depth"
gate: G18 (`.github/workflows/**`, approved by Kevin 2026-10-02)
spend_usd: 0

## Why

Every PR waits for CI's full suite before it can merge. Since HV-016-30, that suite (`bun test
packages test`, one step of the `quality` job) takes about 3 h 30 min: 548 files, 3,091 tests,
12,689 s in run 36943269474. A one-line fix takes half a day to land. A flaky package install or a
conflict costs another 3.5 hours.

HV-016-34 profiled the slow suites and stopped. Their time is production's per-access checks, run
faithfully, and no test-only change removes it. It named sharding as the remedy it could not use,
because `.github/workflows/**` is frozen. Now that the repository is public (G17), parallel jobs cost
nothing. Kevin approved the workflow change on 2026-10-02 (G18).

## What this increment does

- **`scripts/ci/test-shards.ts`** finds the files `bun test packages test` runs. It uses bun's
  test-file names among the tracked files, filtered by the same two path filters. It then deals
  them into N shards.
  - It deals the heaviest file first, into the lightest shard. Ties break on path and then on
    shard number, so the result depends only on the files and the measurements.
  - `list <shard> <total>` prints one shard's files as `./` paths. `bun test` reads a `./` argument
    as a path, not a name filter.
  - `check <total>` proves every suite file is in exactly one shard and that no shard is empty or
    holds anything else.
  - `measure <log>... <source>` rebuilds the measurements from CI job logs.
- **`scripts/ci/test-durations.json`** holds the seconds each file took in run 36943269474. They
  come from the timestamps of bun's per-file group headers; the 4,533.7 s for
  `current-film-mixed-worker.test.ts` equals the sum of its nine cases. The measurements only
  balance the shards. A new file counts as 10 s, and a stale entry changes balance, never coverage.
- **`.github/workflows/ci.yml`**:
  - **A new `tests` job**, a matrix of shards 1–4 with `fail-fast: false`. Each shard is a fresh
    runner with the same PostgreSQL and object-store services, env, roles, buckets, ffmpeg and full
    history as `quality` had. It runs `bun test` on its own list.
  - **`quality` no longer runs the suite.** In its place, the `check 4` step fails the run if the
    shards ever miss or double a file. Its hang guard drops from 300 to 60 minutes, since the job
    now takes about 4.
  - **ffmpeg installs are bounded and retried** in `quality`, `tests` and `benchmark-gate`. Each
    `apt-get` attempt has a timeout, with three attempts. That step has hung for over an hour and
    been cancelled by hand more than once.
  - `benchmark-gate` still needs `quality`. It now starts after about 4 minutes instead of 3.5 hours.

### Expected time

The measured split puts `current-film-mixed-worker.test.ts` alone in shard 1, at about 76 minutes.
Shards 2–4 take about 45 minutes each. A PR's CI should take about 80 minutes, down from about
3 h 30 min.

That file can't be split further by sharding. Its nine cases are one lifecycle, each case building
on the one before. Its 46-minute "admits and completes the genuine approved final" case is
production's proof verification, HV-016-34's option 2. That is a design decision, not part of this
increment.

## Acceptance criteria

1. **Coverage.**
   - Shard `list` outputs for 1–4 together equal the suite, each file once.
   - `check` fails on a lost, doubled, foreign or empty shard.
   - The suite found is the 548 files of run 36943269474, plus this increment's test, with no
     measured file missing.
2. **Discovery** takes bun's names (`.test`, `_test`, `.spec` and `_spec`, with a JS or TS
   extension) and leaves out `node_modules`, snapshots, fixtures with other extensions, and paths
   outside the two filters.
3. **Balance.**
   - The deal is deterministic and independent of input order.
   - An unmeasured file counts as the default.
   - On the real suite, the heaviest file runs alone in shard 1 and every other shard measures less.
   - A shard count outside 1–64 is refused.
4. **The workflow matches the plan.**
   - The `tests` matrix is shards 1–4 and runs `list ${{ matrix.shard }} 4`.
   - `quality` runs `check 4`.
   - No job still runs `bun test packages test`.
   - `tests` has the same services and env as `quality`, the same setup steps, and full history.
   - Every ffmpeg install is bounded and retried.
5. **Measuring.**
   - A file's time runs from its bun header to the next header, and the last file's to the summary
     line.
   - Groups that are not test files are ignored.
   - `measure` writes the table's shape, and refuses a log with no test files.
6. **The run itself.** This PR's own CI runs the new workflow, because pull requests use the
   head's workflow. All four shards must pass, which also proves no test file depended on running
   after another file in one shared database. The PR reports each shard's measured time.

- Tests: `test/ci-test-shards.test.ts`.

## Known gaps this leaves

- **The floor is one file.** About 80 minutes is the time of `current-film-mixed-worker.test.ts`
  alone. Going lower needs HV-016-34's option 1 or 2, both production design calls.
- **The measurements age.** Refresh them by hand from the shards' job logs:
  `bun scripts/ci/test-shards.ts measure <log>... "<source>" > scripts/ci/test-durations.json`.
  Stale numbers only unbalance the shards.
- **More runners, more setup.** Each shard repeats about 2 minutes of setup, and an apt flake now
  has four more chances to hit. The bounded retry is the mitigation.
