# HV-023-01 — One save replayed the whole history, once per sequence, twice over

epic: HV-023
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

`editHistoryReplay` walks a sequence's edit history from the root, and `applyEditOperation`
validates the whole timeline **twice** per event (`edit-timeline.ts:106`, `:133`). Nothing memoized
it anywhere in the repository.

One `PATCH /api/projects/:id/edit/sequences/:sid` runs it **2S + 2** times, where S is the number of
sequences in the project's library:

| Where | How many replays |
|---|---|
| `edit-library.ts:32` — `validateEditLibrary` on the way in, one per sequence | S |
| `edit-history.ts:40` — `appendEdit` reads the history it was handed | 1 |
| `edit-history.ts:49` — `append` validates the history it produced | 1 |
| `edit-library.ts:38` — `validateEditLibrary` on the way out, one per sequence | S |

`admitEditSource` is worse: 2S + 4.

Measured at a 256-clip root, which is the clip limit (`edit-timeline.ts:87`):

| events | stored | one replay | `appendEdit` | one PATCH, 1 sequence | one PATCH, 32 sequences |
|---|---|---|---|---|---|
| 62 | 78 KB | 313 ms | 748 ms | 1,375 ms | 20,788 ms |
| 125 | 105 KB | 625 ms | 1,263 ms | 2,513 ms | 41,286 ms |
| 250 | 160 KB | 1,243 ms | 2,626 ms | 5,111 ms | 82,170 ms |
| 500 | 271 KB | 2,638 ms | 4,471 ms | 9,747 ms | 173,284 ms |
| 999 | 491 KB | 4,822 ms | 10,392 ms | 20,036 ms | 318,976 ms |

`appendEdit ≈ 2 × replay` at every size, which is the trace above confirmed by the clock. Every one
of those numbers is inside the limits the routes themselves enforce: 1000 history events
(`edit-history.ts:20`), 256 clips, 32 sequences (`edit-library.ts:15`), 64 MiB of library metadata.
Half a megabyte of stored metadata buys **five minutes** of a single-threaded server, from an
ordinary edit, and every other project waits behind it. Because reaching *n* events takes *n*
requests, the cost of a normal editing session is quadratic in the session.

Memory matched: `edit-history.ts:21,29` keeps every node's full timeline, and one replay at 999
events moved RSS from 58 MB to 192 MB.

The same file one directory over already knew the answer — `edit-sources.ts:26` and
`edit-jobs.ts:53` both memoize validation, and `api/src/historical-validation-cache.ts` is a third.

## What this increment does

- **`editHistoryReplay` answers from its own revision.** The revision is `contentHash` of everything
  else in the history, so it is a sound key for exactly what the replay computes.
- **The revision is recomputed, not trusted.** A cache keyed on a number the caller supplies is a
  cache that will serve a validated answer to a forged question: a history naming a revision that
  was once valid, with different events, would have been handed the real history's replay. The hash
  is linear in the stored bytes — under a millisecond against the replay's seconds — so checking it
  first costs nothing and closes that entirely. A history that fails the check is not cached and
  falls through to the full replay, which refuses it exactly as it did before.
- **A hit hands out a copy.** Callers mutate what they are given (`edit-library.ts:44-48` rewrites
  `sequence.sourceRevisions` from a catalog), and the replay already cloned its timeline on the way
  out. The cache keeps the original and copies per call, so the change is *when* the work happens
  and never *what* it answers.
- **Bounded at 64 entries**, twice the 32 sequences a library may hold, so a save that touches every
  sequence twice does not evict its own working set. Least-recently-used, and the count is exported
  so the bound is a tested number rather than a comment.
- **And one quadratic beside it.** `edit-sources.ts:82` compared two file inventories with
  `known.some(k => !receipt.files.some(f => contentHash(k) === contentHash(f)))`, recomputing
  `contentHash(f)` for every pair — 2N² digests to compare N files with N files. A tier allows 60
  shots at up to 4 files each, so N is about 240 in practice. Measured: 15 ms at 60, 105 at 240,
  1,647 at 960, 6,736 at 1,920 — fourfold per doubling — against 0.6, 1.1, 3.8 and 6.8 ms for the
  same comparison with each digest taken once.

## Acceptance criteria

1. **A forged history is still refused**, hit or miss: same revision, fewer events, refused with
   "The edit history changed." — and the real history still answers afterwards, so the forgery does
   not poison the entry.
2. **A hit is a copy.** Mutating a returned timeline, its children, its catalog and its receipts
   changes nothing for the next caller, and the next caller's answer equals a replay of the same
   content built independently.
3. **The second replay of one history is at least twenty times faster than the first**, with the
   first measured above 20 ms so the ratio means something.
4. **`appendEdit` on a history already replayed costs under three quarters of a cold one**, because
   one of its two replays is now a hit and the other is new content and always will be.
5. **The cache is bounded**: two hundred distinct histories leave exactly sixty-four held.
6. Removing only the cache lookup — leaving everything else — makes criteria 3 and 4 fail (run by
   hand; recorded here). Removing the whole change makes the test file fail to load.

- Tests: `packages/planner/test/edit-history-replay.test.ts` (1–5).

## Known gaps this leaves

- **The cache is per process and never warmed.** The first PATCH after a deploy still pays 2S + 2,
  and so does the first PATCH to a sequence nobody has touched in 64 replays. The measured worst
  case is unchanged for that one request; what changes is that it stops being every request.
- **`append` re-replays from the root a history whose prefix was validated one line earlier.**
  `appendEdit` validates the history at `edit-history.ts:40` and `append` validates the history plus
  one event at `:49`; the second could extend the first's node map rather than rebuild it. That is a
  real halving of the cold path and it is a change to the replay's structure rather than a cache, so
  it is its own increment.
- **The memory shape is untouched.** `editHistoryReplay` still keeps every node's full timeline
  while it runs, so one cold replay of a 999-event history still costs ~130 MB of peak RSS. Sixty-four
  cached *results* are bounded and small — one timeline each, not one per node — but the transient
  is not.
- **Nothing measures the route.** The numbers above are of the primitives, timed directly. A test
  that drove `PATCH` through the server and asserted a wall-clock bound would be the honest
  end-to-end assertion and would be timing-dependent in CI, so the tests here assert the mechanism
  and the table records the route arithmetic.
