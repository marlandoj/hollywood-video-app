# HV-029-05 — A review link a real reviewer can use

epic: HV-029
release: 1 (build order step 3)
spend_usd: 0

## Goal

Release 1 exit criterion 2: a reviewer on a second device opens the review link, watches the film, and approves or requests changes. As shipped, that failed in ordinary use.

## The defects

1. **A view was counted before the route knew it had anything to show.** `useReviewLink` incremented first. Opening the link before the render finished (404), on a cut the gate refused (409), or while losing the first-view binding race (409) each spent one of three views. Three early opens made the link dead before the cut existed. This was the audit's "view burn" (AUDIT-2026-09-17, AUDIT-PHASE-2026-09-18).
2. **Every reload was a view.** Three reloads, and the link was dead.
3. **Whoever watched on the last view could not decide.** `submitReviewDecision` refused once `views >= 3`, and deciding spent a view of its own (`link.views += 1`). So the third viewer, and a reviewer who reloaded twice, could watch but never approve.
4. **The limit was fixed at 3.** FR-047 says "3 views (configurable)", and nothing configured it.

**The roadmap's "link-unfurl prefetch" wording overstated one cause.** The token is in the URL fragment, which link previewers never send, so a preview that only fetches the page never reached the API. `docs/REVIEW-LINKS.md` says what is true: a preview that runs the page's JavaScript counts as one viewer.

## What this increment does

- **A view is one viewer who was shown the cut.**
  - `openReviewLink` checks the link without counting anything.
  - The route then resolves the cut, runs the permission gate and settles the binding.
  - Only after that does `recordReviewView` count the view. If the last view went to someone else meanwhile, it returns `null`, and the route refuses rather than serving past the limit.
- **Viewer ids** (`packages/api/src/review-views.ts`):
  - The review page makes a random 128-bit id per tab, kept in `sessionStorage` (never a cookie).
  - It sends the id as `x-hv-review-viewer`.
  - The link stores only a domain-separated SHA-256, one per counted viewer.
  - A known viewer is not counted again, and may return after the limit is reached.
  - A missing or malformed id counts on every serve, as before.
- **Decisions:**
  - On a link that counts viewers, only a counted viewer may decide.
  - A link without viewer ids decides up to and including its last view.
  - Deciding no longer spends a view.
- **The owner's limit:** `maxViews` from 1 to 25 when creating the link, refused with 400 otherwise. Absent, it's FR-047's 3. The export gains a "Viewers allowed" box, and the review page states the remaining viewers.
- **Persistence:**
  - `ReviewLink` gains optional `maxViews` and `viewers`. Old links are unchanged and keep 3.
  - `validateSnapshot` refuses a limit outside 1–25, and refuses a viewer list that is longer than `views`, duplicated, or not hex hashes.
  - The Postgres wrapper passes the viewer and the limit through with the same signatures as `ProjectService`.
- **CORS:** allows `x-hv-review-viewer`.
- **Docs:** new `docs/REVIEW-LINKS.md`; `docs/STORAGE-DELIVERY.md`'s one-line summary is corrected.

## What this increment does not do

- **It does not add roles, comments, or revoke and reissue in the interface.** Those are Release 2's HV-029 slice.
- **It does not stop a determined reviewer from opening new tabs to use up the limit.** Each tab is a viewer. The limit bounds how far a link spreads; it is not an identity check.
- **A JavaScript-running link previewer is one viewer.** It can't be told apart from a person without tracking, which ADR-0018 rules out.
- **`useReviewLink` keeps its old per-call semantics** for callers without a viewer. It is implemented as open plus record, and the HTTP route no longer uses it.

## Acceptance criteria

All in `packages/api/test/review-views.test.ts`, over HTTP against a real server unless noted.

1. **Five opens before the render finishes cost nothing.** The first open after it finishes leaves 2 of 3. A cut the gate refuses costs nothing.
2. **Reloads don't count.** Four reloads by one viewer count once, a second viewer counts, and a third is refused, with or without an id. The first viewer can still return at 0 remaining.
3. **The link stores the hash, never the raw id.** A malformed id counts every serve.
4. **The viewer on the last view (limit 1) can decide,** and deciding spends no view. A viewer who was never shown the cut, or a request with no id, is refused with 409 on a counting link. A link without viewer ids decides after its third view, which the old rule refused.
5. **The limit:**
   - `REVIEW_MAX_VIEWS` is still 3, and a link created without `maxViews` admits 3.
   - 1, 10 and 25 are accepted.
   - 0, 26, −1, 1.5, "3", `null` and `true` are refused with 400 before any link exists.
6. **Persistence:**
   - The limit and viewers survive a restart.
   - A state snapshot carrying them validates.
   - A bad limit, a duplicated, non-hash or over-long viewer list, or a non-array list is refused.
