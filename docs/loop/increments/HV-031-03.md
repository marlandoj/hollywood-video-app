# HV-031-03 — A restore may not invent when or why a takedown happened

epic: HV-031
spend_usd: 0

## Goal

Make the two halves of a takedown record agree, since nothing made them agree; and remove the code that completed the missing half with the restore's own clock and the word "takedown", rather than guarding it.

## The defect

`PersistedState` keeps a takedown in two places. `takenDown` is a list of project ids — the tombstone, which is the part that matters for safety. `takedownLog` is a list of `{projectId, at, reason}` — when it happened and why, which is the part that matters legally.

`validateSnapshot` checked each list's own shape: `unique(takenDown)`, each id well-formed and absent from `projects`, and each log entry's `projectId`, `at` and `reason` individually. **It never checked that the two lists described the same set of projects.** So a snapshot could carry a tombstone with no record, and `importState` completed it:

```ts
const event = snapshot.projects.takedownLog.find(event => event.projectId === id);
const at = event?.at ?? new Date().toISOString();
await tx`insert into hv_projects (id,body,delete_after,taken_down_at,takedown_reason)
  values (${id},'{}'::jsonb,${new Date(Date.parse(at) + 30 * 864e5).toISOString()},${at},${event?.reason ?? "takedown"})`;
```

Three things follow, all silent:

1. **The database asserts a false date.** A takedown performed months ago is recorded as having happened at the moment of the restore, with no error, no counter and no log line.
2. **The reason becomes the word "takedown".** Whatever the operator actually recorded — a verified legal request, a specific complaint — is replaced by a generic string.
3. **The retention window moves.** `delete_after` is derived from the fabricated date, so the tombstone is silently extended thirty days past the restore instead of thirty days past the takedown.

And then `exportStateSnapshot` re-emits `taken_down_at` and `takedown_reason` as the record, so the fabricated values *become* the record and the original date and reason are unrecoverable. This is the falsification the P14 rights clause forbids, performed by the restore path itself.

**It was reachable without hand-editing anything.** `ProjectService.reload` reads `this.takedownLog = state.takedownLog ?? []` while `this.takenDown = new Set(state.takenDown ?? [])`. A state file written before `takedownLog` existed therefore loads tombstones with no records at all, and the next snapshot taken from that service carries the mismatch into the import.

## The shape of the repair

**The two lists are held in exact correspondence, at the point an operator can still fix the file.** `validateSnapshot` now requires: one record per tombstone (`missing`), no record for a project that is not tombstoned (`orphaned`), and no two records for the same tombstone (`unique`). The error names the count and the project ids, because an operator repairing a snapshot needs to know which projects to look up. An import is a deliberate operator action, so refusing it is proportionate; the alternative — completing the record — is the defect.

The third check matters as much as the first two: `ProjectService.takedown` appends exactly one record per project, guarded by its own `takenDown.has` early return, so two records for one tombstone are two different answers to "when did this happen".

**The fabrication is removed, not guarded.** The loop now walks the *records* rather than the tombstones:

```ts
for (const event of snapshot.projects.takedownLog) {
  await tx`insert into hv_projects (…) values (${event.projectId}, …, ${event.at}, ${event.reason})`;
}
```

Validation holds the two lists in exact correspondence, so this inserts the same rows either way — but iterating the records leaves **no "tombstone with no record" case to handle**, and therefore nothing to complete. A first draft kept the `takenDown` loop and added `if (!event) throw`; perturbation T1 restored the `??` defaults on that version and **nothing failed**, because validation had already made the guard unreachable. A guard that cannot fire is not protection, it is a place for the defect to come back to. Removing the loop is what makes the fabrication unexpressible.

## Declared changes beyond the defect

- **A snapshot that was previously accepted can now be refused.** That is the entire point, but it is a behaviour change at a restore boundary and deserves saying plainly: an operator holding a state file with a tombstone and no record can no longer import it, and will see an error naming the project. The repair is to add the record — the date and reason are in whatever the takedown was raised from — or, if the tombstone itself is wrong, to remove it. There is no automatic repair, because inventing the missing values is the thing this increment removes.
- **Every staging state file was checked before tightening.** All five `projects.json` files under the staging runtime carry `takenDown: []`, `takedownLog: []` and the `takedownLog` key present, and the checked-in golden archive fixture has both lists empty. Nothing in the deployment or the repository is refused by the new checks.

## What this increment does not do

- **It does not stop `ProjectService.reload` loading a mismatched state.** `state.takedownLog ?? []` still accepts a file with tombstones and no records, and the API still serves from it. Refusing there would convert a record-keeping gap into a total outage — `reload()` runs on every method call, so the API could not even enforce the takedowns it holds — and would make the tombstone *less* effective, not more. The gap becomes visible at the moment it can be acted on: any attempt to move that state into PostgreSQL is now refused with the project named. That is a deliberate boundary, not an oversight, and the residual is that a live JSON deployment can hold a tombstone whose date and reason are unknown without saying so.
- **It does not backfill or repair anything.** No migration; no rewrite of existing rows. `taken_down_at` values already fabricated by a previous restore stay as they are, because editing a rights record after the fact to say something it did not say is the opposite of what this increment is for. There is no way to tell a fabricated value from a real one after the fact, which is precisely why the fabrication had to stop.
- **It does not give takedown an operator surface.** The audit's finding stands: takedown is library-only, with no route and no console action. Nothing here changes that.
- **It does not address the other takedown findings in this epic.** `HV-031-01` stopped generation continuing after a takedown; this fixes the restore record. P14's absent surface — rights ledger, legal hold, appeals, image and audio moderation, watermarking, signing — is untouched.

## Acceptance criteria

1. A tombstone with no takedown record is refused, and the error names the count and every affected project id. — `packages/storage/test/takedown-record.test.ts` case 1, including the two-tombstones-one-record shape; T2.
2. A takedown record naming a project that is not tombstoned is refused. — case 2; T3.
3. Two records for the same tombstone are refused. — case 2; T4.
4. A snapshot with no takedowns at all is still valid, so the tightening does not refuse the ordinary case. — case 3.
5. A restore writes the takedown's own date and its own reason. — case 4; T1, T6, T7.
6. `delete_after` is derived from the takedown's date, not the restore's clock, so a restore cannot extend a tombstone's retention. — case 4, which asserts the computed value and that it is already in the past; T5.
7. An export round-trips the record it was given, and the round trip passes the validation that refused the corrupt input. — case 4.
