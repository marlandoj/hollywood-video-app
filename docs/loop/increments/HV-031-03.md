# HV-031-03 — A restore may not invent when or why a takedown happened

epic: HV-031
spend_usd: 0

## Goal

Make the two halves of a takedown record agree, since nothing made them agree; stop the restore completing the missing half with its own clock and the word "takedown"; and make sure the record the restore now preserves survives the next retention sweep, because the fix's own retention arithmetic made that sweep reach it.

## The defect

`PersistedState` keeps a takedown in two places. `takenDown` is a list of project ids — the tombstone, which is the part that matters for safety. `takedownLog` is a list of `{projectId, at, reason}` — when it happened and why, which is the part that matters legally.

`validateSnapshot` checked each list's own shape: `unique(takenDown)`, each id well-formed and absent from `projects`, and each log entry's `projectId`, `at` and `reason` individually. **It never checked that the two lists described the same set of projects.** So a snapshot could carry a tombstone with no record, and `importStateSnapshot` completed it:

```ts
const event = snapshot.projects.takedownLog.find(event => event.projectId === id);
const at = event?.at ?? new Date().toISOString();
await tx`insert into hv_projects (id,body,delete_after,taken_down_at,takedown_reason)
  values (${id},'{}'::jsonb,${new Date(Date.parse(at) + 30 * 864e5).toISOString()},${at},${event?.reason ?? "takedown"})`;
```

Three things follow, all silent:

1. **The database asserts a false date.** A takedown performed months ago is recorded as having happened at the moment of the restore, with no error, no counter and no log line.
2. **The reason becomes the word "takedown".** Whatever the operator actually recorded — a verified legal request, a specific complaint — is replaced by a generic string.
3. **The retention window moves.** `delete_after` is derived from the fabricated date, so the tombstone is silently extended thirty days past the restore instead of thirty days past the takedown.

`exportStateSnapshot` then re-emits `taken_down_at` and `takedown_reason` as the record, so the fabricated values *become* the record and the original date and reason are unrecoverable. This is the falsification the P14 rights clause forbids, performed by the restore path itself.

**It was reachable without hand-editing anything.** `ProjectService.reload` reads `this.takedownLog = state.takedownLog ?? []` while `this.takenDown = new Set(state.takenDown ?? [])`, and `snapshot()` writes both back — so a state file written before `takedownLog` existed loads tombstones with no records and persists the mismatch forward. The same leniency can manufacture the other two shapes as well, which an earlier draft of this doc did not say: a file carrying a record for a still-live project loads clean, and `takedown()` on that project then appends a second record, because its guard tests `takenDown` and not `takedownLog`. All three of the new checks are reachable that way, not just the first.

## The shape of the repair

**The two lists are held in exact correspondence, at the point an operator can still fix the file.** `validateSnapshot` now applies five checks to the takedown record: no duplicate record per project, one record per tombstone (`missing`), no record for a project that is not tombstoned (`orphaned`), a non-empty reason, and a date that is not in the future. The first three errors name the count and the project ids, because an operator repairing a snapshot needs to know which projects to look up. An import is a deliberate operator action, so refusing it is proportionate; completing the record is the defect.

The duplicate check matters as much as the correspondence: `ProjectService.takedown` appends exactly one record per project, guarded by its own `takenDown.has` early return, so two records for one tombstone are two different answers to "when did this happen".

**A record has to be plausible, not merely present.** `date()` is `Number.isFinite(Date.parse(...))` and `text()` is a length bound, so a first draft of this increment accepted `reason: ""` and `at: "1970-…"` — and, worse, `at: "2099-01-01"`, which since `delete_after` derives from `at` bought a seventy-three-year extension of the tombstone. The cross-check moved the fabrication out of the code and into whatever an operator types into the file; requiring a non-empty reason and a date no more than `TAKEDOWN_CLOCK_SKEW_MS` ahead of the validating host's clock is what stops the fabrication simply changing hands.

**The obvious shape of the fabrication is removed, not guarded — and that is a smaller claim than the first draft made.** The insert loop now walks the *records* rather than the tombstones, so there is no `event?.at ?? …` to write. A first draft kept the `takenDown` loop and added `if (!event) throw`; perturbation T1 restored the `??` defaults on that version and **nothing failed**, because validation had already made the guard unreachable. That is a real reason to prefer the rewrite. But the draft then claimed "removing the loop is what makes the fabrication unexpressible", and that is false: `takenDown.includes(event.projectId) ? event.at : new Date().toISOString()` re-expresses it inside the new loop. **What actually holds the record honest is the correspondence check**; the loop rewrite removes the shape a maintainer would reach for by accident, and the new loop depends on that same check just as much — only in the other direction, which is the next paragraph.

**The new loop's dependency runs the opposite way, and it needed its own test.** Because the loop is driven by the records, a tombstone with no record is not written to `hv_projects` in *any* form — the safety half is silently dropped, which is worse than the false date the old loop wrote. The critic pass on this increment weakened the check to `missing = recorded.size ? [] : takenDown` and measured the whole suite green, because both cross-checks were only ever exercised with the *other* list empty: two tombstones and one record appeared nowhere in the suite, while the doc's acceptance criterion claimed it did. That shape is now a case, and so is a PostgreSQL restore of two tombstones and two records that asserts the row count and each row's own values.

**The sweeper had to change too, and this is the part the fix itself caused.** Deriving `delete_after` from the takedown's own date is correct — a takedown from months ago has an overdue retention window — and it makes the restored row immediately sweep-eligible. `PostgresRetention.purgeProject` then ran `takedown_reason = 'content removed'` **unconditionally**, while coalescing `taken_down_at` on the line directly above. So the first sweep tick after a restore erased the reason the restore had just preserved, and the next export emitted the generic string as the record: the exact harm this increment exists to remove, now triggered by its own arithmetic. The measured before-and-after was `reason "verified legal request" → reason "content removed"` after one sweep. `takedown_reason` is now coalesced like its neighbour. Preserving the date and losing the reason would have been a worse record than the one this increment replaced.

## Declared changes beyond the defect

- **`PostgresRetention.purgeProject` no longer overwrites a recorded takedown reason.** Required by the change above. A project purged for ordinary expiry still gets `"content removed"`, because that row has no recorded reason and the generic string is the right value there; a case pins both halves.
- **`exportStateSnapshot` names a row it cannot export instead of emitting an invalid record.** `takedown_reason` is nullable, and the export read it with no fallback while `PostgresProjectService` read the same column as `row.takedown_reason ?? ""` — the two disagreed. A NULL therefore produced a record the validator the export returns through then refused, with the generic message `invalid takedown history` naming neither the project nor the problem, which blocked a rollback export an operator might be running mid-incident. It now refuses with the project id and the reason why. **The asymmetry with `projects.ts` is kept deliberately**: refusing to serve one project because its takedown reason is missing would be worse than substituting an empty string there, while refusing to *export* is the right answer because an export becomes the record.
- **`validateSnapshot` gained a `now` parameter**, defaulting to `Date.now()`, so the future-date boundary can be asserted against a chosen instant rather than against whenever the suite runs.
- **A snapshot that was previously accepted can now be refused.** That is the entire point, but it is a behaviour change at a restore boundary: an operator holding a state file with a tombstone and no record can no longer import it, and will see an error naming the project. The repair is to add the record from whatever the takedown was raised from, or to remove the tombstone if it is wrong. There is no automatic repair, because inventing the missing values is what this increment removes.
- **The rollback direction is unaffected; the re-cutover direction can be blocked.** `validateSnapshot` runs before `database.sql.begin`, so a refusal cannot leave partial state and nothing is dropped. The documented rollback (PostgreSQL → JSON, `docs/STORAGE-DEPLOYMENT.md:15`) derives both lists from the same row and can never trip the new correspondence checks, so an operator can always retreat. What can be blocked is the JSON → PostgreSQL cutover, including the re-cutover after a rollback — and that is reachable exactly in the situation this increment declines to fix, a `reload()` that accepted and re-persisted a mismatched file. An earlier draft did not name that.

## What this increment does not do

- **It does not stop the sweeper fabricating a takedown record for a project that merely expired.** `purgeProject` sets `taken_down_at = coalesce(taken_down_at, <sweep clock>)` for *every* purged project, including one that only reached its retention date and was never subject to a takedown, and `exportStateSnapshot` keys on `taken_down_at` alone — so that project is emitted in both `takenDown` and `takedownLog` as `{at: <sweep time>, reason: "content removed"}`. **That is the same three harms this increment fixes, on the ordinary-expiry path that every project traverses, rather than the restore path that runs at cutover.** The new cross-checks cannot catch it, because both lists are derived from the same row and therefore always agree. Fixing it properly means distinguishing expiry from takedown in the schema — a new column, a migration, and a G4 gate — so it is not folded in here. A case pins the current behaviour so the follow-up has a failing expectation to change rather than a sentence to rediscover.
- **It does not stop `ProjectService.reload` loading a mismatched state.** `state.takedownLog ?? []` still accepts a file with tombstones and no records, and the API still serves from it. `this.reload()` is called from fourteen places in `packages/api/src/index.ts`, one of them the constructor, and `reload` is the only path that populates `takenDown` — so a throw there fails construction, not merely one call, and it would break `isTakenDown()`, which is how the API enforces the tombstones it holds. Refusing there would convert a record-keeping gap into a total outage and make the tombstone *less* effective. The gap becomes visible at the moment it can be acted on: any attempt to move that state into PostgreSQL is refused with the project named.
- **It does not backfill or repair anything.** No migration; no rewrite of existing rows. `taken_down_at` values already fabricated by a previous restore stay as they are, because editing a rights record after the fact to say something it did not say is the opposite of what this increment is for — and there is no way to tell a fabricated value from a real one after the fact, which is precisely why the fabrication had to stop.
- **It does not give takedown an operator surface.** The audit's finding stands: takedown is library-only, with no route and no console action.
- **It does not address the rest of P14.** `HV-031-01` stopped generation continuing after a takedown and `HV-031-02` fixed the provenance timestamp; the absent surface — rights ledger, legal hold, appeals, image and audio moderation, watermarking, signing — is untouched.

## Acceptance criteria

1. A tombstone with no takedown record is refused, naming the count and every affected project — for no records at all, and for **two tombstones with one record**, which is the shape that distinguishes a real correspondence check from one that only fires on an empty list. — `packages/storage/test/takedown-record.test.ts` case 1; T1, T2.
2. A takedown record naming a project that is not tombstoned is refused, with a non-empty `takenDown` as well as an empty one. — case 2; T3.
3. Two records for the same tombstone are refused. — case 3; T4.
4. A record with an empty, whitespace or tab-only reason is refused, and so is one dated beyond the declared clock-skew allowance; the boundary is asserted at a chosen instant through the `now` parameter. — case 4; T9, T10.
5. A snapshot with no takedowns at all is still valid. — case 5.
6. A restore writes **each** takedown's own date and reason, with the row count asserted, so a dropped tombstone is a failure. — case 6; T1, T6, T7.
7. `delete_after` is derived from each takedown's own date, not the restore's clock. — case 6; T5.
8. An export round-trips both records it was given. — case 6.
9. **A retention sweep purges the restored tombstone and keeps the reason it was given**, while a project purged for ordinary expiry still gets the generic string. — cases 7 and 8; T8.
10. A row tombstoned with no recorded reason is named by the export rather than emitted as a record the validator then refuses. — case 9; T11.

## Perturbations

Each edit was applied to `packages/storage/src/snapshots.ts` or `packages/storage/src/retention.ts`, the suite measured, and both files restored from byte copies. The suite is `packages/storage/test/takedown-record.test.ts`: 9 tests, five pure and four against per-run PostgreSQL databases the fixture creates and drops one per case — a state import refuses a non-empty destination, so they cannot share one, and staging is never touched.

Without the three database URLs the four PostgreSQL cases skip, so T1, T5, T6, T7, T8 and T11 measure `5 pass / 0 fail / 4 skip` rather than a failure. CI supplies the URLs at the job level.

|---|---|
| baseline | `9 pass / 0 fail` |
| T1 — the `takenDown` loop and its `??` defaults restored, with the missing-record check removed | `8 pass / 1 fail` |
| T2 — **the missing-record check weakened to fire only when there are no records at all** | `8 pass / 1 fail` |
| T3 — **the orphaned-record check weakened to fire only when there are no tombstones at all** | `8 pass / 1 fail` |
| T4 — duplicate records per tombstone allowed again | `8 pass / 1 fail` |
| T5 — retention derived from the restore's clock instead of the takedown's date | `7 pass / 2 fail` |
| T6 — the takedown's reason replaced by the generic word at restore | `7 pass / 2 fail` |
| T7 — the restore stamps its own clock as the takedown date | `7 pass / 2 fail` |
| T8 — **the sweeper overwrites the recorded reason again, as it shipped** | `8 pass / 1 fail` |
| T9 — **an empty reason accepted** | `8 pass / 1 fail` |

**The six bold rows are the critic pass's findings.** T2 and T3 were green against the first draft: both cross-checks were exercised only with the other list empty, so `missing = recorded.size ? [] : takenDown` passed the whole suite while accepting a snapshot whose second tombstone the restore then dropped entirely. T8 is the regression the fix itself introduced. T9, T10 and T11 are the plausibility and NULL-reason holes.

**T1's first measurement is why the loop was rewritten**, and it is worth stating precisely: applied to the draft that kept the `takenDown` loop with `if (!event) throw`, restoring the `??` defaults measured `4 pass / 0 fail` — validation had made the guard unreachable, so the fabrication could be put straight back and nothing noticed. T1 above is the compound now required to express it: the loop *and* the correspondence check both have to go. That does not make the fabrication unexpressible, only unavailable to a maintainer writing the obvious thing; the correspondence check is what holds the record honest either way.
