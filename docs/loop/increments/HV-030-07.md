# HV-030-07 — A finished film thrown away by the step after it, and paid for again

epic: HV-030
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

A critic pass over `packages/frontend`.

`studio.js` states the rule itself, in `voiceFinal`'s own comment:

> Idempotency keys are fixed by line, character and voice policy, so a retry or a second pass never
> pays for a line twice.

Every cheap render in the file obeys it — `crew-voices-${cut.id}`, `crew-score-${cut.id}`,
`crew-titles-${cut.id}`, `${id}-${spec.revision}`. The three **picture** renders, which are the
expensive ones, did this:

```js
const queued = await api(projectPath("/jobs"), json("POST", {idempotencyKey: crypto.randomUUID()}));
```

A fresh UUID is the one value that cannot deduplicate anything. And the server did not need to be
told: `POST /projects/:id/jobs` with **no** key derives one from what the render is *of* —
`${stage}:${scriptVersion}:cast-${castingVersion}[:direction-${directionVersion}]` — and answers a
repeat with the job it already admitted (`server.ts`, over `queue/src/index.ts:344` and
`storage/src/ledger.ts:98`). The studio overrode its own server's correct answer with a random one.

On its own that is a latent risk. What made it reachable is two unguarded steps that run **after** a
render has been paid for:

- `approveRoughCut` ran `voiceFinal` bare, between `scoreFinal` and `titleFinal`, which are both
  wrapped in `try/catch` and add a note. Any failure in it — starting with the first
  `GET /audio-takes` — propagated out of the approval **before** the `state = {...state, step:
  "final", final, …}` assignment. The finished final render was dropped from state, the step stayed
  `rough-cut`, and the only control left on screen was "Approve and make the final film".
- `approveLook` ran `pinStills` bare after the rough cut had been rendered and polled — a still
  fetch, an anchor upload and a `PUT /direction` per shot, any of which can fail on a version
  conflict — with the same consequence one approval earlier.

So: the render is paid for, the state is discarded, and the only available action mints a new random
key and pays again. Measured on a fake that applies the server's own rule and charges $1 for a rough
cut and $8 for a final:

```
after the failure:  step = rough-cut,  state.final = undefined
final renders admitted after two presses = 2, with 2 distinct random keys
the spend line still on screen           = $1.00 of its $40.00 limit
the ledger                               = $9.00
```

The number the creator reads while deciding whether to press again was the number from before the
render that press already paid for, because `spend` was refreshed only in the object literal on the
success path.

## What this increment does

- **The three picture renders send no request key.** The server's derived key stands, so a second
  press is answered with the first job. It is content-derived, so it moves exactly when it should: a
  re-plan changes the cast or direction version, a new screenplay changes the script version, and
  pinning the stills moves the direction version — which is why the pinned re-cut is correctly its
  own job rather than needing a key of its own.
- **A paid render goes into the state the moment it lands**, before anything that can fail is
  attempted. Everything after that point costs a note, not a film.
- **`voiceFinal` is guarded like its two siblings**, and says what it could not do: the film keeps
  its temporary voices.
- **`pinStills` is guarded**, and says so on the rough-cut screen: the final begins from the script.
  `renderRoughCut` draws those notes, as `renderFinal` already drew its own.
- **The spend is read again after each render lands**, so the figure beside the button is never the
  pre-render one.

## Acceptance criteria

1. **A finishing step that fails keeps the film it was finishing**, with the step advanced, the
   film in state, the failure named in `finishNotes`, and **one** final render admitted.
2. **And so does the approval before it**, when pinning the storyboard stills fails: the rough cut
   is kept with a note, one animatic render is admitted, and the final is then made from it.
3. **The spend the creator reads is the post-render figure** — $9 in the ledger and $9 on screen,
   asserted after a failing finishing step.
4. **Pressing a picture render twice admits one job**, driven twice through a fake that applies the
   server's own rule, including a mid-poll connection failure and a retry; and the pinned re-cut is
   a second job under the key `animatic:1:cast-1:direction-2`, named in full.
5. **No picture render mints a key that cannot deduplicate**, asserted over the source: no
   `crypto.` appears beside an `idempotencyKey`, and the five that remain are all fixed strings.
6. **The rule the studio now relies on is exercised through the real server**: a render asked for
   twice with no key is one job; three presses with fresh random keys are three films and three
   presses without are one; and a new screenplay version is correctly a different key.
7. Reverting `studio.js` makes all five frontend tests fail.

- Tests: `packages/frontend/test/studio-retry.test.js` (1–5),
  `packages/api/test/job-request-key.test.ts` (6).

## Known gaps this leaves

- **Nothing reconciles a film that was paid for twice before this.** Any project that hit this on
  staging has two admitted renders of one film in its ledger, and there is no path that notices.
  Staging's picture pool is `mock` and spend is $0, so there is nothing to reconcile today.
- **`pollJob` still has no poll cap.** `for (;;)` with a 1.5 s wait, against `INSPECTION_POLLS = 120`
  on the inspection loop next to it: a job that never leaves `queued` holds the approval screen
  forever with no way out but a reload. That is a different defect and deserves its own increment.
- **The retry story is about the creator pressing again, not about two tabs.** Two approvals racing
  in two windows now converge on one job instead of two, which is an improvement, but nothing in the
  studio serialises them and the second one's `pinStills` will still fail on a version conflict —
  now with a note instead of a lost film.
- **The `POST /jobs` route does not compare a request hash.** Its siblings — the graphic, lip-sync
  and delivery routes — refuse a key that belongs to a different request. This one returns the
  existing job whatever was asked for. With a derived key that cannot happen, because the key *is*
  the request; with a caller-supplied key it can, and the Director's desk supplies its own.
- **Two `fetch` calls in `studio.js` are not pinned to `credentials: "omit"`/`redirect: "error"`**
  (`:19` and `:302`) while every other asset fetch in the frontend is. That is a real inconsistency
  with the house rule, found in the same pass and not fixed here because it is a different subject.
