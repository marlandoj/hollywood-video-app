# HV-024-09 — A sound-mix key used on one cut got that cut's job back on another

epic: HV-024
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

`POST /sound-mixes/:cut` looks its idempotency key up among the project's jobs. When it finds one,
it answers with that job if the request body hashes the same. The cut is in the URL, not the body,
so the same session sent with the same key to a second cut hashed the same. It came back 202 with
the first cut's sound mix. The caller took that for the second cut's mix, and nothing was queued for
it.

The sibling routes each bind the resource in the URL into this check:

- lip-sync and dialogue hash the source job;
- graphics hash the graphic id;
- editorial compares the sequence;
- delivery binds the output revision.

## What this increment does

- **The sound route also compares the cut** the found job was made from. A key used on another cut is
  refused: *"This key belongs to a different sound session."*
- **The same request to the same cut** is answered with its job, as before.

## Acceptance criteria

1. **Another cut.** A sound-mix key used on one cut is refused with 400 on another, and nothing is
   queued for that cut.
2. **The same cut.** The same request to its own cut is answered with its job.
3. Reverting `sound-api.ts` fails criterion 1.

- Tests: `packages/api/test/sound-key-other-cut.test.ts`.
