# HV-029-07 — The other twenty listings

epic: HV-029
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

HV-029-06 found that `scopedJobs(projectId)` narrows the *store* on PostgreSQL and hands back the
shared store on the JSON backend — which is what `createApiServer()` defaults to and what
`docker-compose.yml` runs — where `all()` is every job in the studio. Thirteen listings in
`server.ts` knew that and wrote `job.projectId === project.id` by hand. The character-sheet listing
did not, and a stranger with their own free project could read another project's character-sheet
jobs.

It put the filter in one place in that file and asserted over the source that `all()` was called
nowhere else in it. Its own gap list said what was left:

> **This is `server.ts` only.** `graphic-api.ts`, `sound-api.ts`, `lipsync-api.ts`,
> `delivery-api.ts` and `edit-api.ts` are handed `scopedJobs` and call `all()` themselves. Each one
> filters correctly today — read, one by one, while writing this — but nothing keeps them doing so,
> and the guard above does not reach them.

There were twenty such call sites across **six** modules (`living-script-generation-api.ts` too).
Every one of them was correct. That is the point: the thirteen in `server.ts` were correct as well,
which is precisely what made the fourteenth invisible. A rule that twenty places follow by hand is a
rule with twenty chances to be broken, and it has already been broken once.

## What this increment does

- **`projectJobs(store, projectId)` in `packages/api/src/project-jobs.ts`** is the narrowing, and it
  is the only place under `packages/api/src` that calls `all()` on a per-project store.
- **Twenty call sites go through it** and drop their hand-written conjunct. `server.ts` keeps its
  local name and delegates, so its fourteen call sites are unchanged.
- **The guard reads the whole package.** Every `X.all()` in every source file is collected with the
  thing it is called on, and the result must be exactly: the helper's own
  `store(projectId).all()`, and `server.ts`'s two reads of the **unscoped** store — the health
  route's queue depth and the operator's diagnostics, both of which are about the studio and not
  about a project. Anything else fails the test rather than the review.

Nothing about what any route answers changes. Every filter removed was replaced by the same filter
one call deeper, and the api suite is the assertion that says so.

## Acceptance criteria

1. **The package calls `all()` in one place**, asserted by collecting every call and its receiver
   across every file in `packages/api/src` and comparing the whole map — so a new file with a new
   call fails, not just a new call in a known file.
2. **The two deliberate studio-wide reads are named**, rather than excluded by a pattern that would
   also excuse a mistake.
3. **At least thirty-four call sites go through the helper**, which is the fourteen in `server.ts`
   plus the twenty moved here.
4. **The character-sheet leak stays closed** and the listing stays project-scoped — the two
   behavioural tests from HV-029-06, unchanged.
5. **The api suite passes**, which is what says the twenty replacements changed no answer.

- Tests: `packages/api/test/project-scoped-jobs.test.ts` (1–4), `bun test packages/api` (5).

## Known gaps this leaves

- **This is a hygiene increment, not a fix.** No route was serving another project's jobs before it;
  HV-029-06 was the one that was. What changes is that the rule is now structural instead of
  repeated, which is the only reason to do it at all — and it should be read as such rather than as
  a second leak.
- **The guard is textual.** It reads the source for `.all()` and its receiver; a listing that
  obtained a store some other way, or aliased the method, would pass it. A type that made an
  unscoped store unusable from a route would be the real answer and is a much larger change to the
  two store classes.
- **`edit-api.ts` still calls `this.context.store(project.id).get(...)` directly** in several
  places, and `get` is project-safe only because every caller checks the job's `projectId`
  afterwards — which four of them do explicitly. That is the same shape one method over, and it is
  not covered here.
