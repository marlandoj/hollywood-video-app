# HV-029-03 — the media path checked permission only for jobs shaped a certain way

epic: HV-029
spend_usd: 0

## Goal

Make `/artifacts/` ask one question — *what guards this job's media?* — answered by the job's stage, rather than six questions each answered only when the job happened to carry a particular optional field. Close the hole that left a plain cut's media ungated, and make the stages that are still ungated say so out loud.

## The defect

The artifact route verified the token signature, the project's existence, its `deleteAfter` and its takedown state. Then:

```ts
if(mediaJob?.output?.shotRenders?.some(r=>r.clip.speech)){…assertSelectedOutput…}
if(mediaJob?.lipSync){…}  if(mediaJob?.dialogueReplacement){…}
if(mediaJob?.soundMix){…} if(mediaJob?.pictureEdit){…}  if(mediaJob?.assemblyEdit){…}
```

Six blocks, each reached only when the job carried one particular optional field. **A plain `animatic` or `final` cut carries none of them** — unless one of its shots happens to have dialogue, which is what the first line tests. So the cut of a scene with no dialogue was served with no permission check at all.

**The speech condition is wrong on its own terms, not merely incomplete.** `assertSelectedOutput` reaches `assertDialoguePermissions`, which calls `assertCurrentCastPermission` for every shot's `characterIds`, and `charactersForScene` (`packages/planner/src/casting.ts:139`) matches a character named in a scene's **action** exactly as readily as one with a line:

```ts
const source = [scene.heading, ...scene.action, ...scene.dialogue.flatMap(…)].join("\n");
return snapshot.characters.filter(character => [character.name, ...character.aliases].some(name => mentioned(name, source)));
```

A revoked character standing silently in frame is that character's likeness, and permission is about the likeness. Gating on `clip.speech` asks whether they *said* anything.

**This is where HV-029-02's remaining bypass lived.** That increment closed the review path — an unbound review link skipped the permission gate — and recorded, without fixing, that redeeming the signed artifact URL the answer contained re-checked permission only for certain job shapes. This is that check. An artifact token's `exp` is clamped to `min(job.linkExpiresAt, project.deleteAfter, now + 30 days)`, so expiry and project deletion were enforced transitively even here; cast revocation was not enforced at all for a silent cut, on any path, for owner or reviewer alike.

**The existing coverage hid it.** `packages/api/test/performances.test.ts` asserts that after revoking a character the cut's `mp4Url` answers 404 — but its fixture's shots have dialogue, so it exercised precisely the branch the condition did reach.

## The shape of the repair

**One total function over `JobStage`.** `artifactPermission(stage)` returns the rule that guards that stage's media, and the route calls whatever comes back. Adding a stage without deciding what guards its media is now a type error and a test failure, rather than a silent hole — which is the actual defect, since nothing was ever *decided* about a plain cut; it simply did not match any of the six conditions.

**`null` is a decision, and the two reasons for it are kept apart.** `ARTIFACT_PERMISSION_OWN_PATH` (`motion-graphic`, `audio-take`) are answered earlier in the route by their own rules — a graphic checks `assertGraphicPermission` plus its retained bundle, an audio take checks take permission plus the voice policy's permission revision. `ARTIFACT_PERMISSION_UNGUARDED` (`take-preview`, `take-final`, `character-sheet`) have **no** gate, which is stated below rather than left to be discovered.

**Which file list an artifact must appear in still depends on the job's shape**, and that part stays keyed to the shape — it is a lookup, not a permission decision.

## What this increment does not do

- **It does not guard takes or character sheets, and that gap is the point of `ARTIFACT_PERMISSION_UNGUARDED`.** A take and a character sheet carry the cast's likeness exactly as a cut does, so the same revocation should stop serving them. Neither can be expressed with what exists: `assertSelectedOutput` answers "is this a selectable retained cut", which they are not, and `assertDialoguePermissions` calls `renderShots`, which refuses a take outright — measured, not assumed: routing `take-final` through it answered *"Reuse requires a film render with an admitted provider plan."* A take's permission has to be derived from `shotTakes.source` and its scene, and a character sheet's from its subject. That is new permission logic on a media path and it deserves its own increment with its own adversarial pass, rather than a line written in passing here. Until then a revoked character's take clips and character sheet keep being served for up to `min(linkExpiresAt, deleteAfter, 30 days)`.
- **It does not change how long an artifact token lives.** A token minted before a revocation is still a valid token; what changed is that redeeming it now consults the permission. Nothing revokes tokens themselves.
- **It does not measure the cost of checking on every request.** `assertSelectedOutput` on a film stage parses the screenplay and re-derives the shot plan, and HLS playback fetches many segments. That cost was already being paid on every lip-sync, sound, picture-edit and assembly-edit segment before this increment; it now extends to plain cuts. No caching is introduced, because a cached permission check is how a bypass gets rebuilt — but if this shows up in the operator panel's latency rows, the answer is a shared derivation per request, not a memo of the verdict.
- **It does not audit the non-media routes.** The same optional-field shape appears at `server.ts:457` in the owner's job view, where a refusal is swallowed into `mediaUnavailable` and a plain cut is never checked. That is a display path rather than a media path, and it is left for the same increment that does takes.

## Acceptance criteria

1. A cut whose every shot is silent, and whose character is named only in the scenes' action, stops being served — `mp4`, HLS playlist and captions alike — the moment that character's permission is revoked; and it was served before the revocation, so the refusal is the revocation. — `packages/api/test/artifact-permission.test.ts` case 1; Y1, Y2.
2. The speaking cut still refuses, so the narrower condition was not the thing carrying it. — case 2; Y1.
3. Every `JobStage` has a named rule: the switch is total with no `default:`, the stage union is read from where it is declared, every stage is in exactly one of gated / own-path / unguarded, and the route selects by stage rather than by any job-shaped field. — case 3; Y3, Y4, Y5.
4. The unguarded stages are named in this document, not only in the code. — case 3.

## Perturbations

Each edit was applied to `packages/api/src/server.ts`, the suite measured, and the file restored from a byte copy. The suite is `artifact-permission.test.ts` plus `performances.test.ts` and `takes.test.ts`, the two existing suites that exercise this route's permission behaviour.

| perturbation | artifact permission |
|---|---|
| baseline | `9 pass / 0 fail` |
| Y1 — the gate goes back to `if(mediaJob?.output?.shotRenders?.some(r=>r.clip.speech))` | `7 pass / 2 fail` |
| Y2 — the gate runs but the project passed to it is given a future `deleteAfter` | `8 pass / 1 fail` |
| Y3 — `character-sheet` is answered by `default: return null` instead of a case | `8 pass / 1 fail` |
| Y4 — `take-preview` is moved from the unguarded list to the own-path list | `8 pass / 1 fail` |
| Y5 — the route picks the rule from the job's optional fields instead of its stage | `6 pass / 3 fail` |

Y1 is the shipped defect. It takes two of nine: the silent cut is served again, and the family case sees `clip.speech` back in the route. Y5 is the same defect written the other way round — choosing the rule by shape rather than by stage — and it takes three, because the silent cut, the *speaking* cut and the family case all fail: a plain cut carries none of those fields either way. Y3 and Y4 are the guard on the declaration itself: a `default:` makes the switch total without deciding anything, and moving a stage between the two `null` lists changes what the code claims about it while changing no behaviour at all.
