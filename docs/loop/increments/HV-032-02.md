# HV-032-02 — Give the fair-share weight a horizon

epic: HV-032
spend_usd: 0

## Goal

Stop the queue's fair-share weight being a lifetime total, because a lifetime total inverts the requirement it exists to satisfy; declare the horizon once, since two cost ledgers compute the weight; and hold the two implementations to the same answer rather than only to the same constant.

## The defect

`FR-029` and `AC-025` say: *each anonymous project gets a weighted fair share of GPU time; no project can starve another* (`docs/PRD.md:164`, `docs/spec/build-spec.prompt.md:107,218`). The weight was `CostLedger.gpuSecondsByProject()` — a sum over **every event the ledger had ever recorded**, with no window:

```ts
for (const event of this.state.events) totals[event.projectId] = (totals[event.projectId] ?? 0) + event.gpu_seconds;
```

`fairShareOrder` sorts ascending on that number, so a project's whole history is a permanent handicap. Concretely: a project renders 5,000 GPU-seconds on its first day and then goes quiet. A project created today renders 60 seconds. Both have a job queued. The established project loses — and it loses to *every* project newer than itself, for the remaining twenty-nine days of its thirty-day retention, no matter how idle it has been. That is one project starving another, which is the thing FR-029 forbids. The direction of the failure is the notable part: the mechanism meant to stop a heavy project monopolising the fleet instead permanently penalises a project for work it has already finished.

**It was written twice.** `packages/operator/src/index.ts:89` computes it over a JSON array; `packages/storage/src/ledger.ts:471` computes it in SQL. Neither had a window. Directly below each of them sits a `rollup(period)` that *does* window — `day`, `week` or `month` — so the file already contained the idea of a horizon and the scheduling weight simply did not use it.

**What was and was not tested.** `packages/queue/test/queue.test.ts` holds three fair-share tests, and an earlier draft of this doc called one of them "the only fair-share test in the repository", which was simply wrong and hid the shape of the gap. `:113` calls `fairShareOrder` with values written by hand; `:133` claims through `DurableJobStore.claimNext` with a non-empty weight map — the only test anywhere that did so; `:139` covers the tier ahead of the weight. So the *ordering* was covered, and the in-memory store's consumption of the weight was covered. Three links were not, and the critic pass on this increment turned each into a green defect — an edit that reintroduces unfair scheduling with the whole repository passing:

| unguarded link | the edit that was green |
|---|---|
| the horizon's value | `FAIR_SHARE_WINDOW_MS = 28 days`, which inside a 30-day retention *is* the lifetime sum |
| the worker's call site, `packages/queue/src/worker.ts:164` | pass `{}` instead of the ledger's weights, disabling fair share outright |
| the live job store, `packages/storage/src/jobs.ts:197` | `gpuSecondsUsed: 0`, ignoring the map on the backend staging actually runs |

All three now have guards, and the perturbation table measures each.

## The shape of the repair

**One horizon, declared beside the ordering it feeds.** `FAIR_SHARE_WINDOW_MS` lives in `packages/queue/src/index.ts` next to `fairShareOrder`, with `withinFairShareWindow(at, now)` beside it. Both ledgers reach for it: the JSON side calls the predicate, the SQL side needs a timestamp to bind so it names the constant.

**A day, and it is a policy number rather than a derived one — and it is pinned.** It matches the `day` rollup the ledgers already compute beside the weight; it is 48 times the default job timeout (`HV_JOB_TIMEOUT_MS ?? 30 * 60 * 1000`, `packages/api/src/server.ts:1245`), which is the number that actually settles whether a project's own in-flight render can age out under it — it cannot, and an earlier draft argued from the thirty-day retention, which does not settle that question; and it is a fifteenth of that retention, which is what made the lifetime sum indefensible. The value itself is asserted, because every other assertion in both suites is written in terms of the constant and is therefore value-agnostic: the critic pass set it to 28 days — inside a 30-day retention, that *is* the lifetime sum — and measured the whole repository green. It is a hard window, not a decay curve, so a weight does step down as its oldest events age out — a scheduler may do that, and a half-life would put a second policy number in the same place without removing the first.

**The method is renamed for what it is used for.** `gpuSecondsByProject` → `fairShareWeights(now)`. A method with the old name quite reasonably returns a lifetime total; the bug was handing one to a scheduler. The `claimNext` parameter is renamed to match in both job stores.

**Equality between the backends is the assertion, not the constant.** Sharing `FAIR_SHARE_WINDOW_MS` stops the two *numbers* diverging and does nothing about the two *expressions*: the JSON side compares in JavaScript, the SQL side in Postgres, and `>=` on one with `>` on the other would put two queued jobs in a different order depending only on which storage backend a deployment runs. `packages/storage/test/fair-share-window.test.ts` seeds the same five events into both ledgers and requires the same map at three instants — inside the window, exactly at the edge's boundary, and past it — **and** pins each side to the map the horizon implies. Both halves are asserted because the cross-implementation comparison alone is the weaker of the two: every perturbation that breaks one backend also fails the literal pin, so the pin is doing most of the work and the comparison mostly improves the failure message. What the comparison adds that the pin cannot is a defect present in *both* implementations at once, which is the case a shared constant does not cover.

The third instant was decoration in the first draft: with the newest event at `NOW - 60_000`, every event was outside the window by `NOW + FAIR_SHARE_WINDOW_MS + 1`, both sides answered `{}`, and two empty maps are equal whatever either implementation does. A fifth event dated after `NOW` fixes it, and incidentally pins the horizon's one-sided shape: an event dated ahead of `now`, by clock skew or otherwise, counts, on both backends alike. Perturbations Q3 and Q4 make each side exclusive in turn; each fails.

## Declared changes beyond the defect

- **An ambiguous count in a shipped comment, now two counts.** `MAX_JOB_NOTIFICATIONS`'s doc comment said "Seven call sites appended to it … six in this file and one in `packages/storage/src/ledger.ts`". That was true at `HV-032-01`'s branch base and stale by the time it merged. The first draft of this increment replaced it with eight, which is right for the *pre-bound* state and wrong for anyone counting `notify` call sites today — there are nine, eight of them in that file, the extra being the dead letter that arrived with the bound. The critic pass counted the live call sites and reported eight as wrong; both readings were defensible, which is the actual defect in a comment of this kind. It now states both numbers and which is which. It remains a comment no test can hold, which is why it says what it says rather than a bare number.
- **A redundant guard was removed rather than kept for looks.** The first draft of `withinFairShareWindow` opened with `Number.isFinite(recorded) &&`. Perturbation Q6 removed it and nothing failed — because an unparseable timestamp is `NaN` and every comparison with `NaN` is already false, so the check never decided anything. A redundant check that a test appears to cover is worse than no check; it is gone, and the behaviour it was pretending to provide is asserted instead.

## What this increment does not do

- **It does not make fair share resist a determined abuser, and it makes that slightly easier.** Under ADR-0018 there are no accounts, so a fresh project with a zero weight is free, and shortening the memory from a lifetime to a day shortens the memory a window scheme relies on — the sybil path is cheaper after this change than before it. The real bound is not fair share at all and it is worth stating exactly rather than reassuringly: `TIERS.free.maxConcurrent` is `1` *per project*, and `projectCreate` is rate limited to 20 per hour per IP (`packages/api/src/server.ts:130`), so an IP can hold on the order of 480 fresh single-slot projects a day. There is no per-IP concurrency bound anywhere; `packages/operator/src/index.ts` hashes IPs for rate limiting and nothing else. So fair share orders *honest* queued work and is claimed for nothing more. This increment makes that order stop depending on ancient history; it does not make the fleet abuse-proof, and an earlier draft of this paragraph offered the per-project cap as if it did.
- **It does not distinguish `created_at` from the event body's `at`.** The SQL side filters on the `created_at` column and the JSON side on `event.at`; the insert at `packages/storage/src/ledger.ts:396-400` sets `created_at` from `event.at`, so today they are the same value and the equality test cannot tell them apart. Perturbation Q7 switches the SQL side to `(body->>'at')::timestamptz` and everything still passes, which is recorded here rather than presented as coverage. If those two ever diverge, this test will not notice.
- **It says nothing about most stages' usage.** `gpu_seconds` is non-zero only for video renders (`packages/generator/src/fal.ts:292`, `packages/generator/src/index.ts:106`); image, graphic, audio, edit, sound and lip-sync all record `gpu_seconds: 0`. The weight is therefore blind to those stages, before and after this change. That is pre-existing and not fixed here, but it bounds what the horizon buys: fair share between two projects doing only audio work is decided by the job-id tie-break.
- **It does not window anything else.** `rollup`, `monthSpend` and the budget reservations are untouched. `all()` still returns every event, and the events themselves are never deleted by this change — only the weight is windowed, which the last assertion of each suite checks by summing the ledger's whole history and finding it intact.
- **It does not add a decay curve, priority tiers, or any notion of a project's age.** `fairShareOrder`'s `priority` field and its `jobId` tie-break are unchanged.

## Acceptance criteria

1. Usage older than the horizon does not weigh against a project, while the event itself is still recorded. — `packages/operator/test/fair-share-window.test.ts`, case 1; Q1.
2. The boundary is inclusive at exactly the horizon's age and exclusive one millisecond beyond, and the same events a millisecond later age out. — case 2; Q3 and Q4.
3. Several events for one project inside the horizon add up, and an absent project and a zero-weight project order identically. — case 3.
4. The starvation FR-029 forbids no longer happens: a long-idle project is not behind a newcomer, measured against the lifetime sum computed from the same events. — case 4; Q1.
5. **The horizon's value is a day**, equal to the `day` rollup the ledgers already compute, far longer than the job timeout, and a small fraction of the project retention. — case 5; Q6.
6. The horizon is declared in exactly one file across all of `packages/*/src`, both ledgers **apply** it inside `fairShareWeights` rather than merely importing it, and neither method body contains a duration literal of its own in any spelling this codebase uses. — case 6, whose refusal is itself exercised against five duration spellings and four innocent ones; Q2 and Q5.
7. Both ledgers answer the same weights for the same events at three instants including the boundary, and each answer is the one the horizon implies. — `packages/storage/test/fair-share-window.test.ts`, case 1; Q2, Q3, Q4.
8. **The worker hands `claimNext` the ledger's weights**, at the same instant, rather than the `{}` the parameter defaults to. — `packages/queue/test/fair-share-wiring.test.ts`, case 1; Q7.
9. **Both job stores order the claim by the weights they are handed** — the in-memory one and the PostgreSQL one that staging actually runs. — wiring case 2 and storage case 2; Q8 and Q9.
