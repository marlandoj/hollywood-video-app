# HV-032-02 — Give the fair-share weight a horizon

epic: HV-032
spend_usd: 0

## Goal

Stop the queue's fair-share weight being a lifetime total, because a lifetime total inverts the requirement it exists to satisfy; declare the horizon once, since two cost ledgers compute the weight; and hold the two implementations to the same answer rather than only to the same constant.

## The defect

`FR-029` and `AC-025` say: *each anonymous project gets a weighted fair share of GPU time; no project can starve another* (`docs/PRD.md:164`, `docs/spec/build-spec.prompt.md:107,218`). The weight was `CostLedger.gpuSecondsByProject()` — a sum over **every event the ledger had ever recorded**, with no window:

```ts
for (const event of this.state.events) totals[event.projectId] = (totals[event.projectId] ?? 0) + event.gpu_seconds;
```

`fairShareOrder` sorts ascending on that number, so a project's whole history is a permanent handicap. Concretely: a project renders 5,000 GPU-seconds on its first day and then goes quiet. A project created today renders 60 seconds. Both have a job queued. The established project loses — and it loses to *every* project newer than itself, for the remaining twenty-nine days of its thirty-day retention, no matter how idle it has been. That is one project starving another, which is the thing FR-029 forbids. The direction of the failure is the notable part: the mechanism meant to stop a heavy project monopolising the fleet instead permanently penalises a project for work it has already finished.

**It was written twice.** `packages/operator/src/index.ts:89` computes it over a JSON array; `packages/storage/src/ledger.ts:471` computes it in SQL. Neither had a window. Directly below each of them sits a `rollup(period)` that *does* window — `day`, `week` or `month` — so the file already contained the idea of a horizon and the scheduling weight simply did not use it.

**Nothing tested where the number came from.** The only fair-share test in the repository, `packages/queue/test/queue.test.ts:113`, calls `fairShareOrder` with `gpuSecondsUsed` values written by hand. The ordering was covered; the weight was not, by anything.

## The shape of the repair

**One horizon, declared beside the ordering it feeds.** `FAIR_SHARE_WINDOW_MS` lives in `packages/queue/src/index.ts` next to `fairShareOrder`, with `withinFairShareWindow(at, now)` beside it. Both ledgers reach for it: the JSON side calls the predicate, the SQL side needs a timestamp to bind so it names the constant.

**A day, and it is a policy number rather than a derived one.** It matches the `day` rollup the ledgers already compute; it is long enough that a project cannot reset its weight between two renders of the kind this service produces; and it is well inside the thirty-day project retention, which is what made the lifetime sum indefensible. It is a hard window, not a decay curve, so a weight does step down as its oldest events age out — a scheduler may do that, and a half-life would put a second policy number in the same place without removing the first.

**The method is renamed for what it is used for.** `gpuSecondsByProject` → `fairShareWeights(now)`. A method with the old name quite reasonably returns a lifetime total; the bug was handing one to a scheduler. The `claimNext` parameter is renamed to match in both job stores.

**Equality between the backends is the assertion, not the constant.** Sharing `FAIR_SHARE_WINDOW_MS` stops the two *numbers* diverging and does nothing about the two *expressions*: the JSON side compares in JavaScript, the SQL side in Postgres, and `>=` on one with `>` on the other would put two queued jobs in a different order depending only on which storage backend a deployment runs. `packages/storage/test/fair-share-window.test.ts` seeds the same four events into both ledgers and requires the same map at three instants — inside the window, exactly at the edge's boundary, and past it. Perturbations Q3 and Q4 make each side exclusive in turn; each fails.

## Declared changes beyond the defect

- **A stale count in a shipped comment.** `MAX_JOB_NOTIFICATIONS`'s doc comment said "Seven call sites appended to it … six in this file and one in `packages/storage/src/ledger.ts`". That was true at the branch base of `HV-032-01`; by the time it merged there were eight, seven of them in that file, as `HV-032-01`'s own increment doc records. The comment now says eight.
- **A redundant guard was removed rather than kept for looks.** The first draft of `withinFairShareWindow` opened with `Number.isFinite(recorded) &&`. Perturbation Q6 removed it and nothing failed — because an unparseable timestamp is `NaN` and every comparison with `NaN` is already false, so the check never decided anything. A redundant check that a test appears to cover is worse than no check; it is gone, and the behaviour it was pretending to provide is asserted instead.

## What this increment does not do

- **It does not make fair share resist a determined abuser.** Under ADR-0018 there are no accounts, so anyone can have a fresh project with a zero weight for the asking, and the horizon shortens the memory that a window-based scheme relies on. Fair share is not the abuse bound here and is not claimed as one: `TIERS.free.maxConcurrent` is `1`, so a project cannot hold more than one worker slot at a time whatever its weight. Fair share decides the order among *queued* jobs, and this increment makes that order stop depending on ancient history.
- **It does not distinguish `created_at` from the event body's `at`.** The SQL side filters on the `created_at` column and the JSON side on `event.at`; the insert at `packages/storage/src/ledger.ts:396-400` sets `created_at` from `event.at`, so today they are the same value and the equality test cannot tell them apart. Perturbation Q7 switches the SQL side to `(body->>'at')::timestamptz` and everything still passes, which is recorded here rather than presented as coverage. If those two ever diverge, this test will not notice.
- **It does not window anything else.** `rollup`, `monthSpend` and the budget reservations are untouched. `all()` still returns every event, and the events themselves are never deleted by this change — only the weight is windowed, which the last assertion of each suite checks by summing the ledger's whole history and finding it intact.
- **It does not add a decay curve, priority tiers, or any notion of a project's age.** `fairShareOrder`'s `priority` field and its `jobId` tie-break are unchanged.

## Acceptance criteria

1. Usage older than the horizon does not weigh against a project, while the event itself is still recorded. — `packages/operator/test/fair-share-window.test.ts`, case 1; Q1.
2. The boundary is inclusive at exactly the horizon's age and exclusive one millisecond beyond, and the same events a millisecond later age out. — case 2; Q3 and Q4.
3. Several events for one project inside the horizon add up, and an absent project and a zero-weight project order identically. — case 3.
4. The starvation FR-029 forbids no longer happens: a long-idle project is not behind a newcomer, measured against the lifetime sum computed from the same events. — case 4; Q1.
5. The horizon is declared in exactly one file, both ledgers reach for it, and neither `fairShareWeights` body contains a duration literal of its own. — case 5; Q5.
6. Both ledgers answer the same weights for the same events, at three instants including the boundary. — `packages/storage/test/fair-share-window.test.ts`; Q2, Q3, Q4.

## Perturbations

Each edit was applied to the shipped files, both suites measured, and the file restored from an explicit copy. `json` is `packages/operator/test/fair-share-window.test.ts` (5 tests); `pg` is `packages/storage/test/fair-share-window.test.ts` (1 test, against a throwaway PostgreSQL 16 cluster, never staging).

| perturbation | json | pg |
|---|---|---|
| baseline | `5 pass / 0 fail` | `1 pass / 0 fail` |
| Q1 — the JSON ledger sums every event ever, exactly as it shipped | `0 pass / 5 fail` | `0 pass / 1 fail` |
| Q2 — the PostgreSQL ledger left unwindowed, so only one backend has the horizon | `5 pass / 0 fail` | `0 pass / 1 fail` |
| Q3 — the JSON boundary made exclusive | `4 pass / 1 fail` | `0 pass / 1 fail` |
| Q4 — the PostgreSQL boundary made exclusive, the same disagreement from the other side | `5 pass / 0 fail` | `0 pass / 1 fail` |
| Q5 — the PostgreSQL side writes its own `24 * 60 * 60 * 1000` instead of naming the constant | `4 pass / 1 fail` | `1 pass / 0 fail` |
| Q6 — `Number.isFinite` removed from `withinFairShareWindow` | `5 pass / 0 fail` | `1 pass / 0 fail` |
| Q7 — the PostgreSQL side filters on `body->>'at'` instead of `created_at` | `5 pass / 0 fail` | `1 pass / 0 fail` |

Q1 takes every case down in both suites, which is what a defect in the weight itself should do. Q2 is the row the cross-backend suite exists for: the JSON suite is entirely happy while one backend has no horizon at all. **Q6 and Q7 are passes and are recorded as passes.** Q6 said the guard it removed was never doing anything, and the guard is now deleted rather than left in place looking tested. Q7 says the equality test cannot distinguish the `created_at` column from the body's `at`; that limit is stated above rather than papered over.
