# HV-039-11 — The dialogue-revision studio locked and redrew itself every three seconds while media generated

epic: HV-039
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

While a revised preview or film generates, the "Revise dialogue and its cut" studio checks its
status every three seconds:

```js
poll=setTimeout(()=>{void safe(()=>store.showJob(s.job.id))();},3000);
```

`store.showJob` is also what the creator's own **Check generation status** runs. It sets `busy` and
emits before the request, then emits again after it. Every emit runs `render()`, which rebuilds the
recovery, library, draft, proposal, generation, media, mapping and review sections. `busy` disables
every control until the answer arrives. So every three seconds, for as long as the generation ran:

- **every section was rebuilt twice.** An open listing collapsed, and focus on any button fell to
  the page body;
- **every control was disabled while the check was in flight**, so a click that landed in that
  window did nothing;
- **any error on screen was wiped**, because `safe` starts with `localError=null`. An error from
  something the creator had just tried disappeared within three seconds.

## What this increment does

- **`showJob(jobId,{quiet:true})`** is the status check. It doesn't set `busy`. If the job comes back
  unchanged, it changes nothing and only re-arms the next check. "Unchanged" means the same status,
  output revision, and failure or cancel reason. Signed media links are ignored, because they are
  signed again on every request. If the job has changed, the studio redraws exactly as before.
- **The poll no longer goes through `safe`**, so an error on screen stays until the creator's next
  action. A failed check still shows its own error.
- **A check that comes due while the creator's own request is in flight waits.** It can no longer
  bump the store's epoch and discard that request's answer.
- **Check generation status**, pressed by the creator, is unchanged.

## Acceptance criteria

1. **A check that finds the job still rendering redraws nothing.** Every element is the one that was
   there before, and the next check is scheduled.
2. **While a check is in flight, no control is disabled.**
3. **An error on screen is not wiped by a check.**
4. **When the job finishes, the check draws the finished film** and stops checking.
5. Reverting `living-script.js` and `living-script-state.js` fails criteria 1–3.

- Tests: `packages/frontend/test/living-script-poll.test.js`, using the living-script fixture. The
  three-second check is run by hand, and the job request is held open to look inside the check.

## Known gaps this leaves

- **The job's own transitions still redraw every section** (queued to running to done). Each happens
  once, and "done" has to draw the player.
- **Other rebuilds in this studio**, such as a mapping edit that moves a row, still rebuild their
  section and are not covered here.
