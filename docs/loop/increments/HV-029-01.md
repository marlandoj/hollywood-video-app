# HV-029-01 — Stop rounding an unknown review capability up to `approve`, and give "the latest cut" one comparator

epic: HV-029
spend_usd: 0

## Goal

Close the two defects that let a review link carry more authority, or point at a different cut, than the owner asked for. Both are the same shape: **one rule spelled out in more than one place, where one of the copies is wrong.**

1. `POST /api/projects/:id/reviews` read the capability as `body.permission === "read" ? "read" : "approve"`. Anything the route did not recognise — a P13 role name, a typo, a missing field, a non-string — became **`approve`**, the capability that can record a decision on a cut. The closed set was declared independently in six places; five of them agreed, and the sixth is the one an untrusted request body reaches first.
2. The owner's create path and the reviewer's read path both answered "which is the latest finished cut?", with two different comparators: completion time then identity on one side, identity alone on the other. Job identities are random UUIDs, so the two orders agree only by chance.

**How this increment was found.** The program-wide re-verification of the pre-loop credit ran one auditor per epic across all 22 epics that had never had the pass `docs/loop/STATUS.md` says the first planner is supposed to run. HV-029 came back `scaffolding-only` with four defects, two of which are closed here. This is the seventh instance in this program of a rule that the repository states more than once and defends nowhere.

## Acceptance criteria

1. **An unrecognised or absent capability is refused, not rounded up.** The create route answers `400` with `Choose read or approve for this review link.` and mints nothing for `"reviewer"`, `"READ"`, `"Read"`, `"read "`, `""`, `"approve\n"`, `"owner"`, `"director"`, an absent field, `null`, a number, a boolean, an array and an object. Satisfies FULL-SCOPE §10 read with ADR-0020 fail-closed, and CLAUDE.md "Safety refusals … may grow, never shrink" — this only narrows what a link may do.

2. **The closed set is declared once, and no file under `packages/*/src` or `scripts/` outside the module names the privileged capability.** `packages/api/src/review-capability.ts` holds `REVIEW_PERMISSIONS`, the type `ReviewPermission`, `isReviewPermission`, `reviewPermission`, `mayApprove` and `ReviewCapabilityError`, and imports nothing. The five readers — `api/src/tokens.ts`, `api/src/index.ts`, `api/src/server.ts`, `storage/src/snapshots.ts`, `storage/src/projects.ts` — import it and name no member at all; `mayApprove` exists so that the two decision checks in `index.ts` need not. A test scans every `packages/*/src/**/*.{ts,js,html}` and `scripts/**/*.ts` for `approve` as a quoted literal **in any quote style, at any distance, under any identifier**, because any re-declaration of this set must name the privileged member somewhere. Two files are allowed to name it and are listed by name with the reason: `packages/frontend/src/index.html` and `scripts/runtime-smoke.ts` are wire callers that cannot import a TypeScript module. The test states in its own comment what it does **not** catch: a literal assembled at runtime, and a member named only in a test file. Satisfies FULL-SCOPE §10 "Evidence before promotion".

3. **"The latest finished cut" has one comparator.** `latestFinishedCut` in `packages/planner/src/render-stage.ts` — beside `isFilmStage`, which it uses — is called by both the owner's binding path and the reviewer's unbound path. A test mints an unbound link while the project has no finished cut, then completes two cuts whose identity order and completion order are made to **disagree on purpose**, asserts that they disagree, and asserts that the reviewer's resolution equals the owner's binding. Satisfies CLAUDE.md "Every criterion gets a real test."

4. **No behaviour outside these two answers changes, and nothing frozen is touched.** The diff touches nothing under `docs/legal/**`, `docs/adr/**`, `.github/workflows/**`, `packages/safety/**` or `infra/drizzle/**`; adds no `package.json` or lockfile entry, no HTTP route, no cookie, tracking, account, tier or payment path; changes no budget default; constructs no provider and reads no key. `docs/loop/STATUS.md` and `docs/PROGRAM-EXECUTION.md` are not in the diff; RECORD owns both.

## Demonstrated, not asserted

Five perturbations, each applied on this branch, measured against the **final** test file, and reverted:

| perturbation | result |
|---|---|
| A — restore `body.permission === "read" ? "read" : "approve"` in the route | `2 pass / 2 fail` — criteria 1 **and** 2 |
| B — restore the reviewer's identity-only comparator | `3 pass / 1 fail` — criterion 3 |
| C — restore the verifier's `!== "read" && !== "approve"` chain in `tokens.ts` | `3 pass / 1 fail` — criterion 2 |
| D — keep the module import but restate half the set inside `server.ts` | `3 pass / 1 fail` — criterion 2 |
| E — add `const LEGACY_LINK_CAPS = ['read', 'approve'];` to `snapshots.ts`, single-quoted, far from any occurrence of the word `permission`, in a file that still imports the module | `3 pass / 1 fail` — criterion 2 |

Perturbation A trips two criteria because the restored line names a member inside a reader, which is the point: the fail-open default and the extra copy are the same defect seen from two sides.

**The criterion-2 test was wrong twice before it was right, and both drafts are recorded because both are the failure this increment is about.** The first matched only `"read" | "approve"` and `["read", "approve"]`; restoring the comparison chain (C) passed it. The second matched a member within 120 characters of the word `permission`; a single-quoted copy under a different identifier, placed further away (E), passed that. An earlier version of this table also reported A as `3 pass / 1 fail`, which was the figure measured against the first draft of the test and was never true of the file being shipped. The figures above are from one run of the final file per row.

## What this increment does **not** do

- **It does not deliver P13's eight capability-link roles.** FULL-SCOPE P13 names owner, producer, director, writer, editor, sound, colourist and reviewer "with scoped permissions, expiry, and revocation". Their scoped permissions are not specified anywhere in this repository, and adding eight role names that no route can mint and no reader honours would be scaffolding, not a capability — the same shape this audit criticises in `hv_workers.classes`. What this increment delivers is the single place those roles will be added, so that adding them is one data edit rather than a seventh independent copy. The module says so in its own header.
- **It does not remove the unbound review link.** The audit recommends deleting the "latest cut" fallback so that every link binds to the cut it was minted for. That is a capability removal and a separate decision; making the two comparators agree is the minimal repair of the defect that exists today. Recorded here as the named follow-up, not as work done.
- **It does not fix the burned-view defect.** `useReviewLink` increments the view counter before the route can discover that there is no cut to show, so a failed view permanently consumes one of three. That is a different shape — ordering of side effects, not a duplicated rule — and `peekReviewLink` already exists as the seam for it. HV-029-02.
- **It does not close FR-046's creator half** (the decision is written and read by no route) or AC-015's revocation (`revokeReviewLink` is reachable only from unit tests). Both remain open and uncredited.

## Declared behaviour changes beyond the two answers

Criterion 4 says nothing outside these two answers changes. Two consequences are declared here rather than left to be discovered:

- **`ProjectService.createReviewLink` can now throw.** It is typed `ReviewLink | null` and previously never threw; it now re-validates through `reviewPermission()` as defence in depth, so a caller that bypasses the route and passes an unknown capability gets a `ReviewCapabilityError` instead of a minted link. The same reaches `createBoundReviewLink` and both delegating methods in `packages/storage/src/projects.ts`. No in-tree caller can reach it, because the route validates first; the server's catch-all renders it as a 400.
- **Validation order in the route is unchanged on purpose.** The capability check is placed *after* the `jobId` / `expectedOutputRevision` type check, so a body that is wrong in both ways still reports the cut error first, exactly as before. An earlier draft of this increment put it first and silently changed which message that body receives.
