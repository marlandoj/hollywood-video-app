# HV-037-03 — The paid benchmark pass, made runnable on the staging host

epic: HV-037
release: 3 "Features"
gate: G21-202610041254 (Kevin approved the paid benchmark pass at about $11: Kling 2.5 Turbo Pro on the 24-shot corpus, Kling O3 reference on its 10 reference shots)
spend_usd: 12
providers: fal `fal:kling-v2.5-turbo-pro` (24 shots, planned $8.40) and fal `fal:kling-o3-standard-reference` (10 reference shots, planned $2.52)

## Why

Release 3 step 9 wants one paid pass of the 24-shot corpus per fal video model, declared, with its
measured records committed under `docs/evidence/release-3/` so quality routing (HV-019-14) ranks on
real scores. G21-202610041254 approved it: $8.40 + $2.52 = $10.92, declared here as $12.

HV-037-02 built the harness at $0 and named what stood between it and the run:

- **It recorded only to the JSON ledger, and refused a database ledger, "which is the staging
  setup".** A pass on staging could not run, and if it had, its spend would have been invisible to the
  studio's $500 cap and the $450 alert.
- **The corpus had no character references.** Its tests used synthetic lavfi patterns.

This increment fixes both. It runs nothing paid: the build session has no key. The operator runs the
pass on the staging host with the runbook below, and a follow-up commit adds the evidence.

## What

**1. The pass records to the studio's PostgreSQL ledger** (`packages/benchmarks/src/paid.ts`).
When the runtime names a database ledger (`HV_STORAGE=postgres`, `HV_WORKER_DATABASE_URL` or
`HV_API_DATABASE_URL`), the harness opens `PostgresCostLedger`, the class the studio's admissions and
workers use. Otherwise it uses the JSON `CostLedger` at `HV_COST_LEDGER_PATH`, as before.

- **It connects as the worker role.** The studio's workers record fal spend with
  `PostgresCostLedger.record` as `hv_worker`. The API role can read the ledger but cannot write a cost
  event (HV-040-03). So the harness requires `HV_WORKER_DATABASE_URL` for the `hv_worker` role, and
  refuses before connecting if only the API URL or `HV_STORAGE=postgres` is set, or if the URL names
  another role or is not a PostgreSQL URL. On the host that URL is in `storage-worker.env`, not
  `storage-api.env`.
- **The same cap.** The declared amount is reserved with `PostgresCostLedger.reserve` into
  `hv_reservations`, against `hv_budget_accounts`' monthly cap and the last 30 days of
  `hv_cost_events` plus every other hold. These are the same sums every studio admission checks.
- **Every shot's cost is a cost event** under project `benchmark:HV-037-03` and the pass's job id.
  The month's rollup, which the operator's health view, the $500 cap and the $450 alert read,
  includes it.
- **Earlier passes under the increment** are read from that same ledger, so the second run sees the
  first run's spend.
- **The hold survives the workers.** A studio worker's `reconcile` releases any hold whose job is not
  in its queue a minute after it was taken. A pass has no queued job, so on a host with running
  workers its hold would be dropped after the first minute. The pass now takes its hold again before
  every shot (`runMeasuredBenchmark`'s `hold`). That is a no-op while the hold stands. Otherwise it is
  a new hold for what the declaration has left, checked against the month's cap again. If the cap
  refuses, the pass stops, and the remaining shots are recorded as skipped with that reason.
- **The record is never written over.** `--out` must not exist. The record is written mode 600, and
  the clips go beside it in `clips/<spec>/`.
- **The command prints a summary** (`hv-benchmark-paid-summary/1`). It holds the ledger kind, the job
  id, the record's aggregate, the pass's cost read back from the ledger (`recordedUsd`) and the month's
  spend after the pass. The runbook keeps it beside the record as evidence of where the spend went.

**2. Invented KEEPER and SAILOR references, drawn at $0**
(`packages/benchmarks/src/references.ts`, `packages/benchmarks/fixtures/references/`). Both are
cartoon head-and-shoulders portraits built from flat shapes. Neither is a photograph or a likeness of
anyone:

- KEEPER is an older lighthouse keeper: grey beard, navy peaked cap, yellow oilskin, a night sky and a
  lighthouse behind him.
- SAILOR is a young sailor: red knit cap, striped shirt, open peacoat, sky and sea behind him.

The drawing uses only additions, multiplications, comparisons and integer colours, with 4x4
supersampling, so the pixels are identical on every host. `references.json` pins the committed PNGs'
sha256, their pixels' sha256, and a description of each that the safety gate admits. Both are 512x512
and not flat, and their identity hashes are far apart (similarity 0.61).

The corpus fixture (`benchmark-24shot.fountain`, v1.0.0) is unchanged. The references are a separate
asset whose hashes every record carries. The routing reader already refuses records measured
against different references. No corpus version bump, and no baseline change, was needed.

**3. One results file for the router** (`packages/benchmarks/src/results.ts`).
`bun run benchmark:results --out <file> <record.json>...` joins the records into one array, ordered
by spec. It writes the file only if HV-019-14's `routingQualityFrom` accepts the exact bytes, and it
never writes over a file. Its refusal carries the reader's reason.

**4. The evidence test** (`packages/benchmarks/test/release-3-benchmark-evidence.test.ts`). It is
skipped until `docs/evidence/release-3/benchmark/routing-results.json` exists. Then it checks:

- the router reads the file with no fallback, and it is exactly the two committed records;
- each record is a fal pass under HV-037-03 on the committed references;
- each summary says `ledger: "postgres"`, a `benchmark:HV-037-03:<spec>:` job, and a `recordedUsd`
  equal to the record's cost;
- the two costs together are within `spend_usd`.

## Host runbook (operator, on the staging host, as root)

Run this after HV-037-03 is merged and deployed. The active release must carry this doc and the
references, because the harness reads the declaration from the release it runs from. The turbo pass
renders 24 shots one after another at up to 3 minutes each, so the passes run detached. `FAL_KEY` is
loaded into that one subshell only and never printed.

```bash
# 0. Check the release and make the private output directory.
. /etc/rough-cut/host.env
A=$(cat "$RC_RUNTIME/active-release.txt")
test -f "$A/docs/loop/increments/HV-037-03.md" && test -f "$A/packages/benchmarks/fixtures/references/keeper.png" || echo "STOP: deploy a release that carries HV-037-03"
OUT="$RC_RUNTIME/runs/benchmark-release-3"
mkdir -p "$OUT" && chmod 700 "$OUT"
ls -A "$OUT"   # must be empty: a record is never written over

# 1. The two passes, then the results file. Detached; progress in $OUT/run.log.
nohup setsid bash -c '
  set -euo pipefail; umask 077
  . /etc/rough-cut/host.env
  cd "$(cat "$RC_RUNTIME/active-release.txt")"
  export PATH="$RC_RUNTIME/bin:$PATH" R="$RC_RUNTIME"
  OUT="$RC_RUNTIME/runs/benchmark-release-3"
  set -a
  . "$RC_RUNTIME/runtime-config.sh"    # the studio caps ($500 month, $5 shot) and fal price settings
  . "$RC_RUNTIME/storage-worker.env"   # HV_WORKER_DATABASE_URL + HV_DATABASE_TLS_DIR: the role workers record fal spend with
  . "$RC_RUNTIME/secrets.env"          # FAL_KEY, never printed
  set +a
  export HV_STORAGE=postgres
  bun run benchmark:paid --provider fal:kling-v2.5-turbo-pro --declared-usd 9 --increment HV-037-03 --references packages/benchmarks/fixtures/references --out "$OUT/kling-v2.5-turbo-pro.json" > "$OUT/kling-v2.5-turbo-pro.summary.json"
  bun run benchmark:paid --provider fal:kling-o3-standard-reference --declared-usd 3 --increment HV-037-03 --references packages/benchmarks/fixtures/references --out "$OUT/kling-o3-standard-reference.json" > "$OUT/kling-o3-standard-reference.summary.json"
  bun run benchmark:results --out "$OUT/routing-results.json" "$OUT/kling-o3-standard-reference.json" "$OUT/kling-v2.5-turbo-pro.json" > "$OUT/routing-results.summary.json"
' > "$OUT/run.log" 2>&1 &

# 2. Watch it. Done when routing-results.json exists. A refusal exits 2 and names the reason in run.log.
tail -f "$OUT/run.log"
ls -l "$OUT" "$OUT/clips"/*
```

- **Where things go.** `$RC_RUNTIME/runs/benchmark-release-3/` (mode 700) holds:
  - the two records and their `.summary.json`;
  - `routing-results.json` and `routing-results.summary.json`;
  - `run.log`;
  - the clips, in `clips/fal_kling-v2.5-turbo-pro/` and `clips/fal_kling-o3-standard-reference/`.

  The clips stay on the host. Their sha256 are in the records.
- **The declarations.** $9 covers the turbo plan ($8.40), and $3 covers the reference plan ($2.52).
  $9 + $3 = $12 = `spend_usd`. The second command is admitted only if the first one's recorded spend
  plus $3 fits $12. A pass can overrun its estimate by at most one shot. If the turbo pass did and the
  second command is refused, rerun only the second command with `--declared-usd` set to $12 minus the
  turbo summary's `recordedUsd`, rounded down to the cent. The reference plan needs at least $2.52.
- **If a pass is interrupted,** its shots so far are already cost events. The hold is released by the
  next worker reconcile, within about a minute. Running the same command again is refused while its
  `--out` exists, and the spend already recorded counts against $12. Ask before spending again.

**3. Copy the results for the follow-up evidence commit.** Copy these five files from `$OUT` into
`docs/evidence/release-3/benchmark/` of a checkout of `main`, on a new branch:

- `kling-v2.5-turbo-pro.json` and `kling-v2.5-turbo-pro.summary.json`;
- `kling-o3-standard-reference.json` and `kling-o3-standard-reference.summary.json`;
- `routing-results.json`.

From a build session, fetch each one with the `rough-cut-staging` connector's `host_transfer_file`. On
the host itself:

```bash
D=docs/evidence/release-3/benchmark; mkdir -p "$D"
for f in kling-v2.5-turbo-pro kling-o3-standard-reference; do install -m 644 "$OUT/$f.json" "$OUT/$f.summary.json" "$D/"; done
install -m 644 "$OUT/routing-results.json" "$D/"
bun test packages/benchmarks/test/release-3-benchmark-evidence.test.ts packages/benchmarks/test/routing-results.test.ts
```

Commit only once that test passes, with all three of its cases run and none skipped (CLAUDE.md). The
run log and clips are not committed.

**4. Afterwards.** Once the evidence commit is merged and deployed, quality routing reads the file by
its path relative to the release root:

```
HV_ROUTING_QUALITY_RESULTS_PATH=docs/evidence/release-3/benchmark/routing-results.json
```

It is used with `HV_ROUTING_STRATEGY=quality`. The API is the only role that reads it.

## Acceptance criteria

1. **On a PostgreSQL runtime the pass is held and recorded in the studio's ledger.**
   - The declaration is a `final` hold in `hv_reservations`, counted by `reservedUsd`, before shot 1,
     after shot 1, and again after a worker released it mid-pass.
   - 24 shots make 24 cost events under the increment and the pass's job.
   - Nothing is left held.
   - The month's rollup rises by the pass's cost, per provider too, and `recordedUsd` reads it back.
   - The JSON ledger the runtime config also names is never written.

   *Test:* `packages/benchmarks/test/paid-postgres.test.ts` → "the declaration is reserved under the program's cap…".
2. **Earlier PostgreSQL spend counts against the declaration.** $1.20 already spent under a $5 doc
   refuses $4 more, before a provider is resolved.
   *Test:* "earlier passes recorded in PostgreSQL count…".
3. **The program's cap in PostgreSQL decides.** A stored cap without room refuses the hold before
   any shot. A released hold the cap no longer admits stops the pass mid-way: 3 rendered, 21 skipped
   "the month's cap refused the hold", 3 cost events, nothing held.
   *Test:* "the program's cap in PostgreSQL refuses the hold…" and "a released hold that the cap no longer admits stops the pass…".
4. **The database ledger is only ever the worker role's, and that is decided before connecting.** These
   are refused:
   - `HV_API_DATABASE_URL` alone;
   - `HV_STORAGE=postgres` alone;
   - a worker URL with no role, the API role, a non-PostgreSQL scheme, or that is not a URL;
   - no ledger at all.

   *Test:* `paid-harness.test.ts` → "no ledger at all, or a database ledger the pass could not record to…".
5. **On the JSON ledger, a released hold is taken again before the next shot.** The hold is released
   during shots 1 and 12. All 24 shots still run, and before each shot the unspent declaration
   ($20 − $0.25 × shots done) is held. 24 events are recorded, nothing is left held, the clips are
   beside the record, and the record is mode 600.
   *Test:* "a hold a worker's reconcile releases mid-pass is taken again…" and "a record that already exists is never written over".
6. **HV-037-02's refusals still hold.** Every case in `paid-harness.test.ts` passes, unchanged except
   the database-ledger case above.
7. **The references are invented, committed and reproducible.**
   - The committed PNGs match the manifest's sha256 and decode to exactly the generator's pixels.
   - Their descriptions pass the safety gate.
   - They are valid private PNG references, not flat, and told apart (similarity under 0.75).
   - They lock the corpus's 10 character shots (KEEPER ×6, SAILOR ×4).
   - Offline, they price the approved pass at 24 shots / $8.40 and 10 shots / $2.52.

   *Test:* `packages/benchmarks/test/corpus-references.test.ts` (4 cases).
8. **The record's shape is what HV-019-14 reads.** Both runbook passes run through the harness on
   local stand-ins and the committed references:
   - Each record reads back with the corpus sha256, the metric, both references, and 10 scored shots.
   - The joined file is refused only because the records are stand-ins, and nothing is written.
   - With that one field relabelled, the same records go through `bun run benchmark:results`. The
     file's bytes are `routingResultsText`, `readRoutingResults` accepts them with no fallback, and
     the scores are the records' means.
   - The reference-holding model ranks first (above 0.9), and the text-only one scores below 0.8.

   *Test:* `packages/benchmarks/test/paid-routing-shape.test.ts` (4 cases).
9. **This doc authorizes exactly the runbook it contains.** Each `benchmark:paid` line in the runbook
   parses, and is authorized against this doc on the staging environment, ledger `postgres`. The
   lines:
   - name both providers;
   - use the committed references;
   - write under `$OUT`;
   - each declare at least their offline plan;
   - in order, fit `spend_usd: 12`.

   A dollar more on either line passes `spend_usd` by the time the second line runs, and that line
   is refused. The results line joins exactly the two records.
   *Test:* `packages/benchmarks/test/hv-037-03-runbook.test.ts`.
10. **The deterministic gate is untouched.**
    - `baseline.json`, the fountain fixture, `BENCHMARK_FIELDS` and `scripts/benchmark/compare.ts`
      are not in the diff.
    - `bun run benchmark:compare` passes.
    - `benchmark.test.ts` and `metric-classification.test.ts` pass.

## Known gaps

- **The paid pass is not run here.** The build session has no key. The evidence lands in a follow-up
  commit, after the operator runs the runbook.
- **`HV_ROUTING_QUALITY_RESULTS_PATH` has no staging switch yet.** `staging-providers.py` writes no
  such setting. An `export` added to `runtime-config.sh` by hand reaches the API, but every cutover or
  rollback rewrites that file. A `--routing quality` flag would be a small later increment.
- **The pass keeps no provider-attempt journal.** The studio's workers journal each fal request
  (`hv_provider_attempts`, `attachRequest`), so an interrupted request stays held until it is
  reconciled. Those rows belong to a project and a leased job, and a benchmark pass has neither. Here, a
  request cut off mid-flight (crash, timeout) records only what the provider reports as sunk. A
  charge fal makes for it would not reach the ledger until the operator reconciles fal's invoice.
- **While a shot renders, a worker may release the hold.** Until the next shot takes it again, that
  shot's estimate is not held. Its real cost is still recorded when it returns. Another admission in
  that window could take the month past the cap by at most that one shot, $0.42 here. That is the same
  bound as the studio's "a shot is admitted on its estimate" overrun.
- **The $450 alert sees the spend through the app's ledger** (month rollup, operator health). The
  loop's `scripts/loop/status.ts paid-total` reads only `.loop/paid-ledger.jsonl`. The build session
  that commits the evidence should append the recorded total there, as for any paid increment.
- HV-037-02's gaps about the measure itself still stand:
  - it is whole-frame structure, not face identity;
  - the anchored keyframes model is not benchmarkable;
  - the reference model renders only the 10 character shots.
