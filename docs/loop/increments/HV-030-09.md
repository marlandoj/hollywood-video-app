# HV-030-09 — The crew's budget line followed the generation ledger into PostgreSQL

epic: HV-030
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

`docs/CREW.md` named this under "Not yet", in its own words:

> **The crew ledger lives on one host, in a JSON file.** Moving it into PostgreSQL with the rest of
> the accounting needs a migration and is Release 2 work.

The crew ledger is the crew's own $1,000 budget line (G13), separate from the $500 generation cap. It
holds the dollars spent on the model, the ceiling the operator has approved, and the alerts already
raised at $25, $100, $200 and $1,000. It guards itself with `withFileLock` — **a lock on one
filesystem**.

The generation cost ledger had exactly this shape and moved to PostgreSQL for exactly this reason.
The crew's did not, so with two API processes on two hosts:

- each could read a spend below a threshold, each record, and **each miss the alert** the operator is
  supposed to get — the alert that exists so a runaway crew is noticed;
- or each could cross it and **both raise it**, so the operator is told twice;
- and `assertCanSpend` could let two calls through at the ceiling, because the read and the record
  are not one decision.

There is a second, quieter problem. The file ledger keeps a running `spentUsd` **beside** the events,
because it drops events past five thousand and the dollars have to survive the drop. Two numbers that
must agree, maintained by hand.

## What this increment does

- **`hv_crew_events`**, append-only: one row per model call, with the tokens and the dollars and
  nothing else — no prompts and no answers, which is what the file ledger's own header promises. The
  spend is `sum(usd)`, so there is one number and no way for two to disagree.
- **`hv_crew_budget`**, one row: the approved ceiling and the alerts raised.
- **`record` takes the budget row `FOR UPDATE` before it reads the spend**, so the crossing is
  decided once, by whichever transaction holds the row. That is the whole point of the move.
- **`approveCeiling` raises in the `where`** — `where approved_ceiling_usd < $1` — rather than
  reading and then writing, so two operators raising at once both succeed and the higher stands.
- **The interface is the file ledger's, returning promises.** That is the arrangement the generation
  ledger already uses: `CostLedger` answers directly, `PostgresCostLedger` answers a promise, and
  every caller awaits. The crew paths take one `await` each and nothing else changes; the file
  ledger stays for a single-host deployment and for the tests.
- **`alertsOf` refuses a column that is not an array**, which is not defensive decoration — see
  below.

### What the cluster check caught

This was verified against a **throwaway database on the staging cluster**, created and dropped for
the purpose, and it found a real defect that would have reached CI at best and staging at worst:

```
update … set alerts = ${JSON.stringify(value)}::jsonb   ->  typeof alerts === "string"
update … set alerts = ${value}::jsonb                   ->  Array.isArray(alerts) === true
```

The driver JSON-encodes a **string** parameter before the cast sees it, so the stored jsonb is a JSON
string holding a JSON array. A ledger that read its alerts that way would find `alerts.some(...)`
undefined — or, with a looser read, would find no matching threshold and **re-raise every alert it
had already raised**. The write now passes the array itself, which is the form the rest of the
package uses, and `alertsOf` refuses anything that is not an array rather than working around it.

## Acceptance criteria

1. **The two tables are declared and created** — schema and migration agreeing, both with FORCE ROW
   LEVEL SECURITY — and the grants name the verbs the policies police: `hv_crew_events` is
   append-only (no UPDATE, no DELETE, for either role).
2. **The PostgreSQL ledger answers what the file ledger answers**, over the same sequence of events:
   every `record` return and every `summary` compared, up to the ceiling, the refusal at it, and the
   raise past it. Every declared threshold crossed exactly once.
3. **A ledger with no row yet reads as an empty one** and creates nothing.
4. **The API role can do each thing it needs**, through its own policies and grants rather than as
   the owner — and cannot delete an event, because the grant does not include DELETE.
5. **Two processes recording at once cross a threshold once**, not twice and not never: three real
   `Bun.spawn`ed processes, eight records of two dollars each, one alert between them and the right
   total. A single-threaded runtime cannot exhibit this, which is why it is separate processes.
6. **The whole ledger reads back in the file ledger's own shape**, and the event table's columns are
   exactly the eight that hold tokens and dollars.
7. Reverting `crew-ledger.ts` makes criteria 2–6 fail to load.

- Test: `packages/storage/test/crew-ledger-postgres.test.ts`; criterion 1 runs everywhere, 2–6 need a
  cluster. Verified on a throwaway database on the staging cluster: 5 pass, 0 fail.

## Known gaps this leaves

- **Nothing migrates an existing file ledger into the database.** A deployment that has been spending
  through the JSON ledger and then gains a database starts the crew's line at zero, and its raised
  alerts come back. Staging's crew ledger is at $0 today, so this costs nothing now; a one-shot
  import is its own increment and would need the operator to say which file.
- **`approveCeiling` has no route.** It is the operator's and is called from nothing but tests, in
  either store. The move does not change that.
- **`state()` reads every event.** It is for an operator readout and there is no pagination; at the
  file ledger's own five-thousand-event scale that is nothing, but the table does not trim and this
  method does not bound.
- **The ceiling and the thresholds are still constants in `packages/operator`.** The database holds
  what was spent and what was approved; what the thresholds *are* is still code, so changing them is
  a deploy.
- **No index on `project_id` is used by anything yet.** It is there because a per-film crew readout
  is the obvious next question, and creating it later on a table with rows costs a lock.
