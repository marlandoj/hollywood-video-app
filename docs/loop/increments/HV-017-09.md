# HV-017-09 — The look a character renders with is the one that was locked

epic: HV-017
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0 — no provider is called. This changes which images an existing request carries, not
what is requested or from whom.

## Why

Release 2's slice of HV-017 is "identity locks beyond per-shot references". FULL-SCOPE P2 states the
lock as three things:

> "Identity lock: per-character identity representation (reference set + embedding + optional
> per-project fine-tune) that every downstream render is conditioned on."

Two of the three need model work this studio has not built, and the third — the reference set — is
missing in a way that is easy to miss. Today it is one line:

```ts
const referenceAssets = characters.flatMap(character => character.references ?? []);
```

Every render is conditioned on **whatever the cast holds at plan time, in upload order**. Nothing
records which images were ever accepted as the character's look. So adopting one more character
sheet view, or importing an actor share, silently changes what every shot of that character is
conditioned on, and the order the provider's numbered reference map uses shifts under it. The live
evidence names this exactly: `docs/evidence/release-1/live-reel-anchored.json` records "storyboard to
final: consistent; across shots: not locked", and `release-run.json`'s known gaps say "Character
identity is not locked across shots".

The frame-anchor work (HV-017-06) pinned a *frame* for *one shot*. Nothing pins a *set* for a
*character*.

## What this increment does

- **`packages/planner/src/reference-lock.ts`** — `ReferenceLock` (`hv-reference-lock/1`): one to four
  of the character's own images, **ordered**, with a name, a note, the instant it was locked, and its
  own revision. The lock names each image's `sha256` as well as its id, so an image re-uploaded under
  a reused identity cannot pass as the locked look.
- **The lock lives on the cast record** (`CastCharacter.referenceLock`), so it inherits the cast's
  versioning, history, restore, export and validation rather than adding a parallel store. It is
  re-judged against the character's own images every time the cast is read.
- **`applyCast` conditions the render on the lock**: `renderReferences(character)` is the one place
  that decides what a shot carries, and the prompt's numbered reference map is built from the same
  list, so the numbering and the images cannot disagree.
- **`PUT /api/projects/:id/cast/:characterId/reference-lock`** sets or clears it, optimistic on the
  cast version like every other cast route. It is its own route because a creator's character save
  carries no images — `saveCharacter` restores them from the stored record afterwards — so a lock
  submitted there could not be validated against anything. That save now preserves the lock the way
  it already preserves references.
- **Removing a locked image is refused**, naming the character and saying what to do, instead of
  silently unlocking or leaving the look pointing at an image that is gone.
- **`docs/CASTING.md`** gains "The locked look", and its two standing disclaimers are narrowed
  precisely: a locked look fixes what a render is conditioned on and establishes nothing about what
  comes back.

## Acceptance criteria

1. **A lock can only name images the character already retains**, one to four, distinct, in a
   meaningful order: the same choice in a different order is a different lock, and an unknown id, a
   duplicate, an empty set, five images, an empty name or an unsupported field is refused.
2. **A stored lock is re-judged on every read.** A character whose lock names an image it no longer
   holds, or whose bytes changed under a reused id, is unreadable rather than quietly renderable.
3. **A locked look decides what conditions the render, and in what order.** The shot's reference
   assets are the locked set in the locked order, and the prompt's numbered map counts that set and
   not the images left out of it. An unlocked character still carries everything it holds.
4. **Adding another image to a locked character changes no render** — the same shot plan produces
   the same references and the same prompt — while the same adoption on an unlocked character
   changes both. That contrast is the defect this closes, so the test states both halves.
5. **The route is the creator's**, owner-only and optimistic on the cast version, and a plain
   character save preserves the lock.
6. **A locked image cannot be removed by accident**: the removal is refused with the character's
   name, an unlocked image is still removable, and clearing the lock then allows it.
7. **Nothing else changes.** The casting, actor-library, references, sheets, direction and crew
   suites pass unchanged, and no permission, limit or refusal moves.

- Tests: `packages/planner/test/reference-lock.test.ts` (1–4),
  `packages/api/test/reference-lock-route.test.ts` (5–6).

## Known gaps this leaves, stated rather than implied

- **This is the reference-set third of P2's identity lock.** The embedding and the optional
  per-project fine-tune are not built. The `identityLocks` capability dimension stays at 0 for every
  adapter and a locked look does not raise it, because a chosen set of reference images is not
  embedding conditioning and asking the router for one would make every render unroutable.
- **A locked look is not evidence that shots match.** Nothing measures similarity; Release 2's
  "identity locks hold across 8 shots on the corpus" needs a measurement that does not exist in this
  codebase, and `docs/CASTING.md` still says so.
- **The crew does not lock anything yet.** A creator locks a look by hand; a Casting persona
  proposing one from the approved storyboard stills is later work.
- **No frontend control ships in this increment.** The route and the record are the increment; the
  Director's desk and the studio front door get the button with the persona work above.
