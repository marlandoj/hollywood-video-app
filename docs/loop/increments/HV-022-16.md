# HV-022-16 — A screenplay revision's generation ignored the film's spending limit on the local backend

epic: HV-022
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

Every paid admission is supposed to check the film's own limit (`HV_FILM_SPEND_CAP_USD`, $40 by
default) before it reserves any money:

- The render route calls `assertFilmBudget` on the local ledger.
- PostgreSQL checks the limit inside `admit`'s lock.
- HV-022-14 passed the limit into the living-script generation route's PostgreSQL `admit` call, and
  its test checks that the argument is passed.

The route's local branch skipped the check and went straight to the reserve:

```ts
await ledger.reserve(submitted.id,submitted.stage,submitted.budgetReservedUsd??0,monthlyBudgetUsd);
```

The reproduction ran on the JSON store with the film limit set to $0.03:

1. A paid preview of a screenplay revision was admitted, holding $5.00.
2. The film's next ordinary render was then refused as over its limit.

The one route that never asked was how the limit got passed. A creator can generate revisions again
and again, so only the monthly cap stood in the way. Staging runs on PostgreSQL. Local and
development deployments run on the JSON store.

## What this increment does

- **The local branch checks the film's limit before it reserves**, the same way the render route
  does: what the film has spent, plus what its jobs hold, plus this reservation. A revision that
  would pass the limit gets a 429 carrying the limit's own message, and nothing is held.

## Acceptance criteria

1. **A revision's paid preview that would pass the film's limit is refused before anything is
   held.** The response is 429 with "This film has reached its spending limit of $0.03". Spend is
   unchanged, and no living-script job exists.
2. **A preview that fits the limit is admitted as before**, and holds its reservation.
3. Reverting `living-script-generation-api.ts` fails criterion 1.

- Tests: `packages/api/test/living-script-film-cap.test.ts`, which runs a real film render on the
  dub-studio fixture with a paid storyboard pool configured and no provider called. The film-cap,
  film-budget and living-script API suites pass (79 / 0).

## Known gaps this leaves

- **Living-script quotes hold the full per-stage cap** (for example, $5 for a preview), not the
  estimate that HV-019-06 introduced for ordinary renders. A revision therefore reaches the film's
  limit sooner than its real cost would. This was noticed but not reproduced here.
