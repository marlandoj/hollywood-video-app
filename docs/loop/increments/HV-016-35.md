# HV-016-35 — The crew's line notes quote the script's own lines, and a note that can't be applied is counted, not lost

epic: HV-016
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

The Release 2 exit run on staging (2026-10-01 23:15 UTC) asked the live crew for line notes on film
A. The crew was OpenRouter's `anthropic/claude-sonnet-5.5`, and the request was "Tighten the dialogue
in the last scene". The answer was `source: "openrouter"`, `notes: 0`, `dropped: 0`, and it cost
$0.004664. A paid answer produced nothing, and nothing said why.

What HV-016-32's code allows us to conclude from that answer:

- **It wasn't dropped notes.** Every note that failed a check was already counted in `dropped`, and
  `dropped` was 0.
- **It wasn't an unreadable answer.** A bare array, prose or broken JSON fell to the stand-in
  (`source: "stand-in"`), and the source was `openrouter`.
- **So the answer held a `notes` list, and the list was empty.** Film A's last scene has one spoken
  line, "Go on, then.", and the prompt told the crew to give "none if the script is fine".
  - At $2 in and $10 out per million tokens, the prompt (about 700 tokens) costs about $0.0014.
  - The rest, about 300 output tokens, was most likely prose before an empty list. The old reader
    threw that prose away.
- **The response couldn't tell these cases apart.** "The crew read the script and has no line
  changes to suggest" was also what an answer whose every note was dropped would have looked like to
  the writer, apart from a bare count.

The old design was also fragile in ways this run happened not to hit:

- The crew had to quote each line byte for byte in `before`. A curly quote, a cue in front, or
  different spacing lost the note.
- The crew was shown every line, cues and headings included, with nothing saying which ones it may
  change.
- A bare array, or a fenced answer with braces in the prose around it, was unusable.

## What this increment does

- **The crew is shown only the lines it may change, by number** (`lineNotesPrompt`).
  - A spoken line or an action line, shown whole, starts with its number and `| `.
  - Every other line starts with `-| `: headings, character cues, parentheticals, transitions, the
    title page, blank lines, and lines holding a `[[…]]` note or boneyard.
  - A row `== Scene 4 of 4, the last scene ==` marks each scene's heading, so "the last scene" can
    be found.
  - When the writer asks for something, the crew is told to answer it on the lines it is about, and
    to give none only if none of those lines can be improved.
- **The crew answers with a line number and the new text**: `{persona, line, after, reason}`.
  - The studio takes `before` from the script itself, so it is always the line's exact text.
  - The version and SHA-256 binding, and every apply check, are unchanged.
  - A `before` the crew sends anyway must quote the line it numbers, counting only letters and
    digits. So curly quotes, spacing and the cue don't matter, but a note that quotes another line
    is dropped.
  - A `line` sent as `"16"`, a persona in capitals, or an `after` starting with its own `16| ` are
    read as meant.
- **Every dropped note is counted under one fixed reason.** The result has `droppedReasons`, beside
  `dropped`:
  - `unknown_line`, `locked_line`, `unchanged`, `too_long`, `element_change`, `gate_refused`,
    `duplicate`, `malformed` and `too_many`.
  - Only reasons with a count appear. It is `{}` when nothing was dropped.
  - The route answers with the result as it is, so both fields reach the client. They are additive.
- **When the crew offered notes and none survived, the message says so.** It gives the count and the
  commonest reason, in fixed studio wording that never quotes the model. For example: "The crew
  suggested 3 line notes, but none could be used. The most common reason, for 2 of them: it named a
  line the crew doesn't change (…)."
  - An empty list still says "The crew read the script and has no line changes to suggest".
- **The answer is read in any of the usual shapes** (`readLineNotesAnswer`):
  - `{"notes": [...]}` or a bare array;
  - alone, in a code fence, or with prose around it.
- **An answer that can't be read says why.** It gets `fallbackReason: "model_unusable"`, as before,
  plus `unusableReason`:
  - `not_json`: there was no JSON in it.
  - `no_notes_list`: it was JSON with no list of notes.
  - `unreadable_answer`: the crew model's adapter couldn't use the reply. It was empty, declined,
    cut off or withheld.

  Its message names the reason, and its cost stays on the crew line.
- **The studio panel** shows the server's message alone when no notes are left, because the
  message already counts them. With some notes left, it still adds "N of the crew's notes couldn't
  be used and were left out."
- **HV-030-25's `unusableReason` and `crew.answer_unusable` log are not on main.** Its branch isn't
  pushed either, so these reason codes stay local to line notes. See Known gaps.
- **Every safety rule is kept.** These checks are unchanged:
  - the gate on `after`, on `after` with its `reason`, on the script with the note applied, and on
    the whole request before it is sent;
  - the element-type check, no line breaks, locked note and boneyard lines, and at most 12 notes.

  The crew may now change fewer lines than before, never more.

## Acceptance criteria

1. **Line numbers, not quotes.**
   - A note quoted with curly quotes, its cue, other spacing or no quote at all is kept, with
     `before` taken from the script.
   - Accepting it changes only that line's text, byte for byte, CRLF and indentation included.
   - A `line` sent as a string, a capitalised persona and an `after` prefixed with its number are
     read as meant.
2. **The crew is shown what it may change.** Spoken and action lines are numbered. Headings, cues, a
   parenthetical, a transition and a boneyard line are shown as `-| `. Each scene is marked, and the
   last one says so. The answer shape asks for `line` and `after`, not `before`.
3. **Every drop is counted under its reason.** One note for each reason is counted once, under that
   reason: `unknown_line` (an unknown line, a blank line, or a quote of another line), `locked_line`,
   `unchanged`, `too_long`, `element_change`, `gate_refused`, `duplicate` and `malformed`. Notes past
   12 count as `too_many`. `dropped` is their sum. No refused note's text is in the result.
4. **Locked lines are refused.** A note on a heading, a cue, a parenthetical, a transition or a
   boneyard line is dropped as `locked_line`.
5. **The message says why there are no notes.**
   - All of three notes dropped: "The crew suggested 3 line notes, but none could be used. The most
     common reason, for 2 of them: …".
   - One note dropped: "…but it couldn't be used: …".
   - An empty list: "has no line changes to suggest", with `droppedReasons: {}`.
   - No message quotes the model.
6. **Parsed robustly.** A bare array, a `{notes}` object, a fenced answer and prose around them all
   give the same notes, including a single note in a bare array after prose.
7. **An unreadable answer is unusable, with its reason.**
   - Prose is `not_json`, and so is cut-off JSON.
   - `{"notes": "none"}`, `null` and an object without notes are `no_notes_list`.
   - The adapter's billed-but-unusable reply is `unreadable_answer`, and its $0.04 stays on the crew
     line.
   - None of them is reported as "no notes".
8. **Film A's last scene.** A plausible fenced answer gives at least one note the writer can apply.
   It has a cue-prefixed, curly-quoted `before` on line 36, a note on line 33, and a note on the cue.
   The line-36 note applies as "Go on.", and the cue note is counted as `locked_line`.
9. **At the route,** `droppedReasons` and `unusableReason` come back, a fenced bare array is read,
   and a refused note's text isn't in the response.
10. **In the panel,** when no notes are left, the server's message is shown once, with nothing to take.
11. Reverting `line-notes.ts` fails every test in `crew-line-notes-reasons.test.ts` (it no longer
    exports what they import) and the route test of criterion 9. Reverting `line-notes.js` fails
    criterion 10's panel test. Separately:
    - Taking `before` from the model's quote again fails criteria 1, 3, 5, 6 and 8.
    - Removing the changeable-line check fails criteria 3, 4, 5 and 8.
    - Restoring the old first-`{`-to-last-`}` reader fails criteria 6 and 7.
    - Counting every drop under one reason fails criteria 3, 4, 5 and 8.

- Tests: `packages/planner/test/crew-line-notes-reasons.test.ts` (new),
  `packages/api/test/crew-line-notes-route.test.ts` (one new test),
  `packages/frontend/test/line-notes.test.js` (one new test). Updated pin:
  `packages/planner/test/crew-line-notes.test.ts`, where a hidden-line drop now also reports
  `droppedReasons: {locked_line: 1}`.

## Known gaps this leaves

- **Not re-run live.** This increment spends $0. The exit run should ask film A's crew again on
  staging to confirm that the prompt now gets notes on the last scene. If the crew still answers
  with an empty list, the message now says so plainly, rather than the run guessing.
- **The crew's reason for giving no notes isn't shown.** Prose around the JSON is dropped. A short,
  gated "why none" field would let the writer see it. That is not built.
- **No log line.** Log events and fields are an allow-list in `packages/observability`. HV-030-25's
  `crew.answer_unusable` isn't on main, and its branch isn't pushed. When it lands, line notes should
  log their `unusableReason` and `droppedReasons` counts through it. Until then the counts are only
  in the response.
- **The crew no longer proposes heading changes.** Headings aren't among the lines it may change. A
  heading reworded as a heading still applies through `…/accept`, as HV-016-32 tested.
- **The `before` cross-check is loose.** A quote that is a fragment of the numbered line, for
  example only its last words, is accepted. The writer still sees the exact `before` and `after`
  before accepting anything.
