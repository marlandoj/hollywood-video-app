# HV-040-04 — Published, versioned archive manifest schemas and conformance suite
epic: HV-040
spend_usd: 0

## Goal
Make the portable project archive a contract rather than a convention. Today the `hv-project-archive/1` manifest (`archive.json`), the `hv-state/<n>` snapshot manifest (`snapshot.json`) and the `hv-clips/1` checkpoint manifest (`clips/manifest.json`) exist only as hand-rolled checks scattered across `scripts/archive-package.py` (`inspect`, `project_scope`, `verify_execution_media`), `packages/storage/src/snapshots.ts` (`readStateSnapshot`, `writeStateSnapshot`) and `packages/storage/src/artifacts.ts` (`checkpoint`, `importCompletedJob`, `restoreCheckpoint`), and as prose in `docs/PROJECT-ARCHIVE.md` (which still calls the state layer "`hv-state/1`" although the writer emits `hv-state/1` through `hv-state/13`). A self-hosted instance that wants to read or produce an archive has no machine-readable definition to build against, and nothing proves that the Python packer and the TypeScript reader agree on the shapes or the limits (100,000 files, 8 GiB per file, 64 GiB total, 8 MiB manifest, 256 MiB state file, compression ratio 200). This increment commits the three contracts as JSON Schema (draft 2020-12) files in `packages/storage/schemas/`, validates every manifest against them on the writing side and the reading side in both languages with a small dependency-free subset validator, adds a committed golden archive fixture whose manifest round-trips byte-for-byte through pack, unpack and re-pack, and cross-checks the schema constants against the reader limits and the TypeScript schema union so they cannot drift. Nothing is published to the internet: the schemas carry URN identifiers, not URLs, and gate G7 stays closed; publication belongs to HV-033. The archive format does not change; every archive produced today still validates.

## Acceptance criteria
1. **The three contracts exist as machine-readable schema files in-repo.** `packages/storage/schemas/hv-project-archive.1.schema.json` (the `archive.json` manifest), `packages/storage/schemas/hv-state.1.schema.json` (the `snapshot.json` manifest, whose `schema` field is an enum of exactly `hv-state/1` … `hv-state/13`) and `packages/storage/schemas/hv-clips.1.schema.json` (`clips/manifest.json`) are JSON Schema draft 2020-12 documents with `$schema: "https://json-schema.org/draft/2020-12/schema"`, a `$id` of the form `urn:hollywood-video:schema:<name>:<version>` (no `http`/`https` URL anywhere in the file except the dialect line), `title` and `description`, and use only the keyword subset both validators implement (criterion 3). The `hv-project-archive` schema fixes `schema` as the constant `hv-project-archive/1`, `projectId` to `^[A-Za-z0-9_-]{1,128}$`, `files` as an array of `{path, bytes, sha256}` objects with `additionalProperties: false`, `path` to `^[A-Za-z0-9_./-]+$` and at most 1024 characters, `bytes` as an integer in `[0, 8589934592]`, `sha256` to `^[a-f0-9]{64}$`, `files.maxItems` = 100000 and `totalBytes` as an integer in `[0, 68719476736]`. Satisfies FULL-SCOPE §3 P16 Exceed "Studio as a Protocol: the project archive and manifest schema are published, so films are portable across any Hollywood Video instance, including self-hosted ones." (the in-repo, versioned half of "published"), §3 P16 "Self-host distribution: … documented archive schema for portability.", §3 P12 "Archive: portable project archive (documented schema, content hashes, manifest, all sources), restore on any instance." and the §9 register row "HV-040 | Storage and Archive at Scale (PostgreSQL, S3, lifecycle, portable archive)".
2. **Writer and reader validate against the schema files in both languages, before finalizing and before inserting.** TypeScript: `writeStateSnapshot` validates the `snapshot.json` object against `hv-state.1` before serializing it; `readStateSnapshot` validates the parsed `snapshot.json` before the checksum comparison; `exportProjectArchive` validates the `hv-clips/1` object before `writeFileSync`; `PostgresArtifactStore.checkpoint` validates the `hv-clips/1` object before uploading it; `importCompletedJob` and `restoreCheckpoint` validate an object-form manifest after parsing and before any upload or database write, while still accepting the legacy bare-array local form exactly as today. Python: `pack` validates the manifest it built against `hv-project-archive.1` before writing any byte of the ZIP, `inspect` validates the parsed `archive.json` before any hand-rolled check, `project_scope` validates `snapshot.json` against `hv-state.1` so both `pack` and `unpack` enforce it, and `verify_execution_media` validates an object-form clips manifest. Every existing hand-rolled check stays; the schema is an additional, earlier layer, and a schema failure is reported as `archive schema violation: <json-pointer>: <reason>` from both languages. `importProjectArchive` therefore cannot reach `importStateSnapshot` with a manifest that fails the contract. Satisfies FULL-SCOPE §3 P12 "restore on any instance", §8 "Security: … upload bombs" and §10 "Evidence before promotion: tests, benchmarks, post-flight evals, gap audits."
3. **A bounded, dependency-free subset validator, identical in both languages, that fails closed on anything outside the subset.** `node_modules` contains no JSON Schema validator, so `packages/storage/src/archive-schema.ts` (imports from `node:fs`, `node:path`, `node:crypto` only) and a `validate_document` function in `scripts/archive-package.py` (stdlib only) implement exactly: `type` (`object`, `array`, `string`, `integer`, `number`, `boolean`, `null`), `required`, `properties`, `additionalProperties` (boolean), `enum`, `const`, `pattern`, `minimum`, `maximum`, `minLength`, `maxLength`, `items`, `minItems`, `maxItems`, `uniqueItems` and local `$ref` to `#/$defs/<name>`; `$schema`, `$id`, `$defs`, `title`, `description`, `$comment` and `examples` are annotations and ignored. Any other keyword in a schema file makes both validators throw `unsupported schema keyword` rather than silently pass, so the schema files cannot outgrow the validators. `integer` means a safe integer in TypeScript and `int` (not `bool`, not `float`) in Python; every `pattern` in the three files is `^…$`-anchored (the test asserts this) and is applied with `RegExp.test` in TypeScript and `re.fullmatch` on the unanchored body in Python, so the two languages agree on strings with trailing line terminators. No entry is added to any `package.json`, lockfile or pip requirement. Satisfies FULL-SCOPE §10 "Provider independence and versioned adapters" (a versioned contract with no vendor in the loop) and CLAUDE.md "Never add keys, accounts, or vendors."
4. **Schema constants and the reader limits cannot drift.** `archive-schema.ts` exports `ARCHIVE_LIMITS = {maxFiles: 100000, maxFileBytes: 8 * 1024 ** 3, maxTotalBytes: 64 * 1024 ** 3, maxManifestBytes: 8 * 1024 ** 2, maxStateFileBytes: 256 * 1024 ** 2, maxCompressionRatio: 200}` and `STATE_SNAPSHOT_SCHEMAS` (the thirteen `hv-state/<n>` strings, now the single source for the union in `snapshots.ts`). Tests assert the `hv-project-archive` schema's `files.maxItems`, `bytes.maximum` and `totalBytes.maximum` equal the TypeScript limits and the Python `MAX_FILES`, `MAX_FILE_BYTES`, `MAX_TOTAL_BYTES` module constants; that the `hv-state` enum equals `STATE_SNAPSHOT_SCHEMAS` and the Python accepted list; that `stateSnapshotSchema()` never returns a value outside the enum; and that `validateSnapshot` and `readStateSnapshot` reject `hv-state/14` ("Unknown schema versions fail closed" in `docs/PROJECT-ARCHIVE.md`). The compression ratio and the manifest and state-file byte bounds are container limits, documented next to the schema rather than expressed in it. Satisfies FULL-SCOPE §3 P12 "content hashes, manifest" and §10 "Evidence before promotion".
5. **A committed golden archive round-trips byte-for-byte and is the conformance oracle.** `packages/storage/test/fixtures/archive-golden/source/` holds one drained `hv-state/1` project (no review links, no tokens, no secrets; `deleteAfter` far in the future; one completed `animatic` job with a checkpoint) with its state files written by `writeStateSnapshot`, a `clips/manifest.json` in `hv-clips/1` form, and small placeholder media under `artifacts/<projectId>/<jobId>/` (well under 64 KiB in total). Alongside it, `archive.json` is the expected manifest and `receipt.json` records `{projectId, files, bytes, manifestSha256}`. The suite proves: `readStateSnapshot(source)` validates and `writeStateSnapshot` of the result reproduces the state files byte-for-byte; Python `pack` of `source` produces an `archive.json` entry byte-identical to the committed file with the committed `manifestSha256`; `unpack` then `pack` of the extracted tree produces the identical manifest again; packing the same tree twice in the same interpreter produces identical ZIP bytes (the `archive.json` entry is written through a fixed-date `ZipInfo` like every other entry, so the container is reproducible; `archiveSha256` is recorded in evidence but not pinned in the fixture because it depends on the interpreter's `zipfile`); the manifest contains exactly the keys `files`, `projectId`, `schema`, `totalBytes` and no timestamp, host name or absolute path; and TypeScript's canonical serialization (`canonicalManifestBytes`: recursively sorted keys, no whitespace) of the committed `archive.json` hashes to the same `manifestSha256` Python stores in `hv_archives.manifest_sha256`. Satisfies FULL-SCOPE §9 Wave G exit "self-hosted deploy produces identical manifest output" (the in-repo half, verifiable now) and §3 P12 "content hashes, manifest".
6. **A rejection matrix proves both validators refuse the same malformed manifests.** A shared table of at least the following mutations of the golden manifests is rejected by the TypeScript validator and by the Python validator with the same JSON pointer: `schema: "hv-project-archive/2"`, missing `totalBytes`, an extra top-level key, `files: {}`, a file entry with an extra key, `bytes: -1`, `bytes: 8589934593`, `bytes: "12"`, `bytes: true`, `sha256` uppercase or 63 characters, `path` with `\`, a space, a leading `/`, a trailing `\n` or 1025 characters, `totalBytes` above 64 GiB, 100,001 file entries; `snapshot.json` with `schema: "hv-state/14"`, a missing `files` key, a fifth or a missing state path in `files`, a non-hex digest, a `summary` with an extra or negative field; `clips/manifest.json` with `schema: "hv-clips/2"`, a third top-level key, a clip missing `path` or `cost`, a `seed` of `-1` or `1.5`, a `durationSec` of `"1"`, a `cost` missing `total_cost_usd`. Each row is also fed through the real entry points (`inspect` via a rewritten ZIP, `readStateSnapshot`, `importCompletedJob`'s manifest branch through a fake) and the archive-level rejection leaves no `restored.*.pending` directory, exactly like the existing `rejected()` helper in `scripts/test_archive_package.py`. Satisfies FULL-SCOPE §8 "Security: … upload bombs" and §10 "Evidence before promotion".
7. **Backward compatibility: every archive produced today still validates and no shape changes.** The schema version strings stay `hv-project-archive/1`, `hv-state/<n>` and `hv-clips/1`; no field is added to or removed from any manifest; `hv_archives.schema_version` keeps storing `hv-project-archive/1`; the legacy bare-array local `clips/manifest.json` that `restoreCheckpoint` writes remains readable; `readStateSnapshot` still tolerates a directory without `snapshot.json`. Proof: `packages/storage/test/snapshots.test.ts`, `current-screenplay-archive.test.ts`, `assembly-snapshots.test.ts`, `living-script-*-snapshots.test.ts`, `shot-execution-snapshots.test.ts`, `execution-capture-projects.test.ts`, the existing classes of `scripts/test_archive_package.py` and the S3-lane `backups.test.ts`, `graphics.test.ts` and `audio-jobs.test.ts` archive export/import cases pass with only fixture-helper edits (the Python fixtures gain a `files` map in `snapshot.json`, which the TypeScript reader already required). Satisfies FULL-SCOPE §9 Wave A exit "Staging runs on PostgreSQL + S3 with the existing E2E passing" and §10 "Provider independence and versioned adapters".
8. **Nothing is published, nothing frozen changes, no dependency, account, vendor or user-facing surface is added.** No schema is served by any HTTP route, uploaded to any bucket, or referenced by a public URL; `docs/PROJECT-ARCHIVE.md` states that the schemas are in-repo contracts and that internet publication is deferred to HV-033 under gate G7. The diff touches nothing under `docs/legal/**`, `docs/adr/**`, `.github/workflows/**` or `packages/safety/**` (the CI step "portable archive validation" keeps running `python3 -m unittest discover -s scripts -p test_archive_package.py` and picks up the new test class unchanged), adds no `package.json` or lockfile entry, no key, account, tier, cookie or tracking, and changes no budget default. Satisfies ADR-0020 "public deployment, public branding, terms publication, and live paid generation remain fail-closed", FULL-SCOPE §10 "Free and anonymous for every end user; no billing code reachable." and "Safety refusals expand only."

## Out of scope
- Publishing the schemas to any URL, registry, bucket or the API (`/api/schemas/...`), OpenAPI or SDK generation from them, and any public identity: HV-033 under gate G7 (ADR-0020).
- A `hv-project-archive/2` or `hv-state/14` format, any new manifest field (for example per-file content types or a signed manifest, which is C2PA/HV-031 territory), or changing the ZIP container rules.
- Schema coverage of the state file payloads themselves (`state/projects.json`, `queue/jobs.json`, ledger, reviews): those are validated by the planner and `validateSnapshot`; the contract here is the manifest layer, with the payload validators cited as the second layer.
- Adding a general JSON Schema library, `$ref` to other files, `format`, `oneOf`/`anyOf`, `patternProperties`, or any keyword outside the subset; any `package.json`, lockfile or pip change.
- Changing `PostgresArtifactStore` upload, retention, lifecycle, signed-URL or row-security behaviour (HV-040-01/02/03); editing `.github/workflows/ci.yml`; touching private staging.
- A CLI `--validate` subcommand for `scripts/storage-archive.ts` (useful, but it belongs with the CLI work in HV-033).
- Any new npm or pip dependency, vendor, account or key.
