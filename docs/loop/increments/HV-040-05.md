# HV-040-05 — Wave A exit re-verified under the loop: live staging evidence, deferred register, epic to `review`
epic: HV-040
spend_usd: 0

## Goal
Close HV-040 honestly. Increments -01 (lifecycle), -02 (signed media contract), -03 (row-level coverage) and -04 (archive schemas) are merged and deployed. What remains is not code but proof: the §9 Wave A exit "Staging runs on PostgreSQL + S3 with the existing E2E passing; fleet of ≥3 workers" is today credited to pre-loop PRs (#12–#15, release `489621e`, `docs/PROGRAM-EXECUTION.md` bullets of 2026-09-05/06) and to `hv-managed-storage-check/1` files produced by an ad hoc script that was never committed. This increment adds a committed, read-only evidence collector, `scripts/storage-wave-a-evidence.ts`, that runs on the private staging host against the live runtime and writes `docs/evidence/hv040-storage/wave-a-exit.json` (schema `hv-wave-a-exit/1`) from what it actually observes: active release sha and backend from the runtime's release markers and `storage-deployment.json`, migration head from `drizzle.__drizzle_migrations` matched against `infra/drizzle/meta/_journal.json`, the worker slots from `hv_workers` (latest incarnation per name, fresh heartbeat) and the supervisor, the bucket lifecycle state from a signed `GET ?lifecycle` plus the sweeper's last `incompleteUploads` line, the `storage-readiness.ts` probe result under the `hv_api` role file, the edge `/health` answer, the backup service status, and the CI `quality` job step conclusions ("unit + integration", "three-worker PostgreSQL and S3 flow", "private staging smoke") for the exact release sha via `gh`. Every section fails closed to `pending` with a reason when its source is unreachable; nothing is typed in by hand. The same increment writes the "Deferred from HV-040 (with reason)" register into `docs/STORAGE-DEPLOYMENT.md` naming what HV-040 does not deliver and which epic or gate owns it, so the operator's G6 acknowledgement is of a bounded, stated scope. The diff does not touch `docs/loop/STATUS.md`; the RECORD stage moves HV-040 to `review` at merge time (see "Doc to update"). No runtime code path, route, migration, budget default, provider, dependency or frozen path changes; spend is 0 and providers stay `mock`.

## Acceptance criteria
1. **A committed, read-only collector produces the Wave A exit evidence from live state.** `scripts/storage-wave-a-evidence.ts` exports `collectWaveAExit(probes, options)` and, under `import.meta.main`, runs against the host named by `--runtime <dir>` (the private staging runtime root) and `--repo <dir>` (the checkout holding `infra/drizzle/meta/_journal.json`) with the `hv_admin` connection and object credentials taken only from the process environment (the operator sources `storage-backup.env`; the script never opens `secrets.env`, never prints a URL, key or password, and refuses to run if `HV_PG_ADMIN_URL` names a user other than `hv_admin`). All database reads run inside one `set transaction read only` block with a `statement_timeout`; the only object-store calls are signed `GET /{bucket}?lifecycle` and `GET /{bucket}?uploads&max-uploads=1`; the only subprocesses are `storage-readiness.ts`, `supervisorctl … status`/`tail`, and `gh run …`. It writes `--output <path>` atomically and prints the JSON to stdout. Satisfies FULL-SCOPE §9 Wave A exit "Staging runs on PostgreSQL + S3 with the existing E2E passing; fleet of ≥3 workers" and §10 "Evidence before promotion: tests, benchmarks, post-flight evals, gap audits."
2. **Every section is observed or `pending`, never fabricated.** The output has schema `hv-wave-a-exit/1` and the sections `release`, `database`, `migrations`, `workers`, `objectStore`, `readiness`, `health`, `backup`, `ci`, each carrying `status: "recorded" | "pending"`; a `pending` section carries `reason` and null data fields, a `recorded` section carries non-null data. `waveAExit` is derived, not asserted: `{postgresBackend, s3Backend, workersRegistered, workersExpected, fleetAtLeastThree, migrationsInSync, readinessPassed, existingE2ePassing, satisfied}` where every boolean is `false` unless its source section is `recorded` and the observed value meets the exit, and `satisfied` is the conjunction. A missing `gh`, an unauthenticated `gh`, a CI run still `in_progress`, a run whose `headSha` differs from the live release sha, a readiness timeout, an unreachable edge, or a `storage-deployment.json` that fails the same shape checks as `storage-runtime-launch.py:deployment()` each produce `pending` with the reason, and a non-zero exit code only when `--require-satisfied` is passed. Satisfies CLAUDE.md "Never fabricate launch, legal, or provider evidence" read with ADR-0020 (fail-closed) and §10 "Evidence before promotion".
3. **The fleet criterion is measured the way the operator console measures it, on the real host.** `workers.registered` counts, from `hv_workers`, the latest row per `body->>'name'` (the `distinct on … order by heartbeat_at desc, id desc` rule of `packages/storage/src/diagnostics.ts`) whose `heartbeat_at` is within 45 seconds and whose state is `idle`, `busy` or `draining`; `workers.expected` comes from `storage-deployment.json.workers`; `workers.supervisor` lists the state of `rough-cut-staging-worker`, `-2`, `-3` from `supervisorctl status`; `workers.names` lists the names only (no ids, no job ids). `fleetAtLeastThree` is true only when `registered >= 3` and `registered >= expected` and all three supervisor programs are `RUNNING`. Stale incarnations never count. Satisfies §9 Wave A "fleet of ≥3 workers", §3 P15 "Render farm: horizontally scaled worker fleet" and `docs/WORKER-FLEET.md` ("A stale heartbeat is not evidence that a process is still alive").
4. **"Existing E2E passing" is pinned to named checks on the exact live release.** `ci` records, for the GitHub Actions `ci` workflow run on `push` to `main` whose `headSha` equals `release.sha`, the run id, conclusion and the conclusions of the `quality` job steps `unit + integration` (which contains `test/e2e-12shot.test.ts`), `three-worker PostgreSQL and S3 flow` (`scripts/storage-fleet-smoke.ts`) and `private staging smoke` (`bun run smoke:runtime`). `existingE2ePassing` is true only when all three are `success` on that sha. The doc states explicitly that `private staging smoke` is the offline JSON runtime smoke and that the PostgreSQL + S3 + three-process flow is the fleet step. Satisfies §9 Wave A "with the existing E2E passing" and §10 "Evidence before promotion".
5. **Storage facts are read from the system of record, not from deployment notes.** `database` records the PostgreSQL `version()` string, the count of `hv_*` relations with `relrowsecurity and relforcerowsecurity` true, and the counts of `hv_projects`, `hv_jobs`, `hv_artifacts` and `hv_queue_counts()` (no ids, no bodies); `migrations` records `applied` (rows in `drizzle.__drizzle_migrations`), `journalEntries`, `head` (the journal tag whose `when` equals `max(created_at)`), and `inSync = applied === journalEntries && head === last journal tag`; `objectStore` records endpoint scheme, bucket name, `lifecycle: "declared" | "absent" | "unsupported" | "pending"` with `daysAfterInitiation` when declared, `multipartListing: "supported" | "unsupported" | "pending"`, and `sweeper.incompleteUploads` parsed from the last JSON status line of the sweeper's stdout; `backup` records `state`, `lastCompletedAt`, `objects`, `localRepositoryOnly` through `readBackupStatus` from `packages/observability/src/diagnostics.ts`. Satisfies §3 P15 "Data: PostgreSQL as system of record and job coordinator; Drizzle migrations; row-level capability checks." and "Storage: S3-compatible object storage with multipart upload, lifecycle policies …".
6. **The deferred register exists, is specific, and names an owner or gate for each item.** `docs/STORAGE-DEPLOYMENT.md` gains a section "Deferred from HV-040 (with reason)" listing at least: CDN delivery and regional placement (edge/CDN vendor, gate G3; owned by HV-032); off-host replication, 5-minute RPO, multi-region and disaster-recovery drills (owned by HV-038; draft PR #19; today `localRepositoryOnly: true`, 120-second same-host snapshots); public publication of the archive schemas (HV-033, gate G7, ADR-0020; in-repo URNs only after HV-040-04); per-review-link artifact revocation (future HV-040-0N or HV-029; needs a versioned token payload, see `docs/STORAGE-DELIVERY.md`); the `coalesce(current_setting('hv.project_id', true), '') <> ''` guard present on the 0015 policies but not on the 0001 `*_capability` policies (safe today because `''` never equals a project id; uniformity needs an additive `ALTER POLICY` migration, not an edit of the hashed 0001 file); the bucket-level `AbortIncompleteMultipartUpload` rule not declared on the live staging bucket (the application sweeper enforces the 24-hour grace; declaring it is a one-time `prepare-object-bucket.py` run against the live bucket that needs explicit operator approval as a live object-store configuration change, gate G8 by analogy); and the `pending` state of `docs/evidence/hv040-storage/object-lifecycle.json` unless criterion 8 records it. Satisfies §10 "Evidence before promotion: tests, benchmarks, post-flight evals, gap audits." (a gap audit) and EXECUTION-LOOP G6 "every increment merged, evidence linked".
7. **Offline tests pin the collector's contract and the committed evidence's honesty.** `packages/storage/test/wave-a-evidence.test.ts` (always runs) drives `collectWaveAExit` with injected probes and asserts the schema, the fail-closed rules of criterion 2, the worker counting rule of criterion 3, the CI sha-match rule of criterion 4, the lifecycle classification (200 + `DaysAfterInitiation` → `declared`; 404 `NoSuchLifecycleConfiguration` → `absent`; 501/`NotImplemented` → `unsupported`; anything else → `pending`), the migration head mapping against the real `_journal.json`, and that the serialized output contains no value matching a connection URL, an access key id, a secret, a token or a job/project id. A second case parses the committed `docs/evidence/hv040-storage/wave-a-exit.json` and asserts it validates the same shape, that `recordedAt` is an ISO timestamp, that `release.sha` is 40 hex characters, and that `waveAExit.satisfied` equals the conjunction recomputed from the sections. Satisfies §10 "Evidence before promotion" and CLAUDE.md "Every criterion gets a real test."
8. **The committed evidence comes from the real host, on the release that includes HV-040-04.** `docs/evidence/hv040-storage/wave-a-exit.json` is the unedited output of one run on the staging host after PR #89 has been merged and deployed with `deploy-storage-staging.py --release-sha`; `release.sha` equals the merge commit of PR #89 (or a later `main` commit if one deploys first), `waveAExit.satisfied` is whatever the run observed, and the increment doc's build notes quote the run command and the `recordedAt`. Satisfies §9 Wave A exit and CLAUDE.md "tests use a per-run database/bucket prefix, never the staging data."
9. **No frozen path, dependency, budget default, account, vendor, migration, staging mutation or user-facing surface change.** The diff touches nothing under `docs/legal/**`, `docs/adr/**`, `.github/workflows/**`, `packages/safety/**` or `infra/drizzle/**`, adds no `package.json` or lockfile entry, no key, account, tier, cookie or tracking, changes no HTTP route, and the collector performs no write, `DELETE`, `PUT`, lifecycle declaration, restart or migration against staging (G8 not triggered). Satisfies §10 "Free and anonymous for every end user; no billing code reachable.", "Safety refusals expand only." and EXECUTION-LOOP frozen list.
