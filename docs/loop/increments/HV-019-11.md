# HV-019-11 — Two real-render queue tests failed the merge gate on a slow runner

epic: HV-019
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

`packages/queue/test/degraded-resume.test.ts` (HV-019-07) renders the same three-shot film with
ffmpeg twice: once straight through, and once interrupted and resumed. It had no timeout of its own,
so it ran under bun's default of 5 seconds. On 2026-09-28 CI failed on PR #246, a frontend-only
change that touches nothing in the queue:

```
(fail) a film interrupted mid-render delivers the same degraded record as one that was not [5000.12ms]
Expected: "done"
Received: "queued"
```

The render was cut off at the 5-second mark, not wrong. The same test times out every time in this
build container, and takes 8.4 s for the file once it is allowed to finish.

Every other real-render test in this package states its own timeout (for example,
`current-film-worker.test.ts` uses 120–300 seconds). A merge gate that fails on how fast the runner
happens to be costs a 45-minute rerun, and it teaches people to rerun red builds without reading
them.

## What this increment does

- **Gives both rendering tests in the file a 120-second timeout**, in line with the package's other
  render tests. The assertions are unchanged.

## Acceptance criteria

1. **Both tests pass where they used to time out.** In this container the file passes 3 / 0 in
   about 8 s. Before the change, the first test failed at 5,000 ms.
2. **Nothing the tests assert is changed.**

- Tests: `packages/queue/test/degraded-resume.test.ts`.

## Known gaps this leaves

- **Other files with real renders that rely on the default timeout** have not been audited. The
  audit would be `grep` for `render(` and `ffmpeg` in tests without a third argument to `test`.
