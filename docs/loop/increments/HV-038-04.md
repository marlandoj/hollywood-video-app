# HV-038-04 — Observability exit evidence from live state, the availability SLI defined but not claimed, and the HV-038 deferred register
epic: HV-038
spend_usd: 0

## Goal
Close HV-038 honestly. Increments -01 (sanitized trace-correlated structured logs), -02 (read-only operator reliability panel: latency percentiles, failure rates by code, per-worker provider circuit state, cost burn by provider) and -03 (off-host encrypted transport rebased onto `main` plus a fixtures-only RPO/DR drill) are merged. What remains is not code but proof and bounding. Today every HV-038 claim rests on offline tests, synthetic browser fixtures, one disposable CI backend job (`telemetry-contract`) and one 2026-09-06 local recording; FULL-SCOPE §P15's "99.9 % control-plane target" has never been instrumented at all, let alone met.

This increment adds a committed, read-only evidence collector, `scripts/observability-exit-evidence.ts`, modelled on `scripts/storage-wave-a-evidence.ts` and run on the private staging host against the live runtime. It writes `docs/evidence/hv038-observability/observability-exit.json` (schema `hv-observability-exit/1`) from what it actually observes: the managed observability runtime (pinned Jaeger / Collector / Prometheus versions from `binaries.json`, the immutable config identity from `runtime.json`, the supervisor state of the three observability programs, the three loopback readiness endpoints); the stored-trace reading through `TelemetryExplorer.recentTraces()`; the four fixed PromQL expressions through `TelemetryExplorer.metrics()` and what the reliability bundle actually returns; the deployed release's structured-log health, judged against `EVENTS` / `LOG_KEYS` / `guardLine` over the last 64 KiB of each service's supervisor stream; the reliability panel's own readings recomputed through `providerHealthReadings` / `costReadings` from the same rows the panel reads; backup freshness through `readBackupStatus`; and the committed off-host drill's measured lag with its negatives carried forward. It does not re-measure anything `storage-wave-a-evidence.ts` already records — it references `docs/evidence/hv040-storage/wave-a-exit.json` through that collector's own `validateDocument`, and reuses its helpers rather than copying them.

Second, it defines the availability SLI precisely — which operation, which success predicate, from which vantage point, over which window, with which exclusions — records one bounded single-vantage instrument check of that predicate from the host's loopback, and states in the file and in the doc that this establishes nothing about availability, because an availability claim needs an off-host vantage and a declared operating window (gate G3; a public probe target is additionally G7/ADR-0020). No availability percentage is ever written.

Third, it writes "Deferred from HV-038 (with reason)" into `docs/OBSERVABILITY.md` in the shape HV-040-05 used in `docs/STORAGE-DEPLOYMENT.md`: each item states what is not delivered, why not here, which epic or gate owns it, and its current truthful state — so the operator's G6 acknowledgement is of a bounded, stated scope.

The diff does not touch `docs/loop/STATUS.md`; RECORD moves HV-038 to `review` at merge time (see "Doc to update"). No runtime code path, route, migration, budget default, provider, dependency or frozen path changes; nothing is written, restarted, enabled or configured on staging (G8 is not triggered); spend is 0 and providers stay `mock`.

## Acceptance criteria

1. **A committed, read-only collector produces the HV-038 exit evidence from live state.** `scripts/observability-exit-evidence.ts` exports `collectObservabilityExit(probes, options)` and, under `import.meta.main`, runs against `--runtime <dir>`, `--repo <dir>` and `--output <path>`, with the `hv_admin` connection taken only from the process environment (the operator sources `storage-backup.env`; the script never opens `secrets.env`, never opens `operator-diagnostics.secret`, never prints a URL, key or password, and refuses to run if `HV_PG_ADMIN_URL` names a user other than `hv_admin`). All database reads run inside one `set transaction read only` block with a `set local statement_timeout`, reusing `readOnlyReads` from `scripts/storage-wave-a-evidence.ts`; the only child processes are `supervisorctl … status` and `supervisorctl … tail`; the only network calls are loopback `GET`s to the observability services and to the edge `/health`. It writes `--output` atomically through the imported `writeAtomically` and prints the JSON to stdout. Satisfies FULL-SCOPE §P15 "Observability: OpenTelemetry traces from session action to provider attempt to export; metrics; structured logs; cost dashboards." and §10 "Evidence before promotion: tests, benchmarks, post-flight evals, gap audits."

2. **Every section is `recorded`, `pending` or `not_configured` — never fabricated, never partial.** The output has schema `hv-observability-exit/1` and the sections `release`, `telemetryRuntime`, `traces`, `metrics`, `logs`, `reliabilityPanel`, `recovery`, `availability`, plus the reference block `waveA`. A `pending` section carries a fixed, whitelisted `reason` (never raw error text, never a URL, never an identifier) and null data fields; `not_configured` is a distinct third status used only when the host states the capability is off (`observability.json` `enabled: false`, or no observability root), mirroring the console's own `not_configured` vs `unavailable` distinction. `observabilityExit` is derived, not asserted: `{tracesQueryable, metricsQueryable, reliabilityPanelReadable, structuredLogsConforming, backupFresh, instrumented, sloClaimed: false, availabilityMeasuredExternally: false}`, where every boolean is `false` unless its source section is `recorded` and the observed value meets the stated rule, `instrumented` is the conjunction of the first five, and the last two are structural constants. A non-zero exit code only when `--require-instrumented` is passed. Satisfies CLAUDE.md "Never fabricate launch, legal, or provider evidence" read with ADR-0020 (fail-closed) and §10 "Evidence before promotion".

3. **Trace and metric health are observed through exactly the code the operator console uses, with no identifier in the output.** `traces` comes from one `TelemetryExplorer.recentTraces()` call and records `{state, windowStart, windowEnd, traces, withJobId, outcomes: {success, error, unknown}, newestStartedAt, spanCountMin, spanCountMax, services}` — counts, timestamps and the closed service set only; no trace id, span id, job id, project id or stage value outside the closed `JobStage` union is ever written. `metrics` comes from one `TelemetryExplorer.metrics()` call and records `{state, series: {expected: 4, present, withSamples}, reliability: {evaluatedAt, windowSeconds, ceilingMs, latencyOperations, latencyCapped, failureOperations, failureCodes, providers}}`, where `latencyOperations`, `failureCodes` and `providers` are values from the closed `OPERATIONS` / `FAILURES` / `PROVIDER_KINDS` sets. Because `metrics()` fails closed as a bundle, a `recorded` `metrics` section is live proof on the staging host of what only the disposable `telemetry-contract` CI job proves today: that Prometheus accepts `LATENCY_QUERY`, `FAILURES_QUERY`, `PROVIDER_ATTEMPTS_QUERY` and the instant-query `limit` against the collector's translated metric names. The collector calls each method once and `close()`s the explorer, so the one-pending/one-deadline/5-second-cache rule is never raced. Satisfies §P15 "Observability: OpenTelemetry traces … metrics" and §10 "Evidence before promotion".

4. **Structured-log health is measured against the logger's own schema, on the deployed release, without copying a line.** `logs` runs `supervisorctl … tail -65536 <program> stdout|stderr` for the API, worker and sweeper programs, drops the leading partial line, and classifies each remaining line with `EVENTS`, `LOG_KEYS`, `LOG_LINE_MAX_BYTES` and `guardLine` imported from `packages/observability/src/logs.ts`. It records per program `{lines, parsed, conforming, events, levels, traceCorrelated, unknownKeyLines, oversizeLines, guardViolations, droppedLines, suppressedLines, configurationInvalidLines, knownNonLoggerLines}` and the window `"last 65536 bytes of each stream"`. `knownNonLoggerLines` counts exactly the two documented exceptions — the sweeper's per-minute `sweptAt` status line and `telemetryFromEnv`'s fixed `telemetry.configuration_invalid` stderr line — so they are never counted as violations. No line, no key name outside `LOG_KEYS`, and no field value is copied into the output; violations are counted, not quoted. `structuredLogsConforming` is true only when every program is `recorded`, `parsed >= 1`, `conforming === parsed` and `guardViolations === 0`. Satisfies §P15 "Observability: … structured logs" and ADR-0018 "privacy-preserving abuse controls" read with `docs/OBSERVABILITY.md`'s identifier rule.

5. **The reliability panel's readings are recorded through the panel's own validators, and the vantage is stated rather than overstated.** `reliabilityPanel` runs, inside the same read-only `hv_admin` transaction, the same SQL shape `storageDiagnostics` uses (latest incarnation per `body->>'name'`, `heartbeat_at` within 45 seconds, state `idle|busy|draining`, the 65-row over-fetch; the 30-day `hv_cost_events` rollup with its 65-row over-fetch) and passes the results through `providerHealthReadings` and `costReadings` from `packages/observability/src/diagnostics.ts`. It records `{circuits: {workers, entries, dropped, truncated, states, stages, providers}, costs: {providers, totals, dailyAverageUsd, lastDayVsAverage, truncated}, queue: {queued, running}, workers: {ready, busy, draining, latestProcesses}}` — no pool `id`, no project, job or attempt id. It also records `{vantage: "hv_admin read-only transaction on the host", httpSurfaceRead: false, httpSurfaceReason: "the diagnostics token is minted by an operator; the collector opens no secret"}`, so the file never implies the live console was read. Satisfies §P15 "Operator console: budgets, provider health, queue depth, failure rates, latency, cost variance …" and `docs/WORKER-FLEET.md` "A stale heartbeat is not evidence that a process is still alive".

6. **Recovery is recorded as freshness plus the drill's measured figure, with the drill's negatives carried forward verbatim.** `recovery` records `{backup: {state, lastSnapshotAt, lastCompletedAt, ageSeconds, freshWithin300s, failureStage, localRepositoryOnly: true}}` through `readBackupStatus` on the manifest's `backupRepository`, and `{offHostDrill: {source, recordedAt, snapshotToCopyMs, encryptionExercised, provesOffHostRpo: false, provesHostLossRecovery: false, restoredIntoLiveDatabase: false, independentDestination}}` parsed from the committed `offhost-drill.json` (re-validated, and `pending` if it fails validation), plus the constants `offHostDestinationConfigured: false` and `lastLiveRestoreAt: null`. `backupFresh` is true only when the backup section is `recorded`, the state is `running` or `healthy` and `freshWithin300s` is true — the same 5-minute rule `OperatorDiagnostics` applies. Nothing in the section is a claim about RPO. Satisfies §P15 "Reliability: … RPO 5 min for state, near-zero loss for approved media, … disaster-recovery drills." (instrumented, not claimed) and CLAUDE.md "Never fabricate launch, legal, or provider evidence."
