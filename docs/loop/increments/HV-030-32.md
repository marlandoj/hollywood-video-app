# HV-030-32 — A sequence's finishing requests do bounded work (Release 3 step 15's rehearsal)

epic: HV-030
release: 3 "Features"
gate: none new
spend_usd: 0

## Why

Release 3's $0 rehearsal (build step 15) ran "The Tide Clock" on staging, on the mock providers: one
project, 202 shots in ten sequences. It stopped at sequence 10. The API is one Bun process, and some of
its finishing routes did minutes of work inside the request. While they ran, every other request
waited. Bun's server idle timeout is 20 s, so the requests that waited too long died with 400 "Idle
timeout reached after 20s". The request that died was `POST /api/projects/:id/jobs`, which normally
takes 0.6–0.9 s, right after the score request.

From the API log, at sequence 9's finishing (the client is `packages/frontend/src/studio.js`):

| Request | Took |
|---|---|
| `POST /dialogue/:finalId` ("Laying the cast's voices into the final") | 47.8 s |
| `POST /sound-mixes/:cutId` ("The Composer is scoring the film") | 101 s (48–105 s over the run) |
| a GET in the same area (the score's quote, the dialogue quote or `/sounds`) | 17–45 s |
| `POST /ambience/:cutId` | 4.5 s |
| `GET /api/jobs/:jobId`, while those ran | 11–15 s, then 20 s (400) |
| `GET /api/jobs/:jobId`, averaged over the run | about 1.5 s (0.2–0.3 s on a small project) |

All of these logged `route: "unmatched"`, so the log couldn't say which route was slow.

**The measured cause.** The same screenplay was run here through the studio flow, on the mock providers,
as far as sequence 1 (23 shots) and its score. The score's quote took 41.9 s, the score 102 s, the
dialogue quote 18–19 s and the ambience 8.3 s: the staging numbers, on the first sequence alone. A CPU
profile and a count of each request's work showed why:

- **Each check of a retained film planned the whole feature once per shot.** `dialogueSource` verified
  each shot record with `sourceRenderRecord`. That call validated the film's execution evidence and
  planned the film's shots again (`renderShots`), for every record. A sequence render's plan is the
  whole feature's plan, filtered to the sequence. Planning 202 shots takes about 0.21 s, nearly all of
  it the safety gate over every shot's prompt (`directShots`, `directCast`).
- **Each request checked the same film many times.** The score's quote verified it 7 times (its
  source, its plan, its permission), and the score 17 times. That came to 169–171 plans of the feature
  for one quote, about 36 s, and the view of a finished score job (`GET /api/jobs/:jobId`) did the same.
- **Each request read every job of the project.** The dialogue, score and render routes read every job
  body to find one request key, and again to count the running jobs. A score or dialogue job carries
  the film it was made from, so a feature's jobs are 0.7–2 MB each, and tens of megabytes by the tenth
  sequence. On PostgreSQL every read is parsed on the event loop. This is the part that grows with each
  sequence made.

The plans are counted per shot of the sequence being finished, so the 48–105 s range follows each
sequence's size (9 to 24 shots) as well as the project's growth.

## What this increment does

**1. A film is verified with one plan of it** (`packages/planner/src/shot-reuse.ts`).

- `sourceRenderRecords(film, records, at)` makes every check `sourceRenderRecord` made, for each record,
  in the same order. What depends only on the film is checked once for all of them: its execution
  evidence, its planned shots, its parsed screenplay and its provider plan. Those checks read nothing
  from the record, so for each record they hold or throw exactly as before. `sourceRenderRecord` is now
  the one-record case. `dialogueSource`, `editOriginalJob`'s film check and the editorial
  source media check use the batch.
- **`renderShots` is memoized on exactly what it reads.** That is the job's project, stage, tier,
  screenplay, cast, direction, sequence and style bible, and the time it plans at. Planning is a pure
  function of those. The key is the SHA-256 of their exact serialization, through the planner's
  `HistoricalValidationCache` (moved from the API, which re-exports it). A value it can't serialize
  exactly (an `undefined`, a getter, `-0`) is planned afresh. A plan that throws is never kept, so every
  refusal, the safety gate's included, runs every time. Each caller gets its own copy.
- **A passing verification is remembered.** It is kept under the SHA-256 of the exact film, records and
  time. A film or record that differs in any byte, or a different time, is verified again. A failure is
  never remembered.

So each check still proves what it proved: the same function of the same bytes, either computed or
remembered from an earlier computation in this process. No check is removed, narrowed or reordered
for a single record. The memos are bounded: 32 plans (64 MB) and 256 verified digests.

**2. The finishing routes ask the store one question** (`packages/api/src/project-jobs.ts`,
`packages/queue/src/index.ts`, `packages/storage/src/jobs.ts`).

- `projectJobWithKey`, `projectRunningCount` and `projectJobsAt` replace "read every job, then filter"
  at seven call sites:
  - the dialogue route's key lookup, running count and the quote's finished auditions;
  - the score route's key lookup and running count;
  - the render route's (`POST /jobs`) key lookup and running count.
- PostgreSQL answers from the `(project_id, idempotency_key)` and `(project_id, status)` indexes. The
  JSON store answers from its file, as it does for every read. Each store answers only for its own
  project. A store that can't answer falls back to `projectJobs`.
- Each answer is filtered by the project again, and the three reads are asked in `project-jobs.ts`
  alone.

**3. The request log names each project route** (`packages/observability/src/index.ts`, `logs.ts`).

- `routeLabel` gives the `api.request` line the metric template where there is one. Otherwise it gives
  the project path with each word of the closed list `PROJECT_ROUTE_WORDS` kept and every other segment
  written `:id`, for example `/api/projects/:projectId/dialogue/:id` or
  `/api/projects/:projectId/cast/:id/sheets`. A label never carries a value from the request.
- The log keeps a route only when it is a template or such a pattern (`isRouteLabel`).
- The five finishing routes are metric templates too: `dialogue/:id`, `sound-mixes`, `sound-mixes/:id`,
  `sounds` and `ambience/:id`. That makes 23 templates: 414 series for `http.request`, within the 4,096
  limit, which `metric-overflow.test.ts` computes from the list.
- docs/OBSERVABILITY.md says so in its route-label entry.

After this, on this machine, on the same sequence 1 of the 202-shot feature and the JSON store: the
score's quote takes 0.6 s, the score 1.3 s, the dialogue quote 0.5 s and the ambience 0.1 s. The first
read of the final, in a fresh process, takes 0.4 s, which includes its one plan.

## Acceptance criteria

1. **A retained film is verified with one plan, and refuses what it refused.** Read twice, sequence 1's
   final is verified with no further plan of the feature. With its first or its last shot's record
   changed, it is refused, and refused again. Read past its retention, it is refused right after
   passing.
2. **A finishing request's work doesn't grow with the feature.** Through the studio flow, sequence 1 is
   rendered, scored and voiced. Each of its finishing requests plans the feature at most once and reads
   no project's whole job list: the render requests, the score's quote, the sound library read and
   upload, the ambience, the score, the dialogue quote and the voices. In a feature of seven sequences
   the same requests plan it exactly as often as in a feature of two, and none gates more than the
   feature's 135 shots once. Before, the score planned the feature 71 times for a three-shot sequence
   (9,585 planned shots in the seven-sequence feature), and the score, voices and render requests each
   read every job twice.
3. **The narrow job reads answer for one project.** On PostgreSQL, a request key, the running count and
   a stage's finished jobs are each answered for the project asked, as the whole list would answer
   them. A store scoped to one project refuses another's, and an unscoped store refuses all. The reads
   are asked in `project-jobs.ts` alone, and each answer is filtered by the project there.
4. **The routes are labelled.** The request log names every finishing route by its pattern, and the
   crew's routes too. No request of the studio flow logs `unmatched`, and no log line carries an id.
   Every word the API's handlers match a project path against is in the label's word list. The five
   finishing routes are metric templates. A log route carrying an id or an unknown word is dropped.
5. **Reverting the change fails the new tests.** Restoring the 13 changed source files from `main`
   fails all four tests in `feature-finishing-bounded.test.ts` and the new test in
   `project-scoped-jobs.test.ts` on their assertions. `route-labels.test.ts` and
   `project-job-reads.test.ts` fail on the exports they import (checked).

- Tests: `packages/api/test/feature-finishing-bounded.test.ts` (1, 2, 4; 4 pass),
  `packages/api/test/route-labels.test.ts` (4; 2 pass), `packages/storage/test/project-job-reads.test.ts`
  (3; 1 pass on PostgreSQL, skipped without it), `packages/api/test/project-scoped-jobs.test.ts` (3; 4
  pass). Unchanged and passing: `packages/observability/test/*` (all 8 files), the sound, dialogue (but one test, below),
  job-view, shot-reuse and feature studio suites in `packages/api/test`, `api.test.ts`,
  `mock-profile-locks.test.ts`, `packages/planner/test` (retained shot reuse, retained auditions, living
  script, ambience), and `packages/storage` and `packages/generator` dialogue, sound, jobs and
  editorial suites.

## Known gaps

- **A film's first check in a fresh API process still plans the whole feature once.** That is about
  0.2 s for 202 shots, nearly all of it the safety gate over every shot's prompt. Planning only the
  sequence's own scenes would change what `renderShots` refuses: today it gates every shot of the
  feature. That is left alone.
- **What remains in a request is one sequence's film, verified and hashed.** Here, on the JSON store, a
  23-shot sequence's score takes about 1.3 s. That doesn't grow with the feature or the project, but it
  is still done on the event loop, not in the worker. Nothing was moved to a queued job: once the
  repeated plans were gone, what was left was bounded. The ambience route still renders a bed the
  library lacks inside the request. It does so with ffmpeg in a subprocess, which doesn't block the
  loop, and once per bed per project.
- **No test times the event loop.** The tests count plans, planned shots and whole-project reads,
  because wall-clock assertions are flaky on a shared two-core machine. Staging hasn't been re-measured.
  The rehearsal's rerun will show it.
- **`GET /sound-mixes` (the listing) still reads every job** and builds each score's view. The studio
  flow doesn't call it.
- **Most project routes are still `unmatched` in the metrics.** Only the five finishing routes were
  added, to stay within the series limit. The log names them all.
- **The PostgreSQL test runs in CI's PostgreSQL job.** Here it ran against a private PostgreSQL 16.
- **`dialogue-replacement.test.ts`'s "runs on a clock" test times out at Bun's default 5 s on this
  machine**, on `main` as on this branch (6.4–7.3 s when given longer). This increment doesn't change it.
