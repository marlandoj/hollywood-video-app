# HV-030-11 — A crew ledger that had been spending on one host, carried into the database

epic: HV-030
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

HV-030-09 moved the crew's budget line into PostgreSQL and left this behind, in its own words:

> Nothing migrates an existing file ledger into the database. A deployment that has been spending
> through the JSON ledger and then gains a database starts the crew's line at zero, and its raised
> alerts come back.

A crew line that restarts at zero is a **$1,000 ceiling that has to be crossed twice** and four
alerts the operator is told about a second time. The ceiling is the crew's stop: a line that forgets
$900 of spend is a line that will spend $900 more before it stops. Staging's crew line is at $0
today, which is why this could wait a night; it is not a gap that stays harmless.

## What this increment does

`PostgresCrewLedger.importFrom(state)`, and `scripts/crew-ledger-import.ts` for the operator to run
it against the file they have been spending through.

Two things make it more than an insert loop:

- **The file's `spentUsd` can exceed the sum of its own events.** It is cumulative, and the file
  drops events past five thousand — which is exactly why the file version carries the total
  separately. The database has one number, `sum(usd)`, so the difference is carried across as a
  **single `carried-forward` event**, named for what it is, rather than quietly lost or hidden in a
  column nothing reads. A ledger whose events do add up gets no such event.
- **Importing twice would double a budget line.** The check for an empty ledger and the inserts are
  one transaction, and the check is for *any* event and *any* budget row — either alone means the
  line has already started somewhere.

And two things the cluster taught it, neither of which would have shown up locally:

- **The file's event order is not in its timestamps.** A file ledger records several events in one
  millisecond, and `state()` reads them back ordered by `at` and then by id, so a random id lost the
  order the spending happened in. The imported ids ascend and carry it.
- **`state()` was not returning the file ledger's own shape.** The driver hands back PostgreSQL's
  rendering of a `timestamptz`, not the ISO string the shape promises, so a ledger carried in and
  read back did not match the one that went in. It is ISO again.

It reads the file with the file ledger's **own validator**, so a ledger that ledger would refuse to
open is not carried across either.

## Acceptance criteria

1. **The file ledger's own validator is what decides whether a ledger can be carried**: a good one
   round-trips, and a wrong schema, a negative spend, a ceiling below the default, an alert at an
   undeclared threshold, and an alert below its own threshold are each refused.
2. **A file ledger is carried across whole**: every event, in the file's own order and with `at` in
   the file's own form, the ceiling, and every alert — and an alert already raised is not raised
   again by the next spend.
3. **Dollars the file kept but its events could not account for are carried as their own event**,
   once, named `carried-forward`, with no tokens.
4. **A ledger whose events add to more than its spend is refused rather than reconciled**, and
   nothing is written.
5. **A database that already holds a crew ledger refuses a second import** — with events, with a
   budget row, or with either alone.
6. **An empty file ledger carries across as an empty one, ceiling and all.**
7. Reverting `crew-ledger.ts` fails criteria 2–6.

- Tests: `packages/storage/test/crew-ledger-import.test.ts`; criterion 1 runs everywhere, 2–6 need a
  cluster. Verified on a throwaway database on the staging cluster alongside HV-030-09's own suite:
  11 pass, 0 fail.

## Known gaps this leaves

- **Nothing runs it automatically.** The operator runs the script, naming the file. That is
  deliberate — a startup import would run on every boot of every process and the guard would be the
  only thing between the crew's budget and a double count — but it does mean a deployment that gains
  a database and forgets to run it starts at zero, silently, exactly as before.
- **Nothing exports the other way.** A deployment that loses its database has no route back to a
  file, and `state()` is the shape that would do it.
- **The carried-forward event's timestamp is the last real event's.** It is the only honest instant
  available — the dollars it stands for were spent before that, over events the file no longer holds
  — but it is not *when* they were spent, and nothing says so in the row itself beyond its persona.
- **The file is not marked as carried.** Running the script twice against two databases would put
  the same line in both, and nothing in the file records that it has been imported.
