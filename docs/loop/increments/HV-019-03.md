# HV-019-03 — The conformance suite and revision pins FULL-SCOPE §7 already requires of the Voice and Lip-sync lanes
epic: HV-019
spend_usd: 0

## Goal

Give the Voice and Lip-sync lanes the adapter conformance suite FULL-SCOPE §7 already requires of them, pin their five capability revisions as a CI tripwire, and commit golden delivered records that this build must still be able to read — moving zero bytes of any capability definition. Then write down, with reproductions rather than assertions, why the unification the roadmap sketched is not additive, so the later work is designed against the real constraint instead of discovering it on a restore.

**This is deliberately not the roadmap's increment, and one third of the sketch should not be done at all.** The sketch asked for a `modality` union extended to `audio`, `hv-audio-capability/*` and `hv-lipsync-capability/1` re-expressed as `hv-capability/2` behind an additive shim, and voice/lip-sync selection admitted as a pool plus plan.

- **The `hv-capability/2` re-expression is not additively possible.** `capability()` hashes a definition with no `schema` key and adds the literal afterwards, so the video schema string is in no video revision. Every performance capability builds its definition *with* the schema string inside it and hashes that. Verified on this checkout: `contentHash(definition including schema) === revision` is true for all five, `contentHash(definition excluding schema) === revision` is false for all five, and renaming a performance schema to `hv-capability/2` moves every one of them — before any field is touched.
- **A lookup shim does not sit on the path that breaks.** `audioCapability(revision)` is a lookup and `audio-jobs.ts` does fail a line when it misses, but the paths that matter are live *re-derivations*: `validateAudioLinePlan` recompiles the stored plan from the live constants and hash-compares; `validateLipSyncPolicy` strips `capabilityRevision` and re-derives it; `createLipSyncPlan` / `validateLipSyncPlan` do the same; `validateLipSyncDelivery` does a bare live equality on a delivered record. A shim that keeps old revisions resolvable changes none of those outcomes. Two long-committed tests already demonstrate the failure and nobody drew the conclusion: `packages/planner/test/audio-phrases.test.ts` and `azure-performance.test.ts` both assert that a line plan whose `capabilityRevision` differs from the derived one throws.
- **The `audio` modality is untestable churn and a one-way door.** `capability()` rejects `modality: "audio"` today, and it cannot express an audio contract without fabricating `output.minWidth/minHeight/maxWidth/maxHeight` (required integers in [16, 8192]) into a content-addressed record — which CLAUDE.md forbids — or making the whole `output` block modality-conditional, which is a validator change rather than a union widening. All seventeen registry snapshots resolve to `modality: "video"` at runtime; `"image"` itself has zero reachable snapshots, so a third value has no adapter to assert against. This is the same argument HV-019-02 used to defer `extension`, with more force. Adding the value is a loosening and safe in itself, but it cannot be narrowed again once anything is stored under it.
- **A pool plus plan is HV-022's clause (FULL-SCOPE §P7) and contradicts a stated billing-safety property.** §P5 owns the registry mechanism; §P7 owns voice selection. A pool is a failover set, and `cartesia-audio.ts` says in code: "No automatic retry, alternate voice, or fallback provider may consume a second reservation." Admitting one would break the three single-`heldUsd` reservation invariants (`audio-jobs.ts` requires `job.costCapUsd === take.policy.heldUsd && job.budgetReservedUsd === take.policy.heldUsd`, and `snapshots.ts` cross-checks `estimatedUsd`, `amountUsd` and `remainingUsd` against the same figure), and would need three provider labels the closed telemetry set does not carry plus a widened router `Stage` — `audio-take` and `lip-sync` are job stages but not router stages.

**What makes this increment urgent rather than tidy: nothing guarded those five revisions.** Not one of them appeared as a literal anywhere in the repository — verified by grepping all five across `packages`, `docs`, `scripts` and `infra`, which returned nothing. No committed evidence file carries an audio or lip-sync revision; `docs/evidence/hv019-router/adapter-conformance.json` is the only revision record and it is video-only. Every audio test derives its expectation from the live constant, so an edit moves the expectation along with the code. Demonstrated on this branch: changing `maxLineCharacters` from `20000` to `20001` — one character — leaves `audio-phrases.test.ts`, `azure-performance.test.ts` and `localized-audio.test.ts` at **10 pass, 0 fail**, while the new suite goes to **3 fail**. And a moved revision does not merely fail a new render: `validateSnapshot` reaches `validateAudioTake` on every job and `validateAudioIntent` on every attempt from all four snapshot entry points, so every portable archive and every backup restore containing a single audio take becomes permanently un-importable, on content-addressed records that cannot be rewritten without breaking their own seals. The video lane has exactly this tripwire since HV-019-01. The performance lane had none.

No capability definition is edited. `packages/generator/src/capabilities.ts`, `audio-capabilities.ts`, `azure-capability.ts`, `lipsync-capability.ts`, `packages/planner/src/audio-performances.ts`, `audio-jobs.ts`, `lipsync.ts` and `lipsync-policy.ts` are all out of the diff, and the frozen-path check below names them on purpose. `spend_usd` is 0; no adapter is constructed, no key is read, and `globalThis.fetch` is stubbed to throw and asserted uncalled.

## Acceptance criteria

1. **One enumerable statement of what a performance adapter is, derived rather than transcribed.** `packages/generator/src/performance-registry.ts` exports `PERFORMANCE_REGISTRY` — a frozen array of `{lane, provider, schema, model, apiVersion, capabilityRevision, paid, qualification, doc}` covering all five capabilities — plus `PERFORMANCE_LANES`, `performanceEntry(revision)`, `performanceRevisions(lane, provider?)` and `performanceCapability(revision)`. Every entry is built **from** `AUDIO_CAPABILITIES` and `LIPSYNC_CAPABILITY`, so a new capability constant appears automatically and the suite immediately demands a pin for it; a test asserts the derivation in both directions and field by field. The file builds, copies and mutates no capability definition. Satisfies FULL-SCOPE §7 "each must pass the adapter conformance suite and the studio benchmark before promotion." (the **Voice** and **Lip-sync** rows) and §10 "Provider independence and versioned adapters."

2. **The revision is the key, because `schema` is not unique in this lane.** `hv-audio-capability/3` is carried by two different capabilities — the Azure contract and the Cartesia multilingual one — so the registry has five entries across four distinct schemas. A test asserts exactly that: four distinct `schema` values, five distinct revisions, the shared schema carried by providers `azure` and `cartesia` with different revisions, and `performanceEntry` total and injective over the registry with `undefined` for an unknown revision and for a non-string. `audioCapability()` already keys on revision for this reason; a registry keyed on schema would silently lose one of the two, which is the defect this criterion prevents someone from introducing while "unifying". Satisfies §10 "… gap audits." and CLAUDE.md "Every criterion gets a real test."

3. **The two lanes' hash shapes are reproduced, not asserted in prose.** For every performance capability the suite asserts `contentHash(definition including schema) === revision`, that `contentHash(definition excluding schema) !== revision`, and that renaming the schema to `hv-capability/2` moves the revision. For the video lane it asserts the opposite: `contentHash(definition without schema) === revision`. A separate case pins why the `audio` modality cannot be expressed — `capability()` throws `"Invalid provider capability configuration."` on `modality: "audio"`, and the four `output` dimension fields are required numbers, so an audio contract could only be expressed by fabricating them. These are the facts that make the sketched unification non-additive, held as executable statements rather than as a paragraph someone can contradict. Satisfies CLAUDE.md "Never fabricate launch, legal, or provider evidence." and §10 "Evidence before promotion".

4. **A resolver that spans both lanes.** `performanceCapability(revision)` resolves every registered revision. A test asserts that `audioCapability(LIPSYNC_CAPABILITY.revision)` is `undefined` — `LIPSYNC_CAPABILITY` is in neither `AUDIO_CAPABILITIES` nor that lookup, so a lip-sync revision had no resolver at all — while `performanceCapability` returns it, and returns `undefined` for an unknown revision. Satisfies §10 "… gap audits." and `docs/LIP-SYNC.md`'s revision discipline.

5. **Committed golden records prove this build can still read work it already delivered — the level that actually fails.** Fifteen record shapes pin a performance revision; `packages/generator/test/fixtures/performance-records.json` holds a golden record for **ten** of them, and the pins evidence states that count alongside the five that are not covered and why, so the coverage cannot be read as the whole surface. Each committed record is re-validated on every test run by the validator that reads it back in production: `hv-audio-line/1`, `/3`, `/4` and `/5` through `validateAudioLinePlan`, with each one's `capabilityRevision` asserted against the specific capability it must pin; `hv-audio-line-delivery/1` **and `/2`** through `validateAudioDelivery`; `hv-audio-dispatch/1` **and `/2`** through `validateAudioIntent` **with** its plan; `hv-lipsync-policy/1` through `validateLipSyncPolicy`; and `hv-lipsync-delivery/1` through `validateLipSyncDelivery`. The Azure discriminants are pinned separately on purpose: `validateAudioIntent` hashes an `azureLineRequest` rather than a Cartesia one, so a Cartesia record does not exercise that branch. Two `hv-audio-policy` records are also committed, and are explicitly **not** revision pins — `validateAudioPolicy` resolves no capability at all; it re-derives the record's revisions and its model string from the live `AZURE_AUDIO_MODEL` / `CARTESIA_MODEL` constants, so a model-constant edit is what they catch. The capability-model comparison lives in `audioTakePlan`, which needs a job and a screenplay; both facts are recorded in `unpinnedReadBackPaths` so nobody reads those two records as revision coverage. The records are generated by the suite under `HV_PERFORMANCE_RECORDS_REFRESH` and then committed, so refreshing them has to be a decision — they cannot be hand-written, because `compileAudioLine` re-hashes its source, `validateAudioPolicy` re-derives its permission and price revisions, and the safety gate runs over the character name and dialogue. The policies are validated with `now` omitted, so a fixed validity window is not a time bomb that turns CI red on a date nobody chose. A second case asserts the failure direction: substituting any other live revision into a delivered line plan, a lip-sync delivery or a lip-sync policy makes the record unreadable. Satisfies CLAUDE.md "Every criterion gets a real test." and ADR-0020 fail-closed.

6. **The pins are committed evidence, re-derived on every run, and the run records what it does not prove.** `docs/evidence/hv019-performance/capability-revision-pins.json` (schema `hv-performance-capability-pins/1`) is written when `HV_PERFORMANCE_PINS_EVIDENCE` names a path and re-validated on **every** run — including CI, which sets no such variable: the schema, the lane list, the eight check-family names, and **each recorded `capabilityRevision` against the revision this build produces**. That last assertion is the tripwire. It also carries `schemaIsInsideTheHash`, `videoSchemaIsOutsideTheHash`, the golden-record list with `revisionPinningShapes: 15` and `goldenRecordsCarryingARevisionPin: 10` (the validator refuses a document whose count disagrees with its own list, so the coverage figure cannot drift from the records), an `unpinnedReadBackPaths` block with five entries — `validateAudioPolicy`, `hv-audio-line/2`, `hv-audio-policy/3`, `validateLipSyncPlan` and `validateAudioTake` — each stating why it is not pinned here and which suite covers it, and the honesty fields `poolAdmitted: false`, `newProviderSpendUsd: 0`, `liveProviderDispatches: 0`, `provesVendorAvailability: false`, `provesVoiceQuality: false`, `provesLipSyncQuality: false`, `provesLivePricing: false`. The evidence lands in a **new** directory rather than `docs/evidence/hv019-router/`, because HV-019-01's evidence statement requires a directory-wide grep over that path for `cartesia` to return nothing. Satisfies §10 "Evidence before promotion: tests, benchmarks, post-flight evals, gap audits." and CLAUDE.md "Never fabricate launch, legal, or provider evidence."

7. **Both new files refuse credentials, destinations and host paths — with the two legitimate exceptions allowed by name rather than by loosening the pattern.** Neither the pins file nor the golden records may match `://`, `API_KEY`, `/home/`, `/Users/` or `/tmp/`, and every 32+ hex run in the pins file must be a registered revision. Two exceptions are named explicitly: the Azure line's provider transcript is SSML, whose two W3C XML namespaces necessarily appear in the golden records — they are namespace identifiers that nothing fetches, and the test asserts they are present, substitutes them out, and then applies the full pattern list to the remainder; and lip-sync's pinned `openapiSha256` is a 64-hex value that is not a revision, so the pins file is asserted **not** to contain it rather than the hex rule being relaxed. Satisfies ADR-0018's identifier discipline and `docs/OBSERVABILITY.md`'s redaction rule.

8. **No revision moves, no schema is introduced, no pool exists, no spend is possible, and no frozen path, dependency, budget default, account, vendor, migration, route or user-facing surface changes.** `packages/generator/src/capabilities.ts`, `audio-capabilities.ts`, `azure-capability.ts`, `lipsync-capability.ts`, `packages/planner/src/audio-performances.ts`, `audio-jobs.ts`, `lipsync.ts` and `lipsync-policy.ts` are **not in the diff**, and the frozen-path check names all of them on purpose. `docs/evidence/hv019-router/adapter-conformance.json` is unchanged byte for byte, and `conformance.test.ts` is untouched — its sixteen family names and its `names.length` of 17 do not move, so the committed router evidence's `checks` block does not change. No `CartesiaAudioProvider`, `AzureAudioProvider` or `SyncLipSyncProvider` is constructed; `globalThis.fetch` is replaced by a stub that throws and asserted uncalled; the three provider key variables are asserted empty in the test environment; no `HV_AUDIO_POLICY_FILE` or `HV_LIPSYNC_POLICY_FILE` is written. The diff touches nothing under `docs/legal/**`, `docs/adr/**`, `.github/workflows/**`, `packages/safety/**` or `infra/drizzle/**`; adds no `package.json` or lockfile entry, no HTTP route or request field, no cookie, tracking, account, tier or payment path; and changes no default of `HV_MONTHLY_BUDGET_USD` or `HV_COST_CAP_PER_SHOT_USD`. `docs/loop/STATUS.md` and `docs/PROGRAM-EXECUTION.md` are not in the diff; RECORD owns both. Satisfies FULL-SCOPE §10 "Free and anonymous for every end user; no billing code reachable.", "Safety refusals expand only.", CLAUDE.md "Paid providers stay `mock` unless the current increment doc declares `spend_usd` and names the provider." and the EXECUTION-LOOP frozen list.
