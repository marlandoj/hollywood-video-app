# HV-017-15 — A shared actor keeps the look its creator locked

epic: HV-017
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

Release 2 promises identity locks beyond per-shot references, and a cast library. Both halves were
built, but they did not meet. A creator can lock a character's look to one to four of its own
images, in the order the render numbers them (HV-017-09). A creator can share that character and
someone else can import it (docs/ACTOR-LIBRARY.md). The import threw the lock away (HV-017-10), because the
lock named the source project's image ids and every copy gets a new one.

So an imported actor rendered from whatever images it had, in upload order: the look nobody chose.
The pieces needed to do better were already there. The share carries the whole character record,
lock included, and every copy keeps its source image id and the source image's SHA-256.

## What this increment does

- **The share records the lock, as it already did.** The character record inside a share holds the
  lock's ordered images and each one's SHA-256, covered by the share's revision hash. The share
  format did not change and no migration is needed.
- **The import rebuilds the lock over the copies.** `carriedReferenceLock` finds each locked image's
  copy by its source asset id, checks the copy's SHA-256 against the one the lock named, and builds
  the lock with `referenceLockRecord`, the same builder the lock route uses. It keeps
  the same order, name and note. `importedActor` saves it on the imported character, so
  `renderReferences` gives the creator's pictures in the creator's order.
- **All or nothing.** If a locked image has no copy, or its copy's bytes differ, the actor comes in
  unlocked. The import route returns a plain `lookNote` saying which image and why. Today's route
  refuses a changed image before that point (see Known gaps), so the note is a guard. For example:
  *"The locked look “Act two, after the storm” was not carried over: locked image 2 was not copied
  into this project. The actor was imported unlocked; lock its look again from its images here."*
- **The creator can see a lock and undo it.** Before this, nothing in the frontend read a lock, so
  someone using only the page could never hold one. An import can now bring one, and a lock refuses
  replacing or removing its images ("Unlock the look…"). So the cast card says *"Locked look: <name>
  · N images"* and offers a real **Unlock look for <name>** button. It calls the existing
  `PUT /cast/:id/reference-lock` route with `lock: null`, and the desk's live status line reports
  the save. The share preview says the actor's look is locked, with its name and how many of its
  images, before anyone imports it. An import's `lookNote`, when there is one, appears in the status
  line. All text goes through `textContent`.
- **Everything else imports as before.** A share of an unlocked actor, and any share minted before
  locks existed, has no lock, gets no lock and no note, and renders in upload order.

## Acceptance criteria

1. **The share records the lock.** A share of a locked character carries the ordered image ids and
   their SHA-256.
2. **A locked import renders the same images in the same order.** The imported actor's lock names
   its own copies, in the creator's order, with the creator's name and note. `renderReferences`
   gives the same SHA-256 sequence as the creator's character, not upload order. The lock is saved
   and survives a reload, and the import response carries no note.
3. **A missing or changed locked image leaves the actor unlocked, with a note.** No partial lock is
   built when only the first image is fine. A locked image whose stored bytes were changed is
   refused by the byte copy, and the destination cast is unchanged.
   A test also checks that a changed image's stored bytes stop the import before any lock is built,
   but it passed before this change too, so it is a regression guard rather than evidence.
4. **A share without a lock imports exactly as before**: no lock, no note, upload order.
5. **The PostgreSQL import stores the lock** on the destination row, naming its own copies in order.
6. **The cast desk shows a locked look and unlocks it.** A locked character's card names the look
   and its image count. **Unlock look** sends `lock: null` on the current cast version, reports the
   save in the live status line, and the lock is gone. An unlocked character shows neither.
7. **The share preview says the look is locked**, and an import's `lookNote` appears in the status line.
8. Reverting the lock carrying in `actor-library.ts` fails "a shared actor keeps the look its
   creator locked, rendering the same images in the same order", "a locked image that is missing or
   changed leaves the imported actor unlocked, with a note saying why", "an imported actor keeps its
   creator's locked look and renders the same images in the same order", "a share of a locked
   character imports, with the lock rebuilt over the copies' new identities" and "an imported locked
   actor's look is stored in the destination row, naming its own copies in order". Reverting
   `casting.js` and `actor-library.js` in the frontend fails "a locked look is shown on its
   character's card and can be unlocked from it", "the share preview says the actor's look is locked
   before it is imported" and "an import whose locked look could not be carried says why in the
   status line".

- Tests: `packages/planner/test/actor-library.test.ts` (1–4), `packages/api/test/actor-library.test.ts`
  (1–4), `packages/planner/test/reference-lock.test.ts` (2), `packages/storage/test/actor-library.test.ts`
  (5, PostgreSQL), `packages/frontend/test/locked-look.test.js` (6–7).

## Known gaps this leaves

- **The note cannot be reached through today's route.** `importedActor` already refuses copies that
  differ from the share, and the byte copy checks every image's checksum. So a tampered image stops
  the whole import rather than arriving unlocked. The check and the note are there so that a future
  path that copies fewer images cannot build a partial lock.
- **The desk can unlock a look but cannot lock one.** Locking is still API-only (HV-017-09). A
  creator who unlocks an imported look cannot lock it again from the page.
- **The carried lock is dated at the import**, not when the creator locked it. The name and note say
  which look it is.
- **The lock's name and note cross projects unread by the public-figure check**, just as a creator's
  own lock name is. Neither reaches a shot prompt.
- The embedding and per-project fine-tune parts of P2's identity lock remain open.
