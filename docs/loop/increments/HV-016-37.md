# HV-016-37 — The API's database connections outlast decoding a feature's joined film

epic: HV-016
release: 3 "Features"
gate: none new
spend_usd: 0

## Why

Release 3's live run was resumed (resume 5) to score sequence 10. Every sequence was scored, the
titles and credits were made, and the Editor's join was asked for and finished (`done`). But the
studio's poll of the join was answered:

> /api/jobs/:id -> 400 Idle timeout reached after 20s

so the run stopped with "The sequences were not joined into one film".

A feature's joined film is one job, and its body carries every sequence film it joins: 47 MiB of
JSON, 21 MiB packed. `GET /api/jobs/:id` reads it in a short transaction (`PostgresJobStore.get`),
and decoding the row is synchronous. The connection saw no statement for 15 s on an idle host and
for over 20 s while the host was finishing other jobs. Bun SQL's default `idleTimeout` (20 s) then
closed it before the commit.

HV-016-30 fixed the same failure for the worker's pool (`WORKER_DATABASE_IDLE_TIMEOUT_SECONDS`,
300 s). The API's pool kept the default.

## What this increment does

- **`API_DATABASE_IDLE_TIMEOUT_SECONDS` (300 s)** and **`apiDatabase(url)`** in
  `packages/storage/src/database.ts`. The pool keeps its eight connections.
- **The API server builds its database with `apiDatabase`.**
- **`packages/storage/test/api-database-idle.test.ts`:**
  - the API pool's idle bound is the worker's, 300 s, not 20 s, with eight connections;
  - the server uses `apiDatabase`.

## Acceptance criteria

1. The API's database pool allows 300 s without a statement, as the worker's does.
2. The API server constructs its database only through `apiDatabase`.

- Tests: `packages/storage/test/api-database-idle.test.ts`.

## Known gaps

- **The joined film's job body is very large.** It embeds every sequence film it joins, so reading it
  takes seconds. Slimming it, so it stores references rather than copies, is a separate change to the
  job schema. This increment only stops a slow read from failing.
