# HV-016-32 — The crew suggests line changes, and the writer takes them one at a time

epic: HV-016
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

Release 2 promises "the crew suggests script revisions the writer accepts line by line". Today no
crew path proposes a screenplay edit.

- The writer can replace one spoken line through the living-script flow, but only by typing it.
- The crew proposes production choices (cast, look, pacing), accepted one question at a time. It
  never touches the words.

## What this increment does

- **Line notes** (`packages/planner/src/crew/line-notes.ts`, `hv-crew-line-notes/1`).
  - A note is `{id, persona, line, before, after, reason}`. `line` is the one-based physical line
    the parser's beats count. `before` is that line's current text, without its surrounding
    whitespace and line ending.
  - Notes are bound to the script version and its SHA-256 they were written against.
- **`applyLineNotes(script, notes, acceptedIds)`** applies only the accepted notes. Each one replaces
  its line's text and keeps the line's indentation, trailing spaces and line ending. Every other byte
  is untouched, CRLF included. It refuses, and changes nothing:
  - a script that isn't the version (or text) the notes were written against (a conflict);
  - a note whose `before` no longer matches its line;
  - two accepted notes on one line;
  - a note whose `after` holds a line break, a control character or Fountain note syntax;
  - a note that changes how the parser reads the script: its scenes, each beat's kind, speaker and
    line count, and what it can't read. So dialogue can't become a heading, action can't become a
    transition, and a cue can't name another speaker;
  - a note on a line holding `[[…]]` or boneyard. The locked lines are found with the parser's own
    scanner (`scanProtectedSpans`), so they are exactly the lines whose shown text isn't what the
    writer wrote;
  - a note the gate refuses.
- **The crew writes the notes.** The prompt carries the numbered script and the writer's optional
  request ("what to work on", 300 characters).
  - The request is gated like the plan step's answers. A refused one is a 400, with nothing sent.
  - The whole prompt is gated before anything is sent. A refusal is `fallbackReason:
    "content_policy"`.
  - The model's answer is read as JSON. At most 12 notes are kept. A note that fails any check above
    is dropped, never repaired. So is a second note on the same line.
  - **An unsafe note is dropped and never shown.** The gate reads its `after`, its `after` with its
    `reason`, and the script with the note applied. The answer counts dropped notes, never their text.
  - The call goes through the crew's budget line, like the read-through and the plan:
    `assertCanSpend` first, then one event, `persona: "crew-line-notes"`.
- **The stand-in writes no notes.** With no key, or when the model can't be reached or its answer is
  unusable, there are no notes. The message says why and that the script is unchanged. It never
  invents an edit.
- **API.**
  - `POST /api/projects/:id/crew/line-notes` answers with the notes and `script: {version, sha256}`.
  - `POST /api/projects/:id/crew/line-notes/accept` takes `{version, notes, acceptedIds}`.
  - The accept applies the notes to the current script under the project's lock (a row lock with
    PostgreSQL), and commits it as `PUT /script` commits a save.
  - A stale version (or a `sha256` that isn't that version's) answers 409 and writes nothing.
  - A refused note answers 400 and writes nothing.
  - The same accept sent again after it landed answers with the version it made (`replayed: true`),
    and writes nothing.
  - Project-token auth, the API rate limit and the error shapes are those of the other crew routes.
- **Safety refusals only grow.** This adds places where the gate is checked, not rules.

## Acceptance criteria

1. **Byte-exact apply.** Accepting some of the crew's notes changes only those lines' text. Every
   other byte, including CRLF endings, indentation and trailing spaces, is kept. At the route, the
   next script version is exactly that text.
2. **Stale notes write nothing.** Notes bound to an older version, or to different text under the
   same version, are refused as a conflict. The route answers 409, and the script stays at its
   version. A retried accept that already landed answers with the version it made.
3. **Refusals.** `applyLineNotes` refuses:
   - a `before` that no longer matches its line;
   - two accepted notes on one line (accepting one of them works);
   - an `after` with a line break;
   - a note that would change the line's element type (dialogue to heading, action to heading or
     transition, heading to action, a cue to another speaker). A heading reworded as a heading
     applies;
   - an unknown or empty `acceptedIds`;
   - a note on a line holding a Fountain note, or on any line the parser hides as boneyard,
     including after a boneyard reopened on the line that closed it;
   - an unsafe note.

   The route answers these with 400 and writes nothing.
4. **The model's notes are validated.** At most 12 are kept. Notes with a wrong `before`, a repeated
   line, an unknown persona or a restructuring `after` are dropped. An answer that isn't JSON notes
   is unusable.
5. **An unsafe note is dropped, never shown.** A note naming a public figure, one whose reason does,
   and one that passes alone but not in the script it would change are all dropped. Their text isn't
   in the answer.
6. **Gated before it is sent.** A refused request is a 400 with the model asked nothing. A request
   that passes alone but not beside the script gets the stand-in, with `content_policy`, and the
   model is asked nothing.
7. **The stand-in, without a key,** answers with no notes, a message saying no crew model is
   connected and the script is unchanged, and $0 spent.
8. **Crew spend.** The live path records its call on the crew's budget line. At the approved
   ceiling it stops before the model is asked. The fake model spends $0. A stranger's token is
   refused with 401 at both routes.
9. Reverting `server.ts` fails every route test. Reverting `index.ts` and `projects.ts` fails
   criteria 1 and 2 at the route. Removing `line-notes.ts` fails every planner test. Removing, one at
   a time, its element-type check, the whole-script gate on a note, the version check, the no-model
   stand-in or the overlap check fails criteria 3, 5, 2, 7 and 3 respectively. Restoring the
   earlier boneyard scan, which ended a boneyard at the first `*/` on a line, fails criterion 3's
   reopened-boneyard test.

- Tests: `packages/planner/test/crew-line-notes.test.ts`, `packages/api/test/crew-line-notes-route.test.ts`.

## Known gaps this leaves

- **No studio panel yet.** The writers' room page doesn't list the notes with Accept and Skip, or
  offer "Apply accepted". The routes are ready for it; the frontend is the next increment.
- **The stand-in writes no notes.** Without a key the feature says honestly that there are none. A
  deterministic note-writer (for example, trimming over-long lines) is not built.
- **Notes don't move with the script.** A note bound to an older version is refused, not rebased
  onto a line that only moved. The writer asks the crew again.
- **A cue can't be renamed,** even by the writer's request, because it would change who speaks and
  the cast is bound to that name. Renaming a character stays the writer's own edit.
- **The PostgreSQL accept path has no test of its own.** It uses the same row-locked `state()`
  wrapper as `editScript`.
