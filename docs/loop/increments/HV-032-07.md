# HV-032-07 — Large uploads racing the API's loopback connect are held, not dropped

epic: HV-032
release: 1 "Studio"
gate: none new
spend_usd: 0

## Why

The Release 1 short stopped at a storyboard-still upload with 502 "upstream unavailable". The API never saw the request.

The API's mutual-TLS front relays bytes to the loopback listener only once that connection opens. It holds anything that arrives earlier, up to 64 KiB, and drops the client if more arrives. That limit guards against untrusted peers. Since HV-032-05, the edge opens a fresh connection per request, so a trusted edge's 0.5 MB still upload often arrives before the loopback connection opens.

On the staging host, 1 in 40 two-megabyte uploads failed this way.

## What this increment does

- **Two hold limits.** An untrusted or pre-handshake peer is still held to 64 KiB. Once the client's certificate chain is trusted, a request is held up to 64 MiB, the edge's own body limit, until the loopback connection opens.

## Acceptance criteria

1. **Large uploads on fresh connections always reach the API.** The test sends 25 two-megabyte requests through the edge and the real mTLS front.
   - Test: `test/staging-edge.test.ts`.
   - On the fast container loopback the race is rare; the staging host measurement is recorded before and after.
2. **The existing mTLS guarantees hold.** An untrusted chain is never relayed.
   - Test: `packages/api/test/mtls.test.ts`.
