# HV-026-06 — The quality check measured every film's luma range as nothing at all

epic: HV-026
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

HV-026-04 replaced `Math.min(...values)` with a reduction, for a good reason it wrote down:

> Reduced as it is read: a spread over a million per-frame values overflows the call stack.

It reduced with the function itself:

```ts
const extreme=(values:number[],pick:(a:number,b:number)=>number)=>values.length?values.reduce(pick):null;
```

`Array.prototype.reduce` hands its callback **four** arguments, and the fourth is the array. So
`Math.min(11, 20, 1, [11, 20, 30])` coerces that array and answers `NaN`. Every film of more than
one frame came back with `lumaMin: NaN, lumaMax: NaN`; a one-frame film was the only survivor,
because `reduce` skips the callback entirely for a single element. A stack overflow had been traded
for a silent wrong answer, which is the worse of the two.

Nothing said so, at any layer:

- `NaN` is a `number`, so the type held.
- `NaN < 16` and `NaN > 235` are both false, so **`illegal-levels` could never fire on any film**.
- `levels-unmeasured` is keyed to `framesSampled`, which was the film's real frame count, so the
  report did not even say the levels had gone unjudged.
- `JSON.stringify(NaN)` is `null`, so the stored report and every `DeliveryOutput.quality` a creator
  sees looked exactly like a film whose meter never ran — and `scripts/picture-qc.ts` printed
  `luma NaN-NaN`, because `??` does not catch `NaN`.

Measured on this host, before and after, on `testsrc2` encoded straight to yuv420p:

```
before:  framesSampled 60  lumaMin NaN  lumaMax NaN  findings []                verdict pass
after:   framesSampled 60  lumaMin 13   lumaMax 226  findings [illegal-levels]  verdict review
```

`docs/evidence/hv026-finishing/first-check.json` holds `lumaMin: 11, lumaMax: 253` on the delivered
master — numbers the shipped code could no longer produce. **The illegal luma range in the master is
one of the decisions waiting on Kevin**, and until this increment the check that found it had stopped
being able to find it again.

Nothing caught it because the one clip that would have shown it was the one the suite was careful
never to make: every film in `picture-qc.test.ts` is encoded through
`scale=in_range=full:out_range=limited`, and the two end-to-end cases assert `framesSampled`, spans,
sound and verdict, and never luma.

## What this increment does

- **The reducer is written out**: `values.reduce((best, value) => pick(best, value))`, with the
  reason recorded at the line, because the line that caused this reads correctly.
- **A luma reading that is not a number is refused.** `assertLevelsRead` runs at the top of
  `pictureQcFindings`, so both a fresh report and a retained one re-derived by
  `validatePictureQcReport` go through it. A check that cannot say what it measured says so by
  refusing, not by reporting a film whose levels it never read as a film whose levels are fine.
  *Absent* stays allowed and is a different fact: the two statistics are printed separately and one
  can be empty while the other is not, which is what `lumaText` is for.
- **The measurement is asserted end to end**, on a film that is not conformed to the limited range —
  the case the existing suite avoided.

## Acceptance criteria

1. **A film of more than one frame has its luma range read**: sixty frames in, two integers out, in
   order, inside 0–255 — and the reading survives `JSON.stringify` and re-validates.
2. **A film whose levels leave the limited range is said so**: `illegal-levels`, a warning, naming
   the floor, containing neither `NaN` nor `null`, with a `review` verdict — and the same film
   conformed on the way out has nothing said about its levels.
3. **A luma reading that is not a number is refused by name**, for `NaN` and for infinity, at both
   `pictureQcFindings` and `pictureQcReport`; an absent reading still produces `levels-unmeasured`,
   and a half-read range still reports the half it read.
4. **The reduction cannot be written that way again**: a source guard, over the code with its
   comments stripped, on `.reduce(Math.min)` and on the same shape with any single-argument builtin.
5. Reverting either source file fails all four.

- Tests: `packages/generator/test/picture-qc-levels.test.ts`. Verified: all four fail on the
  unchanged source.

## Known gaps this leaves

- **`levels-unmeasured` is still keyed to `framesSampled`**, which counts the frames that carried
  *both* statistics. A film whose maximum was printed and whose minimum was not has
  `framesSampled: 0`, so the note fires and says "No frame carried a luma statistic" — which is not
  what happened. HV-026-04 deliberately allows that half-read state, so re-keying the note is a
  decision about what the note is for, not a bug fix, and it is left alone here.
- **Nothing else in the repository is guarded against this shape.** The source guard covers
  `picture-qc.ts` alone; `.reduce(Math.max)` elsewhere would be the same defect and nothing looks.
- **The threshold is unchanged and so is the question behind it.** Whether the studio's master should
  be conformed to 16–235 or the limit relaxed is still Kevin's call; this increment only restores the
  check's ability to ask it.
- **The check still runs outside the deterministic render path**, so a film already delivered with an
  unread range is not re-checked by anything. `scripts/picture-qc.ts` can be pointed at it by hand.
