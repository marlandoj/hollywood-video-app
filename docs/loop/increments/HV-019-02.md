# HV-019-02 — A telemetry label set that separates a paid lane from a free one, and the revision-bump contract for capability changes
epic: HV-019
spend_usd: 0

## Goal

Make the operator reliability panel able to tell a billing provider from a free one, by widening the closed provider label set and every file that must move with it — and make the "what happens to in-flight and retained plans when a capability revision moves" story an executable test rather than a paragraph, so the capability-snapshot work can be done later without guessing.

**This increment is deliberately narrower than the roadmap sketched.** The sketch put the telemetry widening and a set of `CapabilityDefinition` changes in one increment. They have opposite failure signatures and belong apart:

- The capability half is uniformly fail-closed except for exactly one forbidden move. Every consumer of a pinned revision either recomputes it from saved data or compares live against saved and throws a legible message, and the committed conformance evidence turns any revision change into a red CI run before merge.
- The telemetry half contains the only **silent wrong answer** in the whole change set. `ProviderHealth.summary` does `if (!HEALTH_PROVIDERS.includes(pool.provider)) continue;` with no counter and no log; `providerHealthReadings`' `dropped` field only counts entries that *reach* it. Widen `PROVIDER_KINDS` without widening `HEALTH_PROVIDERS` and the operator's circuit table quietly shows fewer rows than there are pool slots, and the console renders that count as fact. Nothing turns red.

That hazard deserves an increment's attention and gets none if it shares a PR with a seventeen-snapshot rehash. What moved out, and where, is in "Out of scope".

**HV-019-01's gap register said three files must move in lockstep. It is six copies of one closed set across five files in two packages**: `PROVIDER_KINDS` in `packages/observability/src/index.ts`, the `provider` union in `logs.ts`, `ProviderHealthEntry.provider` *and* the runtime `KINDS` array in `diagnostics.ts`, `PROVIDER_LIMIT` sized from it in `explorer.ts`, and `HealthSummaryRow.provider` *and* `HEALTH_PROVIDERS` in `packages/generator/src/router.ts`. This increment replaces the six with one leaf module and derives the rest.

**It also corrects a claim HV-019-01 made and got wrong.** That increment's register said widening the declared union of `extension` or `vendorPolicyVersion` "invalidates every existing revision". It does not. `contentHash` hashes runtime *values* through `canonical()`, which enumerates `Object.keys`; widening a TypeScript union while every adapter keeps emitting the same value produces a byte-identical canonical string and changes no revision at all. Only adding a key adapters populate moves a hash, and only *tightening* a validator breaks stored data. The register rows are corrected here.

No capability revision changes. The committed `docs/evidence/hv019-router/adapter-conformance.json` re-records with only `recordedAt` and `telemetryLabels` different — all seventeen `capabilityRevision` and `priceVersion` values byte-identical — and the existing check that re-derives every revision on every test run is what proves it.

## Acceptance criteria

1. **The closed provider label set lives in one dependency-free module and every consumer derives from it.** `packages/observability/src/provider-kinds.ts` (new) exports `PROVIDER_KINDS`, the `ProviderKind` type and `providerKind`, and imports nothing — so `packages/generator/src/router.ts` can use it without pulling `@opentelemetry/sdk-trace-base`, `sdk-metrics` and two OTLP exporters into the generator's module graph, which every generator test would then load. `index.ts` re-exports all three for compatibility; `logs.ts`, `diagnostics.ts` (both copies) and `router.ts` (both copies) reference the exported tuple instead of transcribing its members. A test asserts that the array `ProviderHealth.summary` filters on and the array `providerHealthReadings` validates against are *the same array identity* as `PROVIDER_KINDS`, so the six-copy drift that motivated this increment cannot recur. Satisfies FULL-SCOPE §10 "Provider independence and versioned adapters." and `docs/OBSERVABILITY.md`'s bounded-label discipline under ADR-0018.

2. **The label separates a billing lane from a free one, and `other` becomes a real tripwire.** `PROVIDER_KINDS` becomes `["mock","fal","rich-animatic","rich-animatic-paid","anchor-storyboard","other"]`. `providerKind(name, billed?)` returns `rich-animatic-paid` when the adapter is `rich-animatic` and `billed === true`, `anchor-storyboard` for that adapter, and is otherwise unchanged. `billed` omitted means "not known" and yields the unsplit label — asserted by a test, because an adapter with no capability snapshot must not be reported as paid *or* as free. Call sites pass the fact they already hold: the worker's attempt span uses `provider.capabilities ? provider.capabilities.price.unit !== "free" : undefined` (written as an explicit ternary, not `provider.capabilities?.price.unit !== "free"`, which evaluates to `true` for an adapter with no snapshot and would label an unknown adapter paid), and the heartbeat pool row uses `entry.snapshot.price.unit !== "free"`, where the snapshot is never absent because `instantiateProviderPlan` refuses an adapter whose live capability does not match the admitted one. Nine of the seventeen registered providers are rich animatics and six of those bill, so this is the difference between the console answering "is this lane costing money" and not. After the change no registered adapter reaches `other`, so `other` means only "an adapter this build does not enumerate". Satisfies FULL-SCOPE §3 P15 "Operator console: budgets, provider health, queue depth, failure rates, latency, cost variance" and §3 P5 "Multi-provider routing on capability, price, latency, policy, health".

3. **The row limit moves with the set, and the deploy-window union is bounded, not just the new set.** `PROVIDER_LIMIT` goes 8 → 16 (six kinds × two outcomes = 12 series, four rows of headroom), with its comment restated. `explorer.test.ts`'s existing `PROVIDER_KINDS.length * 2 <= PROVIDER_LIMIT` assertion stays and now reads 12 ≤ 16. The `providerRowCapExceeded` fixture changes from a literal `rows(9, …)` to `rows(PROVIDER_LIMIT + 1, …)`, so raising the limit can never again quietly turn that case into a passing `available` reading and stop testing the cap. A new assertion pins the property that makes the rollout safe: a `rate(...[5m])` window spanning a deploy reports the union of the labels the retired build emitted and the labels this one emits, so the test builds that union explicitly from the retired set and asserts it equals the current set and that its size × 2 is still within the limit. Drop a member instead of keeping it and a complete result exceeds its `limit` — and `TelemetryExplorer.metrics()` fails closed *as a bundle*, taking the latency and failure readings down with it until the next redeploy. Satisfies `docs/OBSERVABILITY.md`'s "widening `Operation`, `FailureCode` or the provider categories without widening the matching limit would make a complete result exceed its `limit` and the panel permanently `unavailable`" and §10 "Evidence before promotion".

4. **The worker publishes the new labels and nothing is dropped without being counted.** `ProviderHealth.summary` still refuses a row whose provider is outside the closed set, but the set is now the derived one, so a pool slot on the paid rich-animatic lane produces a row instead of vanishing. Tests assert: a pool containing a free and a paid rich-animatic slot yields two rows with distinct `provider` values and distinct pool ids; an `anchor-storyboard` slot yields a row; `router.test.ts`'s existing "an unknown stage or provider category is dropped entirely" case stays byte-identical and green with `provider: "vendor"`; and `providerHealthReadings` accepts `rich-animatic-paid` and `anchor-storyboard` entries while still counting an unenumerated one in `dropped` rather than blanking the reading. The heartbeat body stays well inside its 8 KiB cap — the row shape is unchanged and the longest new value adds four characters to at most 24 rows. Satisfies §3 P15 "provider health" read with `docs/WORKER-FLEET.md` "A stale heartbeat is not evidence that a process is still alive", and CLAUDE.md "Every criterion gets a real test."

5. **The widened query is proved against real Prometheus, not only against a fixture.** `scripts/telemetry-explorer-smoke.ts` emitted no `hv.provider` attribute, so the `telemetry-contract` CI job has never proved that `PROVIDER_ATTEMPTS_QUERY` returns a *parsed row* — only that Prometheus accepts the expression. The smoke now emits one `provider.attempt` per `(kind, outcome)` pair, with `parent: null` so each is its own root trace and the correlated `api → job → media` trace keeps exactly its three spans and `recentTraces`' service/operation filter is unaffected. It then requires every kind to come back with both a positive success rate and a positive error rate — twelve rows returned complete under `limit=16` by the checksum-pinned Prometheus 3.14.0. Its final JSON line gains `providerKinds` and `providerRowLimit` alongside `latencyOperations` and `failureCodes`. `.github/workflows/ci.yml` is not edited: the `telemetry-contract` job already runs this script. Satisfies §P15 "Observability: OpenTelemetry traces … metrics" and §10 "Evidence before promotion: tests, benchmarks, post-flight evals, gap audits."

6. **The conformance suite's label assertions become the delivered statement, and the evidence record re-validates them.** In `packages/generator/test/conformance.test.ts` the `telemetry-labels` family is rewritten rather than replaced, so the sixteen-family set and the `names.length` of 17 do not move: `providerKind(entry.adapter)` becomes `providerKind(entry.adapter, entry.paid)`; the collapse set assertion goes from `["anchor-storyboard"]` to `[]`; and the rich-animatic assertion goes from "one label for both lanes" to "two", with a new assertion pinning what is *still* not distinguishable — two different paid image models share one label, deliberately, because a per-model label is unbounded cardinality. The suite also stops importing `../../observability/src/index` for two functions and imports the leaf module instead. The committed-evidence test gains the assertion it was missing: `document.telemetryLabels` must equal the labels this build computes, exactly as `capabilityRevision` already must. Without it the label block goes stale silently — every other check passes because the registry, the revisions and the family names are unchanged, which is precisely the situation this increment creates. Satisfies §7 "each must pass the adapter conformance suite and the studio benchmark before promotion." and CLAUDE.md "Never fabricate launch, legal, or provider evidence."

7. **The revision-bump contract is written down and made executable.** `docs/PROVIDER-ROUTING.md` gains "Capability revision changes and in-flight plans", stating: an enqueued plan fails closed in `instantiateProviderPlan` with the documented "Start a new render" message, and both staging deploy paths drain queued and running jobs before upgrading anyway; a leased job fails closed twice, in `RoutedGenerator`'s constructor and again immediately before dispatch with a terminal `RoutingError(["capability-changed"])` that does not trigger failover; a retained record is re-verified entirely from saved data and never consults the live registry, so it survives a revision bump **provided `capability()` still accepts the stored definition**; and that the one forbidden move is a *required* field or any tightened validator, which makes `capability()` throw on already-stored definitions and propagates through `validateCapability` → `validateProviderPlan` into `renderInputHash`, `validateShotRenderRecipe` and the equivalence chain — every retained plan permanently unreadable and shot reuse permanently dead, on content-addressed records that cannot be rewritten without breaking their own seals. Four checks folded into the existing `snapshot-integrity` family (no seventeenth family, so the committed `checks` block does not move) make the load-bearing half a test: (i) an additive field moves the revision, and a plan pinning the new snapshot against the current pool throws the documented message; (ii) a snapshot minted *with* the field and one minted *without* it both round-trip through `validateCapability`, so the addition is forward- and backward-compatible and a rollback is safe; (iii) removing a currently-required field makes `capability()` throw `"Invalid provider capability configuration."`, the shape of change the doc names as forbidden; (iv) `canonical()` enumerates `Object.keys` and stringifies each value, so an explicit `undefined` does not hash the same as an absent key — an optional field must be spread conditionally or "optional" silently becomes "always present". Satisfies §10 "Evidence before promotion: … gap audits." and ADR-0020 fail-closed.

8. **The reliability-panel evidence is re-recorded without destroying HV-038-02's browser pass.** `docs/evidence/hv038-observability/reliability-panel.json` records `rowCaps.providers: 8`, `labelSetHeadroom.providerKinds: 4` and `providerSeriesAtFullBreadth: 8`; all three become untrue, so the file is re-recorded. Its writer blanked `browserChecks` to `pending` unless `HV_RELIABILITY_BROWSER` was supplied, which would have silently downgraded the recorded headless-Chromium pass cited in `docs/OBSERVABILITY.md` — committed evidence destroyed by a routine re-run. The writer now carries a previously recorded `browserChecks` block forward verbatim, with its own timestamps, when no new browser run is supplied; the console renders the provider cell as text with no hard-coded list, so a label-set change does not invalidate that pass. `backendContract` is **never** carried forward, because it is proof about the exact query strings and `limit` values this increment edits; it is always reset and refilled from this PR head's own `telemetry-contract` run. One test pins both behaviours, including that a previous run which was itself `pending` stays `pending` rather than being treated as a pass. Satisfies §10 "Evidence before promotion" and CLAUDE.md "Never fabricate launch, legal, or provider evidence."

9. **No capability revision changes, and no frozen path, dependency, budget default, account, vendor, migration, route or user-facing surface changes.** `packages/generator/src/capabilities.ts` is not in the diff. `docs/evidence/hv019-router/adapter-conformance.json` changes only `recordedAt` and its `telemetryLabels` block; its seventeen `capabilityRevision` and `priceVersion` values are byte-identical, which the existing check that re-derives every one of them verifies on every test run and is the proof that this increment moved no hash. The diff touches nothing under `docs/legal/**`, `docs/adr/**`, `.github/workflows/**`, `packages/safety/**` or `infra/drizzle/**`; adds no `package.json` or lockfile entry, no HTTP route or request field, no cookie, tracking, account, tier or payment path; and changes no default of `HV_MONTHLY_BUDGET_USD` or `HV_COST_CAP_PER_SHOT_USD`. `docs/loop/STATUS.md` and `docs/PROGRAM-EXECUTION.md` are not in the diff; RECORD owns both. Satisfies FULL-SCOPE §10 "Free and anonymous for every end user; no billing code reachable.", "Safety refusals expand only." and the EXECUTION-LOOP frozen list.

## Out of scope

- **Adding `health` to `CapabilityDefinition` — HV-019-08**, gated on a second reachable value (a vendor status endpoint or the self-hosted lane, both G3). Today every adapter would declare the same constant, so seventeen revisions would move for no information. It must be added as an *optional* field; criterion 7's checks are what make that safe.
- **`extension` as a tri-state — HV-019-03/-04**, with the extension modality. `GenerationModality` is the closed union `"image" | "video"`; no adapter can emit a second value, so the widening is untestable churn today.
- **Populating `policy.vendorPolicyVersion` — deferred with no increment**, until a human checks and cites a fal.ai policy document. The repository's checked vendor facts are model schema and list pricing only; there is no terms-of-service, acceptable-use or content-policy document referenced anywhere and no version identifier for one, and writing a value would violate CLAUDE.md "Never fabricate … provider evidence."
- **Distinguishing one paid image model from another in telemetry.** `rich-animatic-paid` covers the lane, not the model. A per-model label is unbounded cardinality, which ADR-0018 and the metric allow-list refuse.
- Folding the audio and lip-sync capability schemas into the unified registry (HV-019-03, with HV-022).
- Quality presets, the hero-render chain, per-shot batch and priority (HV-019-04/-05).
- Routing on policy or evaluation scores, and provider canaries (HV-019-06; honest scores need live paid dispatch, G1).
- Any kill switch, per-provider disable or other mutating operator control: the console is read-only by construction (owner HV-032).
- The Reproducible Film Manifest, regenerate-from-manifest, the cross-generation diff report (HV-019-07).
- Any live provider dispatch, price confirmation, regional execution claim or visual-quality evaluation.
- Any edit to `.github/workflows/ci.yml`, `docs/adr/**`, `docs/legal/**`, `packages/safety/**`, `infra/drizzle/**`, `packages/generator/src/capabilities.ts`, `docs/loop/STATUS.md` or `docs/PROGRAM-EXECUTION.md`.
