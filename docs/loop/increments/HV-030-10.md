# HV-030-10 — The studio knew the render was free and did not say so

epic: HV-030
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

`POST /projects/:id/jobs` returns the job it has already admitted for a repeated idempotency key
rather than admitting a second one. That is what HV-030-07 took the studio's random
`crypto.randomUUID()` keys away for, and what HV-016-10 and HV-017-12 stopped a no-op save from
defeating — a save that changed nothing used to move the derived key and buy a second film.

The route already **knew**. The repeat has its own branch and its own early return:

```ts
if (existing && !takeQuote) return response({jobId: existing.id, stage: existing.stage, …}, 202);
```

It answered with the same shape as a new admission, so nothing downstream could tell a film that had
just been paid for from one that had been paid for ten minutes ago. Both HV-016-10's and
HV-017-12's gap lists end with the same sentence — *"Nothing tells the creator the render was
free"* — and so does HV-030-08's, about a render it gave up waiting on.

This matters more now that the two no-op fixes landed. Before them, asking again *did* charge, and a
studio that said "this cost nothing" would have been lying. It is true now, and worth saying: a
creator who reloads, or comes back, or presses the button twice, currently has no way to know whether
they have just spent their film's budget again.

## What this increment does

- **The route reports `admitted`**: `true` for a job this request admitted, `false` for one it found.
  Two fields, one on each of the route's two job-returning paths.
- **`askForRender` is the only place the studio reads it.** Both approvals go through it, so they
  cannot come to describe the same thing differently — which is exactly the mistake HV-030-07 found,
  where two of three sibling paths were guarded and the third was not.
- **The note is news, not decoration.** A render that was actually made says nothing; a studio that
  said this every time would be saying nothing. One line, once, above the step.
- **`admitted` is checked for `false`, not for falsiness**, so a response without the field — an
  older server, or a route that does not report it — is never read as "already made". Saying a film
  was free when it was not is the one thing this must not do.

## Acceptance criteria

1. **A render this request admitted says so, and one it found says so too**, with the same job id —
   and repeats keep answering the same way.
2. **A render the studio has not made before is admitted, whatever came before it**: with one job
   already in the project, a second key is admitted, and each key keeps its own answer.
3. **A caller's own idempotency key is answered the same way**, because the branch that finds an
   existing job does not care where the key came from.
4. **A film the crew had already made is said to have cost nothing** — one note, in the creator's own
   words.
5. **A film the crew made just now says nothing about it.**
6. **A server that says nothing at all does not produce the note**, and the studio still renders once.
7. Reverting `server.ts` fails criteria 1–4; reverting `studio.js` fails 4.

- Tests: `packages/api/test/render-already-admitted.test.ts`,
  `packages/frontend/test/studio-reused.test.js`.

## Known gaps this leaves

- **Only the two picture renders are reported.** The audio-take and dialogue-replacement routes have
  their own "already admitted" branches with their own early returns, and they say nothing either.
  They are reached from the finishing passes rather than from a button, so a creator does not press
  them twice — but the same sentence is true of them.
- **The note does not say what it saved.** It says the render was not paid for again; it does not say
  what that render cost, which is in `/spend` and which the studio already shows at every approval.
- **Nothing distinguishes a repeat from a *resumed* wait.** HV-016-11 brings a creator back to a
  render in flight, and if they then press the button anyway they get this note — which is true, and
  is not the same story as the one HV-016-11 tells.
- **The flag is not in the job view.** `GET /projects/:id` lists jobs without saying which request
  admitted each one, so a studio that reloads cannot reconstruct this after the fact; the note lives
  only in the state of the session that asked.
