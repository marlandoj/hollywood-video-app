# HV-022-25 — The first face point, from fal.ai

epic: HV-022
release: 3 "Features"
gate: none new
spend_usd: 0

## Why

HV-022-23 queues a voiced cut's on-camera lines as lip-sync passes, but only lines on a shot where the owner already
chose a face point. On a new film no owner has chosen one, so every on-camera line is `no-face-point`, and the
studio queues nothing. HV-022-24 recorded the owner's answer to who finds the first face point. In Kevin's words,
on 2026-11-11:

> "First face point: VEO or fal.ai"

This increment builds that finder, using **fal.ai**. The studio already works with fal for its picture and stills
(`packages/generator/src/fal.ts`, `fal-image.ts`), and Veo would need a new account. The studio never adds an
account, a key or a vendor by itself.

It is a contract with a closed mock adapter only. Nothing calls fal, no key or policy ships, `HV_STUDIO_LIPSYNC`
stays off by default, and the finder is off unless the operator's policy for it is present.

## The design

The finder is a step inside the creator's one lip-sync approval (HV-022-24), before the passes it may make
possible. It is not a second approval and not a background job. The detection's result decides whether a pass is
admitted, so making the detection a separate earlier step would mean asking the creator twice for one film's
lip-sync. Instead the creator approves the most the step can hold, and the step never holds more.

1. **The frame.** For each line with no owner point, the frame is the middle of the line's window. It is decoded
   and verified by `previewLipSyncFrame`, the same decode the owner's frames and the HV-022-23 re-check use.
   There is no existing helper that picks a better frame.
2. **Exactly one face, or no point.** `parseFaceDetection` reads fal's undocumented `text_output` strictly. It
   accepts only `{"points":[{"x":…,"y":…},…]}`, with each coordinate a number in [0, 1]. Exactly one face inside
   the frame gives the frame's own pixel. Any other answer gives no point, and the line stays `no-face-point`
   with its detail:
   - zero faces;
   - two or more faces ("2 faces found; choose the speaker under Direct lip-sync.");
   - a face outside the frame;
   - an answer that cannot be read;
   - a call that failed.

   The request sends `combine_points: false`, so fal never merges two faces into one point.
3. **A suggestion, kept apart.** A detected point is never stored as an owner's point. It lives in its own record
   (`hv_face_detections`), and a ready line made from it carries `detectedPoint` with its provenance:
   - `source: "detected"`;
   - the provider and model;
   - the frame hash;
   - the request hash;
   - the policy and capability revisions.

   The owner's point always wins, whenever it was chosen. HV-022-23/24's reuse rules apply to suggestions too: a
   suggestion whose studio pass failed, was cancelled, or was last reviewed as anything but an accept rating 3 or
   more is not offered again. A line is never detected twice on the same picture.
4. **Money.**
   - Each detection holds the finder policy's flat `heldUsd`.
   - The creator approves one amount on the lip-sync step, and `holdApprovedUsd` must equal it to the
     micro-dollar. The amount is the most the step can hold: each ready pass, plus, for each planned detection,
     its own hold and the pass it may make possible.
   - The step shows the detection as its own line: "Face detection: 1 frame at $0.02 each ($0.02), spent even if
     no face is found." It also says that a line's pass is held only where exactly one face is found.
   - The pre-check of the film's limit and the month's cap uses that most, so a list that could exceed either is
     refused whole before anything is held.
   - Each detection is then admitted by `admitFaceDetection`, beside `admitLipSync`, under the ledger's lock. The
     ledger re-checks the open film, the current finder policy, the film's limit (`assertFilmWithin`) and the
     month's cap (`reserveWithin`, stage `face-detection`), and writes the record in the same transaction.
   - The record's id is the **detection key**: the source cut, shot, line, decoded frame hash and policy revision.
     So a replay, from a retry or a racing request, returns the record already held and holds nothing new, and the
     detector is asked once per key.
   - A detection that finds no usable point still spends its hold. The worker's reconcile posts a settled
     detection's whole hold as its cost event and ends the hold.
5. **The pass.** After its detections, the request reads the list again. The approved lines that are now ready,
   the ready ones and the planned ones with one face found, are admitted exactly as in HV-022-23: the frame is
   re-checked, then `admitLipSync` runs per pass under the lock.

**Why a flat hold, not the listed $0.0011 per second.** fal bills compute seconds, which the studio cannot know
before the call. A flat hold per detection, from the operator's policy, is the same shape as the owner's decision
for passes ("a flat hold per lip sync pass"). It is posted whole as the detection's cost, because an operator's
invoice for these calls is not reconciled yet. That over-counts, and never under-counts.

**Why the detector runs in the API request.** The studio's other provider calls run in the worker, as jobs. A
detection is one short call whose answer the same request needs, and a new job stage would touch about thirty
places for one call. The detector is asked once, after its hold commits, with its own 60-second limit, so the
result is recorded even if the creator's request goes away. A detection that never finished stays held, is never
asked again, and leaves its line to the owner.

  - the `faceDetection` option;

    the finder is on;
  - `lipSyncDetectionFrame`, `lipSyncPlannedDetections` and `studioLipSyncApprovalUsd`.
- **The ledger and storage**:
  - `admitFaceDetection`, `settleFaceDetection` and `faceDetections` on `PostgresLipSyncLedger`;
  - `postFaceDetectionsWithin`, run by the worker's reconcile. The reconcile's sweep of stale holds skips
    `face-detection`, as it skips `music-cue`;
  - the `face-detection` cost stage;
  - migration `0022_face_detections`, which adds the table with forced row security, scoped to the admitting film

- **The API** (`packages/api/src/lipsync-api.ts`, `server.ts`):
  - the injected `faceDetector`;
  - the finder's place in the work-list `GET` and `POST`;
  - the answer's `faceDetection` (on `GET`), and `detections` and `detectionHeldUsd` (on `POST`).
- **The studio** (`packages/frontend/src/studio.js`):
  - `lipSyncSummary`'s `detection` line;
  - a list with only detections still asks the creator;
  - the notes say what each detection found and spent, and that a decline spent nothing.
- **Docs**: `docs/LIP-SYNC.md` ("The studio's face-point finder (HV-022-25)").

## What this increment does not do

- No call to fal or any provider, no key, no policy file and no live detector. `createApiServer` takes a detector
  only when one is passed, and only the tests pass one.
- No change to the lip-sync capability, policy, plan, worker or Sync adapter. No budget default changes: the $500
  monthly cap and the $40 and $150 film limits stay. The switch stays off by default.
- No change to `packages/safety`, `docs/legal/**`, `docs/adr/**`, `.github/workflows/**`, the capability pins or
  any evidence.

## Acceptance criteria

1. **Off is unchanged.** Each of these leaves the work list's `GET` answer exactly as before, to its revision,
   and the hold, and asks no detector:
   - no detector;
   - no finder policy;
   - no lip-sync policy;
   - no PostgreSQL.

   With the switch off the route is still the unknown-route 404.
2. **One face.**
   - The list plans one detection on the line's middle frame.
   - The approval is $10.02: the ready pass, the detection and its possible pass. The old $5, or any other
     amount, is refused with 409 before anything is held or asked.
   - Approved, the detector is asked once with the pinned request and the frame, and the record is `one-face`.
   - The line's pass is admitted on the detected pixel. The holds are $0.02 + $5 + $5, and `heldUsd` is 10.02.
   - Read again, the line is `ready` with `detectedPoint`, and nothing is planned or asked again.
3. **Two faces, no face, an unparseable answer, a failed call.**
   - The detection's $0.02 is held and reported, and only the ready pass is admitted ($5.02).
   - The line stays `no-face-point` with the outcome's detail, and is never planned again.
4. **Replays.**
   - The ledger's replay of a detection key returns the record and holds nothing new.
   - Two racing approvals ask the detector once and hold the detection once.
   - A detection held but never finished is not asked again, and leaves its line to the owner.
   - A settled detection keeps its first result.
5. **Caps under the lock.** A film limit below the most the approval can hold refuses the request whole. Under the
   lock, each of these refuses the detection and writes no row:
   - a spent film limit;
   - the month's cap;
   - a changed or missing finder policy;
   - another film's project;
   - a key reused for another request.
6. **Posting.** The worker's reconcile keeps an unfinished detection's hold. It posts a settled one's hold once,
   as `face-detection:<id>` from `fal`, and ends it.
7. **The owner's point wins.** An owner point on the line beats a newer suggestion. This is tested in the planner,
   and again through the API after the studio's pass on the suggestion is withdrawn.
8. **The studio** shows the detection as its own line of the hold, sends the whole amount, and says what each
   detection found and spent, including on a refusal. A decline spends nothing.

## Known gaps

- **The `text_output` format is undocumented.** It is read as one exact JSON shape, and anything else is no point.
  Confirm on the first live call, with the operator present, before any live detector is built.
- **The frame goes as a PNG data URI.** fal's size limit for a data URI is not documented. A large frame might
  need fal's upload instead. Confirm on the first live call.
- **No live detector exists, and where its key lives is not decided.** The API has no provider keys today. A
  later increment must choose between the API holding a fal key for this one call and running detections in the
  worker as jobs.
- **The flat hold is posted whole as cost.** fal's actual compute seconds are not reconciled against an invoice.
  This over-counts, and never under-counts.
- **A detection that never finished stays held.** Its line is not detected again on the same picture, so the
  owner chooses its face under Direct lip-sync.
- **One line, one frame.** A line whose middle frame shows no face, or two, is not tried on another frame. That
  would be a second paid detection, and the owner did not ask for one.
