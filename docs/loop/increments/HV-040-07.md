# HV-040-07 — The archive path re-asked one question per job, and did not ask another at all

epic: HV-040
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

Two findings from a critic pass over `packages/storage`, the package that backs the PostgreSQL the
staging host actually runs.

### The validation was the export

`validateSnapshot` runs a block for every job that carries a `direction` (`snapshots.ts:411`):
validate the direction, check every shot's frame anchors against the project's reference catalog,
parse the screenplay, plan every scene into shots, check every picture direction, and direct the
shots. Every job of a project carries **its own copy of the same `scriptText`** — up to 200,000
characters — and every admitted `animatic`, `final` or take job carries a direction
(`ledger.ts:175`), so this ran once per job on inputs that are identical byte for byte.

Measured with a 181,384-character screenplay, one project, jobs sharing one direction snapshot —
which is what a project's jobs look like:

| jobs | before | after |
|---|---|---|
| 8 | 93.0 ms | 28.0 ms |
| 16 | 183.3 ms | 17.8 ms |
| 32 | 336.7 ms | 18.6 ms |
| 64 | 664.3 ms | 16.4 ms |
| 128 | 1,264.2 ms | 23.6 ms |
| **256** | **2,550.6 ms** | **24.8 ms** |

Doubling with the job count before; flat after. **103× at 256 jobs**, and the shape changes rather
than the constant. Omitting `direction` from the same 256 job bodies — the only thing that skips the
block — takes 12.3 ms, so the block *was* the validation and everything else in it is noise.

Where it runs is what makes it matter. `validateSnapshot` is called twice on export
(`exportStateSnapshot:628`, then `writeStateSnapshot:505`) and twice on import, and the first of
those runs **inside** the `begin(...)` callback that has already issued
`set transaction isolation level repeatable read, read only` (`:594-596`). So a CPU-bound
validation holds a snapshot open on the cluster and pins `xmin` against vacuum for its whole
duration. A project with a thousand renders spends about ten seconds per call and twenty inside the
export transaction.

### And a deliverable could round-trip as zero bytes

`assertRenderedFiles` compares a job's stored artifact rows against the media its checkpoint names.
It has a branch for the current film, the living script, shot executions, lip-sync, sound, graphics,
picture edits, assemblies, audio, dialogue and shot renders. It had none for `delivery`.

A deliverable is the one media a job may hold **without** a `job.output`, because
`validateDeliveryJob` forbids one — *"a deliverable retains its own single file and nothing else"*.
So every branch keyed on `job.output` or on another stage's field reached it never:

- `assertRenderedFiles` never compared `deliveryOutput.file` with anything.
- `importCompletedJob`'s missing-media gate is inside `if (job.output)`, permanently false for a
  delivery job.
- `restoreCheckpoint` calls eight `verify…Media` functions; `verifyDeliveryMedia` exists, is used by
  `checkpointDelivery`, and was not among them.
- `archives.ts:90` skips `importCompletedJob` entirely for a job it believes carries nothing, and
  that list named neither the deliverable **nor five of the checkpoints** — sound, editorial,
  assembly, dialogue and current-film.

A project archive exported and re-imported therefore yielded a `delivery` job still marked `done`,
still carrying `deliveryOutput.file` with its digest, with no artifact row and no object behind it —
and a receipt reporting `mediaFiles` and no error. The creator clicks download and gets nothing.

## What this increment does

- **The direction block is asked once per distinct answer.** It is a pure assertion over five things
  a job carries plus the project it belongs to, so the key is a content hash of exactly those:
  project, tier, stage, the screenplay's digest, the direction, the cast and the take group. The
  screenplay is hashed once per distinct text as well, because a project's jobs share it.
- **The parse is memoized per call**, which also covers the take-context check and the picture
  performance check outside the block.
- **The per-job `find` over every project** is a map, built once.
- All three live for one `validateSnapshot` call rather than in the module: a cache keyed on content
  would be sound across calls, but one that cannot outlive its question is one less thing to reason
  about.
- **`assertRenderedFiles` has a delivery branch**, so the stored rows must be the deliverable the
  checkpoint names, on both paths that call it — `restoreCheckpoint` and `importCompletedJob`.
- **`importCompletedJob` refuses an archive that does not carry the deliverable's file.**
- **The archive's skip list names every media field a job can hold**, the five missing checkpoints
  included, and a test derives that list from `Job`'s own fields rather than repeating it.

## Acceptance criteria

1. **Thirty-two times the jobs is not thirty-two times the work**, on a 181,384-character
   screenplay, with an absolute ceiling beside the ratio.
2. **The job that is wrong is still refused**, whether it is the first or the last of eight
   otherwise identical jobs — the memo answers "these inputs were checked", so a job differing in
   any of them is a new question.
3. **Identical valid jobs still validate**, and two projects sharing one screenplay are two
   questions, because the anchor catalog the check reads is the project's own.
4. **Every `…Checkpoint` and `…Output` field of `Job` is named in the archive's skip list**, derived
   from the interface rather than written down.
5. **`assertRenderedFiles` and `importCompletedJob` name the deliverable** — asserted over the
   source, because both run only against a database.
6. Making the memo answer "checked" for everything makes criterion 2 fail; removing it entirely
   makes criterion 1 fail. Both run by hand and recorded here.

- Tests: `packages/storage/test/snapshot-validation-cost.test.ts` (1–5).

## Known gaps this leaves

- **`restoreCheckpoint` still does not call `verifyDeliveryMedia`.** The row comparison added here
  runs on that path and catches a deliverable whose stored bytes differ from its checkpoint; what it
  does not do is re-probe the file the way the seven siblings do. Adding it means deciding whether a
  resume should pay a full decode of a lossless master, which is the same question HV-027-05 asked
  about the render's own deadline, and it deserves its own increment rather than a line here.
- **The delivery check is asserted over the source, not exercised.** `assertRenderedFiles` is
  private and both callers need PostgreSQL, so the run-time proof is CI's.
- **`hv_artifacts.object_key` and `hv_archives.object_key` have no index.** `0004_artifact_objects.sql`
  added the column with a bare `ALTER TABLE` and none was added since, and `retention.ts:151-152`
  does an equality probe on each, once per stored object, in an hourly sweep that walks up to
  200,000 keys — as `hv_worker`, whose RLS policy is `using (true)`, so no project predicate narrows
  the scan either. It is a one-migration fix (`create index … on hv_artifacts (object_key)`, the
  same for `hv_archives`, mirrored in `schema.ts`). It is not here because it cannot be measured
  from this container and a migration deserves a `EXPLAIN` beside it.
- **`PostgresReviewQueue.resolve` is not project-scoped.** It updates `where shot_id = $1 and
  resolved_at is null` with no project, while its sibling `flag` keys the row on
  `sha256(projectId + "\0" + shotId)` — and shot ids are per-project strings like `shot-1-1`, so one
  call would resolve every project's review of the same shot. There is no production caller today
  (`worker.ts` calls `flag` only), so it cannot fire; it is a trap for the first caller, and the
  same is true of `OperatorReviewQueue.resolve` next to it. Fixing both means changing a signature
  with no callers, which is a small increment and not this one.
- **`validateSnapshot`'s other super-linear loops** — `events.filter(e => e.attemptId === a.id)` per
  attempt, `audio.some(...)` per event — are genuinely quadratic and were two orders of magnitude
  below the block at every size measured. They are still there.
