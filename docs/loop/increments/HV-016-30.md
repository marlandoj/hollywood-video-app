# HV-016-30 — Mixed films run: admission, claim, the worker's mixed branch, and the PostgreSQL lifecycle

## Why

PR #83 ("Run mixed films with owned proof and atomic recovery") is rebuilt on main as HV-016-23 to
HV-016-31. The first seven increments ported the contracts, media helpers, assembly, local proof,
PostgreSQL and S3 custody, and `hv-state/16` recovery. Each one kept V3 (mixed) jobs refused at
admission, so none of it could run. This increment turns V3 on; HV-016-31 finishes the review and
delivery surface.

The PR's own real PostgreSQL and S3 lifecycle test never passed CI. Running it locally, against
PostgreSQL 16 and an S3 stand-in (moto), found five separate causes, and all five are fixed here.
It also showed that a mixed final is slow; that is recorded under the gaps, not changed.

## What this increment does

**Turns V3 on:**

- **Local queue** (`packages/queue/src/index.ts`). `enqueue`, idempotency and `claimNext` now go
  through the runtime switch. A complete V3 plan is admitted and claimed. V2 bodies are still
  checked strictly: a V2 request that carries `currentFilmOrigins` or `currentFilmProof` is
  refused, and so is any V3 request carrying private progress.
- **PostgreSQL ledger** (`packages/storage/src/ledger.ts`, the hunks held back from HV-016-28).
  - Admission, held checks and dispatch use the runtime switch.
  - V3 admission resolves and compiles the complete proof copy specification before it reserves
    anything. It runs after main's film-cap check (HV-027-11).
  - Provider dispatch is refused for any slot that is not a prepared, selected fresh slot.
- **Worker** (`packages/queue/src/worker.ts`), the PR's mixed branch merged with main:
  - It prepares proof and then originals, checkpointing each, before any slot.
  - Selected slots adopt a take with no provider; fresh slots generate through
    per-invocation provider output.
  - Every slot is checkpointed as a mixed row, then the film is assembled with a real `assembledAt`
    and completed atomically.
  - It watches the workspace and deadline, and never evicts a shared cache.
  - Merged with main: the delivery dispatch step, main's `assertPendingContext` (the PR still
    called it `checkPendingContext`; every mixed call site uses main's name), HV-022-01's
    rough-cut dialogue, HV-038-06's refusal of an unreadable manifest (a mixed job has no clip
    manifest), and HV-019-07's resumed degraded shots. A mixed prefix's degraded verdicts are
    recomputed from its owned rows, and review flags are flushed before each mixed checkpoint.

**Fixes found by running the real PostgreSQL lifecycle:**

1. **Proof publication refused every real query result.** `PostgresArtifactStore` proof selection
   (`proofRows`) required `Array.prototype`. Bun returns `SQLResultArray`, an `Array` subclass. So
   the first worker failed with "Retain actual bounded proof query rows." — the error 92abf79's
   instrumentation surfaced in the phase "settles the first worker at actual proof/origins
   custody". It now reads rows through `sqlResultRows`, as the proof and mixed-context modules
   already did (PR commit 3ee5f00). The artifact test's transport double now returns Bun's
   container and string byte counts, so this cannot pass unnoticed again.
2. **Held worker transactions hit Bun SQL's 20 s idle timeout.** Bun's `idleTimeout` also closes a
   connection reserved by an open transaction. A V3 envelope is large, and on a loaded host a
   heartbeat or checkpoint transaction went more than 20 s between statements. The failure was
   "Idle timeout reached after 20s", traced to `PostgresJobStore.heartbeat` and
   `checkpointCurrentFilmMixed`.
   - The worker's database now uses `WORKER_DATABASE_IDLE_TIMEOUT_SECONDS` (300 s,
     `packages/storage/src/database.ts`), and the lifecycle test's worker database uses the same
     value.
   - Held mixed artifact transactions also send `select 1` every 5 s while they re-verify media
     (`heldMixedTransaction`).
3. **A mixed final could not keep a mixed preview as proof.** Verifying a V3 preview in its copied
   namespace nests the proof verifier, which left an empty `.proof-check` directory inside the
   final's proof tree. The final's exact-tree check then refused it: "The owned proof tree contains
   an unreviewed directory." The verifier now removes its emptied scratch parent, and a concurrent
   verifier that loses the race recreates it once.
4. **A long held transaction outlived its own lease.**
   - `held` locks the job row `for update`, and that also blocks this worker's own heartbeat. The
     final's completion transaction re-verifies the whole film, which re-verifies its proof, and
     that ran past the lease. Its fence failed with `lease_expired`, and the final came back
     still `running`.
   - No other worker could have claimed the row meanwhile, because `claimNext` skips locked rows.
   - So a held mixed transaction now renews the lease itself every third of a lease, as the
     blocked heartbeat would have (`renewHeldLease`). It renews only a row this worker still holds,
     at the same lease version, whose lease has not yet run out by the database clock. It never
     revives an expired lease, and the commit fence is unchanged.
   - A short transaction never renews. So the PR's case "origins transaction rolls back ... when the
     original lease expires" still passes unchanged. (A first version renewed eagerly at the start
     of every held transaction. That broke this case, and it was replaced.)
   - The heartbeat that waited behind such a transaction then shortened the lease again. It carries
     the time it was sent, so after a wait of minutes it wrote `sent + lease`: earlier than the
     renewed lease, and sometimes already past. The worker's next fence saw an expired lease and the
     final came back `running` with no failure. `PostgresJobStore.heartbeat` now never shortens the
     lease its holder already has; the holder and fence checks are unchanged. A new case in
     `packages/storage/test/jobs.test.ts` fails without this.
   - The domain write inside such a transaction still used the lease it began with. Proof, origins
     and mixed checkpoint transactions built their domain write (and the origins transaction its
     staged body) from the job as read at the start, so the renewal never reached them. A
     transaction that outlived its starting lease was refused `lease_expired`, and the final came
     back `running` with no failure reason. On this host the origins and checkpoint transactions
     run about 210 s and the heartbeat comes every 100 s, so one begun more than about 90 s after
     the last heartbeat failed. This was the intermittent lease loss in the lifecycle's final (2 of
     9 local runs). The domain write now uses the lease the row holds after the last in-transaction
     `held` check. A new case in `current-film-mixed-artifacts.test.ts` renews inside an origins
     transaction and then lets the starting lease run out: it fails with `lease_expired` without
     this fix and publishes with it.
5. **The archive packager's 60 s Bun bridge was too short for a mixed final.** The final's
   snapshot carries its proof, which holds the whole mixed preview and the preview's own proof.
   Validating it (`validateSnapshot`) timed out in the lifecycle's export phase. The `hv-state/16`
   bridges (the full snapshot and the mixed media check) now allow 900 s
   (`MIXED_BRIDGE_TIMEOUT_SECONDS` in `scripts/archive-package.py`); every older bridge keeps 60 s,
   and a new `MixedArchiveTests` case pins both bounds.

## Acceptance criteria

1. **Admission and claim.** A complete V3 plan is admitted, replays to the same job and is claimed
   as V3. A V3 request carrying origins, proof or a checkpoint is refused, as is a V2 request
   carrying origins or proof, and a resealed selection.
2. **Local worker.**
   - It copies complete originals, adopts native speech without dispatch, and publishes an
     independently verifiable preview.
   - Origins-only and proof-only interruptions resume with the original start time.
   - A fully adopted film settles and resumes without constructing providers or recording
     generation costs.
   - Expiry, a changed workspace owner and a stale worker are refused.
3. **PostgreSQL admission.** Proof resolution and copy capacity complete before reservation. Missing
   or changed historical previews, indexes or bootstrap evidence are refused before any spend.
   Exact replay keeps its original reservation.
4. **Archives.** Mixed output, origins-only and positive-prefix archives survive `hv-state/16`
   pack and unpack with the original jobs and paths absent. Unindexed files and altered provenance
   are refused.
5. **Real PostgreSQL and S3 lifecycle, all nine phases:** atomic admission, the first worker settled
   at proof and originals custody, restore, resume with selective dispatch, the preview decision,
   an approved final, export and import into an independent database and bucket, independent
   restore, and refusal of index or object corruption with repaired custody.
6. **Bun result shape.** Proof selection and the artifact transport accept Bun's `SQLResultArray`
   and string byte counts. A real PostgreSQL result normalizes to dense rows.

## Known gaps this leaves

- **HV-016-31:** the preview decision taken through the API and consumed by a local final,
  `docs/CURRENT-FILM-MIXED-ASSEMBLY.md`, and named refusals of a finished mixed film as an
  editorial source or a delivery source.
- **No product surface submits a mixed film yet.** The API compiles only V2 plans, so a mixed film
  is admitted when a plan is built with `compileCurrentFilmMixedJob`. A creator-facing route that
  chooses takes to keep is the next piece of work.
- **Mixed films as editorial sources.** This needs a V3 source receipt contract (`/4`), inspection
  and save, and conform and preview integration.
- **A mixed final is slow.** Its proof holds the whole mixed preview, and every verification of the
  final re-verifies that preview and the preview's own proof. On PostgreSQL a held publication
  verifies twice (before upload and inside the transaction). On this 2-core host one final
  verification took 3 to 6 minutes, and the lifecycle's final phase 50 to more than 60 minutes.
  Caching a verified proof per job, or pinning it by the artifact index after preparation, would
  remove most of this. That is a design change, not a port, so it is left.
- **Timing.** Several suites need more than one file's 590 s budget on a 2-core host (measured:
  `current-film-v3-worker` 2,291 s, `current-film-mixed-artifacts` 2,079 s,
  `current-film-mixed-archive` 884 s, and the PostgreSQL and S3 lifecycle 5,757 to 5,930 s). CI runs
  them all in the one `bun test packages test` step of the `quality` job, which has no
  `timeout-minutes` and so gets GitHub's 360-minute default.
