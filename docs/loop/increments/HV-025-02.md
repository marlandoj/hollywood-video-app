# HV-025-02 — A retained graphic receipt is evidence, not a claim about the host validating it

epic: HV-025
spend_usd: 0

## Goal

Stop every retained graphic receipt being re-bound, at each validation, to the machine doing the validating — because that made an ordinary dependency bump refuse every state snapshot restore. Move the runtime qualification to render admission, where it belongs and where it is stronger than before, and leave behind the fixture that makes the drift visible.

## The defect

`validateGraphicReceipt` did two live reads of the validating host:

```ts
if(!["HeadlessChrome/"+GRAPHIC_CHROME_VERSION,"Chrome/"+GRAPHIC_CHROME_VERSION].includes(r.browser)
  || !/^(win32|linux|darwin)\/(x64|arm64)$/.test(r.platform)
  || r.enginePackageSha256 !== graphicHash(readFileSync(new URL(import.meta.resolve("@hyperframes/engine/package.json")))))
  editFail("The graphic renderer differs from its qualified package or browser.");
```

The second comparison recomputes a hash of the **installed** `@hyperframes/engine/package.json` and compares it to the value frozen into the receipt when the graphic was rendered. So a receipt stopped validating the moment the host changed — and "changed" is a low bar: a version bump, a registry republish, or bun re-resolving the lockfile so that one file's bytes differ at all. The first comparison has the same shape against the pinned Chrome build.

**The blast radius is not graphics.** `validateSnapshot` reaches the receipt through five hops:

```
validateSnapshot → validateEditLibrary → validateEditSourceReceipt → editOriginalJob → validateGraphicOutput → validateGraphicReceipt
```

(`packages/storage/src/snapshots.ts:211`, `packages/planner/src/edit-library.ts:16`, `packages/planner/src/edit-sources.ts:43`, `packages/planner/src/graphic-jobs.ts:51`.) So after such a bump, **a whole-state snapshot refuses to restore** — every project, every job, every ledger row — if any one project's editorial library holds a single graphic source. A restore is a cold process, so the in-process `validReceipts` cache cannot soften it, and the failure is a `editFail` about a "graphic renderer", which names nothing an operator would connect to a dependency bump.

**Nothing in the repository failed at the moment of such a bump, and that is the part worth naming.** There was no checked-in receipt fixture. Every test built its receipt with `enginePackageSha256: graphicHash(readFileSync(import.meta.resolve("@hyperframes/engine/package.json")))` and `browser: "HeadlessChrome/" + GRAPHIC_CHROME_VERSION`, in the same process that then validated it — so the two sides were computed from the same live source and always agreed. This is the recurring defect in this program: **an expectation derived from the very thing it is meant to pin.** The suites that use a real retained receipt are gated behind `HV_GRAPHICS_CHROME_PATH`, so they were not running either.

## The shape of the repair

**Two different questions, separated.** *Is this retained evidence valid?* is answered by `validateGraphicReceipt`, from the receipt and the plan alone. *Is this host qualified to render?* is answered by `assertQualifiedGraphicRuntime`, at render admission. Conflating them meant the second question's answer could invalidate the first question's evidence.

**The validator keeps every structural check and loses only the two live reads.** The receipt still has to be internally sealed (`revision === contentHash(body)`), bound to its plan and recipe, carry the composition, font and licence hashes the repository's own assets produce, and name a runtime: three 64-hex hashes, a platform matching `^(win32|linux|darwin)/(x64|arm64)$`, and a browser matching `GRAPHIC_BROWSER_SHAPE` — a Chrome build string of any version. What it no longer does is compare that version, or those package bytes, to the host running the check.

**Admission is stronger than it was.** `graphic-render.ts` previously checked only the browser, inline, with `browser.endsWith("/" + GRAPHIC_CHROME_VERSION)`. It now calls `assertQualifiedGraphicRuntime(browser)`, which checks the browser *and* the engine version — the latter was checked nowhere before. The engine is compared by **declared version** against `GRAPHIC_RECIPE.version`, not by package bytes: bytes change when a registry republishes or a lockfile re-resolves, and neither of those is a different renderer, whereas a version is what the recipe declares and what `package.json` pins.

**Those two declarations are now held equal.** `GRAPHIC_RECIPE.version` is `"0.8.31"` and the root `package.json` pins `"@hyperframes/engine": "0.8.31"` — one rule in two places, which is how this defect's cousin gets in. A case asserts they match and that the *installed* version is that one, so the admission check is not passing by accident.

**The fixture is the increment's centre.** `packages/generator/test/fixtures/graphic-receipt-foreign-runtime.json` is a sealed receipt recorded on a different host: `HeadlessChrome/131.0.6778.85`, `darwin/arm64`, and an `enginePackageSha256` that is not this machine's. It is checked in as bytes, so no test computes its runtime values, and the first case asserts each of them differs from this host — because if any ever coincided, the suite would be proving nothing again.

## Declared changes beyond the defect

- **The engine version is now a render gate.** Before this, nothing checked which `@hyperframes/engine` was installed; the hash was recorded and re-compared but never *required* to be anything. A host with a mismatched engine could render and the output was accepted. It now refuses, naming both the qualified version and the version the host has.
- **`graphic-render.ts` no longer names `GRAPHIC_CHROME_VERSION` except to re-export it.** The inline browser check moved into the shared helper; the re-export is unchanged because other modules import it from there.
- **`GRAPHIC_BROWSER_SHAPE` and `installedGraphicEngineVersion` are new exports** of `graphic-receipt.ts`, both used by the tests and the second by the admission helper.

## What this increment does not do

- **It does not stop the recipe comparison from re-binding a receipt.** `validateGraphicReceipt` still requires `contentHash(receipt.recipe) === contentHash(GRAPHIC_RECIPE)`, so changing the recipe — including bumping its `version` field — still invalidates every retained receipt, with the same snapshot-restore blast radius. That is deliberately left: unlike a package's bytes, the recipe is a declared, versioned artefact in this repository, and a recipe change is a decision someone makes, not something a lockfile does. It carries a `schema` field for exactly the migration this would need. **The consequence stands and is not softened here: qualifying a new engine version means editing `GRAPHIC_RECIPE.version`, which invalidates every existing graphic receipt and therefore every snapshot containing one.** Fixing that is a receipt-versioning increment of its own.
- **It does not cover the render path behaviourally.** `renderMotionGraphic` launches a real Chrome and is gated behind `HV_GRAPHICS_CHROME_PATH`, which neither this container nor CI provides, so `packages/generator/test/motion-graphics.test.ts` and `packages/generator/test/edit-graphic-sources.test.ts` skip. The admission call's guard is therefore a comment-stripped source scan, which is stated in the test rather than dressed up: perturbation V9 removed the call and was green against every runnable suite until that scan existed.
- **It does not exercise a whole snapshot restore.** The chain case calls `validateGraphicOutput` — one hop below `editOriginalJob`, three below `validateSnapshot`. Building a project, an editorial library and a file inventory around it would add no further link in *this* chain, so the hop count is stated rather than implied.
- **It does not re-render or re-seal anything.** Receipts already retained keep their recorded runtime, which is the point: they are records of what a host did.
- **It does not address the audit's other HV-025 findings.** The sound-lane recipe exposure (`SOUND_FINISH_RECIPE`, `RESTORATION_RECIPE`) has no capability-revision pin equivalent to `docs/evidence/hv019-performance/capability-revision-pins.json`; untouched here.

## Acceptance criteria

1. The fixture's runtime differs from this host in browser, engine hash and platform, and its revision is the hash of its own checked-in body. — `packages/generator/test/graphic-runtime-binding.test.ts` case 1.
2. A receipt recorded on another qualified host validates. — case 2; V1, V2, V3.
3. The receipt still has to name a runtime in the right shape: six rejected browser strings, two rejected platforms, three rejected hash fields. — case 3; V4, V5.
4. Render admission refuses a foreign browser and a foreign engine version, accepts the qualified pair, and names the version the host has. — case 4; V6, V7.
5. `GRAPHIC_RECIPE.version` and the root `package.json` pin agree, and the installed version is that one. — case 5; V8.
6. `validateGraphicReceipt` names neither `GRAPHIC_CHROME_VERSION` nor `import.meta.resolve`, while both still appear in the file's admission helper. — case 6; V1, V2, V3.
7. The restore path reaches the receipt and a foreign one no longer stops it. — case 7; V1.
8. The render path admits through the shared helper and re-implements neither half of it. — case 8; V9.

## Perturbations

Each edit was applied to `packages/generator/src/graphic-receipt.ts`, `graphic-render.ts` or the root `package.json`, the suite measured, and every file restored from a byte copy. The suite is `packages/generator/test/graphic-runtime-binding.test.ts`: 8 tests, all offline — no Chrome, no provider, no network.

| perturbation | runtime-binding |
|---|---|
| baseline | `8 pass / 0 fail` |
| V1 — the validator re-binds the receipt to this host, exactly as it shipped | `4 pass / 4 fail` |
| V2 — only the pinned browser version re-bound, the engine hash left alone | `4 pass / 4 fail` |
| V3 — only the engine package bytes re-bound, the browser shape dropped | `4 pass / 4 fail` |
| V4 — the browser field no longer checked at all | `7 pass / 1 fail` |
| V5 — the browser shape weakened to match anything | `7 pass / 1 fail` |
| V6 — render admission stops checking the engine version | `7 pass / 1 fail` |
| V7 — render admission stops checking the browser version | `7 pass / 1 fail` |
| V8 — `package.json` pins an engine version the recipe does not declare | `7 pass / 1 fail` |
| V9 — **the render path stops calling the admission check** | `7 pass / 1 fail` |

V1 is the shipped defect, and it takes down half the suite: the foreign receipt, the source scan and the restore-path chain all fail. V2 and V3 show each half of the re-binding is independently caught, so neither is protected only by the other.

**V9 is the row worth reading.** Measured before its guard existed it was `8 pass / 0 fail` — removing the admission call from the render path changed nothing, because the only suites that execute that path need a real Chrome and skip here and in CI. Its guard is a comment-stripped source scan, and the test says so.
