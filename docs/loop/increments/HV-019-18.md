# HV-019-18 — A retained film is planned with the worker's reference budget (Release 3 step 15's rehearsal)

epic: HV-019
release: 3 "Features"
gate: none new
spend_usd: 0

## Why

Release 3's third $0 rehearsal (build step 15, `studio-run.ts --format feature --lock WREN,OSWIN
--continuity-repair`) stopped at sequence 1's rough cut:

```
undefined is not an object (evaluating 'job.providerPlan.pool')
```

Two increments merged on the same day and broke each other:

- **HV-019-17 (#371)** made shot planning read the render pool's reference budget. The line it added
  to `planShots` in `packages/planner/src/shot-reuse.ts` read
  `poolReferenceBudget(job.providerPlan.pool)`.
- **HV-030-32 (#373)** memoized `renderShots`. The memo hands `planShots` only the fields planning read
  before #371. The provider plan wasn't one of them.

So `job.providerPlan` is `undefined` inside `planShots` for every film. No retained job is missing its
plan: `renderShots` refuses any job that has none. Instead, every call threw: the API's checks of a
retained film, shot reuse, and anything else that plans a film's shots. The rough cut was the first.
`bun run typecheck` on `main` says the same:

```
packages/planner/src/shot-reuse.ts(38,224): error TS2339: Property 'providerPlan' does not exist on type 'ShotPlanInput'.
```

## What this increment does

- The memo's input gains `referenceBudget`, the one thing planning reads from the provider plan.
  `renderShots` computes it exactly as the worker does: `poolReferenceBudget(job.providerPlan?.pool)`
  (`packages/queue/src/worker.ts`, the film branch). `planShots` passes it to `directCast`.
- The memo key now includes the budget. Two films that differ only in their pool's budget are planned
  apart and never answered with each other's plan.
- Nothing else changes. `renderShots` still refuses a film without a provider plan, a plan that throws
  is still never kept, and no check moves.

The other `providerPlan` dereferences that #371 and #373 added were checked:

- `shotInputHash`'s `providerPlan!.revision` is reached only after its callers have checked for a plan
  (`renderInputHash`, and `checkSourceRenderRecords`, which refuses without one).
- The worker's `job.providerPlan?.pool` is already optional.
- Admission reads the configured pool, not a job's.

## Acceptance criteria

1. **A retained sequence render is planned as the worker planned it.** WREN and OSWIN are locked to
   four views each. On the referenced profile's rough-cut pool (budget 4), their shared shot sends four
   images. On the mock's pool (budget 32), it sends all eight. In each case `renderShots` equals the
   worker's own expression, and asked again in either order each pool gets its own plan.
2. **Nothing else moves.** HV-019-17's budget tests, the referenced profile's end-to-end test,
   HV-019-16's mock-profile locks (the rehearsal's own flow: the lock, the continuity repair, sequence
   1's rough cut and final), HV-030-32's finishing test and the shot-reuse suite pass unchanged.
3. **Reverting the change fails the new test.** Restoring `packages/planner/src/shot-reuse.ts` from
   `main` fails `shot-plan-reference-budget.test.ts` with the rehearsal's exact error (checked).

- Tests: `packages/planner/test/shot-plan-reference-budget.test.ts` (1, 3; 1 pass). Unchanged:
  `packages/planner/test/reference-budget.test.ts`, `packages/api/test/referenced-profile.test.ts`,
  `packages/api/test/mock-profile-locks.test.ts`, `packages/api/test/feature-finishing-bounded.test.ts`
  and `packages/api/test/shot-reuse.test.ts` (2; 24 pass in all, with the new test).
