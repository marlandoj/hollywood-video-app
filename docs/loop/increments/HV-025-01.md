# HV-025-01 — Pin the graphic render identity, and tie the recipe's dependency versions to package.json
epic: HV-025
spend_usd: 0

## Goal

Make the five values that every retained graphic receipt is re-bound to at validation time enumerable, committed and re-derived on every test run — and tie the three dependency versions `GRAPHIC_RECIPE` restates back to `package.json`, so the copies cannot drift. No behaviour changes.

**How this increment was found.** A program-wide re-verification of the pre-loop credit ran one auditor per epic across all 22 epics that had never had it, as `docs/loop/STATUS.md` says the first planner pass is supposed to do. It found this defect family — a content-hashed identity pinned into an already-delivered record with nothing guarding it — for the third and fourth time in this program. HV-019-01 found one instance. HV-019-03 found five more in the performance lane. This is the graphics lane, and it has the widest blast radius of them: a moved value refuses whole-state snapshot restore, not just the feature that moved.

**What `validateGraphicReceipt` re-derives on every call.** `contentHash(GRAPHIC_RECIPE)` against `receipt.recipe`; `GRAPHIC_CHROME_VERSION` against `receipt.runtime.browser`; the sha256 of the **installed** `@hyperframes/engine/package.json` against `receipt.runtime.enginePackageSha256`; and `compileGraphic(plan)`'s recompiled `htmlSha256`, font evidence and licence hash against the receipt's own. Any mismatch throws "The graphic output differs from its reviewed plan." or "The graphic renderer differs from its qualified package or browser."

**Why it is worse than the earlier instances.**

1. **The blast radius exceeds the feature.** `validateSnapshot` reaches `validateGraphicReceipt` by two independent routes — through `validateEditLibrary` → `validateEditSourceReceipt` → `editOriginalJob` for library sources, and directly on every job's `graphicCheckpoint` and `graphicOutput`. So a moved value does not merely orphan graphics; whole-state snapshot restore refuses, and it does so even for a project with no editorial library at all.
2. **One of the five is not source.** `r.enginePackageSha256 !== graphicHash(readFileSync(new URL(import.meta.resolve("@hyperframes/engine/package.json"))))` hashes the bytes of an installed dependency. To be fair to the existing design, `bun.lock` already pins that tarball by sha512 integrity and CI installs with `--frozen-lockfile`, so a byte-different same-version install is foreclosed by a tracked file; this pin is defence in depth against an install that bypasses the lockfile, not the primary binding. The evidence file says so in those words rather than overstating it.
3. **`GRAPHIC_RECIPE` restates three dependency versions** — `version: "0.8.31"`, `font: "@fontsource/inter@5.2.8"`, `fontValidation: "fontkit@2.0.4-cmap"` — that also live in `package.json`, with nothing tying the copies together. A routine dependency bump changes `package.json` and silently leaves the recipe describing a package that is no longer installed, or moves the recipe hash, depending on which one is edited.

**Demonstrated, not asserted.** On this branch, changing `GRAPHIC_RECIPE.version` from `0.8.31` to `0.8.32` — the value every retained receipt is validated against:

```
existing graphics suites (6 files, 16 tests)   0 fail   313 expect() calls
packages/generator/test/graphic-identity.test.ts   3 fail
```

That is the defect: the expectation moves with the code, so the suite cannot notice.

**This increment changes no behaviour.** Separating "is this retained record readable" from "is this renderer qualified to render now" is the real repair, and it is a loosening of a validator on stored data — safe in direction, but a behavioural change that deserves its own increment and its own critic. These pins are the precondition for doing it safely: they are what will prove that repair moved nothing.

## Acceptance criteria

1. **The five identity values `validateGraphicReceipt` re-derives are pinned and re-checked on every run — and the literals it also re-derives are declared rather than silently uncovered.** `docs/evidence/hv025-graphics/graphic-identity-pins.json` (schema `hv-graphic-identity-pins/1`) records `recipeRevision`, `chromeVersion`, `enginePackageSha256`, the three `dependencyVersions`, and per-`GRAPHIC_KIND` the `htmlSha256`, `fontsRevision` and `licenseSha256`, plus an `escapeProbeHtmlSha256` for a plan carrying all five HTML-escapable characters — without it, `compileGraphic`'s `escape` map sits outside every hash even though it decides the recompiled HTML for any owner-authored title containing `&`, `<`, `>`, `"` or `'`. It also records `unpinnedValidatorLiterals`: seven bare literals and formulas inside `validateGraphicReceipt` (`index.html`, `INTER-LICENSE.txt`, `rgba-frames.txt`, `graphic.mkv`, the frame path, the two accepted browser strings, the credits speed formula), each with its second copy in `graphic-render.ts` and the consequence of renaming it. Those are **declared, not pinned**, deliberately: a transcribed copy in a test is a third copy of the same string, not a tripwire — renaming the source would leave all three disagreeing with stored data while the test still passed. A real guard for them is behavioural and needs a fully-formed receipt fixture; that is HV-025-02's work, named in Out of scope. It is written when `HV_GRAPHIC_PINS_EVIDENCE` names a path and **re-validated on every test run including CI**, which sets no such variable: the schema, and each pinned value against the value this build derives. A seventh `GRAPHIC_KIND` cannot be added without a pin for it, because the test asserts the pinned kind set equals `GRAPHIC_KINDS`. Satisfies FULL-SCOPE §10 "Evidence before promotion: tests, benchmarks, post-flight evals, gap audits." and CLAUDE.md "Never fabricate launch, legal, or provider evidence."

2. **The recipe's three dependency versions are tied to `package.json`.** A test asserts `GRAPHIC_RECIPE.version` equals the manifest's `@hyperframes/engine`, `GRAPHIC_RECIPE.font` equals `@fontsource/inter@<manifest version>`, and `GRAPHIC_RECIPE.fontValidation` equals `fontkit@<manifest version>-cmap`. Because `GRAPHIC_RECIPE` is content-hashed into every receipt, these strings are identity rather than documentation, and a bump that edits one copy and not the other now fails at test time instead of at restore time. Satisfies §10 "Provider independence and versioned adapters." read with ADR-0020 fail-closed.

3. **The installed package is the one the recipe names, and the byte hash is pinned separately.** A test asserts the installed `@hyperframes/engine` version equals `GRAPHIC_RECIPE.version`, and states in the assertion's own comment why that is necessary but not sufficient: the receipt binds to the package's *bytes*, so a same-version reinstall with different metadata still moves the hash — which is precisely why `enginePackageSha256` is pinned as its own value. Satisfies §10 "Evidence before promotion".

4. **The failure direction is demonstrated rather than described.** A test seals a receipt under a recipe this build does not produce and asserts `validateGraphicReceipt` throws "The graphic output differs from its reviewed plan." — the exact refusal a restore would hit for every retained graphic once the recipe moves. Satisfies CLAUDE.md "Every criterion gets a real test."

5. **The evidence file carries no credential, destination or host path, and its honesty fields are explicit.** The file matches none of `://`, `API_KEY`, `/home/`, `/Users/`, `/tmp/`, and every 32+ hex run in it is one of the pinned identities. It carries `behaviourChanged: false`, `newProviderSpendUsd: 0`, `provesRenderQuality: false`, `provesBrowserAvailability: false`, a `reboundAtValidation` list of all eight things the validator re-derives (the five pinned identities plus the three declared-but-unpinned literal groups, each marked as such), and a `blastRadius` field stating both snapshot-restore routes and, honestly, that `bun.lock` already forecloses the reinstall path so the byte hash is defence in depth. Satisfies ADR-0018's identifier discipline and CLAUDE.md "Never fabricate … evidence."

6. **No behaviour, frozen path, dependency, budget default, account, vendor, migration, route or user-facing surface changes.** `packages/generator/src/graphic-receipt.ts`, `packages/generator/src/graphic-composition.ts` and `packages/planner/src/motion-graphics.ts` are **not in the diff**, and the frozen-path check names them on purpose. The diff touches nothing under `docs/legal/**`, `docs/adr/**`, `.github/workflows/**`, `packages/safety/**` or `infra/drizzle/**`; adds no `package.json` or lockfile entry, no HTTP route or request field, no cookie, tracking, account, tier or payment path; and changes no budget default. No browser is launched, no graphic is rendered, no provider is constructed and no key is read — `compileGraphic` is pure composition. `docs/loop/STATUS.md` and `docs/PROGRAM-EXECUTION.md` are not in the diff; RECORD owns both. Satisfies FULL-SCOPE §10 "Free and anonymous for every end user; no billing code reachable." and the EXECUTION-LOOP frozen list.

## Out of scope

- **Separating retained-record validation from renderer qualification — HV-025-02.** That is the real repair for the BLOCKER: a receipt should be readable on its own sealed evidence, while the *live* renderer is checked against the pins before rendering. It is a loosening on stored data and therefore safe in direction, but it is a behavioural change to a validator that whole-state restore depends on, and these pins are what will prove it moved nothing.
- The four uncredited P10 clauses the audit found absent: seven of the eleven compositing items, maps and data callouts, generated inserts, and the Exceed clause.
- **A behavioural guard for the seven unpinned validator literals — HV-025-02.** Each is a bare literal or formula in `validateGraphicReceipt` with a second copy in `graphic-render.ts`; a coordinated rename orphans every stored receipt while every fresh-render test stays green. Guarding them means constructing a receipt valid in every respect except the literal and asserting the validator's exact refusal, which needs a fully-formed receipt fixture. They are enumerated in the evidence file so the surface is written down in the meantime.
