# HV-031-01 — Make a takedown actually stop generation

epic: HV-031
spend_usd: 0

## Goal

Turn `ProjectService.takedown` from a read-side 404 into a revocation, and make it impossible to perform half of it.

Before this increment, `takedown` added the project to `takenDown`, removed it from `projects`, appended to `takedownLog` and persisted. `authorize` and `peekProject` then returned `null`, so no *new* job could be admitted. That was all of it. `packages/queue` contained **no occurrence of the string "takedown"**, so the project's already-queued jobs stayed claimable and its running job kept calling a provider until it finished and wrote a cut. FULL-SCOPE P14 requires that "revocation stops future generation without falsifying history"; neither half was true.

**How this increment was found.** The program-wide re-verification of the pre-loop credit ran one auditor per epic across all 22 epics that had never had the pass `docs/loop/STATUS.md` says the first planner is supposed to run. HV-031 came back `partially-delivered` with one BLOCKER: *"Project takedown does not stop generation: the queue has no takedown awareness, and the worker's mid-render project re-check is conditional."* Verified against the source before any code was written: `grep -ril takedown packages/queue/` returns nothing, and `assertPendingContext` (`worker.ts:222`) returns early for every job that is not a `currentFilm` or `livingScript` job.

## The shape of the repair

**Revocation is not cancellation.** `DurableJobStore.cancel` is a *worker* action: it goes through `holder(id, workerId, now)` and therefore requires the lease of the job it is stopping. Nothing outside a running worker could ever stop that worker's job. A takedown comes from outside the queue — and so, later, will a legal hold, a withdrawn consent and an appeals-driven suspension — so it needs a verb that does not need the lease of the job it is stopping. `revokeProject` is that verb.

**The lease is the kill switch, and it already existed.** Clearing `claimedBy` and `leaseExpiresAt` is what stops a *running* job: the worker refreshes its lease on a timer inside `keepingLease`, that refresh goes through `holder()`, `holder()` now raises `not_running`, and the raised error is passed to `jobAbort.abort(...)`, which is the signal handed to the provider adapter. No new kill path was invented; the revocation is simply made visible to the one the worker already obeys. On PostgreSQL the same job is fenced a second way: the lease version is bumped inside the revoking transaction, so a heartbeat that lands in the same instant fails with `fence_changed`.

**Delivered records are not touched.** Terminal jobs are skipped. A takedown that rewrote completed job bodies would be falsifying history, which is the other half of the P14 clause.

**The type system is what stops half a takedown.** `ProjectService.takedown` now requires a `GenerationRevoker` and awaits it. That is the whole reason for the signature change: a future caller cannot write the takedown half and forget the queue half, because the code will not compile. Both job stores implement the interface, so the required argument is always something real — the five existing test call sites that have no queue pass `new DurableJobStore(null)`, which is a real, empty store rather than a stub.

**The user-facing notice carries none of the operator's reason.** `GENERATION_REVOKED_NOTICE` is a fixed string with nothing interpolated. The operator's stated reason lives in `takedownLog` and in `hv_projects.takedown_reason`, where it already lived; a revoked job record is not the place for it.

**On PostgreSQL both halves are one transaction.** `PostgresProjectService.takedown` already holds `for update` on the project row inside `state`; `revokeProjectWithin` takes `for update` on that project's non-terminal jobs in the *same* transaction, so a `claimNext` cannot slip between the two halves.

## Acceptance criteria

1. **A takedown stops the project's queued generation.** Every non-terminal job of the project becomes `cancelled` with `GENERATION_REVOKED_NOTICE`, no `claimedBy`, no `leaseExpiresAt`, and the notice appended to `notifications`; `claimNext` never returns one of them again. Satisfies FULL-SCOPE P14 "revocation stops future generation".

2. **A takedown stops a job that is already running, mid-provider-call.** With a provider that blocks inside `generate` until its abort signal fires, a takedown issued while the call is outstanding aborts that call with a `LeaseError` whose reason is `not_running`, and `processNextJob` returns the job as `cancelled` with the revocation notice. No second attempt is made. Satisfies P14 and ADR-0020 fail-closed.

3. **History is not falsified.** A `done` job of the same project keeps its status, its `completedAt` and its output, and gains no `cancelReason`. Another project's queued job is untouched and still claimable. A second takedown of the same project reports `false` and changes nothing. Satisfies FULL-SCOPE P14 "without falsifying history".

4. **A takedown cannot be performed without revoking.** `ProjectService.takedown` requires a `GenerationRevoker` and awaits it. Satisfies CLAUDE.md "Safety refusals … may grow, never shrink" read with ADR-0020: this only adds a refusal.

5. **On PostgreSQL the two halves are atomic and the worker is fenced.** In one transaction, the project becomes a tombstone and its non-terminal jobs are cancelled with the lease version bumped; a worker holding one of those jobs fails its next heartbeat with `fence_changed`; one `job.revoked` outbox event is written per stopped job and none for the delivered or foreign one.

6. **Nothing frozen is touched, and no new dependency, vendor, key, route, account, tier, payment path or budget default appears.** No migration: `revokeProjectWithin` writes only columns that already exist. `docs/loop/STATUS.md` and `docs/PROGRAM-EXECUTION.md` are not in the diff; RECORD owns both.

The JSON rows are one run each of `packages/queue/test/generation-revocation.test.ts` (3 tests); the PostgreSQL rows are one run each of `packages/storage/test/generation-revocation.test.ts` (1 test) against a throwaway PostgreSQL 16 cluster created for this increment — **not** the staging database.

## What this increment does **not** do

- **It does not add a takedown route or any operator surface.** There is none today, which is why these tests are written against the queue and the worker. The primitive has to be correct before a surface lands on it; building the surface is a separate increment and touches the operator-gate discipline.
- **It does not make the worker's mid-render project re-check unconditional.** The audit recommends that as well. `assertPendingContext` still returns early for every job that is not `currentFilm` or `livingScript`, and `context.projects` is still optional — twenty test files construct a worker without it. Making the authority mandatory is a real change with a twenty-file blast radius and belongs in its own increment; **for takedown specifically it is not the chokepoint**, because the revocation reaches the worker through the lease it already obeys rather than through a project read. Stated here so that the remaining hole is on the record: a worker whose `context.projects` is absent still cannot detect any *other* kind of permission change mid-render.
- **It does not close the other HV-031 defects.** Snapshot restore still fabricates the takedown timestamp and reason when the log entry is absent, and `validateSnapshot` still permits that snapshot (MAJOR). The provenance manifest still records a hardcoded 1970 epoch as the assembly time (MAJOR). The content-credential claim string is still a bare literal duplicated across one producer and four verifiers (MINOR). None is touched here.
- **It delivers no part of the rights ledger, legal hold, appeals, image/audio moderation, watermarking, signing or risk challenges.** P14 remains mostly absent and HV-031 stays `in_progress` at most.
