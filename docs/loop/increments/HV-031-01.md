# HV-031-01 — Make a takedown actually stop generation

epic: HV-031
spend_usd: 0

## Goal

Turn `ProjectService.takedown` from a read-side 404 into a revocation, and make the queue half impossible to omit.

Before this increment, `takedown` added the project to `takenDown`, removed it from `projects`, appended to `takedownLog` and persisted. `authorize` and `peekProject` then returned `null`, so no *new* job could be admitted. That was all of it. `packages/queue` contained **no occurrence of the string "takedown"**, so the project's already-queued jobs stayed claimable and its running job kept calling a provider until it finished and wrote a cut. FULL-SCOPE P14 requires that "revocation stops future generation without falsifying history"; neither half was true.

**How this increment was found.** The program-wide re-verification of the pre-loop credit ran one auditor per epic across all 22 epics that had never had the pass `docs/loop/STATUS.md` says the first planner is supposed to run. HV-031 came back `partially-delivered` with one BLOCKER: *"Project takedown does not stop generation: the queue has no takedown awareness, and the worker's mid-render project re-check is conditional."* Verified against the source before any code was written: `grep -ril takedown packages/queue/` returns nothing, and `assertPendingContext` (`worker.ts:222`) returns early for every job that is not a `currentFilm` or `livingScript` job.

## The shape of the repair

**Revocation is not cancellation.** `DurableJobStore.cancel` is a *worker* action: it goes through `holder(id, workerId, now)` and therefore requires the lease of the job it is stopping. Nothing outside a running worker could ever stop that worker's job. A takedown comes from outside the queue — and so, later, will a legal hold, a withdrawn consent and an appeals-driven suspension — so it needs a verb that does not need the lease of the job it is stopping. `revokeProject` is that verb.

**The status transition is the kill switch, and it already existed.** Setting the job terminal is what stops a *running* job: the worker refreshes its lease on a timer inside `keepingLease`, that refresh goes through `holder()`, `holder()` raises `not_running` on the very first check, and the raised error is passed to `jobAbort.abort(...)`, which is the signal handed to the provider adapter. Clearing `claimedBy` and `leaseExpiresAt` is hygiene rather than the mechanism — a perturbation that leaves both set still stops the worker — and it is pinned by a test so the record does not become a lie later. On PostgreSQL the job is fenced a second way: the lease version is bumped inside the revoking transaction, so a heartbeat landing in the same instant fails with `fence_changed`.

**Aborting is delivery, not enforcement, and the guarantee is stated in those terms.** `keepingLease` calls `jobAbort.abort(...)` from its timer but still awaits the outstanding step and only rethrows afterwards, so an adapter that ignores `params.signal` runs to completion. What revocation actually guarantees is narrower and is tested as two separate things: an adapter that honours its signal is aborted mid-call, and **no revoked job can produce a deliverable whatever the adapter does**, because every write that finishes a job goes through `holder()`.

**The detection window is bounded by the lease refresh, and it is not small.** The refresh timer is `max(50, leaseMs / 3)`; the default lease is five minutes, so a revoked project's running job can keep calling a provider for up to **100 seconds** before it is stopped, and `HV_JOB_LEASE_MS` can raise that. The tests set a 1.5-second lease, which compresses the window about 200×. Closing it needs a per-attempt permission read, which is the deferred work named below. Stated here rather than discovered later.

**Delivered records are not touched.** Terminal jobs are skipped. A takedown that rewrote completed job bodies would be falsifying history, which is the other half of the P14 clause.

**What the required argument does and does not buy.** `ProjectService.takedown` requires a `GenerationRevoker` and awaits it, so a caller cannot *omit* the queue half — it will not compile. It does **not** guarantee the argument is a queue holding this project's jobs: `GenerationRevoker` is a structural interface, an empty `DurableJobStore(null)` satisfies it, and nothing in a signature can check that. Perturbation P7 is exactly that bypass, deliberately kept in the table. Every fixture in this diff that owns a real queue now passes it.

**The user-facing notice carries none of the operator's reason.** `GENERATION_REVOKED_NOTICE` is a fixed string with nothing interpolated. The operator's stated reason lives in `takedownLog` and in `hv_projects.takedown_reason`, where it already lived; a revoked job record is not the place for it, and a test asserts no job record in the store contains it.

**Order, and the JSON path's window.** The tombstone is written first, because that is what stops admission; revocation follows, because that is what stops work already admitted. On the JSON path these are separate writes to separate files, so a revoker that throws leaves the project down and its jobs running. That window is real. It is not made permanent: revocation now also runs on the already-taken-down branch, so re-issuing the takedown retries it and reports `false` for the project. `PostgresProjectService` does both halves in one transaction — `state` already holds `for update` on the project row and `revokeProjectWithin` takes `for update` on its non-terminal jobs in that same transaction — and a test observes the difference by holding a lock on one of those jobs from outside and checking that the tombstone has not committed while the lock is held.

## Acceptance criteria

1. **A takedown stops the project's queued generation.** Every non-terminal job of the project becomes `cancelled` with `GENERATION_REVOKED_NOTICE`, no `claimedBy`, no `leaseExpiresAt`, and the notice appended to `notifications`; `claimNext` never returns one of them again. Satisfies FULL-SCOPE P14 "revocation stops future generation".

2. **A takedown stops a job that is already running.** With an adapter that honours its abort signal, a takedown issued while the provider call is outstanding aborts that call with a `LeaseError` whose reason is `not_running`, and `processNextJob` returns the job as `cancelled` with the revocation notice. With an adapter that **ignores** its abort signal, the call runs to completion and the job still ends `cancelled` with **no output**, because the completing write needs the lease. Satisfies P14 and ADR-0020 fail-closed.

3. **History is not falsified.** A `done` job of the same project keeps its status, its `completedAt` and its output, and gains no `cancelReason`. Another project's queued job is untouched and still claimable. A second takedown reports `false` and leaves every job record — status, `completedAt`, notification count — byte-identical, compared against a snapshot taken before the second call rather than against the jobs' agreement with each other. The operator's stated reason appears in `takedownLog` and in no job record.

4. **A takedown cannot omit the revocation, and a failed revocation can be retried.** `ProjectService.takedown` requires a `GenerationRevoker` and awaits it. A revoker that throws leaves the tombstone written and the jobs alive; re-issuing the takedown with a working revoker returns `false` and stops them. Satisfies CLAUDE.md "Safety refusals … may grow, never shrink" — this only adds a refusal.

5. **On PostgreSQL the two halves are one transaction, observably, and the worker is fenced.** A lock held on one of the project's jobs from a second connection blocks the takedown, and the project tombstone has **not** committed while that lock is held. In the same transaction the non-terminal jobs are cancelled with the lease version bumped; a worker holding one of them fails its next heartbeat with `fence_changed`; one `job.revoked` outbox event is written per stopped job, carrying the worker that was fenced, and none for the delivered or foreign one.

6. **Nothing frozen is touched, and no new dependency, vendor, key, route, account, tier, payment path or budget default appears.** No migration: `revokeProjectWithin` writes only columns that already exist. `docs/loop/STATUS.md` and `docs/PROGRAM-EXECUTION.md` are not in the diff; RECORD owns both.

## Demonstrated, not asserted

Ten perturbations, each applied on this branch, measured against the **final** test files, and reverted. The JSON rows are one run each of `packages/queue/test/generation-revocation.test.ts` (5 tests); the PostgreSQL rows are one run each of `packages/storage/test/generation-revocation.test.ts` (2 tests) against a throwaway PostgreSQL 16 cluster created for this increment — **not** the staging database, and not any database this repository's deployments use.

| perturbation | result |
|---|---|
| P1 — `takedown` never calls the revoker (the defect exactly as it shipped) | `1 pass / 4 fail` |
| P2 — revocation also rewrites terminal jobs | `3 pass / 2 fail` |
| P3 — revocation spares a job that is already running | `1 pass / 4 fail` |
| P4 — the notice carries the operator's stated reason | `2 pass / 3 fail` |
| P5 — revocation leaves `claimedBy` and `leaseExpiresAt` in place | `4 pass / 1 fail` |
| P6 — a takedown whose revocation failed cannot be retried | `4 pass / 1 fail` |
| P7 — the PostgreSQL takedown passes a revoker that does nothing | `0 pass / 2 fail` |
| P8 — revocation does not move the lease fence | `1 pass / 1 fail` |
| P9 — revocation writes no outbox event | `1 pass / 1 fail` |
| P10 — the two PostgreSQL halves become two transactions | `1 pass / 1 fail` |

P3 is the most plausible wrong implementation — "do not disturb a running worker" — and it is the one that leaves the BLOCKER open, so it is deliberately in the table.

**Two of these rows are corrections to an earlier draft of this increment.** P5 originally *passed*, which proved that the draft's claim — "clearing `claimedBy` and `leaseExpiresAt` is what makes a running job stop" — was false: the status transition alone stops it, because `holder()` checks status first. The claim is corrected above and the fields are now pinned by a test. P6 also originally passed, because the retry branch did not exist and nothing tested it; the branch was added and a test written for it. P10 did not exist at all: criterion 5 claimed atomicity while every assertion in the suite inspected only end state, which one transaction and two produce identically.

## What this increment does **not** do

- **It does not add a takedown route or any operator surface.** There is none today, which is why these tests are written against the queue and the worker. The primitive has to be correct before a surface lands on it; building the surface is a separate increment and touches the operator-gate discipline.
- **It does not make the worker's mid-render project re-check unconditional, and that is what leaves the 100-second window open.** The audit recommends it. `assertPendingContext` still returns early for every job that is not `currentFilm` or `livingScript`, and `context.projects` is still optional — twenty-one of the fifty test files that call `processNextJob` construct a worker without it. Making the authority mandatory is a real change with a twenty-one-file blast radius and belongs in its own increment. For takedown the lease is a sufficient chokepoint, but it is a *slow* one: up to `leaseMs / 3`, which is 100 seconds at the default lease. A per-attempt permission read is what shortens that to one attempt, and it is also the only thing that would catch any *other* kind of permission change mid-render.
- **It does not close the other HV-031 defects.** Snapshot restore still fabricates the takedown timestamp and reason when the log entry is absent, and `validateSnapshot` still permits that snapshot (MAJOR). The provenance manifest still records a hardcoded 1970 epoch as the assembly time (MAJOR). The content-credential claim string is still a bare literal duplicated across one producer and four verifiers (MINOR). None is touched here.
- **It delivers no part of the rights ledger, legal hold, appeals, image/audio moderation, watermarking, signing or risk challenges.** P14 remains mostly absent and HV-031 stays `in_progress` at most.
