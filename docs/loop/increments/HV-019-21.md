# HV-019-21 — Prompts are counted as strictly as fal's validator may count them, and a 422 is not retried (Release 3, G23)

epic: HV-019
release: 3 "Features"
gate: none new
spend_usd: 0

## Why

HV-019-20 (#381) was deployed and the run was resumed again at 08:15. Shots 1-8 were reused. Shot 9
(`shot-2-1`) was refused again with the same 422: "prompt: size must be between 0 and 2500". The operator
read the refused request back from fal. The prompt fal echoed is
`packages/queue/test/fixtures/fal-received-shot9.txt`:

| Measure of the echoed prompt | Size |
|---|---|
| UTF-16 units | 2,491 |
| Code points | 2,491 |
| UTF-8 bytes (HV-019-20's measure) | 2,499 |
| JSON-escaped, non-ASCII kept | 2,516 |
| JSON-escaped, non-ASCII as `\uXXXX` | 2,536 |
| `promptSize` (HV-019-21) | 2,600 |

- It is exactly the prompt the worker planned, with O3's four-image note: 25 line breaks and 4 curly quotes.
  So whatever checks it counts more than every plain measure of that string.
- No fal or Kling schema in this repository says how the prompt is counted.
- "size must be between 0 and 2500" is the default message of a Java `@Size` check. That check counts the
  characters of the string it gets, so the string it got was longer than the one fal echoed.
- There are two plausible ways it could be longer. The prompt may be counted as escaped JSON, or fal may
  rewrite the four `@ImageN` tokens before forwarding.
- Shot 9 was sent three times, once per job retry, and the ledger booked $0.588 for each.

## What this increment does

- **`promptSize` counts both possibilities.** It counts a prompt as JSON writes it with every non-ASCII
  character escaped: line breaks, tabs, quote marks and backslashes are 2, and other control and non-ASCII
  characters are 6. It adds 16 for each `@ImageN` token, more than any bracketed image name.
- **Why 16.** The margin is justified by the evidence above. It costs 64 characters on a four-image shot.
- **The size is a sum over the text**, so the image note's size comes off the limit: O3 reference takes 2,315
  from the planner with four images.
- **Everything uses it.** The fit, the mock and the fal guard all use `promptSize`. The guard measures the
  `prompt` field of the serialized request body.
- **The fit record is `hv-prompt-fit/3`**, with `originalSize`, `fittedSize`, `fromSize` and `toSize`.
- **Typographic quotes are not normalised.** Doing it to every prompt would change shots 1-8: each one
  carries WREN's cast direction, which quotes the script in curly quotes. So all eight would be re-rendered,
  at $0.42-0.59 each. The new measure already counts each quote as 6.
- **A fal 422 is permanent.** It is `FalInputRejectedError` (name `FalInputRejected`). The router and the
  failover don't try another provider for it, and the worker cancels the job naming the shot. A
  `PromptLengthError` is cancelled the same way. After `COMPLETED`, the render is still booked as billed,
  once, because whether fal bills a refused input is not known.
- docs/PROVIDER-ROUTING.md has both notes under "Prompt limits".

**Shots 1-8 keep their input hashes and stay reused.** Their sent sizes by the new measure are 2,425,
2,375, 2,328, 2,333, 2,384, 2,344, 2,351 and 2,330. None is over 2,500, so none is fitted. Their prompts are
unchanged and every recorded `inputHash` still matches. No shot of 1-8 changes.

**Shot 9 and the rest of the sequence.** Shot 9 is now sent at 2,390 characters, 2,499 by `promptSize`.
Every other shot of sequence 1 is at most 2,500 by it.

## Acceptance criteria

1. **The counter-example fails the new measure.** The prompt fal echoed is 2,491 characters, 2,491 code
   points, 2,499 UTF-8 bytes and 25 line breaks. It is within HV-019-20's measure, 2,516 JSON-escaped and
   2,600 by `promptSize`. The fal adapter refuses that exact body field with zero requests.
2. **Shots 1-8 are unchanged.** Every recorded `inputHash` in the job's shot reuse equals the current one, and
   `validateReusePlan` passes.
3. **Shot 9 fits.** As fal receives it, shot 9 is at most 2,500 by `promptSize`, and so is every shot of the
   sequence. Its fit record is `hv-prompt-fit/3`.
4. **The guard uses the measure.** The fal adapter refuses anything over its limit by `promptSize` before any
   request: one over with no images, with one image and with four. At the limit exactly, it sends. The mock
   refuses the same prompts.
5. **A 422 is not retried.** With retries allowed, a fal 422 at result time cancels the job naming the shot.
   It is not requeued, there is one submit, the secondary is never called, and $0.35 is booked once.
6. **Reverting the change fails the new tests.**
   - Restoring `prompt-limits.ts` from main fails the counter-example test.
   - Restoring `worker.ts` and `router.ts` from main fails the 422 test.
   - Restoring all six sources fails the file on its imports (checked).

## Known gaps

- **The measure is the strictest plausible, not fal's documented one.** A prompt could still be refused if
  fal rewrites the tokens by more than 16 characters each, or adds text of its own. If that happens, it is
  now one refusal, booked once, and the job is cancelled.
- **Prompts are cut a little more than fal may need.** A four-image shot loses up to 185 characters to the
  note's allowance.
- **Whether fal bills a 422 after `COMPLETED` is not known.** It is still booked as billed.
- **Only fal's 422 is permanent here.** Other 4xx answers (rate limits, auth) keep the existing retry.
