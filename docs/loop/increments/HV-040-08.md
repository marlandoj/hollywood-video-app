# HV-040-08 — The sweeper asked an unindexed question, twice per object, every hour

epic: HV-040
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

`PostgresRetention`'s orphan sweep walks the object store and asks, for every key it finds, whether
any row still references it (`packages/storage/src/retention.ts:151-152`):

```sql
select key from hv_artifacts where object_key = $1 limit 1
select id  from hv_archives  where object_key = $1 limit 1
```

`0004_artifact_objects.sql` added `object_key` with a bare `ALTER TABLE ... ADD COLUMN`. No index was
ever added, on either table, and nothing in the repo said so. Measured against the **staging
cluster** — a temporary table with the real key shape and 200,000 rows, so it touches no staging
data and vanishes with the session:

```
=== 200,000 rows, no index on object_key ===
Limit  (cost=0.00..5577.00 rows=1) (actual time=15.165..15.166 rows=1 loops=1)
  ->  Seq Scan on t_artifacts  (actual time=15.163..15.164 rows=1 loops=1)
        Rows Removed by Filter: 123455
        Buffers: local read=1900 written=1019
Execution Time: 15.177 ms

=== the same query, indexed ===
  ->  Index Scan using t_artifacts_object_idx  (actual time=0.028..0.029 rows=1)
        Buffers: local read=4
Execution Time: 0.043 ms
```

```
no index  | hit 15.49 ms | miss 23.01 ms
indexed   | hit  0.34 ms | miss  0.15 ms
```

A **miss is the sweeper's normal case**: an orphan is the thing it is looking for, and an orphan
misses in both tables — which is also the worst case for a sequential scan, because a miss reads the
whole table rather than stopping at the first match. The sweep runs hourly over up to 200,000 keys
and probes both tables per key: about **2.6 hours of query time per hourly sweep** at that size,
against roughly a minute with the indexes. It runs as `hv_worker`, whose RLS policy on these tables
is `using (true)`, so no project predicate narrows the scan either.

Staging's `hv_artifacts` and `hv_archives` are empty today (0 rows each), and confirmed to carry no
`object_key` index — so this is a cost that arrives with the first real volume, not one already
being paid.

## What this increment does

- **Two btree indexes**, `hv_artifacts_object_key_idx` and `hv_archives_object_key_idx`, on the
  column the sweeper probes, declared in `packages/storage/src/schema.ts` and created by
  `infra/drizzle/0017_object_key_indexes.sql`.
- **A guard that the two descriptions of the database agree.** The defect was a column added by a
  migration with no index behind it and nothing saying so; the general form of that defect is the
  schema and the migrations disagreeing. The test reads both and asserts the index sets are equal in
  **both directions** — 21 declared, all created, none created that is not declared.
- **A guard that the journal names every migration file, in order, once.** A migration file the
  journal does not name is never applied, which is the same defect one step further along: an index
  that exists in the repo and not in the database.
- **And a check against a real cluster**: after `migrate()`, both indexes exist on `object_key`, and
  `EXPLAIN` on the sweeper's own query names `hv_artifacts_object_key_idx` rather than a seq scan.

## Acceptance criteria

1. **Every index the schema declares is created by a migration**, and every index a migration creates
   is declared by the schema — the set equality, both directions.
2. **The two the sweeper needs are among them by name**, in both the schema and the migrations.
3. **The journal names every `.sql` file in `infra/drizzle`**, and no file the journal names is
   missing.
4. **The journal's indices are `0..n-1` in order** — it is zero-indexed, and an entry out of sequence
   is an unapplied migration waiting to happen.
5. **After `migrate()` against a real PostgreSQL, both indexes exist** and are on `(object_key)`.
6. **The planner uses one for the sweeper's own query** — `EXPLAIN select key from hv_artifacts where
   object_key = $1 limit 1` names `hv_artifacts_object_key_idx`.
7. Reverting `schema.ts` makes criteria 1 and 2 fail (declared ≠ created); reverting the migration
   file makes 1, 2 and 3 fail; reverting the journal entry makes 3 fail.

- Test: `packages/storage/test/object-key-index.test.ts`. Criteria 5 and 6 run only with
  `HV_PG_ADMIN_URL` and `HV_API_DATABASE_URL` set, which is the repo's existing convention for
  cluster-backed tests; 1–4 run everywhere, including CI.

## Known gaps this leaves

- **A plain `CREATE INDEX` takes an ACCESS EXCLUSIVE lock.** `CREATE INDEX CONCURRENTLY` would not,
  but it cannot run inside a transaction, and drizzle's migrator wraps each file in one. Free today,
  because both tables are empty on staging and the lock is held for the length of a build over zero
  rows — but a consideration for the same statement against a large table later, and the reason it is
  written down here rather than discovered then.
- **The repo's drizzle snapshots are stale.** `drizzle-kit generate` emits a large unrelated drift
  (RLS enables, a dropped and re-added check constraint, a new column, policies) because snapshots
  exist only for 0006 and 0007. So this migration is hand-written, as every migration since 0008 has
  been. The set-equality guard above is the check that hand-writing did not go wrong; regenerating
  the snapshots is its own increment and is not attempted here.
- **Only the two columns the sweeper probes.** The same pass found no other unindexed predicate on a
  hot path, but the guard added here proves *agreement* between schema and migrations, not
  *sufficiency* of the indexes for every query the code issues. Nothing yet reads the query text and
  asks whether an index covers it.
- **The measurement is a temp table, not these tables.** A temp table gets the same planner and the
  same btree, but no RLS and no concurrent write load. The ratio is what is claimed here — three
  orders of magnitude on a miss — not the absolute milliseconds on a production-sized
  `hv_artifacts`.
