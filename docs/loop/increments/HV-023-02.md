# HV-023-02 — A coverage edit scanned the scene once per beat it named

epic: HV-023
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

A critic pass over the editorial planner, recorded during HV-016-04 and built now.

`sceneCut` checks that every beat a coverage shot names belongs to the scene it is covering. It
checked it like this, inside the per-shot map (`scene-cuts.ts:41`):

```ts
shot.beatIds.some(id => typeof id!=="string" || !narrative.some(b => b.id===id))
```

`narrative.some` walks the whole scene. So the check cost **ids × beats**, and both numbers are
large and are set by different things:

- `validateSource` permits **10,000 beats** in a scene, and a 10,000-beat scene is an ordinary
  screenplay of about 40,000 characters, well inside the script route's 200,000-character limit.
- the shot list permits **60 shots** of up to 10,000 ids each, and `reviewSceneCut` takes those
  shots from the request body under `jsonBody`'s **250,000-byte** limit — which holds about 15,500
  beat ids.

The scene the ids are checked against is the server's own parse of the saved screenplay, not part of
the body, so the two bounds multiply rather than trading off.

**Measured**, on a 10,000-beat scene with a **248,401-byte** body — inside the route's own limit —
carrying 15,480 ids that each name a real beat and do not cover the scene:

```
before   580 ms   to produce a 400
after     30 ms
```

The api bucket is 120 requests a minute. One address was entitled to **69.6 seconds of blocked CPU
per 60-second window** on a single-threaded server, from a route it is allowed to call, for
responses that are all refusals.

The ordinary path was quadratic too, because a scene's own coverage names each of its beats exactly
once — that is what the "cover every beat exactly once" rule requires:

| beats in the scene | before | after |
|---|---|---|
| 1,000 | 9.0 ms | 5.9 ms |
| 2,000 | 14.3 ms | 8.9 ms |
| 4,000 | 39.2 ms | 17.0 ms |
| 8,000 | 160.0 ms | 32.5 ms |
| **10,000** | **299.6 ms** | **38.3 ms** |

Approaching fourfold per doubling before; the doubling itself after. And `validateSceneCuts` runs
`sceneCut` again for every accepted cut in the library, from `directionSnapshot` — which is built on
every direction save — so the per-scene figure is paid once per scene of the film, not once.

Isolating the check from the scene's own validation, on one 8,000-beat scene, 60 ids against 6,000:

```
before   9.0 ms  ->  172.4 ms
after    7.8 ms  ->    9.9 ms
```

## What this increment does

- **The membership check is a set.** `narrative`'s ids are collected once per call and each shot's
  ids are tested against it. The refusals are unchanged, by message: an id that names no beat, an
  id from another scene's numbering, an id that is not a string, and an id naming a transition beat
  — which is not narrative and so may not be covered — all still throw
  `Choose source beats from this scene.`
- **The scene-numbered shot-id pattern is compiled once.** It depends on `source.sceneIndex`, not on
  the shot, and it was being built inside the same per-shot map. It still follows the scene it was
  built for, which the test asserts by running scene two's cut against scene one's ids.

Nothing else changes. `sceneCut` is a validator that returns a content-hashed record, so a behaviour
change would move every stored cut's revision; the scene-cuts suite is the assertion that it did not.

## Acceptance criteria

1. **The check costs the ids, not the ids times the scene**, measured as two runs against the *same*
   8,000-beat scene with sixty ids and six thousand — so the comparison is between two measurements
   on one machine rather than against a number that depends on the runner.
2. **A body the route itself would accept is refused in a bounded time**: a 10,000-beat scene and a
   body under 250,000 bytes carrying more than 15,000 real beat ids, refused with its own message.
3. **Every refusal it made before it still makes**, by message — four shapes of bad beat id, three
   of bad shot id — and a valid cut still round-trips through `validateSceneCut`.
4. **The scene-numbered pattern is built once and before the shot loop**, asserted over the source
   with comments stripped, together with the set having replaced the scan.
5. Reverting `scene-cuts.ts` makes 1, 2 and 4 fail; 3 passes either way, which is its job.

- Tests: `packages/planner/test/scene-cut-cost.test.ts`, and `packages/planner/test/scene-cuts.test.ts`
  unchanged for the behaviour.

## Known gaps this leaves

- **`sourcePlan` has the same shape one function over.** It resolves each shot's beats with
  `shot.beatIds.map(id => cut.source.beats.find(b => b.id===id))` (`scene-cuts.ts:~100`), which is
  the same scan, over the same two bounds, for every accepted cut in the film. It is not in this
  increment because it runs on cuts that have already been accepted — so the ids are the scene's own
  and the count is the scene's own, not a caller's — and because it is on the render path rather
  than a request path. It is a Map away and deserves its own measurement.
- **`validateSource` is still linear per call and called repeatedly.** An 8,000-beat scene costs
  about 7.8 ms to validate before any id is checked, and `validateSceneCuts` pays that for every cut
  in the library on every `directionSnapshot`. That is the remaining cost in the table above, and
  memoizing it is the HV-023-01 pattern applied one level up.
- **The 10,000-beat and 60-shot limits are unexamined.** This increment makes the work linear in
  them; it does not ask whether a scene with ten thousand beats is a thing the studio should accept.
- **`appendEdit` still replays an edit history from the root**, which HV-023-01 left and which is
  the larger of the two editorial costs: 5.8 s for one `PATCH` at 999 events, measured after
  HV-023-01's memo, because the history it produces is new content the memo has never seen. It is
  its own increment.
