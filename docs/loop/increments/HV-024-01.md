# HV-024-01 — Pin the sound lane's re-derived identity, and tie the two closed stem sets together
epic: HV-024
spend_usd: 0

## Goal

Pin the values a delivered sound record is validated against — five recipe revisions **and** the rendered FFmpeg filter string that a recipe hash does not cover — and assert that the two closed stem sets declared in different files are the same set rather than two sets that happen to agree. No behaviour changes.

**How this increment was found.** A program-wide re-verification of the pre-loop credit ran one auditor per epic across all 22 epics that had never had the pass `docs/loop/STATUS.md` says the first planner is supposed to run. It found this defect family — a content-hashed identity pinned into an already-delivered record with nothing guarding it — for the sixth time in this program. HV-019-01 found one. HV-019-03 found five in the performance lane. HV-025-01 closed the graphics lane. This is sound.

**What is pinned into delivered sound records.** `validateSoundOutput` refuses a record whose `report.recipeRevision` differs from `contentHash(SOUND_MIX_RECIPE)`; the finishing and restoration reports re-derive `contentHash(SOUND_FINISH_RECIPE)` and `contentHash(RESTORATION_RECIPE)` the same way; `validateNarrationMix` re-derives `NARRATION_MIX_RECIPE_REVISION`, and that report is re-validated inside delivered dialogue-replacement records; and `SOUND_CONVERSION_RECIPE` is the recipe half of `soundRuntimeRevision()`, stored as `engineVersion` on every sound asset, plan and report. Five constants, all living in the repository, all edited like ordinary configuration, all guarded by nothing.

**A recipe hash is not the whole identity, which the first draft of this increment got wrong.** `validateRestorationReport` re-derives the *entire FFmpeg filter string* per track and refuses any mismatch — and most of that string is bare literals that do not appear in `RESTORATION_RECIPE` at all (`nt=w`, `tr=0`, `ad=0.5`, `nl=average`, `bm=1.25`, `om=o`). Editing `bm=1.25` makes every delivered restoration record unreadable without moving the recipe hash by a single bit. The rendered string for a fixed probe track is therefore pinned alongside the recipes; verified on this branch, that edit now fails the guard. The finishing lane has the identical shape in `processingFilter` / `filterTarget`, which are module-private: pinning their output would need an export, which is a source change this no-behaviour-change increment does not make, so they are **declared** in the evidence as a known uncovered surface with the consequence spelled out.

**Demonstrated, not asserted.** On this branch, adding one field to `SOUND_MIX_RECIPE` — the value every delivered sound version is validated against:

```
nine existing sound suites   24 tests   22 pass  2 skip  0 fail  447 expect() calls
sound-identity.test.ts (new)                                     1 fail
```

That is the defect: the expectation is derived from the same live constant as the code, so the suite cannot notice. The consequence is not a failed render — it is that every sound version already delivered becomes permanently unreadable, on content-addressed records that cannot be rewritten without breaking their own seals.

**The second half closes a related defect.** `RESTORATION_TRACKS` and `RESTORATION_STEMS` are declared in `packages/planner/src/sound-restoration.ts`; `SOUND_ROLES` and `SOUND_STEMS` are declared in `packages/planner/src/sound-session.ts`. They agree today by coincidence of maintenance, not by construction, and `generator/src/sound-restoration.ts` indexes the restoration outputs positionally, so the *order* is load-bearing as well as the membership. Every remaining P9 clause — score, foley and SFX, ambience beds, auto-spotting — must widen the cue roles. Today that edit leaves every unit test green, and its two real consequences are worse than they look: a non-restoration mix *renders*, but `packages/generator/src/sound-mixer.ts` hardcodes the three role names when summing (`me = music + ambience + effects`), so the new stem is written to disk and silently omitted from both summed stems — a wrong deliverable, not a failure; and a restoration session dies with a raw `ENOENT`, because the raw stems are written for `SOUND_STEMS` while only `RESTORATION_TRACKS` are restored, and the digest step then opens a file that was never produced.

## Acceptance criteria

1. **Every recipe revision a delivered record pins is committed and re-derived on every run, and so is the rendered filter a recipe hash does not cover.** `docs/evidence/hv024-sound/recipe-revision-pins.json` (schema `hv-sound-recipe-pins/1`) records five recipes — `SOUND_MIX_RECIPE`, `SOUND_FINISH_RECIPE`, `RESTORATION_RECIPE`, `NARRATION_MIX_RECIPE` and `SOUND_CONVERSION_RECIPE` — each with its constant name, its own `schema` string, `contentHash(...)`, and the record field it is pinned into together with the validator that re-derives it. It also records `renderedFilters` (the `restorationFilter` output for a fixed probe track, with the validator that re-derives it) and `unpinnedReDerivedValues`, which names the module-private finishing filter as a known uncovered surface with the reason and the consequence. The file is written when `HV_SOUND_PINS_EVIDENCE` names a path and **re-validated on every test run including CI**, which sets no such variable. The env value is resolved against the repo root and asserted to equal the committed path, so regeneration from another working directory cannot silently write a stray file and report success. Satisfies FULL-SCOPE §10 "Evidence before promotion: tests, benchmarks, post-flight evals, gap audits." and CLAUDE.md "Never fabricate launch, legal, or provider evidence."

2. **The two closed stem sets are asserted equal, in order.** A test asserts `RESTORATION_STEMS` equals `SOUND_STEMS`, that `RESTORATION_TRACKS` equals `["dialogue", "narration", ...SOUND_ROLES]`, that `SOUND_STEMS` equals `[...RESTORATION_TRACKS, "me", "mix"]` — order included, because the restoration filter indexes its outputs positionally — and that the stem set has no duplicate. Widening the cue roles in one file now fails here rather than at the first restoration session. Satisfies §10 "Provider independence and versioned adapters." read with ADR-0020 fail-closed.

3. **The rendered restoration filter is pinned, and the gap it closes is named in the test itself.** A test calls the same exported `restorationFilter` that `validateRestorationReport` calls, asserts the recipe-derived values appear in the rendered string (which is why pinning the recipe *felt* sufficient), and then asserts for each of the six bare literals that it is present in the rendered string and absent from the recipe — so the reason the recipe hash is insufficient is an assertion rather than a comment. An earlier draft asserted instead that adding a field to a recipe changes its `contentHash`; that was a tautology about `contentHash` which would pass for any object, and it is gone. Satisfies CLAUDE.md "Every criterion gets a real test."

4. **The evidence file carries no credential, destination or host path, and its honesty fields are explicit.** The file matches none of `://`, `API_KEY`, `/home/`, `/Users/`, `/tmp/`, and every 32+ hex run in it is one of the three pinned revisions. It carries `behaviourChanged: false`, `newProviderSpendUsd: 0`, `provesLoudnessQualification: false` and `provesRestorationQuality: false` — the last two because the shipped sound docs are explicit that R128/A-85 qualification has not been passed, and this increment does not change that. Satisfies ADR-0018's identifier discipline and CLAUDE.md "Never fabricate … evidence."

5. **No behaviour, frozen path, dependency, budget default, account, vendor, migration, route or user-facing surface changes.** `packages/planner/src/sound-session.ts`, `sound-finishing.ts`, `sound-restoration.ts`, `sound-jobs.ts` and `packages/generator/src/sound-restoration.ts` are **not in the diff**, and the frozen-path check names them on purpose. The diff touches nothing under `docs/legal/**`, `docs/adr/**`, `.github/workflows/**`, `packages/safety/**` or `infra/drizzle/**`; adds no `package.json` or lockfile entry, no HTTP route or request field, no cookie, tracking, account, tier or payment path; and changes no budget default. No audio is rendered, no FFmpeg is invoked, no provider is constructed and no key is read. `docs/loop/STATUS.md` and `docs/PROGRAM-EXECUTION.md` are not in the diff; RECORD owns both. Satisfies FULL-SCOPE §10 "Free and anonymous for every end user; no billing code reachable." and the EXECUTION-LOOP frozen list.

## Out of scope

- **Widening the cue roles** for score, foley, ambience or auto-spotting. Tying the sets together makes *divergence* fail loudly; it does **not** by itself make widening safe. Two hardcodings still silently drop a new role from the summed stems, and both must be fixed in the widening increment: `packages/generator/src/sound-mixer.ts`, which sums `me` from the three role names literally, and the positional `values[2..4]` indexing in `packages/generator/src/sound-restoration.ts`.
- **Deriving `RESTORATION_STEMS` and `RESTORATION_TRACKS` from `SOUND_STEMS` and `SOUND_ROLES`** rather than asserting they agree, and replacing the positional indexing and the hardcoded role sum with named lookups. All are the right repair and all are behavioural changes to code that produces delivered records; this increment's pins are what will prove they moved nothing.
- **Exporting `processingFilter` / `filterTarget` so the finishing filter can be pinned like the restoration one.** Declared in the evidence as uncovered; closing it needs a source change and belongs with the finishing work.
- The two MINOR defects the audit raised in this lane: `RESTORATION_RECIPE`'s hop and tail-padding values duplicated as literals inside `restorationFilter`, so a retained receipt can describe processing that did not run; and the 2048 voice-window bound enforced only at seal time, so a dialogue-dense cut burns a full mix, AAC encode and HLS package before failing with a non-actionable message.
- Any loudness qualification, restoration quality evaluation, render or FFmpeg invocation.
