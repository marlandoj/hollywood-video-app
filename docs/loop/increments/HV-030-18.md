# HV-030-18 — Pressing again after a lost reply admitted, and charged for, a second render

epic: HV-030
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

A critic pass over `packages/frontend`.

The Director's desk asked for both of its picture renders with a key minted on every press:

    body: JSON.stringify({ idempotencyKey: crypto.randomUUID(),...reuseOptions() }),                            // Create film
    body: JSON.stringify({ idempotencyKey: crypto.randomUUID(), stage: "final", animaticJobId,...reuseOptions() }), // Approve and generate

`POST /projects/:id/jobs` answers a repeated key with the job it already admitted. A fresh UUID is
never repeated. So suppose the server admits the render and the reply is lost: a dropped connection,
a gateway 502, or a laptop lid closed. The desk shows the error and re-enables Create film. The
creator's next press is admitted as a second render of the same film, and charged again. On the
final, that second render is the expensive one.

Sending no key would not fix this. The server would derive one from the versions, but the route
returns the existing job for a key whatever its status. A render that *failed* could then never be
asked for again at the same versions.

## What this increment does

- **The desk keeps the key of a render request whose outcome is unknown**, with what the request
  asked for, as HV-017-14 does for character sheets. What it asked for is the project, the saved
  screenplay, the cast and direction versions, the stage, and the reuse options (including forced
  shots). There is one such key per stage. Asking for the same render again resends that key, so the
  server returns the render it may already have admitted.
- **Once the server answers, the key is dropped.** An answer is a job id, or a 4xx that admitted
  nothing. A lost reply (a network error or a 5xx) keeps the key. After an answer, the next request
  gets a fresh `crypto.randomUUID()`, so a render that later fails can be asked for again.
- **A final is keyed by its versions, not by its preview.** The animatic only approves a screenplay,
  cast and direction, so the final is the same render whichever preview of those versions approved
  it. After a lost final reply, the creator's only way back in the page is Create film, then approve
  the new preview. That path resends the final's key, and the server returns the final it already
  has.

## Acceptance criteria

1. **A lost preview reply.** The first preview request is admitted and its reply lost. Pressing
   Create film again sends the identical body with the same key. One preview is admitted, and it is
   shown for approval.
2. **A lost final reply.** The first final request is admitted and answered with a 502. The creator
   presses Create film and approves the new preview. The final request resends the same key, one
   final is admitted, and the export completes.
3. **A failed render can be asked for again.** The first reply is lost, the retry resends the key
   and finds the render, and the render then fails. The next Create film sends a new key, and a
   second preview is admitted and shown.
4. **A different render gets a different key.** The first reply is lost and the screenplay is then
   edited. The next request sends a new key, and a lost reply to that one is retried with its own
   key. One preview of each screenplay is admitted.
5. Reverting `index.html` fails criteria 1, 2, 3 and 4.

- Tests: `packages/frontend/test/desk-retry-key.test.js`. It runs `index.html`'s own module script
  through `packages/frontend/test/desk-page.js`, against a fake `POST /jobs` that applies the route's
  rule for repeated keys.

## Known gaps this leaves

- **The key lives in the page.** A reload forgets it. After a lost reply, the safe path is still to
  reopen the project link: `resumeProject` finds an admitted render as the project's active job and
  waits on it rather than asking again. A render that was admitted and has already finished or
  failed is handled by the resume branches as before.
- **Create film after an answered preview is a new preview.** This matches the desk's behaviour
  before this increment: once the server has answered, the desk does not dedupe a second press of
  the same preview. That is the price of being able to retry a failed one.
- **The screenplay is compared by its saved text, not its version.** The desk does not track the
  script version. An edit that is reverted to the same text before the next press counts as the same
  request, and it would resend a lost request's key for a render of identical text.
- **The route still does not compare a request hash** (HV-030-07's gap). A key the desk resends
  always carries the same request, except that a final may name a different approving preview. In
  that case, returning the existing final is the intended result.
