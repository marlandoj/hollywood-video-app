# HV-030-34 — A feature's join reads its films from the object store (Release 3 step 15's rehearsal)

epic: HV-030
release: 3 "Features"
gate: none new
spend_usd: 0

## Why

Release 3's third $0 rehearsal was the first time a feature reached its join on staging. After all 10
sequences finished, "The Editor is joining the 10 sequences into one film" queued a `feature-film` job
(HV-030-30). Worker-3 claimed it at 23:09:44 UTC and then did nothing for 50 minutes and more:

- The worker was idle (about 1% CPU). The job stayed `running`, its lease renewed, under a 4-hour timeout.
- Its scratch directory (`.feature-film-XXXX`, made at 23:09:47) stayed empty. The first source,
  `film-1.mp4`, never wrote a byte.
- The worker had no open connection to the object store (port 59000), only to PostgreSQL and the
  OTel collector. Nothing was in flight; a promise simply never settled.

Staging runs `HV_ARTIFACT_STORAGE=s3`. There the worker read each source with
`Bun.write(path, await artifacts.response(...))`. `PostgresArtifactStore.response` answers a Response
whose body is the Bun S3 client's stream. Every other worker path that reads the store (shot reuse,
the final's dialogue) streams `response.body` into a writer and checks the size and sha256. The join
neither streamed that way nor checked the bytes. No test ran the join on the object store, so CI
never saw it.

**The measured cause.** On the pinned Bun (1.4.0), `Bun.write(path, response)` never settles when the
Response's body is a stream. Reproduced here against an S3-compatible server on loopback, with Bun's
own `S3Client`, as `PostgresArtifactStore.response` builds it:

| Read | After 4–5 s |
|---|---|
| `Bun.write(path, new Response(s3.file(key).stream()))` | pending, 0 bytes on disk (the store saw 1 request) |
| `Bun.write(path, new Response(<JS ReadableStream of 10 bytes, closed>))` | pending |
| `Bun.write(path, await fetch(url))` | resolved |
| the same S3 Response, `response.body` through `Bun.file(tmp).writer()` | resolved, 300,000 bytes |

So the staging hang is `Bun.write` itself, not the store. The job had no bound of its own on the read:
only the 4-hour timeout, which is checked between steps, never during one.

## What this increment does

- **`copyStoredArtifact`** (`packages/queue/src/stored-artifact.ts`) copies one artifact out of the
  object store, the way shot reuse and the final's dialogue do:
  - it asks `artifacts.response` with the job's signal, and refuses a missing record or a non-200;
  - it reads the store's record from the `etag` and `content-length`, and refuses it if it differs from
    the size and sha256 the source's own job recorded;
  - it streams the body chunk by chunk into `Bun.file(tmp).writer()`, counting and hashing, and refuses
    a stream longer than the record;
  - it checks the size and sha256 at the end, then renames the file into place. On any failure the
    partial file is removed and the stream is cancelled.
- **Every wait is bounded.** The record lookup and each chunk's read wait no longer than the job's
  abort signal, its deadline, or 120 s with nothing sent (`STORED_ARTIFACT_STALL_MS`). A stalled stream
  fails the job instead of holding its lease for 4 hours.
- **The feature-film worker uses it** for each film, caption file and graphic. The expected size and
  sha256 come from the source's recorded files: a dialogue replacement, lip-sync version or sound mix
  lists its files in its output, and a graphic in its `graphicOutput` (the copy re-read and checked
  against the admitted revision just before). A plain final lists none, so the store's checksummed
  record is the expectation. Each failure names the source: "Sequence 2's film failed its checksum: …",
  "Sequence 3's caption file is missing from the object store."
- **The local path is unchanged.** On this host's disk the worker still reads each source in place.
- docs/CREW.md says so in the feature's film section.

## Acceptance criteria

1. **The cause is shown.** On the pinned Bun, `Bun.write` on the store's own Response is still pending
   after 2 s with nothing written, while `copyStoredArtifact` copies the same object with its size and
   sha256 checked and leaves no partial file.
2. **The join completes on the object store.** Three sequence films (two finals and a dialogue
   replacement) and an opening title are read through the real `PostgresArtifactStore.response` and
   Bun's S3 client, each once, and joined into one 5.2 s film. The export is published and the scratch
   directory is removed.
3. **A bad source fails the join and says which.** A film whose bytes were changed, a caption file whose
   store record differs from its job's record, a film cut short and a caption file with no record each
   fail the join with a message naming that source. Nothing is published and no scratch is left.
4. **A stalled source never hangs.** A film whose stream stops part-way fails the join when the job's
   signal is aborted, and at the job's deadline, within seconds. A stream that sends nothing for the
   stall bound fails the copy.
5. **Reverting the change fails the new tests.** Restoring `packages/queue/src/feature-film-worker.ts`
   from `main` (and removing `stored-artifact.ts`) fails all three tests in
   `feature-film-object-store.test.ts`: each join is still pending at its bound, as on staging.
   `stored-artifact.test.ts` fails on the module it imports (checked).

- Tests: `packages/queue/test/stored-artifact.test.ts` (1, 4; 2 pass),
  `packages/queue/test/feature-film-object-store.test.ts` (2, 3, 4; 3 pass). Unchanged and passing:
  `packages/api/test/studio-feature-join.test.ts` (1 pass, 1 skipped without the graphics browser),
  `packages/api/test/artifact-permission.test.ts` and `packages/api/test/feature-interchange.test.ts`
  (7 pass).

## Known gaps

- **The object store in the tests is a loopback stand-in**, not rustfs, and the artifact table's one
  lookup is answered from a map. `response()` and the S3 client are the real ones. No local object store
  or PostgreSQL was running here. The staging rerun will show the join on rustfs.
- **Shot reuse and the final's dialogue keep their own copy loops.** They already stream and check, but
  they check the signal only between chunks, so a stream that stalls there waits as long as the store
  holds it open. They weren't moved onto `copyStoredArtifact`, to keep this change to the join.
- **The 120 s stall bound is fixed.** It is long enough for a slow store and short against the job's
  4 hours. It isn't configurable.
- **A plain final records no sha256 of its own export**, so its film is checked against the store's
  record. That record is itself checksummed when published (`upload`), and a stored object that differs
  from it is still refused.
- **The cause is Bun's.** `Bun.write(path, response)` with a streamed body was not reported upstream
  from here; the first test will start failing if a Bun upgrade fixes it, and the copy can stay as it is.
