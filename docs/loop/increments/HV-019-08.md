# HV-019-08 — What a claim costs

epic: HV-019
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

`DurableJobStore.eligibleToStart` counted a candidate's running siblings by materialising and
filtering **every job in the store**, and `claimNext` asks about every candidate. So one claim cost
Θ(queued × stored). Nothing in this package ever deletes a job from the JSON store — there is no
`jobs.delete` anywhere, and the only retention sweeper is gated on `HV_STORAGE === "postgres"`,
which `docker-compose.yml` does not set — so both numbers grow forever.

Measured in memory (`DurableJobStore.fromJobs`, so no JSON parse or serialise is in the number at
all), five claims averaged:

| jobs, all queued | one `claimNext` | ms / n² × 1e6 |
|---|---|---|
| 1,000 | 17.3 ms | 16.2 |
| 2,000 | 68.2 ms | 15.3 |
| 4,000 | 233.1 ms | 15.8 |
| 8,000 | 1,241.1 ms | 19.8 |

Clean fourfold-per-doubling, and linear in the store at a fixed queue depth, so the cost is
queued × stored rather than either alone.

The multiplier is what makes it matter. Every store call is a full reload and rewrite of
`jobs.json` under `withFileLock`, and a single three-shot job issues **thirty** store transactions
— fourteen heartbeats, five reads, three route decisions, three cost records, three checkpoints,
one claim, one complete — about ten per shot, so roughly 240 for a 24-shot free-tier film. At 8,000
retained jobs a single film spends seconds holding the lock the API's own `enqueue` also needs, and
`withFileLock` gives up after ten.

Separately, and much smaller: the `MAX_JOB_NOTIFICATIONS` comment states how many call sites use
`notify`, and was wrong by one. The comment gives both numbers *deliberately* — it says so — because
an earlier draft gave one number for both and a reader counting call sites got a different answer
from a reader reading the history. HV-027-05 added the tenth and the comment stayed at nine.

## What this increment does

- **`runningCounts(now)` builds the per-project running count once per claim**, and
  `eligibleToStart` reads it. One pass over the store instead of one pass per candidate. The
  predicate is otherwise unchanged, in every branch.
- **The notification comment says ten, and a test counts the call sites** rather than asserting the
  number, so the comment and the code cannot drift apart again. That is the point of a comment that
  states a count: either it is checkable or it should not state one.

Measured after: 0.24 ms at 1,000 queued and 3.00 ms at 8,000 — about twelvefold for eight times the
store, the extra being `fairShareOrder`'s sort.

## Acceptance criteria

1. **Eight times the store is not sixty-four times the work.** Asserted as a ratio with a loose
   bound (thirty; quadratic measured at seventy-three) plus an absolute ceiling, because a ratio
   alone passes when both numbers are terrible.
2. **The claim still answers the same job.** The existing `packages/queue` suite is the assertion:
   the predicate's branches are untouched and the suite exercises lease expiry, queue-behind,
   per-project concurrency, fair share and dead-lettering.
3. **The notification comment's two numbers match the call sites**, counted from the source of both
   files rather than written down.
4. Reverting the source change makes 1 and 3 fail (run by hand; recorded here).

- Tests: `packages/queue/test/queue-arithmetic.test.ts` (1, 3), `packages/queue/test/queue.test.ts`
  and the rest of the package (2).

## Known gaps this leaves — and one decision for the operator

- **Nothing is ever removed from the JSON job store.** This increment makes each claim cheap; it
  does not stop the store growing. Pruning terminal jobs is the other half and is a retention
  decision (how long a finished job's body stays readable to the API) rather than a scheduling one.
- **A `budget_throttle` admission still pins the job behind every active job in the studio**, and
  stores that list — five hundred ids in a five-hundred-job studio, re-serialised on every write to
  that job. That blocks one project on an unrelated project's work, *before* `fairShareOrder` is
  consulted at all, and the note beside `FAIR_SHARE_WINDOW_MS` calls that shape "the thing FR-029
  forbids" while explaining a different instance of it.

  **It is not an oversight, and it is not fixed here.** `queue.test.ts` asserts it by name — "a
  budget-throttled job does not start while any job that was ahead of it is still active" — under
  AC-011 and FR-032. So two requirements are in tension: AC-011/FR-032 say a queued job waits for
  the jobs ahead of it; FR-029 says no project may starve another. Three repairs were considered
  and all three have a cost:

  1. *Refuse a throttled job while anything at all is running.* Same throttle strength, fair
     ordering restored — but with more than one worker the studio may never be idle, so a throttled
     job can wait unboundedly. Worse than what it replaces.
  2. *Refuse a throttled job while another throttled job is running.* Bounded, fair, and identical
     once utilisation is over 80% (everything is throttled then). It does allow a throttled job to
     run beside an unthrottled one during the transition window, which is a spend guard being
     loosened in that window.
  3. *Give a throttled job a `nextEligibleAt` delay instead of a chain.* Bounded and fair, but it
     changes what the throttle **is**, from "serialise the studio" to "wait N seconds", and N is a
     new budget number.

  CLAUDE.md freezes budget defaults upward without a human gate, and every option above moves a
  spend guard in some direction. So the current behaviour is asserted in
  `queue-arithmetic.test.ts` as a baseline, with the measurement beside it, and the decision is
  Kevin's. When it is taken, that test and `queue.test.ts`'s change together, deliberately.
- **The `queuedBehind` list could be bounded without changing behaviour** by pruning ids that are
  already terminal — a terminal job never becomes active again, so dropping it cannot change what
  the job waits for. That is a safe, separate change; it was left out of this one to keep the
  scheduling predicate untouched while the decision above is open.
