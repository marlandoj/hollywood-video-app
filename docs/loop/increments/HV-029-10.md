# HV-029-10 — Which rule a review link follows was decided by whoever opened it first

epic: HV-029
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

HV-029-05 gave the owner a choice at the mint. A link minted with `maxViews` counts **viewers**: a
reload is not a second viewer, and the viewer who watched on the last view may still decide. A link
minted without one keeps FR-047's original rule — three serves, anonymous. The mint is where that is
decided, and it decides it by whether `viewers` exists at all:

```ts
if(maxViews!==undefined){link.maxViews=reviewViewLimit(maxViews);link.viewers=[];}
```

Three readers branch on that field: `peekReviewLink`, `submitReviewDecision`, and the decision route.
But the counter created it regardless of the mint:

```ts
if (viewer) link.viewers = [...(link.viewers ?? []), viewer.hash];
```

The review page sends `x-hv-review-viewer` on every open, so **the first browser to open an old-rule
link turned it into a viewer-identity link for everyone after it**. A second reviewer whose client
sends no viewer id — curl, a link scanner, an embedded webview — was then shown the cut and refused a
decision on it, with *"Open the cut in this review link on this device before deciding on it."* The
identical request would have been accepted had the first reviewer never opened the link.

`submitReviewDecision`'s own comment says *"A link without viewer ids keeps the old rule."* It did
not. It kept the old rule until a browser touched it, and then quietly changed rules under the
owner who minted it.

Nothing caught it because `review-views.test.ts`'s old-rule case opens all three views with no header
at all, which is exactly the case where the defect cannot fire.

## What this increment does

- **A viewer is recorded only on a link that was minted to keep them.** `link.viewers !== undefined`
  is now a property of the mint for the link's whole life, which is what the three readers were
  already assuming.
- **The mint says so where it decides it**: a limit the owner chose is a link that counts viewers,
  and a link minted without one keeps FR-047's original rule.

## Acceptance criteria

1. **A link minted without a view limit keeps the old rule, whoever opens it**: a browser opens it
   and no viewer list appears; a client that sends no viewer id is then served and may still decide.
2. **A link minted with one counts viewers, exactly as before**: a reload is not a second viewer, the
   third viewer spends the last view and may still decide, and someone who was never shown the cut
   may not.
3. **The rule a link follows is a property of the mint, not of its traffic**: over links minted with
   no limit, with 1 and with 25, whatever traffic they see, the field the readers branch on is the
   one the mint decided.
4. Reverting `packages/api/src/index.ts` fails criteria 1 and 3.

- Tests: `packages/api/test/review-link-rule.test.ts`, alongside the existing `review-views.test.ts`,
  which is unchanged and passes. The decision gate is asserted through `peekReviewLink`, which is the
  check the decision route runs beside `submitReviewDecision` and the one both of them make about the
  viewer; `submitReviewDecision` itself also requires a bound link, which is a different refusal.

## Known gaps this leaves

- **A link minted without `maxViews` now never gets reload-forgiveness**, for its whole life. That is
  the old rule and what this makes consistent, but it means an API caller who omits the field gets
  the pre-HV-029-05 behaviour, where a reload spends one of three. The studio always sends the field;
  nothing warns a caller who does not.
- **Nothing migrates the links that already switched.** A stored link minted without `maxViews` that
  a browser has already opened carries a `viewers` array today and will keep following the new rule.
  There are none in staging; a deployment with some would need a one-off correction.
- **`REVIEW_VIEWER_HEADER` is still trusted to be a per-browser id.** A client that sends a fixed
  string gets unlimited views of a `maxViews` link; the hash is a convenience for the honest case,
  not an authentication.
- **The two rules remain.** Whether an anonymous-client link should exist at all is a product
  decision nobody has made; this increment only stops it changing its mind.
