# HV-024-07 — The sound session and dialogue replacement waited on a stuck version for ever

epic: HV-024
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

Both panels wait for a rendered version with a loop whose only exit is a terminal status
(`sound-studio.js` and `dialogue-replacement.js`, `poll`):

    async function poll(id){for(;;){const job=await jobRequest(id);if(job.status==="done")return job;
      if(["failed","cancelled"].includes(job.status))throw …;tell(…);await new Promise(resolve=>setTimeout(resolve,1500));}}

Sometimes a version never leaves "queued", for example when no sound worker is running or the
queue has given up on its lease. The panel then read it every 1.5 seconds for as long as the tab
stayed open. The wait runs inside the panel's `run()`, which has two effects for all that time:

- **Every control in the panel was disabled**, **Close sound session** included.
- **`unsaved` stayed true.** That kept the page's other editors shut too.

Three actions ended in that wait:

- **Render reviewed sound session** or **Render reviewed lines**;
- **Open sound version …** on a queued version;
- **Wait for this version**.

HV-030-08 fixed this shape in `studio.js`. There, `pollJob` counts the polls on which nothing
moved, and after `STALL_LIMIT_MS` of them it stops and says the render is still on the server. The
two panels never got that clock.

## What this increment does

- **Both panels now keep the studio's clock on the same 1.5-second interval.**
  - A poll that sees the same status and output revision as the one before counts toward the limit.
  - Any change resets the count.
  - After thirty unchanged minutes (1,200 polls) the panel stops waiting. The panel is free again.
- **The panel says what is true**:
  - the version has not moved;
  - it is still queued or running on the server, so nothing has been lost;
  - where to open it later: **Retained sound versions** or **Browse all dialogue versions**;
  - rendering the same reviewed draft again returns this version rather than starting another.
- **A reviewed draft keeps its request key.** `approved` is only cleared after the wait succeeds, as
  before. Rendering again sends the same key, and the server answers with the existing job.
- `POLL_INTERVAL_MS` and `STALL_LIMIT_MS` are exported by both panels. The API serves each panel on
  its own, without `studio.js`, so the values are copied rather than imported. A test holds them
  equal to `studio.js`'s.

## Acceptance criteria

1. **Both panels use the studio's interval and stall limit**, which is 1,200 polls.
2. **Opening a sound version that never leaves queued stops** after the first read plus 1,200
   unchanged polls. It shows the retained-version message as an error, re-enables **Close sound
   session** and leaves `unsaved` false.
3. **A sound version whose status or output revision keeps changing is waited on past the limit**
   until it is done.
4. **A stalled sound render keeps the reviewed draft.** Rendering it again sends the same
   idempotency key.
5. **"Wait for this version" on a dialogue version that never leaves queued stops** at the same
   limit. It shows the retained-version message and frees the panel.
6. **A stalled dialogue render keeps the reviewed lines.** Rendering them again sends the same
   idempotency key.
7. Reverting `sound-studio.js` and `dialogue-replacement.js` fails criteria 1, 2, 4, 5 and 6.
   Criterion 1 fails because the exports are missing. With the constants alone restored, criteria
   2, 4, 5 and 6 still fail.

- Tests: `packages/frontend/test/panel-poll-stall.test.js`.

## Known gaps this leaves

- **The clock is copied into two more files.** Moving it into a shared browser module would mean
  serving that module at every prefix (`SHARED_BROWSER_MODULES` in `packages/api/src/server.ts`). The
  test keeps the copies equal in the meantime.
- **A job that does visible work without changing status or output revision could be given up on.**
  One example is a long mix that reports no progress field. That job keeps running on the server and
  can be opened later. Neither job type exposes a progress counter the way a film render exposes
  `checkpointShots`.
- **Other panels that poll on a timer**, such as the graphics desk's renders and character sheets,
  weren't checked against this rule here.
