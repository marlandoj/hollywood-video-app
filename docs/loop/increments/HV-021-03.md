# HV-021-03 — The continuity report stops repeating itself, and stops overcounting

epic: HV-021
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0 — no provider is touched.

depends on: HV-021-02 (PR #168). This branch is cut from it, so its diff carries HV-021-02's commit
until that merges.

## Why

A critic pass over HV-021-01 found two defects and a false claim.

**The report was 99% duplicate text.** Every shot's packet carried the whole scene's cast state —
name, wardrobe, and the character's 600-character "preserve" note — and every shot in a scene has
the *same* cast state, because it comes from `charactersForScene(casting, sceneIndex)`. So a
60-shot film with 24 fully written cast records produced a **1,715,385-byte** report, of which
**8,579 bytes** was everything except the packets. That report is embedded in `GET /direction`,
which is the direction editor's main load — the response a creator waits on every time they open the
desk.

**The reference count was the wrong number.** HV-017-09 gave a character a **locked look**: a chosen
one-to-four subset of their retained images, and the only set the render is conditioned on. The
packet counted `character.references.length` — the whole retained set — so a character locked to two
of four images was reported as anchored by four. `identity-unanchored` read the same wrong set. A
continuity report claiming more anchoring than the film will actually have is the one thing it must
not do, and it is the same class of defect HV-026-04 fixed in the quality check the same night.

**HV-021-01's own doc said identity locks did not exist**, citing `docs/CASTING.md`, though HV-017-09
had merged before it. Two of that doc's acceptance criteria were also wrong about what the code did.

## What this increment does

- **The scene's cast state is on the scene.** `ContinuityScene.characters` replaces
  `ContinuityPacket.characters`. Nothing is lost: it was identical across a scene's packets. Measured
  on the same worst case, the report goes from **1,715,385 to 345,935 bytes**, and what remains grows
  with the *scenes* rather than with the shots — the regression test below pins that.
- **A stale shot gets no packet.** Its saved direction refers to a shot that has changed, so there is
  nothing to compare; it was already given an empty character list and filtered out of every
  comparison. It is still named by the scene's `shotIds`, by `staleShotIds` and by its own
  `source-stale` finding. `continuityRepair` drops its now-impossible filter and **refuses** a report
  that lists a shot as both compared and stale, rather than quietly skipping it.
- **`references` is `renderReferences(character).length`** — the locked look where one is set, the
  retained set otherwise — and the state carries `referencesLocked` so the report says which of the
  two it is counting. `identity-unanchored` reads the same function, so the count and the finding
  cannot disagree.
- **The false claims are corrected** in `docs/CONTINUITY.md`, where a creator reads them, and in a
  **Corrections** section appended to `docs/loop/increments/HV-021-01.md`. The merged text is left
  standing; the correction sits under it. A record that is quietly edited is not a record.

## Acceptance criteria

1. **The cast state is the scene's.** `scene.characters` carries it, a packet has no `characters`
   property at all, and the values are unchanged from what the packet used to carry.
2. **The report does not grow with shots.** On a ten-scene film with twelve fully written cast
   records, going from 10 shots to 60 adds less than 40 KB — the shots' own packets — and the whole
   60-shot report stays under 250 KB. Before this change each of those 50 extra shots carried the
   scene's twelve characters again.
3. **A stale shot has no packet**, is still listed in its scene's `shotIds`, and still gets
   `source-stale`.
4. **A locked look is counted as what the render uses**: a character with four retained images locked
   to two reports `references: 2` and `referencesLocked: true`, and one with no images at all is the
   one `identity-unanchored` names.
5. **A report that contradicts itself is refused**: `continuityRepair` throws on a report whose
   packets include a shot listed in `staleShotIds`.
6. **Nothing else moves.** The continuity, continuity-repair, direction and casting suites pass, and
   the API's continuity and repair routes answer as before with the cast state read from the scene.

- Tests: `packages/planner/test/continuity.test.ts` (1–4), `packages/planner/test/continuity-repair.test.ts` (5),
  `packages/api/test/continuity-route.test.ts` and `packages/api/test/continuity-repair-route.test.ts` (6).

## Known gaps this leaves

- **345 KB is still the ceiling, and it is still cast text.** A character's `preserve` note and
  wardrobe description are repeated once per *scene* they appear in, because wardrobe genuinely
  resolves per scene while `preserve`, `name` and the reference count do not. Normalizing those three
  to a report-level record would take the same worst case to roughly 40 KB. It is not done here
  because there is no consumer yet to join the two, and a second lookup with no reader is a shape
  chosen for a guess. The measured ceiling is recorded here so the next person does not have to
  rediscover it.
- **The realistic figure is much smaller than the ceiling**: it assumes 24 cast records with every
  text field at its limit. A film with six characters and a sentence of preserve each is tens of
  kilobytes.
- **`GET /direction` still computes the whole continuity report on every load**, alongside coverage
  and the scene-cut staleness scan. That cost is CPU, not payload, and it has not been measured.
- **Nothing here is visual.** The locked look this increment now counts correctly is the
  reference-set half of an identity lock; there is still no embedding and nothing compares a
  generated frame to anything.
