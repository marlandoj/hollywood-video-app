# HV-022-12 — The read is asked for at a rate every plan returns

epic: HV-022
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

The second attempt at the live proof got further than the first: the crew cast three ElevenLabs
voices, the take route admitted all four lines, and each one was dispatched. Then all four failed:

> Audio delivery failed. The original attempt remains pending billing reconciliation.

`outcome.dispatched` was true, so the request reached the service. Asking it directly gave the
answer in one line:

```
HTTP 403  {"code":"subscription_required",
           "message":"Output format 'pcm_44100' is only available on the Pro tier and above."}
```

HV-022-05 pinned `pcm_44100` because it is the best the service offers. It is also sold with the Pro
plan, and the operator's account — like every free and Starter account — cannot use it. Probing the
account's own key for what it will return:

| Format | This account | |
|---|---|---|
| `pcm_44100` | **403** | Pro and above |
| `mp3_44100_192` | **403** | Creator and above |
| `mp3_44100_128` | 200 | lossy |
| `pcm_24000` | 200 | lossless |
| `pcm_22050` | 200 | lossless |

So the contract named a format the studio could not actually use, and nothing could have caught it
short of asking the service: a capability file states what the adapter *will* ask for, and every
fixture reasonably assumed that was available.

## What this increment does

- **`ELEVENLABS_OUTPUT_FORMAT` is `pcm_24000`, and `ELEVENLABS_SAMPLE_RATE` 24000.** Everything else
  derives from those two constants — the request URL, the ffmpeg input rate, the byte ceiling — so
  the change is the declaration and its reasons.
- **The capability says why**, because the reason is not obvious and the next reader will wonder:
  the rate is fixed for every account rather than chosen from the operator's plan, so one capability
  revision holds across accounts; and it is lossless PCM rather than the MP3 that is equally
  available, because speech energy sits below 8 kHz and a lossless 24 kHz read carries it with no
  codec artefacts before the mix.
- **A latent fixture bug is fixed** that the rate change exposed. Two cases stub the conversion out,
  so the provider's own bytes are delivered and then measured at the studio's 48 kHz. The fixture
  generated them at the provider's rate, which was near enough at 44.1 kHz to pass and became a
  quarter-second claiming to be half at 24 kHz. Those cases now generate at the studio's rate, which
  is what a passthrough conversion means.

Nothing else moves: the model, the controls, the line ceiling, the word-timing basis and every
refusal are exactly as HV-022-05 declared them.

## Acceptance criteria

1. **The request asks for the declared format**, and that format is `pcm_24000` — the assertion names
   the constant and the value, so moving the constant alone cannot silently change what is asked for.
   - Tests: `packages/planner/test/elevenlabs-contract.test.ts`,
     `packages/generator/test/elevenlabs-audio.test.ts`.
2. **A read converts to the studio's 48 kHz** by the recipe the capability declares, with the
   delivered length matching the alignment, from the provider's rate rather than a coincidence of it.
   - Test: `packages/generator/test/elevenlabs-audio.test.ts`.
3. **Every failure still leaves one recorded attempt** with its hold intact and no provider text,
   including the two cases that stub conversion out.
   - Same test.
4. **Nothing else changes.** The ElevenLabs contract, adapter and catalogue suites pass otherwise
   unchanged, and no control range, model, ceiling or refusal moves.

The live proof this defect stopped is HV-022-11, which runs once this is deployed.

## Known gap this leaves

The capability's revision changes with the rate, as it should. The operator's authorized-voice
catalogue on the host binds the account, the voices and the licence — not the capability — so it
stays valid and does not need rewriting. If that ever stops being true, the catalogue must be
rewritten from evidence, never edited.
