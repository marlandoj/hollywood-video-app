# HV-039-20 — Scrubbing the camera path preview, then editing the crop, overwrote the selected keyframe

epic: HV-039
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

A critic pass over `packages/frontend`.

The camera path editor's preview scrubber shows the interpolated framing by writing it into the
viewfinder's own editable crop:

    scrub.oninput = event => {...; showCrop(sample(at), true); ...};   // camera-path.js

Every edit the viewfinder makes to that crop reports the whole crop to the path editor: a position or
size control, an arrow key, or a drag on the source. The path editor copies it into the *selected*
keyframe:

    function setCrop(key, value) {...; crop = {...crop, [key]: value}; ...; pathEditor.cropChanged(crop); ...}   // viewfinder.js
    cropChanged(crop) {...; Object.assign(keyframes[selected], crop); ...}                                    // camera-path.js

Take a creator who scrubbed to the end of the path to look at it and then nudged the first
keyframe's horizontal position. They saved a first keyframe with the *last* keyframe's size and
vertical position. Nothing on screen showed it, because the viewfinder was already showing that
crop, and the next render opened on the wrong framing.

## What this increment does

- **The path editor knows when the viewfinder is showing a preview.** Scrubbing sets `previewing`.
  Putting a keyframe back on screen (`showSelected`) clears it: selecting a keyframe, editing its
  time, inserting or removing one, or filling the editor.
- **An edit made over a preview does not reach the keyframes.** The viewfinder goes back to the
  selected keyframe, and the path editor's status says so and asks for the change again. The next
  edit works on the keyframe's own framing.
- Scrubbing still previews exactly as before.

## Acceptance criteria

1. **A nudge over a preview.** Scrub to the end of the path; the viewfinder shows the last
   keyframe's framing. Then nudge the horizontal position. Both keyframes keep their saved framing,
   the viewfinder and scrubber return to the first keyframe, and the status explains why.
2. **The edit after that.** Two further nudges change only the fields the creator changed on the
   selected keyframe; its size stays its own.
3. **A drag over a preview.** Pressing and dragging inside the previewed rectangle leaves the
   selected keyframe's size and the last keyframe unchanged.
4. Reverting `camera-path.js` fails criteria 1, 2 and 3.

- Tests: `packages/frontend/test/camera-path-scrub.test.js`. It builds the real viewfinder with its
  real path editor on the `audio-studio-dom.js` DOM and dispatches the controls' own handlers.

## Known gaps this leaves

- **A drag that starts over a preview still moves the keyframe.** The press restores the keyframe,
  but the viewfinder measured the grab offset against the previewed rectangle. The rest of that
  drag moves the keyframe's position, not its size, from that offset, so the rectangle can jump.
  The creator sees the move on screen.
- **Reset to full frame over a preview reports success.** The reset is dropped like any other edit
  and the path editor says so. The viewfinder's own status line still says "Full frame restored at
  the current position", because that message is written after `cropChanged` returns.
- **A dropped edit still marks the draft changed.** The viewfinder calls `changed()` after
  `cropChanged` either way, so the unsaved-edit guard counts it, although no keyframe changed.
