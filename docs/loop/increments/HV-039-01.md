# HV-039-01 — Raise the palette above WCAG AA and put a gate under it

epic: HV-039
spend_usd: 0

## Goal

Fix the contrast failures that are live in the shipped product today, collapse the duplicated palette that would otherwise let the fix land on one page and miss the other, and leave behind the epic's first automated accessibility assertion.

**What was failing, measured rather than claimed.** Converting each OKLCH token to sRGB and computing the WCAG relative-luminance ratio:

| pair | ratio | required | criterion |
|---|---|---|---|
| primary button label (`--text` on `--accent-strong`) | **3.25:1** | 4.5:1 | 1.4.3 |
| the same label on `:hover`, which repainted the fill with `--accent` | **2.44:1** | 4.5:1 | 1.4.3 |
| text input / select / textarea boundary against the page (`--line` on `--bg`) | **1.71:1** | 3:1 | 1.4.11 |
| the same boundary against a panel (`--line` on `--surface`) | **1.56:1** | 3:1 | 1.4.11 |
| the mask editor's boundary — a focusable canvas with arrow-key handles | **1.71:1** | 3:1 | 1.4.11 |
| an unselected take card, the other half of a selected-state indicator | **1.71:1** | 3:1 | 1.4.11 |
| the textarea placeholder (an inline `oklch(0.58 …)` the palette never saw) | **4.13:1** | 4.5:1 | 1.4.3 |

Every primary button in both the creator UI and the operator console, and every text control in both, at 16px weight 650 — not WCAG "large text", so 4.5:1 applies. **Nothing in the repository caught any of it: there was no WCAG or contrast assertion anywhere in the twelve packages.** The last three rows were found while writing this increment's test, not by the audit.

**How this increment was found.** The program-wide re-verification of the pre-loop credit ran one auditor per epic across all 22 epics that had never had the pass `docs/loop/STATUS.md` says the first planner is supposed to run. HV-039 came back `partially-delivered` with eight defects and one BLOCKER, and with a correction to the board in the *other* direction: the delivered UI is not accessibility-naive — `lang`, viewport, landmarks, 3px focus rings that already clear 3:1, `prefers-reduced-motion` in both stylesheets, 34 controls at the 44px target, and real keyboard alternatives to both drag surfaces, which satisfies SC 2.5.7. The status `todo` is right; the empty Evidence column is what understated both the ground covered and the live failures. The four ratios above were recomputed from the tokens before any code was written and match the audit to two decimal places.

## The shape of the repair

**One palette, two readers.** `index.html` carried ten tokens and `operator.css` nine, with only **six names in common**. Two more were the same colour under different names — `--accent-strong` / `--action` and `--success` / `--good` — so a contrast fix applied under one name could not reach the other page. `packages/frontend/src/tokens.css` is now the declaration, the duplicate names are gone, and a test holds both pages equal to it. Both pages now declare the **whole** palette, including the three or four tokens each does not yet paint with, because a partial copy is a copy that can drift; that is a deliberate merge and not merely a rename.

**The primary button fill goes darker, not the label lighter.** `--accent-strong` moves from `oklch(0.61 0.17 262)` to `oklch(0.52 0.17 262)`. That is the widest band that satisfies both criteria at once: the label reaches 4.75:1 (1.4.3 wants 4.5) while the button surface still reaches 3.43:1 against the page and 3.13:1 against a panel (1.4.11 wants 3). Lightening the label instead does not work — `--text` is already `oklch(0.94 …)`, and even pure white on the old fill is only 3.87:1.

**The hover state draws an inset ring, not a lighter fill.** `button:hover { background: var(--accent) }` was the single declaration that took the label to 2.44:1, and it was present in *both* files. There is no value of a lighter fill that keeps a light label at 4.5:1 while keeping the button at 3:1 against the page: the band is `L ∈ [0.49, 0.53]`, which is imperceptible as a hover change. An earlier draft of this increment replaced it with `border-color: var(--accent)`, which was **a no-op in the creator UI**: `button` there declares `border: 0`, so there was no border box to colour, and `button.secondary`'s later `border` shorthand has equal specificity and would have overridden it anyway. That draft removed the only hover affordance from every button in `index.html` and replaced it with nothing. Hover now sets `box-shadow: inset 0 0 0 2px var(--accent)`, which needs no border box, cannot be overridden by a `border` shorthand, adds no layout shift, and is visually distinct from the offset 3px `:focus-visible` outline. The `transition` on that rule was retargeted from `background-color`, which no longer changes, to `box-shadow`.

**A separate token for anything a person operates.** `--line` is deliberately left at `oklch(0.35 …)`. SC 1.4.11 does not reach a rule between table rows, a section divider or a panel edge, and raising that token to 3:1 turns every hairline in the product into a visible bar. The new `--control-border: oklch(0.53 0.025 275)` clears 3:1 against all three surfaces — 3.67:1 on `--bg`, 3.35:1 on `--surface`, 3.03:1 on `--surface-raised` — and is applied to text inputs, selects, textareas, secondary buttons, button-styled links, the focusable mask editor, the take card's unselected border and the metrics chart axis — the last because 1.4.11 also reaches graphical objects needed to understand content.

`details` and `fieldset` deliberately keep `--line`. A `border-bottom` on a stacked `details` row is a separator between disclosures and the control's own boundary is the focusable `summary` and its focus ring; a `fieldset` is a grouping container, not a control. That is a judgement, and it is recorded in the test beside the selector list rather than left implicit.

**One pair is unsatisfiable, and it is recorded rather than dropped.** `--accent-strong` against `--surface-raised` is **2.83:1**. No lightness of this hue and chroma clears 3:1 there while the `--text` label still clears 4.5:1 on the same fill — `--surface-raised` is only 1.21:1 from `--bg`, so there is no room. A primary button must therefore not be placed on a raised panel; no current markup does. The test pins the measured 2.83:1 and the 1.21:1 that causes it, so neither can erode unnoticed.

**The thresholds are literals in the test, and the conversion happens in the test.** `4.5` and `3.0` are written into `packages/frontend/test/contrast.test.ts`, never read from the stylesheet, so the test cannot pass by agreeing with whatever the palette currently says — the defect family this program has now found seven times. The test converts each OKLCH triple to sRGB with Ottosson's matrices and computes the WCAG ratio itself: no browser, no headless Chrome, no colour library, and no ratio read from a comment or a doc.

**The rules are checked by computing, not by banning a spelling, and that is a correction.** The first draft of the test banned the string `var(--line)` on a list of selectors and banned the literal declaration `button:hover { background: var(--accent) }`. Both were trivially evaded — `background-color` instead of `background`, `border-bottom` or `border-block-end` instead of `border`, `:active` instead of `:hover`, `outline` instead of a border, a bare `#3a3f4c` instead of a token, a *different* low-contrast token, a thirteenth token written in hex, a selector not on the list, or the same rule split across two lines, which a line-by-line scan cannot see at all. The shipped test parses rule blocks, resolves the token each declaration names, refuses a colour literal where a token belongs (pure white and pure black excepted, for overlays drawn across arbitrary imagery where no token's contrast is knowable), and asserts the ratio. Perturbations P7–P14 are each one of those evasions.

## Acceptance criteria

1. **Every token pair the UI relies on clears its WCAG 2.2 AA threshold, computed rather than asserted.** Twenty-two pairs, all distinct — fourteen text pairs at 4.5:1 under SC 1.4.3 and eight boundary, state and graphical-object pairs at 3:1 under SC 1.4.11 — checked against literal thresholds, with the OKLCH→sRGB conversion and the relative-luminance ratio computed in the test. An earlier draft listed nineteen entries of which three were the *same ordered pair* at both 4.5:1 and 3:1, where the 3:1 entry was logically implied and could never fail alone; the distinct-pair count is now asserted. The palette's thirteen token names are asserted as a set, and any colour token in a notation the test cannot convert is an explicit failure rather than a silent skip. The three values this increment moved are pinned at the ratios they reach, and so is the one unsatisfiable pair.

2. **The palette is declared once, and no third copy exists in any notation.** `tokens.css` holds all thirteen tokens. The creator UI's inline block and the operator console's `:root` are compared to it as whole name→raw-value maps, so a hex rewrite of an existing token diverges as loudly as a changed number. A scan of every `packages/frontend/src/**/*.{css,html,js,ts,mjs}` asserts no fourth file declares a colour custom property.

3. **Every operable boundary, every button fill and every text colour inside a control is a token that clears its threshold — computed, not spelled.** Both files are parsed into rule blocks, so a rule split across lines or two rules on one line are both visible. For a selector naming something a person operates, a `border*`, `outline*` or `box-shadow` colour must be a palette token clearing 3:1 against `--bg`, `--surface` **and** `--surface-raised`; a `color` must clear 4.5:1 against `--bg` and `--surface`. For a button-like selector, a `background*` colour must be a palette token on which `--text` clears 4.5:1 — which catches `background-color`, `:active`, a different low-contrast token and a bare literal, none of which the first draft could see. A colour literal where a token belongs is a failure, except pure white and pure black on overlays drawn across arbitrary imagery. The number of rules the checks reach is asserted, so a parse that matched nothing cannot make the whole test vacuous.

4. **No behaviour, route, dependency, frozen path, budget default, account, vendor or migration changes.** The diff is two modified files (`index.html`, `operator.css`) and three new ones (`tokens.css`, `contrast.test.ts`, this doc). Nothing under `docs/legal/**`, `docs/adr/**`, `.github/workflows/**`, `packages/safety/**` or `infra/drizzle/**`; no `package.json` or lockfile entry; no HTTP route, cookie, tracking, account, tier or payment path; no new environment variable. `docs/loop/STATUS.md` and `docs/PROGRAM-EXECUTION.md` are not in the diff; RECORD owns both.

## Demonstrated, not asserted

Fourteen perturbations, each applied on this branch, measured against the **final** test file, and reverted. P7–P14 are the evasions that defeated earlier drafts of the test; each of them passed a draft and fails the shipped file.

| perturbation | result |
|---|---|
| P1 — restore the old primary button fill (`oklch(0.61 …)`) in all three files | `1 pass / 2 fail` |
| P2 — restore the hover repaint in the creator UI only | `2 pass / 1 fail` |
| P3 — repaint on `:active` with `background-color` instead of `background` | `2 pass / 1 fail` |
| P4 — fix the fill in `tokens.css` and the creator UI but not the operator console | `2 pass / 1 fail` |
| P5 — lower `--control-border` to `L = 0.50`, which is 2.66:1 on `--surface-raised` | `1 pass / 2 fail` |
| P6 — declare a fourth palette at the top of `operator.js` | `2 pass / 1 fail` |
| P7 — an input boundary via `border-bottom`, in a rule split across three lines | `2 pass / 1 fail` |
| P8 — a control boundary as a bare `#3a3f4c` instead of a token | `2 pass / 1 fail` |
| P9 — a control boundary via `--surface-raised`, a different token at 1.21:1 | `2 pass / 1 fail` |
| P10 — a boundary on `[role="button"]`, `.chip` and `label` via `outline` | `2 pass / 1 fail` |
| P11 — a thirteenth token written in hex, used as every control boundary | `1 pass / 2 fail` |
| P12 — the placeholder back to its 4.13:1 inline `oklch` literal | `2 pass / 1 fail` |
| P13 — the mask editor's boundary back to `--line` | `2 pass / 1 fail` |
| P14 — `--placeholder` lowered to `oklch(0.58 …)` in all three files | `1 pass / 2 fail` |

P4 is the one that matters most: it is exactly the half-fix the duplicated palette invited, and it is why criterion 2 exists rather than being folded into criterion 1. P5 and P9 are chosen at or just below the boundary rather than at obviously wrong values. **P12 passed the second draft of this test** — the draft checked boundaries and fills but not text colour inside a control, so reverting the placeholder to its 4.13:1 literal went unnoticed; the text-colour check exists because of it.

## What this increment does **not** do

- **It does not serve one stylesheet to both pages, and that is a deliberate deviation from the audit's recommendation.** The staging edge (`edge.ts` in the staging runtime, not in this repository) serves only `/`, `/index.html` and `/vendor/hls.min.js` from the frontend, and `infra/Dockerfile.frontend` copies only `index.html` into the nginx image. A `<link rel="stylesheet">` to a second file would 404 in staging and render the creator UI **unstyled** — a worse accessibility outcome than the one being fixed. Serving it is a deployment change to a runtime this increment does not own. Until then the two `:root` blocks are copies that a test holds equal, which closes the drift risk without touching the deployment.
- **It does not fix the `aria-busy` live-region defect.** Five panels set `aria-busy` on an ancestor of their own status live region, which suppresses every screen-reader status and error announcement inside it. That is a separate shape — ARIA semantics, not colour — and it is the natural HV-039-02.
- **It does not reconcile the 2.1-vs-2.2 requirement.** Gate V-020 validates WCAG 2.1 AA while the epic is defined as 2.2 AA, a requirement written in five places where four copies disagree with the fifth. Naming which of the five is authoritative is a decision, not a code change, and it is not made here.
- **It does not address the remaining 1.4.11 surfaces or any of the Mobile Review half.** The `placeholder` failure was found while writing the test and is fixed here rather than deferred. What remains uncovered is every surface outside the two gated files — the media and overlay backgrounds written as inline literals in `index.html` (`#000`, `#181818`, the sound-cue chips, the checkerboard), which are content rather than chrome and whose contrast against arbitrary imagery is not knowable from the palette, and every criterion other than 1.4.3 and 1.4.11. Mobile Review is blocked on HV-029, which has one merged increment and no review-room surface yet.
- **It does not claim WCAG 2.2 AA conformance.** It claims that twenty-two specific token pairs clear two specific success criteria, computed, and that three classes of declaration in two specific files are checked by ratio. Conformance is a statement about the whole product against all of 2.2 AA, no part of which has been audited, and nothing in this diff says otherwise.
