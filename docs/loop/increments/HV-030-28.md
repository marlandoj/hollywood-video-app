# HV-030-28 — The feature format and its film limit (Release 3 step 1)

epic: HV-030
release: 3 "Features"
gate: G20-202610031349 (Release 3's criteria and build order agreed; a feature's film limit of $150; the anchored picture profile)
spend_usd: 0

## Why

Release 3 is proven on one 15–20 minute feature of about 200–240 shots (G19-202610030430). At G20
Kevin agreed the build order, starting with the feature format, and decided three things this step
needs: a feature gets its own film limit of $150 while reels and shorts stay at $40; the $500 program
cap and the $450 alert don't change; and the live feature uses the look-matched (anchored) picture
profile, at about $0.42 a shot.

HV-030-27 read three blockers in the code (its constraints 1, 3 and 4):

- **Formats.** `readThroughInput`, the plan step's `planInput` and `styleCardInput` each hard-coded
  `["reel", "short"]`, and so did the studio's format picker and its style-card reader. A feature
  couldn't be pitched.
- **The film limit.** `HV_FILM_SPEND_CAP_USD` ($40) was one number for every film, read at startup
  and handed to every admission. A feature spends about $84–101 of video and holds about $30 more
  while its last 24-shot sequence renders (three attempts at the dearest estimate, HV-019-06).
- **The quote.** The read-through priced every shot on Kling 2.5 (`ESTIMATE_VIDEO_SPEC`, $0.35 a 5 s
  clip) whatever the operator's profile was. On `live-film-anchored` the lead lane is Kling O3
  keyframes at $0.084 a billed second (`FAL_MODELS` in `packages/generator/src/fal.ts`), $0.42 a
  5 s clip, so the quote was a fifth short.

## What this increment does

- **A `feature` format, up to 1,200 s.** `packages/planner/src/crew/formats.ts` holds the three
  formats (`FILM_FORMATS`, `FORMAT_LIMIT_SEC`: reel 90, short 600, feature 1,200) and `isFilmFormat`.
  The read-through, the plan step and the style card validate against it; anything else is refused
  as before. The studio's picker (`FORMAT_CHOICES` in `packages/frontend/src/studio.js`) offers
  "A feature, up to 20 minutes", and a kept style card made for a feature is read.
  `scripts/studio-run.ts` passes `--format` through to the API unchanged, so `--format feature` now
  works there too.
- **A feature is read whole.** The read-through route plans a reel or a short as one render
  (24 shots), as before, and a feature up to 240 shots (`READ_THROUGH_SHOT_LIMIT`), so its runtime,
  shots and quote describe the feature, not its first render.
- **The quote is the active profile's.** `quotedLane` picks the configured final pool's lead lane:
  the first entry priced by the billed second and not retired, the one the `configured` routing
  strategy tries first. Each shot is priced at the clip the Editor will pace it to on that pool
  (`pacedSeconds`, the same rule `crewChanges` applies since HV-017-05): at least the pool's billed
  floor, longer for its lines. Anchored: $0.42 a shot, so 200–240 shots quote $84–$100.80. Live-film:
  $0.35. Mock, with no billed lane, keeps the old reference quote. `estimate.basis` says which
  (`"profile"` or `"reference"`). Both crew routes hand the quote `configuredPool("final")`.
- **A feature's own film limit.** `packages/operator/src/film-budget.ts` adds
  `HV_FEATURE_FILM_SPEND_CAP_USD`, $150 by default, a plain-dollar line under the monthly cap like
  the film's (if it is unset and the monthly cap is below $150, the feature is held to the monthly
  cap). `filmCapFor(project, limits)` returns the feature's limit for a project planned as a
  `feature` and the film's limit ($40) for anything else: a reel, a short, a project never planned,
  or a feature when no feature limit is to hand.
- **The format is kept on the project.** The crew's plan step stores `format` on the project in the
  same write as its cast and direction. It's absent until a plan names one, so an unplanned project's
  state is unchanged. A stored format that isn't one of the three is refused on load and in a state
  snapshot, rather than read as a reel. Planning a feature again as a short puts it back under $40.
- **Every admission asks that project's limit.** Renders, edits, graphics, deliveries, sound mixes,
  lip-sync, audio takes, music cues and screenplay revisions, on both the JSON and PostgreSQL
  ledgers, plus `GET /spend`. Each API module's context now requires `featureCapUsd` beside
  `filmCapUsd`, so an unwired module is a type error (HV-022-14's guard, extended).
- **Docs.** `docs/CREW.md` (read-through formats, the quote, the feature's limit) and
  `docs/PROVIDER-ROUTING.md`.

Nothing here raises the monthly cap, the per-shot cap or the reel's and short's limit. No staging
script sets either film limit. No provider is called and no key is added.

## Acceptance criteria

1. **Three formats.** `FILM_FORMATS` is reel, short, feature with limits 90, 600 and 1,200 s. The
   read-through, the plan step and the style card accept `feature`. Each still refuses `film`,
   `Feature`, `" feature"`, `""`, numbers, `null` and other values, and the API answers 400.
2. **Over format.** A feature is `over_format` only past 1,200 s; a short past 600 s, as before.
3. **Read whole.** The read-through route reads a feature of 120 beats as 120 shots against 1,200 s,
   and a reel of the same script as 24 shots against 90 s.
4. **The quote.** Read from `scripts/staging-providers.py` and `FAL_MODELS`: anchored quotes $0.42 a
   silent shot (`fal:kling-o3-standard-keyframes`, basis `profile`), 200 shots $84 and 240 $100.80;
   live-film $0.35 (`fal:kling-v2.5-turbo-pro`); mock the reference lane at $0.35, exactly as before.
   A shot whose lines outrun 5 s is quoted at the longer clip the Editor paces it to. A retired lane
   is never quoted.
5. **The limits.** $150 for a feature, $40 for a reel, a short and an unplanned film, through
   `GET /spend` on the real routes with the shipped defaults under a $500 month. Each setting is read
   apart from the other, as plain dollars, never above the monthly cap.
6. **Admission.** With the limits scaled to cents ($0.03 film, $0.05 feature; a storyboard render
   holds $0.02), a reel is refused its second paid render (429) and a feature is admitted its second
   and refused its third. A feature planned again as a short is refused at $0.03.
7. **HV-030-27's arithmetic.** 216 anchored shots spent ($90.72) plus a 24-shot sequence's $30.24
   hold fits $150 and not $40. Each limit refuses one cent past it.
8. **Untouched.** `monthlyBudgetCap` reads as before whatever the feature setting is. A feature
   within its own limit is still refused by the month. The staging scripts still write
   `HV_MONTHLY_BUDGET_USD=500`, Release 3's generation line is still $450, and no deploy script sets
   either film limit.
9. **Kept on the project.** A project's state has no `format` until a plan names one, and reads it
   back after. An unknown stored format is refused by `ProjectService` and by `validateSnapshot`.
10. **Every admission names the limit** (`film-cap-admissions.test.ts`): each `admit*` call in the
    API passes the film's cap or `filmCap(project)`/`filmCapFor(...)`. Each module's context requires
    `filmCapUsd` and `featureCapUsd`, and the server reads the limits once.
11. **The studio.** The picker offers exactly the crew's formats with their limits, a feature pitch
    reaches the crew as `feature`, and the plan step sends it back.
12. Reverting the change fails the named tests (checked):
    - `filmCapFor` returning the film's limit always fails 5 of 13 tests in the two limit files;
    - `quotedLane` returning the reference lane always fails 6 tests in the two quote files;
    - dropping `feature` from `FILM_FORMATS` fails 11 tests across the five new files.

## Known gaps this leaves

- **No sequences yet (step 2).** The plan step and a render still make one render's shots: 24 on the
  free tier, 60 with an operator grant. A feature's read-through describes the whole feature, but
  its plan step directs the shots of one render, so the two differ for a feature. Rendering a feature
  project today is refused at admission when the script has more scenes than the tier's shot limit
  ("This tier supports screenplays with up to 24 scenes"). With 24 scenes or fewer, its beats are
  grouped into 24 shots. Splitting a feature into sequences is the Showrunner's job, build step 2.
- **The runtime isn't paced.** The quote prices each shot at the clip the Editor will pace it to, but
  `estimatedRuntimeSec` is still the planned runtime before pacing (2 s a planned shot). So a
  240-shot feature reads as about 480 s and quotes about $101 on the anchored profile. Pacing the
  runtime too would move a reel's and short's `over_format` concern on the live profiles, so it's
  left for its own decision.
- **More than 240 scenes reads more than 240 shots.** The planner gives every scene at least one
  shot, so the read-through's 240-shot ceiling groups beats, not scenes.
- **The quote is the lead lane, not the dearest.** On the anchored profile a shot with no pinned
  still is rendered on Kling 2.5 ($0.35), and a 6–9 s shot costs more on Kling 2.5 (10 s billed) than
  on O3. A render's hold is still the dearest eligible estimate × 3 (HV-019-06), so the quote can
  differ from what is held.
- **A rollback forgets a feature.** No `hv-state` schema bump: a release before this one reads a
  project without its `format` and holds it to $40. That fails closed, but a feature rolled back and
  forward again has to be planned as a feature again.
- **The format is set only by the crew's plan step.** A film made on the desk without the crew is
  held to $40.
- **PostgreSQL isn't exercised locally.** Its ledgers take the limit through the same `admit(...)`
  argument, chosen per project; CI's suite runs those tests.
- **The front door doesn't show the quote's basis.** `estimate.basis` and `videoSpec` are in the
  facts, and the studio still says "at today's prices".
