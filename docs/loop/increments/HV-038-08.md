# HV-038-08 — The queue two processes share, written by neither of them safely

epic: HV-038
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

HV-038-06's own gap, built, together with the one HV-040-07 recorded next to it.

`OperatorReviewQueue` holds the shots the continuity supervisor wants an operator to look at. Its
file is fixed at `/data/state/operator-review-queue.json` (`worker.ts:720`) and **every worker that
flags a shot writes it**. `flag` did this:

```ts
flag(shotId, projectId, score) {
  this.reload();                      // read the whole file
  …find or push…                      // change it
  this.persist();                     // write the whole file back
}
```

Outside any lock. The other two shared-state classes in the same file take one —
`CostLedger.transact` and `CrewLedger.locked` both go through `withFileLock`, whose own comment says
what it is for:

> Interprocess mutual exclusion for a JSON state file shared between the API and worker processes.

Measured, with three real processes flagging 150 distinct shots each — none of them meant to
overwrite anything:

```
450 expected, 404 on disk, 46 lost        (this container)
450 expected, 311 on disk, 139 lost       (a busier one)
```

Every individual call reported success. The size of the loss is the machine's; that there is one is
the code's. `docker-compose.yml` runs one worker today, so this needs the scaled fleet that
`HV_EXPECTED_WORKERS` and the worker registry exist for — which is to say it is exactly the shape of
defect those were built for.

### And one signature beside it

`resolve` took a shot id alone:

```ts
resolve(shotId: string): void {
  const i = this.items.find((x) => x.shotId === shotId && !x.resolved);
```

`flag` keys on the **pair** — this one matches both fields, and `PostgresReviewQueue.flag` hashes
`sha256(projectId + "\0" + shotId)` for its primary key. Shot ids are per-project strings like
`shot-1-1`, so the first caller of `resolve` would have cleared **every project's** review of the
same shot; `PostgresReviewQueue.resolve` had the same `where shot_id = $1` one store over. There is
no production caller today — `worker.ts` calls `flag` and nothing calls `resolve` — which is why
this was a trap rather than a leak, and why changing the signature costs nothing. HV-040-07 recorded
it and left it; the two changes belong together because both are about `resolve` and `flag`
disagreeing about what identifies an item.

`degraded-resume.test.ts` had a line that quietly depended on the old behaviour: it flags
`shot-1-2` for two projects and then calls `resolve("shot-1-2")`, expecting one of them to go. Which
one was whichever the scan found first. It names the project now.

## What this increment does

- **`OperatorReviewQueue.transact`** is the same read-change-write under `withFileLock` that
  `CostLedger.transact` is, and `flag` and `resolve` go through it. A queue with no path — the
  in-memory one the tests use — still works without one.
- **`resolve(shotId, projectId)`**, in both stores. The PostgreSQL one adds
  `body->>'projectId' = ${projectId}` to the `where`.
- **A guard asserts the two stores agree**, because HV-019-07 exists precisely because they once did
  not: both signatures, the PostgreSQL predicate, and the file taking its lock in two places where
  it took it in one.

Nothing about what a single process sees changes: one entry per shot of a project, replaced rather
than repeated, reopened by a later flag — HV-019-07's rule, asserted again here unchanged.

## Acceptance criteria

1. **Three processes flagging at once lose none of it** — real `Bun.spawn`ed processes, because the
   defect is between them and a single-threaded runtime cannot exhibit it at all; 450 distinct shots
   in, 450 on disk, 450 distinct, and the queue reading back 450 pending.
2. **One process's flags are what they always were**: replace, not repeat; a second project's flag
   for the same shot is its own; a resolve then a re-flag reopens it.
3. **Resolving a shot clears that project's flag, not every project's**, including a project with
   no such flag resolving nothing and a second resolve reaching no further.
4. **Both stores take a project before they resolve anything**, asserted over the source, along with
   the lock now being taken in two places in the file rather than one.
5. Reverting `index.ts` and `reviews.ts` makes 1, 3 and 4 fail; 2 passes either way, which is its
   job.

- Tests: `packages/operator/test/review-queue-lock.test.ts`.

## Known gaps this leaves

- **`pending()` still reads outside the lock.** It is a read of a file that is only ever replaced
  atomically by `rename`, so it sees one consistent version or another rather than a torn one; what
  it can miss is a write that lands between its `reload` and its filter. Taking the lock for a read
  would serialise the operator console against every worker, which is the wrong trade for a view.
- **The lock's stale threshold is 30 seconds** (`DEFAULT_LOCK_STALE_MS`), and a lock older than that
  is broken on the assumption the holder died. A process paused longer than that — a very large
  ledger on a slow disk, which HV-038's critic pass measured at 12.2 s for 4,000 cost events and
  rising — could have its lock broken while it still holds it. That is the same lock this queue now
  uses, and it is a property of `withFileLock` rather than of this queue.
- **No caller resolves anything yet.** This increment makes `resolve` safe to call; nothing calls
  it. The operator console shows `pending()` and has no way to clear an item, which is a route and a
  view.
- **This is the JSON store.** The PostgreSQL store was never at risk from the lock — its writes are
  one statement each — and it shared only the `resolve` signature.
