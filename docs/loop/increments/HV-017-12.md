# HV-017-12 — Re-saving a shot's own direction rendered the film again, and charged for it

epic: HV-017
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

The second of the three version fields in the key the server derives for a render when the caller
sends none:

```
`${stage}:${scriptVersion}:cast-${castingVersion}:direction-${directionVersion}`
```

HV-030-07 took the studio's `crypto.randomUUID()` idempotency keys away so that derived key would
stand. HV-016-10 closed the same hole on `scriptVersion`, where a save of identical text advanced the
version and the next render was admitted and charged as a different film. `saveDirectionSnapshot`
had it too — it wrote `current.version + 1` for every save, whatever the settings.

Measured end to end on this repo's own API:

```
PUT /direction/:shot  (the shot's own settings, unchanged)  ->  versions 1, 2, 3

POST /jobs {}                              ->  edfb91b7-…
PUT /direction (unchanged), POST /jobs {}  ->  0b594c34-…   a second animatic, charged
```

The Director's desk saves a shot's direction on every change to any control in its panel, and it
sends the panel's whole settings object. So a control touched and put back, a panel opened and saved
without an edit, or a client that re-sends what it read, was a new version — and the next render was
a new film.

## What this increment does

`saveDirectionSnapshot` returns the current snapshot, unchanged, when the snapshot that would be
saved is identical to it.

A `DirectionSnapshot`'s `revision` is a content hash **including its version**, so the comparison is
made against a candidate built at the *current* version: same project, same version, same entries,
same scene cuts, same revision — nothing happened. That is one line, and it is the same line
`VersionStore.commit` gained in HV-016-10.

- **Every path that writes a direction version goes through it**: a shot's own save, the crew's
  planning pass, the removal of stale directions after a screenplay edit.
- **The first save of a shot nobody had directed is still a version.** Version 0 means "never
  directed" to `directionMatches`; an entry with default settings is not the same thing as no entry
  at all, and the candidate's revision differs from the empty snapshot's, so the rule keeps that
  distinction by construction rather than by a special case.

## Acceptance criteria

1. **Re-saving a shot's own direction does not make a new version**: three more saves of the same
   settings return version 1 and the same revision, each time.
2. **Re-saving it does not render the film again**: the same job id comes back.
3. **A direction that actually changed still makes a version, and a different film** — and saving
   *that* direction again is a no-op in its turn.
4. **The first save of a shot nobody had directed is still a version**: 0 → 1.
5. Reverting `index.ts` fails criteria 1, 2 and 3.

- Test: `packages/api/test/direction-noop-save.test.ts`.

## Known gaps this leaves

- **The cast version is the third field, and this rule does not apply to it.** Measured, not assumed:
  `characterRecord` stamps `permission.attestedAt` from the clock, so two saves of one input are
  genuinely different records — the only field that differs between two records of one input at two
  instants is `permission`. Four identical `PUT /cast/:id` calls gave versions 1, 2, 3, 4. Deciding
  that re-attesting the same permission at a later instant is not a change to the cast is a **consent
  question, not a version question**, and it is not made here. The comment in `saveCast` says so at
  the site.
- **Nothing tells the creator the render was free**, the same gap HV-016-10 named.
- **Scene cuts ride along.** They are part of the snapshot and so part of the comparison, which is
  right; but a save that changes only the cuts and not the entries still makes a version, and no test
  here exercises that path.
- **The 100-snapshot history cap is unchanged.** This makes it harder to reach, and does not change
  what happens at it.
