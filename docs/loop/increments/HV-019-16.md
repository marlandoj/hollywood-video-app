# HV-019-16 — The mock records reference images (Release 3 step 15's rehearsal)

epic: HV-019
release: 3 "Features"
gate: none new (cites G21-202610041254: "a $0 rehearsal of the whole feature runs on mock pictures (build step 15)", which this unblocks)
spend_usd: 0

## Why

Release 3's $0 rehearsal (build step 15) ran on the `mock` staging profile (`HV_ANIMATIC_PROVIDER=mock`,
`HV_PROVIDER_PRIMARY=mock`, `HV_PROVIDER_SECONDARY=mock`):

```
scripts/studio-run.ts --format feature --lock WREN,OSWIN --continuity-repair
```

The desk steps locked WREN's and OSWIN's looks to their turnaround sheets before the look approval
(`scripts/release-3-desk.ts`). The front door then asked for sequence 1's rough cut and got:

```
POST /api/projects/:id/jobs -> 400 No configured provider supports these render requirements: references.
```

The mock adapters declared no reference input (`input.referenceFrames: 0`), and their `generate` threw
"identity conditioning is not implemented" for any reference image. A shot carries its characters'
reference images from `directCast`, a locked look's images or an unlocked character's own, so on the mock
profile no shot of a character with an image could be rendered at all. A feature with locked looks
couldn't be rehearsed at $0, and the mock profile couldn't exercise HV-017-17's identity locks.

## What

**1. The mock accepts reference images and records them** (`packages/generator/src/capabilities.ts`,
`image.ts`, `index.ts`, `animatic.ts`).
- The mock adapters declare `input.referenceFrames: 32`, the most a shot can carry
  (`MAX_CONDITIONING_INPUTS`, the bound `capability()` and `validateRequirements` already put on a count).
  This covers `mock` and `image:mock` on the final stage, and `mock` and `legacy-mock` on the animatic and
  character-sheet stages. A shot of two characters each locked to four views carries eight images, which
  is what the rehearsal's sequence 1 asks for. The mock still takes no identity lock (`identityLocks: 0`).
- They also declare `referenceUse: "recorded-not-rendered"` (`REFERENCES_RECORDED_NOT_RENDERED`), a new
  optional capability field. It says the images are recorded by digest and the picture is not rendered from
  them. `capability()` refuses it on an adapter that takes no reference, and refuses any other value. It is
  absent from every vendor, so their revisions don't move.
- `matchCapability` names the adaptation on every match of a shot with references to such an adapter
  (`REFERENCES_RECORDED_ADAPTATION`). It goes into the route decision and into the clip's `routing`.
- The mock checks the images as the vendors do (`privatePngReferences`: private PNG data URIs only) and
  records them with `recordReferences`: each image's SHA-256 and size, in the request's order. The record
  goes on the still and on the clip (`referenceRecord`). The picture is unchanged: the same bytes and
  fingerprint as the render without references.

**2. The record reaches the shot's provenance** (`packages/assembler/src/index.ts`,
`packages/planner/src/provenance.ts`). An export's `provenance.json` gains an optional `referenceRecord` on
each shot the mock rendered with references, beside HV-017-17's `identityLocks`. A vendor's shot has none,
and a shot with no references has none, so every existing record is unchanged.

HV-017-17's record and drift check need no change on the mock. `identityLocks` states the lock the request
carried, which the mock was given. The new `referenceRecord` states what the mock did with it (recorded,
not rendered), so neither claims more than the mock did. The desk read (`GET /identity-locks`) and
`lockDrift` read the render's recorded cast and shots, whatever rendered them.

**3. The capability revision change, handled like any other.** Five revisions moved: final `mock`, final
`image:mock`, animatic `mock`, animatic `legacy-mock` and character-sheet `mock`. Every vendor's revision
and every price version is unchanged. `docs/evidence/hv019-router/adapter-conformance.json` was rewritten
by the suite (`HV_ADAPTER_CONFORMANCE_EVIDENCE`) after it passed, and its diff is those five revisions, the
date, and boundary-rejection cases 201 → 196. That's one fewer "too many references" case per mock entry:
a request one past 32 isn't a shot at all and is refused by `validateRequirements` before matching, which
the suite now asserts instead. A plan admitted before this deploy with a mock in its pool fails closed at
claim time ("Provider configuration changed after this job was queued. Start a new render…"), as
PROVIDER-ROUTING.md's "Capability revision changes and in-flight plans" describes. Both staging deploy
paths drain first. The new field is optional and set only on the mock, so every retained plan still
validates.

**4. Docs.** REFERENCE-PROVIDERS.md: "The mock records references", including the pool-order note below.
PROVIDER-ROUTING.md: one sentence on `referenceUse`.

Nothing else changes. No vendor capability, price, routing rule, strategy, cap or default moves, and no
key, vendor or spend is added.

### Tests that encoded the mock's lack of references, reviewed

The router takes the first eligible provider in configured order. Four API test files configured
`["mock", <reference vendor>]` and relied on the mock being ineligible for a shot with references, so
those shots went to the vendor fixture. The mock is eligible now, so it would take them:

- `packages/api/test/feature-identity-locks.test.ts` (HV-017-17), `references.test.ts` (third test),
  `direction.test.ts` (first pipeline test) and `actor-library.test.ts` (the imported-actor render): the
  pool is reordered to `[<reference vendor>, "mock"]`. Every assertion is unchanged. A reference vendor
  needs at least one image (`minimumReferenceFrames: 1`), so a shot without references still goes to the
  mock, and every shot with them still goes to the vendor with the same images in the same order.
- `packages/api/test/references.test.ts`, "reference-conditioned scenes cannot silently fall back to
  text-only providers": this asserted the 400 on the default (mock) pool. The rule it protects belongs to a
  text-only vendor, so it's now held on one: `image:fal:flux-schnell`, the live-storyboards profile's rough
  cut. Admission reads its capability only, with no key and no dispatch. The same scene on the mock is now
  admitted, and that's asserted too.
- `packages/generator/test/conformance.test.ts`, boundary rejections: "one more reference than declared"
  can't be built for an adapter declaring 32. For those, the suite asserts `validateRequirements` refuses 33.

Kept unchanged, because they test vendor rules: `router.test.ts` ("unsupported references … cannot
silently degrade", on fal), `reference-providers.test.ts` (the vendors' missing, excessive and malformed
references), `fal-image.test.ts`, `fal.test.ts`, and every other conformance family.

## Acceptance criteria

1. **The rehearsal's defect is gone.** The rehearsal's own screenplay (`feature.fountain`) runs on the mock
   profile's three settings with no pool, through the studio flow `studio-run.ts` drives and the desk steps
   it takes before the look: WREN and OSWIN each get a turnaround sheet and are locked to its four views,
   and the continuity repair is applied. Approving the look admits and renders sequence 1's rough cut,
   23 shots, where it was a 400. The same requests then render sequence 1's final, all on the mock at $0.
   With the mock's declaration removed, the same test fails with the rehearsal's exact error.
2. **The lock reaches the mock and is recorded, not claimed.** In the rough cut and the final, every shot
   names exactly its locked characters' locks (`identityLocks`). Its `referenceRecord` holds exactly those
   locks' images, by SHA-256 and in the lock's order, with `use: "recorded-not-rendered"`. A shot of both
   characters carries eight. Its routing names the mock's capability and the adaptation.
3. **HV-017-17's record and drift check work on the mock.** The desk read lists, per render and shot, the
   locks the provenance records, with no drift. When OSWIN's lock changes after sequence 1, sequence 1 is
   flagged `needsRoughCut`, and the drift names OSWIN's old revision.
4. **A mock render, rough cut and final, records the references.** The final-stage mock and the rich
   animatic over the mock image record each image's digest and size in order. The picture's bytes, poster
   and fingerprint equal the render without references. Malformed, remote or JPEG references are refused,
   and identity locks are still refused.
5. **Only the mock declares it, and every vendor is matched as before.** Exactly the five mock registry
   entries carry `referenceUse`, and no paid one does. Kling O3 reference is eligible with no "recorded"
   adaptation and refuses five images. Kling 2.5 Turbo and FLUX Schnell still refuse references. Every
   vendor's capability revision in the conformance evidence is unchanged. `capability()` refuses the field
   on an adapter that takes no reference, and refuses any other value.

- Tests: `packages/api/test/mock-profile-locks.test.ts` (1, 2, 3),
  `packages/generator/test/mock-references.test.ts` (4, 5),
  `packages/generator/test/conformance.test.ts` and its evidence (5). The reviewed tests above pass with
  every assertion unchanged except the two described.

## Known gaps

- **The live profiles have no reference vendor.** All three live profiles render the rough cut on FLUX
  Schnell, which takes no reference image, so on every one of them a locked character's rough cut is
  refused with this same "render requirements: references". The finals are Kling 2.5 Turbo (no references)
  and, on `live-film-anchored`, Kling O3 keyframes, which takes images only with a pinned first frame (a
  feature's final doesn't pin one yet, HV-017-17's gap). Only `live-storyboards`' mock finals would take
  them now. Step 16's live run needs a profile with FLUX.2 edit and Kling O3 reference first. That's an
  operator profile decision, and it isn't made here.
- **Two locked looks exceed the reference vendors' four images.** The rehearsal locks each character to
  its four turnaround views, so a shot of WREN and OSWIN carries eight. FLUX.2 edit and Kling O3 reference
  take at most four, so such a shot would be refused live even with those vendors. The mock takes up to
  32 by design: like its durations and dimensions, it is permissive rather than a copy of one vendor's
  limits, so the rehearsal can't find this one. It is recorded here instead. The fix is the desk's choice
  of how many views to lock, or a planner rule for a shot's reference budget.
- **The mock's picture ignores the references.** That's the point, and every record says so. Nothing at
  $0 measures identity (build-order step 9, HV-037).
- **A plan admitted before this deploy with a mock in its pool** fails closed and needs a new render, as
  for any capability change. Staging deploys drain first.
- **Mixed pools put the vendor first.** An operator's custom pool that puts the mock before a reference
  vendor now sends shots with references to the mock. No staging profile mixes them, since profiles strip
  pool settings. REFERENCE-PROVIDERS.md says to put the vendor first.
- **The end-to-end test takes about two and a half minutes**: two sheets, then a 23-shot rough cut and
  final on ffmpeg. It drives the studio flow and the desk steps in-process, as `studio-run.ts` does,
  rather than spawning the script. The final is asked for with the two requests the front door sends, so
  its finishing steps (voices, score, mix) aren't run.
