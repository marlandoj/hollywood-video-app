# HV-032-05 — The staging edge reads bodies first and doesn't reuse API connections

epic: HV-032 (capacity and hosting)
release: 1 "Studio"
gate: none new
spend_usd: 0

## Why

The live anchored reel (HV-017-07) stopped at its second storyboard still with 502 "upstream unavailable".

The edge (`infra/staging/edge.ts`) streamed each request body to the API over a pooled mTLS connection. The API refuses a stale upload from its headers and leaves the image unread. The next request sent on that connection then failed with "The socket connection was closed unexpectedly".

This was reproduced on the staging host and in `test/staging-edge.test.ts` against the real API behind its mTLS front: 2 of 10 refusals became 502.

## What this increment does

- **The edge reads a request body before proxying it**, up to `HV_EDGE_MAX_BODY_BYTES` (default 64 MiB). A larger body is refused with 413 and never reaches the API.
- **Each proxied request uses a fresh loopback connection** (`keepalive: false`).

## Operator step after merge

The running edge is the provisioned copy at `$RC_RUNTIME/edge/edge.ts`. Copy the merged `infra/staging/edge.ts` over it, check that the two are identical, and restart `rough-cut-staging-edge`. `scripts/test_storage_deployment.py` already requires that the provisioned copy equals the repository file.

## Acceptance criteria

1. **Refused uploads don't break later requests.**
   - After ten uploads refused from their headers, interleaved with reads, every response is the API's own: 409 or 200, never 502.
   - Test: `test/staging-edge.test.ts`.
2. **An oversized body never reaches the API.**
   - It is refused with 413, and a normal request after it succeeds.
   - Test: `test/staging-edge.test.ts`.
