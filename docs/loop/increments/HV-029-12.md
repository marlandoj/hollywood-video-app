# HV-029-12 — A review link's decision buttons were live with no cut on screen, and both could be sent

epic: HV-029
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

A critic pass over `packages/frontend`.

`openReview` in `index.html` loads the cut and wires the two decision buttons separately:

    api(`/api/reviews/${token}`, ...).then(view => { ...attach the player... }).catch(error => { ...say so... });
    panel.querySelectorAll("button[data-decision]").forEach(button => button.addEventListener("click", async () => {
      try { await api(`/api/reviews/${token}/decision`, ...); ...disable every button... }
      catch (error) { ...say so... }
    }));

Nothing disabled Approve cut or Request changes until a decision had been *recorded*:

- **Before the cut loaded**, a reviewer could approve a cut they had not seen.
- **After the view failed** ("review link is invalid, expired, revoked, or fully used"), both buttons
  stayed live under that message. That suggests the link still accepts a decision.
- **While a decision was in flight**, the other button was still live. Approve followed by Request
  changes before the first reply sent both decisions. The reviewer's final answer then depended on
  which request the server handled second.

## What this increment does

- **Both buttons start disabled** and are enabled only once the cut has loaded. If the view fails,
  they stay disabled.
- **A click disables both** before its request goes out. A recorded decision leaves them disabled,
  as before. A refused decision enables them again, with the server's reason, so the reviewer can
  try again.
- The click handler also ignores a click on a disabled button. A browser already drops those, and the
  check makes the handler behave the same way on its own.

## Acceptance criteria

1. **No decision before the cut.** While the view request is outstanding, both buttons are
   disabled. Once it answers, the cut is described and both are enabled.
2. **No decision on a link that cannot show the cut.** After a 403 "fully used", the status says
   so, both buttons stay disabled, and a click sends nothing.
3. **One decision in flight.** After Approve cut, both buttons are disabled before the reply.
   Request changes pressed in that window sends nothing, so exactly `["approved"]` is sent. The
   status reads "Cut approved." and both buttons stay disabled.
4. **A refused decision can be retried.** Both buttons are disabled while the request is out. On a
   503, the server's reason is shown and both are enabled. A second Request changes is sent and
   recorded.
5. Reverting `index.html` fails criteria 1, 2, 3 and 4.

- Tests: `packages/frontend/test/review-decision.test.js`. It runs `index.html`'s own module script
  at `#/review/tok` through `packages/frontend/test/desk-page.js`.

## Known gaps this leaves

- **Two tabs can still disagree.** The guard is per page. The same link open in two tabs, or opened
  by two viewers, can still send one approval and one request for changes. The server records
  whichever arrives second. Whether a review link should accept a second decision at all is a
  server rule, and this increment does not change it.
- **A lost reply looks like a refusal.** The request can reach the server and the reply can then be
  lost. The page shows the network error and enables both buttons, although the decision was
  recorded. Pressing the other button then sends the opposite decision.
