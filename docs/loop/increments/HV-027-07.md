# HV-027-07 — The reframe recipe said "metadata stripped" and the cut carried the host's ffmpeg

epic: HV-027
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

HV-027-05 found this for the mezzanine and wrote it down:

> The recipe claimed metadata it did not strip. `-map_metadata -1` leaves ffmpeg's own
> `ENCODER: Lavf60.16.100` … the build version is gone now (`+bitexact`), the recipe says what the
> file actually carries, and the render **checks** it.

The sibling was not changed with it. `renderDeliveryReframe` passed `-map_metadata -1` and nothing
else, while `DELIVERY_REFRAME_RECIPE.encode` read:

```
"h264-crf18-yuv420p-30fps, metadata stripped, faststart"
```

That string is hashed into `recipeRevision` and shown on every offer, so it is a promise. Measured
here on a cut made by the old command:

```
format tags: { major_brand, minor_version, compatible_brands, encoder: "Lavf60.16.100" }
stream tags: { language, handler_name, vendor_id, encoder: "Lavc60.31.102 libx264" }
in the video bitstream: "x264 - core 164 ... options: cabac=1 ref=1 deblock=1:0:0 ..."
```

The reframe is the file that **leaves the building** — a 9:16 or 1:1 cut a creator downloads and
hands to a platform. It was carrying the studio host's ffmpeg build, its libx264 build, and x264's
whole option line. The last of those `-map_metadata` could never have reached, because it is inside
the picture rather than beside it, and nobody had looked.

## What this increment does

- **`-fflags +bitexact -flags:v +bitexact`** takes the build versions out of the container and the
  stream tag, exactly as HV-027-05 did for the mezzanine.
- **`-bsf:v filter_units=remove_types=6`** removes the SEI where x264 writes its build and its option
  line. Measured: the cut goes from 39,178 to 38,489 bytes, `x264 - core` is gone, and the file still
  decodes with every frame present.
- **The render checks the delivered file** rather than trusting the command line that made it: the
  container may carry its own brands and nothing else, each stream its `language`, `handler_name`,
  `vendor_id` and an `encoder` name, and no `encoder` tag anywhere may carry a library build. It is
  a build version that is refused, not any digit — `libx264` is a name with a number in it.
- **The recipe says what the file keeps**, which is the only form of that promise a reader can check.

## Acceptance criteria

1. **A delivered cut carries no build version**: the container holds only its own brands, each
   stream only the MP4's structural tags and an unversioned encoder name, the bytes contain neither
   `x264 - core` nor `Lavf`, and the cut still decodes clean.
2. **The old command is shown to produce what this refuses**: a cut made with `-map_metadata -1`
   alone carries `Lavf…` on the container, a versioned encoder on the stream, and `x264 - core` in
   the picture.
3. **The recipe no longer claims a strip it does not perform**, and names what is kept.
4. Reverting `packages/generator/src/delivery-reframe.ts` fails 1; reverting
   `packages/planner/src/delivery-reframe.ts` fails 3.

- Tests: `packages/generator/test/delivery-reframe-metadata.test.ts`. Verified: two of its three fail
  on the unchanged source, and `delivery-reframe.test.ts` passes unchanged.

## Known gaps this leaves

- **The cut is still not byte-stable across ffmpeg builds.** `+bitexact` removes the version
  *strings*; libx264 itself produces different bytes between releases, and this file is re-encoded
  rather than copied, so the mezzanine's "a master that cannot be compared with itself" argument does
  not transfer. `recipeRevision` and `runtimeRevision` are what tie a cut to what made it.
- **`recipeRevision` changes with this.** A reframe result stored before this increment names the old
  recipe and will be re-planned rather than re-validated. Nothing in staging holds one.
- **Removing every SEI is broader than removing x264's.** Nothing else writes one on this path today
  — no HRD, no closed captions, no timecode — but a future encode option that does would lose it
  silently, and the guard above would not notice, because it reads tags rather than the bitstream.
- **The three sibling renders were not audited for this.** The mezzanine has it and the reframe now
  does; the burned-subtitle and SDH paths write their own files and this increment did not read them.
