# HV-038-06 — The state files that forgot everything rather than say they could not be read

epic: HV-038
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

A critic pass over `packages/operator` and `packages/observability`.

`readJsonFile` is how this studio reads every durable JSON state file it keeps
(`packages/queue/src/persist.ts`). It answered `null` for two different things:

```ts
export function readJsonFile<T>(path: string): T | null {
  if (!existsSync(path)) return null;          // there is no file
  try { return JSON.parse(readFileSync(path, "utf8")) as T; }
  catch { return null; }                        // there is a file and it is not JSON
}
```

It has five callers. They are the crew's budget, the operator's review flags, every anonymous
project in the studio, a film's retained clips, and the cost ledger. **Four of them read that `null`
as "nothing yet."**

### The crew's approved ceiling stopped stopping

```
crew before:  $1000.01 spent, alerts [25, 100, 200, 1000], assertCanSpend -> CrewBudgetStop
(the file is truncated to half its length)
crew after:   $0 spent, alerts [], nextAlert $25
              assertCanSpend PASSES -- the crew may spend the whole ceiling again
```

`validateCrewLedger` has always had exactly the right answer for a ledger it cannot read — *"The
crew ledger is unreadable; the crew stays stopped until it is repaired."* The parse failure never
reached it, because `raw === null ? empty() : validateCrewLedger(raw)` handed the parse failure to
`empty()`. So the guard that is supposed to stop the spending was the one that forgot how much had
been spent.

### The operator's review flags deleted themselves

```
5 flags queued
(the file is truncated)
pending() -> 0 items, no error
one more flag rewrote the file as: [ { "shotId": "shot-9-9", ... } ]
```

Not just lost on read: written back. The first flag after the corruption persisted the empty state
over the operator's five, permanently.

### And every project in the studio

```
projects before: 1084 bytes of state, two projects with their screenplays
(the file is truncated)
the first project's script reads: null
creating one project rewrote the file: 404 bytes; project A recoverable: false
```

`ProjectService.reload` did `if (!state) return;`, so an unreadable `projects.json` started an empty
studio — and `persist()` then wrote that empty studio over the file. Every anonymous project's
script, cast, direction, edit library and sound library, gone, with nothing said and nothing left to
restore from.

### And a film's retained clips

`loadCompletedClips` did `readJsonFile<VideoClip[]>(...) ?? []`, so an unreadable clip manifest read
as "no shot was rendered". A checkpoint that names *n* finished shots would then be rebuilt by
paying a provider for all *n* again.

### The one that refused

`CostLedger.reload` throws `cost ledger is unreadable; generation is paused` on the same bytes. That
is what makes this a defect rather than a design: the caller that guards money knew the difference,
and the caller that guards the crew's money did not.

And the argument for refusing is in `writeJsonFile` itself: it writes a temporary file and renames
it, which is atomic on the filesystems the compose volumes use. So an unparseable file is **never a
half-finished write**. It is corruption, truncation, a half-restored backup, or a hand edit — and
none of those is repaired by writing over it.

## What this increment does

- **`readJsonFile` refuses a file it cannot read**, with `UnreadableStateFile` naming the path. A
  file that does not exist still reads as `null`, and so does one that was renamed away between the
  existence check and the read (`ENOENT`), which is an absent file rather than an unreadable one.
- **Each caller says what it means**, in its own words, and keeps the message it already had:
  - `CostLedger` — `cost ledger is unreadable; generation is paused`, unchanged and asserted.
  - `CrewLedger` — *the crew stays stopped until it is repaired*, which is the message
    `validateCrewLedger` was already written to give.
  - `OperatorReviewQueue` — refuses when it is opened, so nothing downstream ever sees an empty
    queue and nothing writes emptiness back.
  - `ProjectService` — refuses to construct: no project is served until the file is restored.
  - `loadCompletedClips` and the two export manifests — propagate, so the attempt fails with the
    retained clips still on disk instead of being re-rendered.
- **A guard names every reader.** The set of files under `packages/*/src` that call `readJsonFile`
  is compared whole against a table, one line each saying what an unreadable file means there. A new
  reader has to join the table, which is the point: the old default was "start over", and the whole
  defect was four callers taking that default without deciding to.

## Acceptance criteria

1. **A file that exists and does not parse is refused**, over six shapes a state file is actually
   found in — empty, whitespace, truncated object, truncated array, trailing garbage, an HTML error
   page — each naming its path; and a file that was never written still reads as absent.
2. **The crew's approved ceiling is not lifted by a truncated ledger**: `summary`, `assertCanSpend`
   and `record` all refuse, and the bytes are still on disk afterwards.
3. **An unreadable review queue does not report an empty one, nor write that emptiness back**, and
   the five flags are all there once the file is repaired.
4. **An unreadable studio state does not serve a studio with no projects in it**, and a path that
   was never written is still a new studio.
5. **The cost ledger keeps the message it always had.**
6. **Every reader of a state file is one that decided what an unreadable file means**, asserted by
   walking `packages/*/src` and comparing the whole set.
7. Reverting the five source files makes the test file fail to load at all, because the class it
   asserts does not exist.

- Tests: `packages/queue/test/unreadable-state.test.ts`.

## Known gaps this leaves

- **`OperatorReviewQueue.flag` still does a read-modify-write with no file lock.** Every other
  shared-state class in that file goes through `withFileLock`, whose own comment says it is for
  state shared between the API and worker processes. Measured with three processes flagging 150
  distinct shots each: **311 of 450 flags on disk, 139 lost**. Today's `docker-compose.yml` runs one
  worker, so it needs a scaled fleet to fire — which `HV_EXPECTED_WORKERS` exists for. It is a
  separate change with a separate risk and belongs in its own increment.
- **This does not make a corrupt file recoverable**, it makes it visible. There is no second copy of
  `projects.json` or the crew ledger to fall back to, and the backup story (`STORAGE-*.md`) is about
  PostgreSQL rather than the JSON deployment. Refusing keeps the bytes for whoever does the
  restoring; it does not do the restoring.
- **Nothing tells the operator.** The refusals are exceptions on the paths that hit them. A startup
  check that reads every configured state file once and reports which are unreadable, before the
  first request, would turn four scattered failures into one message — and it is a different shape
  of change.
- **The `?? []` and `?? {}` defaults are still there**, and are now correct: they mean "no file
  yet". Nothing stops a future caller writing `catch { return [] }` around this on its own.
