# HV-016-10 — Saving the same screenplay again rendered the film again, and charged for it

epic: HV-016
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

`VersionStore.commit` pushed a new version for every call, whatever the text. The version is in the
key the server derives for a render when the caller sends none:

```
`${stage}:${scriptVersion}:cast-${castingVersion}:direction-${directionVersion}`
```

**HV-030-07 took the studio's `crypto.randomUUID()` idempotency keys away precisely so that derived
key would stand**, and a repeated request would return the job it had already admitted rather than
admit and charge for another. A save that changed nothing moved the derived key, so the protection
did not hold across the one path a creator is most likely to take twice.

Measured end to end on this repo's own API:

```
PUT /script "INT. BAR - DAY\n\nShe waits."   ->  version 1
PUT /script  (the same string)               ->  version 2
PUT /script  (the same string)               ->  version 3

POST /jobs {}                                ->  9e1226a3-…
PUT /script (unchanged), POST /jobs {}       ->  4590f8e8-…    a second animatic, charged
```

This is not a theoretical path:

- The studio's own `pitch()` saves the script before anything else, so **pitching again always saved
  again**, and until HV-016-09 pitching again was the only thing a returning creator could do.
- The Director's desk saves on every edit of the script box, changed or not.
- The screenplay's history is uncapped — recorded at HV-016-04 and still an operator decision — so
  each no-op save also grew the stored state by a whole copy of the script. 129 versions of a legal
  200,000-character script measured 25.8 MB there; this is the cheapest way to reach it.

## What this increment does

`commit` returns the current version, unchanged, when the text is identical to the latest:

```ts
const current = this.latest();
if (current && current.text === text) return current;
```

- **The rule is "nothing changed since the last save"**, not "this text has been seen before". A
  screenplay that goes A, B, A ends at three versions, and the third is a real revision away from B —
  which is what a restore is, and what the cut impact of a restore is computed against.
- **Identical means identical.** A change of one trailing space is a change; the comparison is on the
  stored text and nothing is normalised, because normalising here would decide something about the
  writer's screenplay.
- **The record is the same record**: same version, same `createdAt`, same text, and nothing added to
  the history — so a no-op save leaves no trace, which is what "no-op" means.

## Acceptance criteria

1. **A save that changes nothing is not a revision**: three more saves of one string all return the
   first record, with its own `createdAt`, and no second version exists.
2. **A save that changes something still is one**, including a change of a single trailing space.
3. **Only the latest text is compared, never an earlier one**: A, B, A gives three versions, with the
   third parented on the second.
4. **The empty store still takes the first save**, including of an empty string.
5. **Pitching the same screenplay again does not render the film again**: the whole pitch — save,
   attest, render — repeated, returns the same job id, and the project holds one job at version 1.
6. **A screenplay that actually changed still renders again**, because it is a different film, and
   the writer's history holds both.
7. **A refused screenplay is still refused on the second try** — the no-op is decided after the parse,
   so a script with no scenes does not become a silent success by being sent twice.
8. Reverting `index.ts` fails criteria 1, 3, 5 and 7.

- Tests: `packages/parser/test/version-noop-save.test.ts` (the rule),
  `packages/api/test/repitch-idempotency.test.ts` (the charge).

## Known gaps this leaves

- **The history is still uncapped.** This removes the cheapest way to grow it and changes nothing
  about the cap, which remains the operator's decision (carried since HV-016-04).
- **The cast and direction versions are not covered.** They are in the same derived key and have
  their own `commit`-like paths; whether saving an unchanged cast advances `castingVersion` — and so
  charges for a second render the same way — is the obvious next question and is not measured here.
- **Nothing tells the creator the render was free.** Asking for the same film again now returns the
  job that already exists, which is right, but the studio says nothing about it having happened
  before; the message HV-030-08 added for a stalled render is the shape this wants.
- **Two identical saves from two tabs still both write.** The comparison is inside `commit` and the
  project's own save path is serialized per project, so the second is a no-op — but nothing here is a
  concurrency claim, and no test makes one.
