# HV-029-13 — Where a browser cannot remember a reviewer, reloads spent views while the owner was told they did not

epic: HV-029
release: 2 "Voice and crew depth"
gate: G15 (Kevin, 2026-09-30) authorizes the behaviour; none new
spend_usd: 0

## Why

HV-029-05 made a reload of a review link free: the page keeps one random viewer id per tab in
`sessionStorage` and sends it as `x-hv-review-viewer`, and a link with an owner-chosen limit counts
each id once. `reviewViewerId` in `index.html` swallowed a storage failure:

    try {const saved = sessionStorage.getItem(key); ...return saved;} catch {}
    const id = ...random...;
    try {sessionStorage.setItem(key, id);} catch {}
    return id;

Where `sessionStorage` throws (Safari private browsing, sandboxed iframes, some webviews) or accepts
the write and keeps nothing, every load was a new viewer, so each reload spent a view of the link.
Neither side was told. The owner's copy said the opposite: "N viewer(s) can open it; reloading does
not count." The review page said: "Reloading this page does not use another view."

## Decision

G15 in `docs/loop/HUMAN-GATES.md` (Kevin, 2026-09-30): tell the reviewer that this browser cannot be
remembered and reloads will count; the owner's copy says reloads don't count in most browsers. Stay
cookie-free (ADR-0018): no cookie, no `localStorage` fallback, no id in the URL fragment.

## What this increment does

- **`reviewViewerId` says whether the id is remembered.** It returns `{id, remembered}`. A saved id
  is remembered. A new id is remembered only if reading it back after the write returns it, so a
  store that throws and a store that silently keeps nothing are both caught.
- **The review view names the owner's limit.** `GET /api/reviews/:token` now carries `maxViews`, only
  on a link minted with one. Those are the links that count viewers by id. A link without one
  counts every serve in every browser (HV-029-05), so "this browser" would be the wrong reason there.
- **The reviewer is told.** A new `<p id="review-viewer-note" role="status" aria-live="polite">`
  sits empty in the review panel from load, so the text is announced when it arrives. That is the
  live-region pattern HV-039 uses. Once the cut loads, and only when the id is not remembered and the
  view has `maxViews`, it reads: "This browser does not let this page remember you, so each reload
  will use another view of this link. Keep this page open until you have decided." It uses the
  `--warning` token, which `contrast.test.ts` already holds at 4.5:1 on the page background.
- **The owner's copy is qualified.** The desk's share line reads "N viewer(s) can open it; in most
  browsers, reloading does not count." The review page's intro reads "In most browsers, reloading
  this page does not use another view." The studio's own share line
  (`studio.js`) never made the claim and is unchanged.
- `docs/REVIEW-LINKS.md` describes the exception.

## Acceptance criteria

1. **Where `sessionStorage` works:** two loads send the same viewer id, it is the one stored under
   `hv-review-viewer:<token>`, and the note stays empty. — `review-viewer-note.test.js` case 1.
2. **Where `sessionStorage` throws:** two loads send different ids, the cut still loads, and the note
   reads exactly the text above. — case 2.
3. **Where `sessionStorage` accepts the write and keeps nothing:** the note is shown. — case 3.
4. **No `maxViews`, no note**, even where the browser cannot remember the reviewer. — case 4.
5. **A link that cannot show the cut** (403) leaves the note empty. — case 5.
6. **The owner's desk copy** reads "…; in most browsers, reloading does not count." — case 6.
7. **The page makes no flat claim**, and the note is a `role="status"`, `aria-live="polite"` element
   present from load. — case 7.
8. **The API names the limit only on a counting link:** a link minted with `maxViews: 4` answers
   `maxViews: 4`; a link minted without one has no `maxViews` key. — `review-views.test.ts`, "the
   review view names the owner's limit only on a link that counts viewers by id".
9. Reverting `index.html` fails cases 2, 3, 6 and 7. Cases 1, 4 and 5 pass on the old page too;
   they pin what must not change.

- Tests: `packages/frontend/test/review-viewer-note.test.js` runs `index.html`'s own module script
  through `desk-page.js`. `openDesk` gains an optional `sessionStorage`, so a test can hand the page
  a working, throwing or forgetful store. Existing callers are unchanged.

## Known gaps this leaves

- **The note appears only after the cut loads.** The first load in such a browser has already spent
  a view by then. That view would be spent whatever the page said. The note is about the next one.
- **A browser that keeps `sessionStorage` for the load and then drops it** (a webview that clears
  storage between launches) passes the read-back check. It gets no note, and its next launch counts.
- **The studio's share line** says nothing about reloads either way. It is left as it is.
