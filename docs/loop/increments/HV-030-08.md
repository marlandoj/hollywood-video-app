# HV-030-08 — The studio waited on a stuck render for as long as the tab stayed open

epic: HV-030
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

`pollJob` is what every paid step of the studio waits on — the storyboard, the rough cut, the final,
the graphics, the voices, the score, the titles. It was:

```js
for (;;) {
  const job = await api(path, {headers: auth()});
  if (job.status === "done") return job;
  if (job.status === "failed" || job.status === "cancelled") throw ...
  onProgress(...);
  await wait(1500);
}
```

Nothing ends it but a terminal status. A job that never reaches one — queued with no worker
registered, or a queue that stays saturated — was polled every 1,500 ms for as long as the tab
stayed open:

- **2,400 requests an hour from one tab**, against an api bucket of 120 a minute
  (`DEFAULT_RATE_LIMITS.api`). One creator with the page open is entitled to 7,200 an hour, so the
  loop does not even rate-limit itself into stopping; it just keeps going.
- **A promise that never settles.** The step the poll is inside never advances, `state` is never
  assigned, and the only screen the creator is left with is the one that renders again.
- Measured with `wait` stubbed out so the loop runs at full speed: **stopped by the harness at 5,000
  requests, having simulated 7,500,000 ms — just over two hours — of waiting**, and it would not
  otherwise have stopped.

The file already knew. `inspect`, one function over, caps at `INSPECTION_POLLS` and refuses with
*"The Editor is still checking the film."* The **render** loop, the one every paid step waits on,
had no cap at all. That is the shape HV-031-08 and HV-016-05 had: not missing knowledge, knowledge
that did not reach the place that needed it.

## What this increment does

- **The clock is on time without progress, not total time.** A film that is checkpointing is alive
  and may take as long as it takes; what is worth giving up on is a job that has not moved. `moved`
  is the status and the checkpointed shot count together, and either changing resets the count.
- **The bound is the queue's own.** `DEFAULT_LEASE_MS` is five minutes and a job survives
  `MAX_LEASE_RECOVERIES` of them, so a job the server has not yet given up on has moved within
  5 × (5 + 1) = thirty minutes. Past that the server has stopped waiting for it, and so does the
  studio.
- **A guard reads both constants from `packages/queue`** and asserts the arithmetic, so the two
  descriptions of one clock cannot drift apart — the frontend is browser JavaScript and cannot
  import the queue at runtime, which is exactly the condition under which two numbers diverge.
- **The message says where the render is, not that it died.** It names the status and the job id and
  says nothing was lost, because nothing was: the render is still on the server. It also says that
  asking again does not pay twice, which is HV-030-07's property — the studio sends no idempotency
  key for a picture render, so the server derives one from the stage and the script, cast and
  direction versions and returns the job it already admitted.

## Acceptance criteria

1. **The ceiling is the queue's own clock**: `STALL_LIMIT_MS` equals
   `DEFAULT_LEASE_MS * (MAX_LEASE_RECOVERIES + 1)`, read from `packages/queue`, and is thirty
   minutes at a 1,500 ms interval.
2. **A render that never moves stops being polled** — and the refusal names the status and the job
   id and does not call it a failure.
3. **It stops at the ceiling, not near it**: exactly one poll per interval for the whole window, and
   exactly the window's worth of waiting.
4. **A render that is moving is waited on for as long as it keeps moving**: four times the ceiling
   in polls, with a shot finishing just inside each window, finishes.
5. **A status change resets the clock as well as a finished shot**: queued, then running, then
   queued again, nearly three windows in total, none of them stalled.
6. **The terminal answers the loop already had are unchanged**: `done` returns the job on the first
   poll, `failed` and `cancelled` throw with the server's reason, and a `failed` with no reason
   still says "The render stopped."
7. Reverting `studio.js` makes criteria 2, 3 and 5 hang rather than fail, which is the defect.

- Test: `packages/frontend/test/poll-ceiling.test.js`.

## Known gaps this leaves

- **Thirty minutes of not moving is still thirty minutes of polling.** The interval is unchanged, so
  a stuck render still costs 1,200 requests before the studio gives up. Backing off — doubling the
  interval while nothing changes — would cut that to about a dozen, and is a change to how a
  *healthy* render is followed as well as a stuck one, so it is its own increment.
- **`inspect` keeps its own separate cap.** It polls a different route on a different interval with
  a different reason, and this increment does not merge the two; there are now two capped loops in
  the file where there were one capped and one uncapped.
- **The studio does not offer to resume.** The refusal tells the creator the job id and that asking
  again is free, but nothing in the interface takes them back to that job — they re-enter the step.
  Holding a "this render is still going" state across a reload is a state change, not a loop change.
- **Nothing cancels the render.** Giving up on waiting leaves the job queued or running on the
  server, which is deliberate — it may still finish and the creator has paid for it — but it does
  mean a genuinely stuck job stays in the queue until the server's own reconciliation removes it.
