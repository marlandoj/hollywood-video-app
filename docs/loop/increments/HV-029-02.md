# HV-029-02 — a review link that named no cut was a review link nothing checked

epic: HV-029
spend_usd: 0

## Goal

Make the review read path enforce the same permission gate for every link, and make a link name the cut it showed. Both halves of one defect: the gate was reachable only through a field that some links do not have.

## The defect

`packages/api/src/server.ts`, the reviewer read route:

```ts
const latest = use.outputBinding?available.find(job=>job.id===use.outputBinding!.jobId):latestFinishedCut(available,use.projectId);
…
if(use.outputBinding)assertSelectedOutput(latest,reviewed,use.outputBinding);
```

and the same shape again in `packages/api/src/index.ts`, `submitReviewDecision`:

```ts
if(link.outputBinding)assertSelectedOutput(job,this.projects.get(link.projectId),link.outputBinding,now);
```

**`assertSelectedOutput` is the gate.** It enforces that the job is done and retained, that its own `linkExpiresAt` has not passed, that the project's `deleteAfter` has not passed, that the output revision still matches — and, through `assertDialoguePermissions` / `assertEditPermission` / `assertSoundPermission` / `assertDialogueAccess`, that **current cast permission** still covers every shot in it. Revocation, expiry and scene binding all live behind that one call.

**Unbound links skipped it entirely.** A link minted while the project has no finished cut carries no `outputBinding` — that is the route's own behaviour at `server.ts:1354`, the "invite the reviewer now, render later" case. For those links the condition was false, so:

- the reviewer was served the cut, and `signedOutput` minted **signed artifact URLs** for it, in states where the gate refuses;
- a decision could be recorded with no job checked and no job named — `submitReviewDecision` received `undefined` for `job` and asserted nothing;
- and because the unbound branch re-ran `latestFinishedCut` on every request, *which* cut the link showed was re-decided on each view, so a reviewer could be shown a different film than the one they were invited to and an approval could attach to neither.

The shape is worth naming on its own: **a check hung off an optional field is a check that is absent exactly in the case nobody pictured.** The guarded call reads as defensive — "check it if we have a binding" — while the unguarded path is the one that most needed the check.

## The shape of the repair

**One gate for both kinds of link.** The read path derives a binding for whatever cut it resolved and calls `assertSelectedOutput` unconditionally. For a bound link this is the binding it already had; for an unbound one it is `{jobId, outputRevision}` of the cut just resolved. A refusal is a `DialogueSelectionConflict`, which the server already answers as 409 with its message.

**A binding is written on the first successful view.** `ProjectService.bindReviewLink` sets `outputBinding` on a link that has none, after the gate has passed. From then on the link is an ordinary bound link: it resolves by identity, it re-checks on every view, and it cannot drift. `PostgresProjects.bindReviewLink` is the same one-line `reviewer(token, true, …)` wrapper the other review methods use, so both backends take the same path.

**Binding is a one-way door.** `bindReviewLink` returns the existing binding untouched when one is present, and refuses a revoked link or a token that is not a review token. If it could re-point a link, the drift would return one request later.

**A decision needs a cut to be a decision about.** `submitReviewDecision` now refuses an unbound link rather than recording an approval of nothing, and the route answers that particular refusal as 409 with its own message — a valid, unexpired, unrevoked approve link that was simply never opened is none of the four things the existing 403 names, and the reviewer can fix it by opening the cut. A decision reaches an unbound link only when no successful read ever happened through it, since any successful read binds; the reviewer UI reads before it can offer the button. This is a refusal that grows, which is the direction the working agreement allows.

**The stored binding is read back, not assumed.** Two first views can race: both pass the gate, on different cuts if one finishes between them, and only one binding is kept. `bindReviewLink` returns the binding the link *has*, and the route refuses with a 409 when that is not the cut it just resolved — otherwise it would serve media for a film the link does not name and that a later decision would not be about.

## Declared changes beyond the defect

- **An unbound link that resolves a refused cut now answers 409 instead of 200.** That is the defect being fixed, but it is a behaviour change for any existing link pointing at an expired or permission-revoked cut: it stops working, which is the intent.
- **`ProjectService.bindReviewLink` and `PostgresProjects.bindReviewLink` are new.** No new persisted shape: `outputBinding` is already an optional field of `ReviewLink`, already validated on load (`index.ts:201`) and in state snapshots (`storage/src/snapshots.ts:386`).
- **The existing HV-029-01 suite was not renegotiated.** Its "an unbound review link resolves to the same cut the owner's own latest points at" case still passes unchanged: an unbound link still resolves through `latestFinishedCut`, it is now checked and then fixed.
- **One existing acceptance test did have to change, and it is worth saying which.** `packages/api/test/api.test.ts`'s "approve links record approval or request-changes decisions" (AC-015) asserted that a *freshly minted* approve link could record `approved` immediately — against no cut, through the service, with no job in existence. That is the defect stated as a requirement. The case now asserts the refusal, and AC-015's positive demonstration moved to `review-binding.test.ts` case 3, where both `approved` and `changes_requested` are recorded over HTTP against a real finished cut. The acceptance criterion is unchanged; what changed is that demonstrating it now requires a cut to exist.

## What this increment does not do

- **It does not change when a view is burned, and that remains a real defect.** `useReviewLink` increments the counter before the route knows whether there is anything to show, so three refreshes, three link-unfurl prefetches, or three 404s against a project with no finished cut still exhaust a link permanently (`REVIEW_MAX_VIEWS` is 3). This increment makes it slightly more visible, because a view is now also burned by a request the gate refuses — perturbation X7 covers the related ordering question, but the burn itself is untouched. Moving the increment after a successful resolution means splitting `useReviewLink` across both backends and is its own increment.
- **It exercises the gate through one of its conditions.** The case completes a cut long enough ago that its own download link has expired. Cast revocation, project deletion and output-revision drift are the other conditions, and they are enforced by the same single call on the same line — but only expiry is demonstrated behaviourally here. A cast-revocation case needs a script with characters, a casting history and a revocation, which is a larger fixture than this increment carries.
- **It narrows what an unbound link shows, and that is a behaviour change worth stating plainly rather than filing under "does not".** The old semantics were "the newest finished cut at the moment of *each* view". The new ones are "the newest finished cut at the moment of the *first successful* view". Those differ exactly in the scenario the unbound link exists for: a reviewer invited before any render, who opens the link while a draft is the newest cut, is now pinned to that draft. Combined with the three-view cap and the burn-on-any-request behaviour left untouched below, an "invite early" link went from three chances at whatever was newest to one chance at whatever existed first. The bound-mint path — which is what the UI uses once a cut exists — is unaffected.
- **It does not close the media path, and that is the largest thing left open.** The gate runs when the reviewer asks the API what to show. It does not run again when the reviewer redeems the signed artifact URL that answer contained. `/artifacts/` checks the token signature, the project's existence, `deleteAfter` and takedown — and then re-checks permission **only** for jobs carrying `soundMix`, `pictureEdit`, `assemblyEdit`, `dialogueReplacement`, `lipSync`, or a shot render with speech. For a plain `final` cut none of those fire and no permission check runs at all. An artifact token's `exp` is clamped to `min(job.linkExpiresAt, project.deleteAfter, now + 30 days)`, so expiry and project deletion *are* transitively enforced there — but **cast revocation is not enforced on the redemption path at all**, and revoking a review link does not revoke media already handed out. A reviewer who opened a link once keeps playable media for up to thirty days across a revocation. That is a real remaining bypass, it is the same optional-field shape as the defect this increment fixes, and it is a separate increment: it needs a permission check on the artifact route that does not depend on which optional field a job happens to carry.
- **It does not audit the other `assertSelectedOutput` call sites, and there are more of them than "a few".** Seventeen calls across five files. Two are the review paths this increment changes. The rest were read, not rewritten: `edit-api.ts:106` and `edit-preview-api.ts:29` are unconditional, `lipsync-api.ts` calls it three times inside explicit `try` blocks that surface the refusal, and `server.ts` holds ten — six of which are the `/artifacts/` route's `if(mediaJob?.<optionalField>)` calls described above and one of which is the owner's job view at `server.ts:457`, which has the same shape and swallows its refusal into `mediaUnavailable`. The new scan is keyed to the review link's binding, so it says nothing about those; naming them here is the honest alternative to implying they are covered.
- **It does not test any of this against PostgreSQL.** The new suite is offline by construction. `PostgresProjects.bindReviewLink` is the same `reviewer(token, true, …)` wrapper the other review methods use, which persists by rewriting the project row and re-inserting the link set under `select … for update` — so a first view of an unbound link is now a project-row write, which is a cost worth knowing about. What is untested there: that the binding persists at all, that `retainedOutput`'s extra artifact-receipt check does not turn the bound decision path into a refusal the JSON path accepts, and that the re-insert preserves a binding written in the same transaction. CI supplies the three database URLs, so the PostgreSQL suites that exist do run — none of them covers review binding.

## Acceptance criteria

1. An unbound link whose resolved cut the gate refuses answers 409 with the refusal's own message, returns no signed artifact URL and no job identity, and binds nothing. — `packages/api/test/review-binding.test.ts` case 1; X1, X2.
2. The first successful view writes the resolved cut into the link, and a newer finished cut does not move it. — case 2; X4, X6.
3. A decision on a link that was never successfully read is refused as 409 with its own message and burns no view; after a read, the decision is accepted, the link names the job it decided, and a bound approve link records `changes_requested` too. — case 3; X1, X3.
4. Binding is one-way: a second binding returns the first, and a revoked link or a non-review token binds nothing. — case 4; X5, X8.
5. The gate keeps running after the link is bound: a bound link whose cut has since passed its own download expiry is refused on both the read and the decision, and the binding is unchanged. — case 5; X1, X2, X3, X9.
6. The project's deletion date is a second, independent condition of the same gate, tripped through an otherwise healthy cut. — case 6; X10.
7. No `assertSelectedOutput` call in `packages/api/src` or `packages/storage/src` sits in a statement chain that mentions the link's optional binding alongside anything that can make the call conditional; the scan finds at least seventeen calls across the five files that hold them, and is exercised against eight ways of writing the guarded shape and three that must pass. — case 7; X1, X2, X3.

## The critic's findings

An adversarial read of the diff found two green defects, one remaining bypass the increment did not close and did not mention, and four claims the code did not support. X9, X10 and case 7's rewritten scan are the repairs; the bypass is now stated in "What this increment does not do" rather than discovered later by someone trusting this document.

1. **X9 — the decision path's gate call could be deleted outright, with everything green.** Nothing in the repository exercised `submitReviewDecision`'s `assertSelectedOutput` in the refusing direction: the only decision cases were an unbound link (refused one line earlier by the new guard) and an acceptance against a healthy cut. That one line is all that stands between a revoked cast and a recorded approval, and the PostgreSQL path does not compensate — `retainedOutput` checks `status`, `output` and artifact receipts, not expiry, deletion or permission. Case 5 now binds a link, ages its cut past its own download expiry in place, and asserts both the read and the decision refuse by message.
2. **X10 — the gate's other four conditions were green-deletable.** Case 1 tripped `linkExpiresAt` only, so the `deleteAfter`, output-revision and cast-permission terms of the same call were unprotected. Case 6 trips `deleteAfter` through an otherwise healthy cut. Cast permission is still not tripped behaviourally; that gap is now stated rather than implied.
3. **The family scan caught exactly one spelling.** The first draft looked for a paren-free `if` within eighty characters on the same line. Braces defeated it, as did `&&`, a ternary, `Boolean(...)`, an `else`, a hoisted local and a line break. It now examines the statement chain back to the previous `;` and refuses any mention of the binding there alongside anything that can make the call conditional, and all eight evasions are exercised. The criterion was also overstated: "five call sites" is five *files* and seventeen calls, and the scan is keyed to the review link's binding, so it says nothing about the six `/artifacts/` calls hung off optional job fields — which is where the remaining bypass lives.
4. **The remaining bypass, stated rather than fixed.** The gate runs when the reviewer asks what to show, not when they redeem the signed URL that answer contained. For a plain cut the artifact route runs no permission check at all. Expiry and project deletion are transitively enforced by the token's clamped `exp`; cast revocation is not enforced there at all, and revoking a review link does not revoke media already handed out. See "What this increment does not do".
5. **Two first views could race**, with one reviewer served a cut the link does not name. The route now reads back what was stored and refuses when it differs (X11, green — the interleaving is not reachable from a black-box test).
6. **The decision refusal answered the wrong 403.** A valid, unexpired, unrevoked, never-opened approve link is not "invalid, expired, revoked, or read-only", and the reviewer can fix it by opening the cut. It now answers 409 with its own message.
7. **Two assertions proved less than they claimed.** `bindReviewLink(projectToken, …)` returning null proves a map miss, not the token-kind check; and case 3's `mintUnbound(...).catch(() => null)` asserted only that something threw. The second is rewritten to assert the mint response directly; the first is kept with its limitation named.
