# HV-029-06 — The job store's list is the studio's, and one listing forgot

epic: HV-029
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

`server.ts` line 638, written by an earlier increment:

> `// The job store's list is not per project; a film's holds are its own jobs' reservations only.`

It is true. `scopedJobs(projectId)` narrows the *store* on PostgreSQL (`jobs.forProject(projectId)`)
and returns the shared store unchanged on the JSON backend, where `all()` is every job in the
studio. The JSON backend is what `createApiServer()` defaults to and what `docker-compose.yml`
runs.

Thirteen call sites knew this and wrote `job.projectId === project.id` by hand. The
character-sheet listing did not:

```ts
const jobs=(await scopedJobs(project.id).all()).filter(job=>job.stage==="character-sheet" && job.characterSheet?.characterId===parts[4])…
```

**A character id is not a secret from anyone the owner shares an actor with** — that is what an
actor share is for, and the share carries the character. So a stranger, with one anonymous
`POST /api/projects` and no credentials of the owner's at all, could read the owner's
character-sheet jobs by asking their own project for them:

```
GET /api/projects/<the stranger's project>/cast/<the owner's character id>/sheets -> 200
jobs: 1
  job.projectId     : the owner's project
  job.idempotencyKey: <owner project>:character-sheet:1:cast-1:…
  job.characterSheet: the sheet plan, the seed, every view and its direction
  storyboard        : "SPUD — Front", "SPUD — Side", … (the character's name)
  costUsd/costCapUsd, providerPlan, timings
```

The media is still refused: `/artifacts/` asks `artifactPermission(job.stage)` and answers it for
the job's own project, and that gate held (HV-029-03). What went out is the job body — another
project's id, its job id, the character's name, the plan the owner paid for, and the provider
configuration. The same listing also answers identically for a character that exists, one that
exists in another project and one that exists nowhere, only *after* this fix; before it, the three
answers were distinguishable, so the route was an existence probe as well.

This is the third increment in a row to find the same shape: a rule everyone follows by hand, with
one place that does not. The fix is not a fourteenth hand-written filter.

## What this increment does

- **`projectJobs(projectId)` is the only caller of `all()` in `server.ts`.** It is the narrowing,
  written once, and every listing goes through it. The thirteen hand-written conjuncts are gone —
  not because they were wrong, but because agreeing thirteen times is what made the fourteenth
  invisible.
- **The character-sheet listing answers for one project**, and the owner's own listing still
  answers, which a scoping change that answered nothing would also have done.
- **A guard over the source**: exactly one `scopedJobs(…).all()` in the file, inside `projectJobs`,
  and at least fourteen calls to `projectJobs`. A new listing that reaches for the store directly
  fails the test rather than the review.

## Acceptance criteria

1. **The stranger's listing is empty**, and no part of the owner's job — its project id, its job
   id, or the character's name — appears anywhere in the response body at any depth.
2. **The owner's own listing still returns the job**, by id.
3. **Two projects do not see each other's sheets in either direction**, and neither listing grows
   when the other orders one.
4. **The route is not an existence probe**: a character id that exists with a sheet, one that
   exists in another project, and one that exists nowhere give byte-identical answers.
5. **`all()` is called once in `server.ts`**, inside `projectJobs`, and that helper filters by
   `job.projectId === projectId`.
6. Reverting the one line makes all three tests fail (run by hand; recorded here).

- Tests: `packages/api/test/project-scoped-jobs.test.ts` (1–5).

## Known gaps this leaves

- **This is `server.ts` only.** `graphic-api.ts`, `sound-api.ts`, `lipsync-api.ts`,
  `delivery-api.ts` and `edit-api.ts` are handed `scopedJobs` and call `all()` themselves. Each one
  filters correctly today — read, one by one, while writing this — but nothing keeps them doing so,
  and the guard above does not reach them. Passing `projectJobs` to the sub-APIs instead of
  `scopedJobs` is the next step and is a wider change than this one.
- **The audition route's running-job count was also unfiltered** (`runningForProject:
  all.filter(j=>j.status==="running").length`), and would have queued every audition in the studio
  behind one stranger's film. It is fixed by the same helper, and **no test exhibits it, because it
  was not reachable**: the route returns 503 without the operator's PostgreSQL audio service, and
  on PostgreSQL `scopedJobs` had already narrowed the store. It was wrong where it could not run
  and right where it could. Recorded rather than claimed.
- **Nothing here changes what a review link can see.** `assertSelectedOutput` already refuses a
  binding whose job belongs to another project; `projectJobs` only makes the list it searches the
  right list to begin with.
- **The PostgreSQL path is unchanged in effect.** `forProject` already scoped every one of these
  reads, so this increment closes a JSON-backend hole. The JSON backend is the default and the one
  in `docker-compose.yml`, which is why it is a hole and not a nicety.
