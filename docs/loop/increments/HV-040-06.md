# HV-040-06 — The backup that indexed no recording at all

epic: HV-040
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

HV-040 is marked **done**. This is why an epic should not be.

The studio keeps creator media in the private bucket under three families of key:

| Family | Where the key comes from |
|---|---|
| A render's artifacts | rows in `hv_artifacts` |
| A character's reference images | the project body's `referenceAssets` |
| A creator's uploaded recordings | the project body's `soundLibrary` |

Three places in `packages/storage` have to know all three. The orphan sweeper shields them
(`retention.ts:148-149`). The project archive copies them, on export and on import
(`archives.ts:42-43`, `:94-95`). And the backup indexes them (`backups.ts:127-141`).

Two of the three knew about sound.

`createStorageBackupUnlocked` selected from `hv_artifacts`, from `body->'referenceAssets'` and from
`hv_archives`. `soundLibrary` appeared nowhere in the file, and nowhere in any of its three test
files. So a backup of a studio with a sound library carried the database and **none of the
recordings** — and nothing said so:

- `runBackupCycle` reported `state: "healthy"`.
- `verifyStorageBackup` passed, because it verifies the blobs the manifest names and the manifest
  named none of them.
- `restoreStorageBackup` compared four counts and one sum — projects, jobs, cost events, total USD —
  none of which notices a missing file, and returned the manifest.
- The restored studio's projects still listed their sound libraries. Every recording was a 404:
  playback, sound-asset re-read and every `sound-mix` admission failing with "The sound recording is
  not a valid owned file."

It was not a deliberate exclusion. `validateObject` would have **refused** the key if anyone had
tried to add it: a recording is `v1/<project>/sounds/<asset>/<kind>-<sha256>.wav`, whose digest
lives in the last segment rather than its own, so it failed the reference family's
`parts[3] === sha256`.

## What this increment does

- **The backup indexes recordings**, from the same `hv_projects` row and the same query as reference
  images. The two families live in one row and one bucket; only one of them was ever read.
- **The object shape accepts the sound family**, and still proves the content address: the digest in
  the key must be the digest of the object, and the kind must be one of the two that exist.
- **`projectBackupObjects(projectId, body)` is the one place that turns a project body into the
  objects it requires.** The backup builds its index with it and the restore checks against it, so
  the two cannot disagree about what a project's media is.
- **The restore asks the restored database what it expects.** After `pg_restore`, every project's
  reference images and recordings are looked up in the manifest, and a missing one fails the restore
  by name. Four counts and a sum say nothing about a missing file; that is how this stayed invisible.
  It also means a backup taken **before** this fix is refused loudly on restore rather than restored
  into a studio whose sound libraries all point at nothing.
- **A guard over the three files.** Each of `backups.ts`, `retention.ts` and `archives.ts` must name
  both body-derived families. The failure here was an omission, and an omission has nothing to
  assert about at run time.

## Acceptance criteria

1. **A recording's key is a valid backup object**, for both kinds, and is still refused when the
   digest in the key is not the object's digest or the kind is invented.
2. **The reference and archive families are unchanged**, and traversal, a wrong prefix and a short
   key are all still refused.
3. **A project body names two objects per recording and one per reference image**; an empty body
   names none; a library belonging to another project is refused rather than indexed.
4. **All three files name both body-derived families**, asserted over the source.
5. **End to end, with PostgreSQL and a bucket**: a studio holding one render artifact, one reference
   image and one recording backs up **four** objects rather than two, and after a restore into an
   empty database and an empty bucket the recording reads back byte for byte and its library still
   points at it.
6. Reverting `backups.ts` makes criteria 1, 3, 4 and 5 fail (1 and 3 by the exports disappearing;
   run by hand and recorded here).

- Tests: `packages/storage/test/backup-object-index.test.ts` (1–4, no database),
  `packages/storage/test/backups.test.ts` (5, skipped without `HV_PG_ADMIN_URL` and a bucket).

## Known gaps this leaves

- **Nothing checks the bucket against the database outside a restore.** `verifyStorageBackup`
  verifies the manifest's own blobs, and the new check runs at restore time. A studio whose bucket
  has lost an object that its database still references would be found by the next restore and by
  nothing before it. A standing reconciliation is worth having and is its own increment.
- **`hv_archives` object sizes are read one `stat` at a time** during index building
  (`backups.ts:139`), which is a round trip per archive. Not this increment's, and not measured.
- **The `trash/` directory `pruneStorageBackups` creates is never written to.** Dead code, left
  alone.
- **HV-040's status.** This increment reopens an epic that was recorded as done. That is the honest
  record: "Storage and Archive at Scale, done" and "a backup silently loses every uploaded
  recording" cannot both be true, and the board should say so rather than the increment hiding in a
  neighbouring epic.
