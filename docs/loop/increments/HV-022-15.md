# HV-022-15 — The two loops in the studio that HV-030-08 did not reach

epic: HV-022
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

HV-030-08 gave `pollJob` a ceiling and wrote down why: a job that never reaches a terminal status
*"was polled every 1,500 ms for as long as the tab stayed open… a promise that never settles, and a
step of the studio that never advances."* Two loops in the same file kept that shape.

```js
for (;;) {                                        // voiceFinal: the cast's takes
  const jobs = (await api(…/audio-takes)).jobs.filter(job => ids.has(job.id));
  if (jobs.length === ids.size && jobs.every(terminal)) break;
  onProgress(…); await wait(3000);
}

while (!asset) {                                  // scoreFinal: the score upload
  try { …POST /sounds… } catch (error) {
    if (!/being processed/.test(error.message)) throw error;
    await wait(2000); …
  }
}
```

The second is worse than it looks. *"being processed"* is the studio's 429, and the counter behind it
is **server-process-global** — any other film's upload anywhere on that server keeps this branch
retrying, indefinitely.

Both run inside `finishFinal`, after the final has been rendered and paid for, in the try/catch that
makes a failed finishing pass cost a **note** rather than the film. A hang never throws, so that
catch never runs: the creator was left on *"The cast is recording: 1 of 4 lines done."* with an
approval step that could not be reached. Waiting for ever is the one outcome a note cannot describe.

Nothing caught it: `poll-ceiling.test.js` stops at `approveLook` and its fake answers
`unexpected GET /api/projects/p1/audio-takes`, so `voiceFinal` is unreachable from it; the one test
that does drive this loop flips both takes terminal on the third poll and never models a take that
stays running.

## What this increment does

- **The cast's takes stop on `pollJob`'s clock, at their own interval.** "Moved" is a take reaching a
  new status, so a slow queue that is working is not given up on; thirty minutes without any take
  moving is.
- **The score upload stops on the same clock.** There is no progress to measure — it is contention —
  so it is an attempt count against the same half-hour.
- **Each interval has a name**, and each ceiling is `STALL_LIMIT_MS` over it, so the loops cannot
  drift apart from the one they were modelled on.
- **The Editor's source check is brought into the same shape.** It always had a ceiling
  (`INSPECTION_POLLS`) but spelled its interval `5000` and its limit `120` with a comment saying
  "about ten minutes". It is ten minutes now, derived, on its own clock — deliberately not the
  render's half-hour, because it is bounded by the film's length rather than by how long a queue may
  hold a job.

## Acceptance criteria

1. **A cast recording that never moves stops being waited on and costs a note**: the studio reaches
   the final step, the note names the half-hour and how many lines were done, and the loop stops at
   one poll per interval and no more.
2. **A recording that is moving is waited on for as long as it keeps moving**: four times the ceiling
   in polls, with a status change inside each window, finishes with no note.
3. **A sound library that stays busy stops being retried and costs a note**, at exactly the ceiling's
   number of attempts.
4. **Every loop in the studio that waits on the server has a ceiling**: all four waiting loops name
   their interval, name their limit, and end in a refusal.
5. Reverting the two ceilings — keeping everything else — makes this file's suite **not finish**,
   which is the defect rather than a failing assertion.

- Tests: `packages/frontend/test/take-ceiling.test.js`. Verified: with the two `if (… >= …) throw`
  guards removed, `bun test packages/frontend/test/take-ceiling.test.js` was killed at 60 s having
  produced no result.

## Known gaps this leaves

- **The creator is told after half an hour, not during it.** `onProgress` reports how many lines are
  done, and nothing says how long the studio is prepared to wait or how much of that is gone. A
  progress line that counted down would be a different design decision.
- **The score upload's 429 is still a server-global single slot.** This bounds the wait rather than
  removing the contention; two films finishing at once still queue behind each other, and the second
  one now gives up instead of waiting for ever.
- **Nothing retries after the ceiling.** A creator whose takes stalled gets a note and no button; the
  only route back is to ask for the final again, which is free (HV-030-07/HV-030-10) but is not
  offered here.
- **The four loops still have four clocks.** Three share `STALL_LIMIT_MS` and the Editor's check has
  its own ten minutes, which is deliberate — but nothing ties either limit to a measurement of how
  long these actually take.
