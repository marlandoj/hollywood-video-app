# HV-025-14 — The slow picture edit gets bounds and its fast cases

epic: HV-025
release: after Release 3 (the follow-up the roadmap promised when G24 deferred `HV-025.vfx-composite`)
gate: none new (follows G24, which deferred the VFX composite and asked for the slow picture edit to get its own fix)
spend_usd: 0

## Why

G24 (`docs/loop/HUMAN-GATES.md`): Release 3's picture edit with one masked composite (job
`200e977b`) ran for over three hours on private staging and filled the VM's memory. A read-only map of
the code (made on the Zouroboros workshop, 2026-11-10, at `05984fb`) found:

- One composite anywhere sends the whole timeline through the per-pixel RGBA compositor. G24's 30-frame
  overlay put all of the 126-second film (about 3,780 frames) through it.
- The conform runs twice by design (render, then verification by reproduction).
- A job that reached its deadline was queued again from nothing, up to two more times
  (`retryPolicy.maxRetries: 2`), so a 2 h 08 m deadline could become 6 h 24 m.
- Nothing bounded the worker's memory, and no span recorded memory.
- Per frame, almost all of the JS time is a bilinear fit that is a copy for an unmoved film, and a
  float blend that returns the left pixel for an opaque one.

## What this increment does

- **Out of time or memory is final.** `EditResourceLimit` (a subclass of `EditConflict`) is thrown
  for the picture and assembly deadlines and for the new memory cap, and `processNextJob` cancels the
  job with its reason instead of `fail`, which re-queued it.
- **A memory cap beside the deadline.** `editMemoryGuard` checks `process.memoryUsage.rss()` on every
  access call against `HV_EDIT_MAX_RSS_MB` (default 4096 MiB, accepted from 256 to 9,999,999; an empty
  value is refused, not defaulted). Sealing, which hashes every retained file and used to call no
  access check, now runs under the same two-second periodic check as source access, so the deadline
  and the cap hold through every phase. `runWorker` reads the setting at start,
  so a bad value stops the worker by name instead of failing every picture edit. The worker context
  takes `editRss` so tests can inject a reading.
- **Memory on every phase span.** `media.assemble` spans now carry `hv.worker.rss_peak_bytes`, the
  host's `hv.host.mem_cached_bytes`, `mem_dirty_bytes`, `mem_available_bytes` and `swap_free_bytes`
  (from `/proc/meminfo`, absent elsewhere) and `hv.job.retries_used`. The telemetry allow-list
  (`safeAttributes`) admits exactly these.
- **The compositor's two fast cases, byte for byte.**
  - `fitEditCompositeFrame` copies when the clip has no mask, no crop or a full-frame one, no placement
    or an identity one, and a source the timeline's size (`editCompositeFitIsIdentity`): each pixel
    centre then lands on its own source pixel with weight 1 and the other three taps weigh 0. The full
    sampler stays exported as `sampleEditCompositeFrame`, which the test holds the copy to.
  - `blendEditCompositeGroup` copies a full-weight opaque pixel of a single clip: `la` is exactly 1 and
    the background weight exactly 0.
  - The span's five frame buffers are allocated once per conform instead of per span.
- **A reproduction.** `scripts/bench-picture-edit.ts` builds the G24 shape on generated media and
  prints time, peak RSS and a hash over every decoded output frame.
- **Docs.** `docs/PICTURE-EDITORIAL.md` (bounds, attributes, measurements, what is left) and
  `docs/STAGING-LOCAL.md` (the cap, and the host bounds that are the operator's to apply).

## What it deliberately does not change

- **The picture recipe** (`hv-edit-picture/6`) and every output byte. Retained edits keep validating.
- **Composite scope.** Compositing only the spans that hold a composite is the largest remaining win
  for G24, but it changes those spans' output and needs a new recipe (`hv-edit-picture/7`) stored on
  the plan. That is a decision for the operator, recorded here, not taken.
- **Verification by reproduction.** It is the design (`docs/PICTURE-EDITORIAL.md`).
- **The host.** No WSL, cgroup, `nice` or `ionice` change is made by any script; the doc lists them.
- No frozen-list file: nothing in `packages/safety`, `docs/legal`, `docs/adr` or `.github/workflows`.

## Acceptance criteria

1. **Same pictures.** The identity fit equals the full sampler at 64x36, 33x17 and 1280x720 with alpha
   0, 1, 128, 254 and 255, including into a reused target; the opaque blend equals main's loop over
   opaque, transparent and mixed backgrounds and five weightings. The existing composite media tests,
   which hold the real conform to an independent composition across holds, dissolves and seams, pass.
   - Tests: `packages/planner/test/edit-composite-shortcuts.test.ts`,
     `packages/generator/test/edit-composite-media.test.ts`; bench frame hashes below.
2. **Over the cap is cancelled, not retried.** A picture edit whose worker reads over 4096 MiB ends
   `cancelled` with "The editorial render used 5120 MiB, over its 4096 MiB limit (HV_EDIT_MAX_RSS_MB).",
   `retriesUsed` 0.
3. **Past the deadline is cancelled, not retried.** Same, with "The editorial render exceeded its
   processing timeout."
   The same holds when memory is over the cap only while the job is sealing.
   - Tests (2, 3): `packages/api/test/editorial-resource-limit.test.ts`.
4. **The setting is refused by name** for anything but whole MiB from 256 to 9,999,999, an empty value
   included, and defaults only when unset.
   - Test: `packages/queue/test/edit-memory.test.ts`.
5. **Each phase records memory and the attempt.**
   - Test: `packages/api/test/editorial-resource-limit.test.ts` (first case); the existing
     `editorial-render-deadline.test.ts` still sees `render`, `seal`, `verify`.

Build session's container, Bun 1.4.0, ffmpeg, eSpeak NG, 4 CPU. `scripts/bench-picture-edit.ts`,
conform only, one run each, main (`05984fb`) against this branch:

| Shape | main | this branch | Peak worker RSS | Decoded frames |
|---|---|---|---|---|
| 300 frames, 1280x720 | 82.8 s | 42.7 s | 160 / 166 MiB | identical (`654a9d0f…`) |
| 120 frames, 1920x1080 | 87.1 s | 46.9 s | 177 / 210 MiB | identical (`38660ac0…`) |

Worker memory stays flat as the film grows, which points the G24 fill at the host rather than the
worker. That is an inference from these runs; the new span attributes are how a staging run confirms
it.

### Independent review

The workshop (codex) reviewed the patch read-only and found no counterexample to either fast path, no
stale read from the reused buffers, and cancellation ahead of every retry branch in both stores. It
raised two points, both fixed here: sealing ran outside the deadline and memory checks, and the parser
defaulted an empty value and had an unstated upper bound.
