# HV-027-06 — The check runs on the thing it was built for

epic: HV-027
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

HV-026-01 built a quality check on a delivered film. HV-026-03 made it something an operator can
run. HV-026-04 fixed what it claimed when a reading had not been taken. HV-027-01 measured its own
reframes with it — **in a test**. And HV-027-05 ended with this in its own gap list:

> **The quality check still does not run on a deliverable.** HV-027-01 measured its cuts with it by
> hand in a test; nothing measures a delivered file as part of delivering it.

Four increments of check, one increment of deliverable, and the two had never met outside a test
file. A studio that measures a film only when someone remembers to is a studio with no measurement.

## What this increment does

- **Sealing a deliverable measures it**, and the report is retained on the delivery job as
  `DeliveryOutput.quality`.
- **The file is read once.** `measurePictureQc` returns the digest and the size it measured, and
  those *are* the deliverable's digest of record. A lossless master of several gigabytes is not read
  twice to say the same thing.
- **Two readings of one file, made to agree.** The seal's own `ffprobe` still runs independently, so
  `delivered` and `quality.programme` are separate readings taken seconds apart from the same path.
  `assertDeliveryQuality` makes them agree on dimensions, codecs, size and duration, and binds the
  report to the file by `source.sha256`. `validatePictureQcReport` already refuses a report whose
  findings do not follow from its own measurement; this is the half that ties the measurement to
  *this* deliverable. A report moved from another deliverable is refused **even when the output is
  consistently re-sealed around it**, which the test exercises rather than assumes.
- **The creator is shown the verdict, the findings and what was not checked** — never the raw
  measurement, which is the operator's own reading and stays in the retained report. `notChecked`
  travels with the findings, because a check that shows only what it found reads as a clean bill of
  health.
- **A snapshot holding a measured deliverable is `hv-state/15`**, refused to older readers in both
  the TypeScript validator and the Python archive packager, exactly as `hv-state/14` was added for
  the deliverable itself. A deliverable with no measurement is still `hv-state/14`, and that is
  asserted, so the new tier answers a question rather than replacing one.

### The decision this increment did not take

**The verdict does not gate publication.** Every `fail` this check can reach on a deliverable is
inherited from the master the deliverable copies: `silent-programme` and `clipping` come from the
master's own soundtrack, which a reframe and a mezzanine both copy rather than make, and
`audio-missing` cannot fire at all because `validateDeliveryOutput` already requires the delivered
audio codec to be the one the kind promises. So refusing here would make a film undeliverable with
no remedy in the route that refused it — the creator would have to go back and re-finish the film to
get a copy of the film they already finished.

That is a product decision, not a build one. HV-026-01's own framing agrees with leaving it open:
*"anything but pass is a thing to look at, not a failure to ship."* If the operator wants a fail to
block a deliverable, the place is `sealDeliveryJob`, the change is three lines, and this paragraph
is the argument against it.

### What was deliberately not changed

`DELIVERY_TIMEOUT` is untouched. The check adds one decode, and the per-frame allowance is already
3,000 ms for a mezzanine and 1,500 for a reframe — seconds of wall time per frame, against decodes
that run far faster than real time. Above about 2.6 minutes of film the binding constraint is
`maximumMs` (four hours) and not the per-frame figure at all, so raising an allowance that is
already clamped would change nothing except where the clamp bites. Raising it was written, measured
against the test that pins the arithmetic, and reverted.

## Acceptance criteria

1. **A real deliverable carries a real measurement.** In the end-to-end route test, the mezzanine's
   retained report re-derives through `validatePictureQcReport`, its `source` is exactly the file's
   own digest and size, its `programme` names 640×360 FFV1 and PCM, `framesSampled` is non-zero and
   the sound reading is not null — a probe and a decode that produced numbers, not a placeholder.
2. **Each deliverable carries its own.** The square reframe's report names its own bytes and its own
   360×360 H.264 shape, and is a different reading from the mezzanine's.
3. **A foreign report is refused even when the output is re-sealed around it**, and a verdict edited
   under its own measurement is refused by re-derivation rather than by a hash.
4. **The creator's view carries the verdict, the findings and `notChecked`, and not the
   measurement** — asserted by the absence of `programme` and `source`, and by each finding carrying
   exactly `code`, `severity` and `message`.
5. **A measured deliverable is `hv-state/15`**, refused at 14 and at 13 with the new message; an
   unmeasured one is still `hv-state/14`.
6. **Every retained-output fixture still validates**, including the ones that override the file or
   the delivered shape, because the fixture's report follows what it is given.

## Known gaps this leaves

- **Nothing acts on the verdict.** It is retained and shown; no route, worker or persona reads it.
  The obvious next user is the crew — a Finisher persona that reads the findings and says what to
  do about them — and that is HV-030's shape, not this one's.
- **The measurement is not compared with the master's.** The most useful question a creator can ask
  is "did delivering it make it worse", and answering it means measuring the source film too and
  diffing the two reports. The source film is measured by nothing today, so there is nothing to diff
  against; that is a larger increment and it belongs with HV-026's grade half.
- **A reframe's `notChecked` is the same list as a mezzanine's.** It should not be: a crop cannot
  introduce a colour-management problem that its master did not have, and a lossless rewrap cannot
  change levels at all. The list is the recipe's, and narrowing it per kind would mean the recipe
  revision differs per kind, which the report's own `recipeRevision` is not built for.
- **Still no frontend.** The verdict is in the JSON the deliverable list returns and nowhere a
  person looks.
- **The end-to-end test runs on local storage.** The `s3` path seals the same way — the artifact
  reader is what changes — and the object-store suites exercise it in CI, but this test does not.
