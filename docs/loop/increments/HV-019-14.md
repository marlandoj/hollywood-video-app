# HV-019-14 — Routing on measured quality (Release 3 step 10)

epic: HV-019
release: 3 "Features"
gate: none new (cites G20-202610031349: Release 3's build order is agreed, and this is its step 10)
spend_usd: 0

## Why

Release 3's build order, step 10, "Routing on measured quality": "A `quality` routing strategy that
ranks eligible providers by the benchmark's scores, never by invented ones". The parts table's
`HV-019.quality-routing` wants the feature's finals "routed on a measured quality score", with "each
provider plan nam[ing] the benchmark record behind it".

Until now `RoutingStrategy` was `configured | cost | latency`. Nothing in the router could read a
score. HV-037-02 built the measured identity score, the `hv-benchmark-measured/1` record, and
`readMeasuredRecord`. That reader recomputes every score from the fingerprints the record carries, and
refuses edited records and stand-ins. Its doc names this step as the reader's consumer.

## What

**1. A results file, read once and validated** (`packages/benchmarks/src/routing-results.ts`).
`HV_ROUTING_QUALITY_RESULTS_PATH` names one committed file. This follows the existing `HV_*_PATH`
convention, and a relative path is read from the repository root. The file holds one
`hv-benchmark-measured/1` record, or a JSON array with one record per provider spec. It is used only
if every record passes `readMeasuredRecord` with no `allowSynthetic`. It must also be comparable: one
metric, the frozen corpus this build plans (version and sha256), one frame size, one reference set,
no spec twice, 1–16 records, and at most 4 MiB. Any failure refuses the whole file.

The reader never throws at admission. It returns a fallback block that names the reason.

**2. Pinned in the admitted plan** (`packages/generator/src/quality-routing.ts`, `catalog.ts`).
`HV_ROUTING_STRATEGY=quality` adds a `hv-routing-quality/1` block to the job's `hv-provider-plan/1`.
The block holds:

- the file's sha256, the metric and the corpus sha256;
- per measured spec: the provider, model, capability revision, score (`aggregate.identityMean`) and
  scored-shot count;
- or, on a fallback, the `fallback` reason, with no digest and no entries.

The plan carries `quality` exactly when the strategy is `quality`, so the plan's revision covers the
digest. The worker ranks from the plan and never re-reads the file. `validateProviderPlan` validates
the block's shape and bounds: scores in [0, 1], `null` exactly when no shot was scored, and no digest
on a fallback.

**3. The ranking** (`router.ts`, `compareQuality`). Measured providers come first, highest score
first, with ties in configured order. Unmeasured providers follow in configured order with score
`null`. A provider is unmeasured when:

- the file has no record for its spec;
- the record names another capability revision;
- the adapter is synthetic;
- the pass scored no shot;
- or the file was not used.

The frame-anchor native-priority still comes first, as for every strategy. Ranking is the only
change. Eligibility, the per-shot cap, the remaining-budget refresh, circuits, drift and failover are
unchanged, and `quality` is no profile's default.

**4. The decision names it** (`hv-route-decision/1`'s new optional `quality` field, present only on
`quality` decisions). It records:

- `resultsSha256`, `metric` and `fallback`;
- each candidate's `{id, score, reason}`, in ranked order;
- `selectedScore`.

The decision's `strategy` is `quality`, and its `planRevision` covers the pinned block.

**5. Custody re-derives, never trusts.** Three validators recompute a quality decision's scores and
order from the plan's block and refuse any difference:

- the job journal (`DurableJobStore.recordRouteDecision`, and through it the PostgreSQL store). It
  also refuses a `quality` field on any other strategy's decision.
- the execution capture (`shot-execution-capture.ts`, which also re-derives the initial rank);
- the reuse equivalence (`shot-execution-equivalence.ts`).

A quality order is fully determined by the plan, so the equivalence can prove it. It needs no
unrecorded health observation, which `latency` does.

**6. Config.** `docker-compose.yml` passes `HV_ROUTING_QUALITY_RESULTS_PATH` to the API, the only role
that reads it.

## Acceptance criteria

1. **Ranking by measured scores.** With a valid file, the order is the measured providers by score,
   then the unmeasured ones. The highest-scored eligible provider is dispatched. The decision names
   `strategy: "quality"`, the file's sha256, the metric, each candidate's score and reason, and the
   selected score.
   *Test:* `packages/generator/test/quality-routing.test.ts` → "quality ranks eligible providers by their measured score…".
2. **Unmeasured providers rank after measured ones, with score null and the reason.** This covers:
   - no record;
   - a record under another capability revision;
   - a pass that scored no shot;
   - a synthetic adapter, even when a record names its exact revision.

   Each such provider keeps configured order among the unmeasured.
   *Test:* "unmeasured providers rank after measured ones…".
3. **Eligibility and spend limits are unchanged.**
   - A best-scored provider over the cap ranks first and is still skipped for `price`.
   - Every candidate's eligibility, reasons and estimate equal the `configured` decision's.
   - Failover walks the ranked order.
   - The quality plan's pool and `maxShotUsd` equal the configured plan's.

   *Test:* "eligibility, spend limits and failover are the existing ones…", and "admission pins the measured scores…".
4. **A tampered or stand-in file is refused, and the strategy falls back with the reason.** These are
   refused, each with its reason, no digest and no entries:
   - an edited shot score;
   - an edited aggregate;
   - consistently edited scores whose fingerprints disagree;
   - a synthetic record;
   - another corpus;
   - other reference images;
   - a duplicate spec;
   - a wrong schema;
   - 0 or 17 records;
   - non-JSON;
   - no path, or a missing file.

   Through the router, a refused file keeps the configured order. Every candidate's score is `null`,
   the reason starts "not measured: the benchmark results were not used (the results file was
   refused: …", and `selectedScore` is `null`.
   *Test:* `packages/benchmarks/test/routing-results.test.ts` → "a tampered, stand-in or incomparable results file is refused whole…"; `quality-routing.test.ts` → "a tampered or stand-in results file is refused…".
5. **No invented scores.** Every unmeasured candidate in every case above asserts `score: null`. The
   plan's validator refuses these:
   - a score outside [0, 1] or NaN;
   - a score with no scored shots;
   - `null` with scored shots;
   - a duplicate spec;
   - a fallback carrying a digest or entries.

   An edited pinned score fails the plan's revision. A journal entry with an invented score, a changed
   digest or a missing `quality` field is refused, and the job is unchanged.
   *Test:* "the router accepts a quality block only with the quality strategy, and only a valid one", "admission pins…", and `packages/queue/test/routing-custody.test.ts` → "the held journal records a quality decision only with the scores its admitted plan derives".
6. **Selectable the way the other strategies are, and never the default.**
   - `HV_ROUTING_STRATEGY=quality` admits a plan and runs through `processNextJob`.
   - The journal accepts every decision, and the worker seals an execution capture per shot.
   - Both local adapters are synthetic, so both score `null` and the order stays configured.
   - With no `HV_ROUTING_STRATEGY` the plan is `configured`.

   *Test:* `packages/queue/test/quality-routing-worker.test.ts`, and "existing strategies are unchanged…".
7. **Evidence re-derives the quality order.**
   - A capture of a quality route validates.
   - A capture with a reversed rank fails "routing policy".
   - An edited candidate score fails "quality scores", and a dropped `quality` field fails exact fields.
   - Reuse equivalence of a quality route is `consistent`. Reversed candidates fail "admitted routing
     policy", and an edited score fails "quality scores".

   *Test:* `packages/planner/test/shot-execution-capture.test.ts` → "captures reproduce a quality rank…"; `shot-execution-equivalence.test.ts` → "a quality rank is fully determined by the plan's pinned scores…".
8. **Existing strategies are unchanged.**
   - `configured`, `cost` and `latency` plans keep exactly their seven keys and their revision formula,
     even with a results path set.
   - Their decisions carry no `quality` field.
   - Their orders are as before.
   - The existing router, custody, capture and equivalence suites pass unchanged.

   *Test:* "existing strategies are unchanged: no quality block…", plus `router.test.ts`, `routing-custody.test.ts` (first case), `shot-execution-capture.test.ts` and `shot-execution-equivalence.test.ts`.

## Known gaps

- **No results file is committed, so on staging `quality` always falls back today.** The paid pass
  of the corpus is HV-037's next increment, about $10.92 for the two runnable fal models (HV-037-02's
  pricing table), declared there. It must commit its records under `docs/evidence/release-3/` as one
  results file (or an array). Until then, choosing `quality` is harmless: it keeps the configured
  order and every decision says "no benchmark results file is configured" (or why the file was
  refused). `HV-019.quality-routing`'s front-door exercise, the feature's finals routed on a measured
  score, waits on that file.
- **Only the identity score exists to rank by.** It is a whole-frame structural measure, not face
  identity (HV-037-02's known gap). It applies only to models that can render the corpus's character
  shots. The anchored `kling-o3-standard-keyframes` profile G20 chose cannot be benchmarked yet, so it
  will rank as unmeasured behind any measured model in the same pool. The operator should keep that in
  mind before choosing `quality` for a pool that mixes it with measured models.
- **A score belongs to one capability revision.** A price override (`HV_FAL_USD_PER_BILLED_SECOND`)
  moves the revision without changing the picture, and the record then stops counting. This is
  deliberate: the revision is the only identity a record and a pool share. Re-measuring, or a
  picture-only revision key, would be a later decision.
- **The worker does not re-read the file.** The plan pins the block at admission, and the plan's
  revision covers it. The worker trusts an admitted plan, as it does for prices. A file changed after
  admission affects only later admissions.
- **The ranking is per shot over the whole pool, not per shot kind.** A model that scores well on
  character shots ranks first for a landscape shot too. The benchmark's per-shot scores would allow a
  finer rule, but none is built here.
- **`hv-route-ranking/1` (the private initial-rank capture) carries no scores.** They are derivable
  from the plan, and the capture validator re-derives them. Adding them would change a sealed record
  shape for no new evidence.
