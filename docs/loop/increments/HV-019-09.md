# HV-019-09 — A render the vendor had already billed reported no cost at all

epic: HV-019
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

A critic pass over `packages/generator`. Everything in `FalVideoProvider.generate` after the queue
reports `COMPLETED` runs on a clip fal has rendered and **charged for**: reading the result,
downloading the file, normalising it locally, fingerprinting it. Whatever fails there, the money is
spent.

The adapter attached that cost to a local failure only when the model was `anchored`:

```ts
}catch(error){
  if(!anchored)throw error;
  …
  throw Object.assign(failure,{sunkCost:this.costRecord(…)});
}
```

`anchored` is true for exactly one of four models — `kling-o3-standard-keyframes`. The other three
include **`DEFAULT_FAL_MODEL`**. For those, a failed download, a result carrying no video URL, or an
`ffmpeg normalize failed` rethrew bare, and then:

- `sunkCostsOf(error)` found nothing.
- `FailoverGenerator.attempt` set `costs = sunkCostsOf(failure)` — empty — and had nothing to hand
  `onAttemptCost`.
- `chargeCost` in the worker never ran, so the per-shot cap never ran either.
- The film's `costUsd`, `hv_cost_events` and the month's spend were all short by the full price of
  that render. On PostgreSQL the attempt settled `unknown` with `actual_usd = 0` while the adapter
  had the exact figure in hand; on the JSON ledger there was no record at all.

Measured on a stubbed fal that reports `COMPLETED` and hands back an undecodable clip — the same
failure, the same line, two models:

```
kling-v2.5-turbo-pro          ffmpeg normalize failed …   sunkCostsOf(error) = []
kling-o3-standard-keyframes   FrameAnchorError            sunkCostsOf(error) = [{…,"total_cost_usd":0.42}]
```

**And then it paid again.** A plain `Error` is not in `stopped()`, so the router records a health
failure and tries the next candidate with `costs` still empty; when the candidates run out the
worker falls through to `store.fail`, which requeues while `retriesUsed <= maxRetries`, and render
jobs are admitted with `maxRetries: 2`. The failed shot was never checkpointed, so it is dispatched
again. Up to **three billed renders of one shot, none of them in the ledger**. The budget hold is
sized for exactly that — `const attempts = 3` at admission — so the money was reserved; what was
lost was the record of having spent it.

The sibling image adapter has always done this right: `submitted && mayBeBilled ? cost : undefined`.

## What this increment does

- **Every model carries what the vendor billed** when the local half fails. The `FrameAnchorError`
  wrapping stays for the anchored model, because its message is about a paid request that will not
  be repeated; the cost is attached on both branches.
- **A model that refuses *before* it reaches the vendor still charges nothing.** Two of the four
  refuse a request they cannot make — one wants reference images, one wants frame anchors — and
  nothing was spent, so nothing is recorded. A fix that attached a cost to every failure in this
  method would have invented spending, which is the same error in the other direction.
- **The clip URL is checked**, with the rule the image adapter in this same package has always
  applied: `https`, no port, no credentials, no fragment, and a `fal.media` host. It came out of the
  response body and was fetched verbatim — any host, any scheme. The queue URLs were checked by
  `trustedQueueUrl`; the media URL was not.
- **The download is bounded** at 256 MiB, declared or streamed, and written through a sink rather
  than buffered. There was no cap at all: a rogue host could fill the artifact volume before
  anything inspected the file. Measured: 40 MiB accepted from `http://127.0.0.1:…` in the old code.
- **Three synchronous ffmpeg calls get a timeout.** `normalizeClip` and `frameFingerprint` run
  `Bun.spawnSync` on the vendor's bytes, and `DeterministicMockProvider` on its own; none had one,
  while three other synchronous calls in this package (`sound-audio`, `audio-timeline`,
  `graphic-render`) all pass `timeout: 10000` and every asynchronous spawn carries a timer and an
  abort listener. Being synchronous they also stop the timers that *do* exist around them: measured
  on a benign six-second 720p clip, **zero heartbeat ticks in 2.1 s**, and a cancel scheduled 100 ms
  in was never delivered. The lease is five minutes and beats every hundred seconds, so this is not
  a lease loss at those durations — it is that nothing bounded the duration at all.
- **The `sunkCostsOf` comment says which path charges.** It read as though both the result's
  `sunkCosts` and a thrown error's were charged to the job. One is: `attempt` drains a thrown
  failure's records through `onAttemptCost`. The `sunkCosts` it then re-attaches to the error, and
  the field on `FailoverGenerator.generate`'s result, are read by nothing in `packages/queue`,
  `packages/api` or `packages/storage` — and anything that charged them would double-bill every
  discarded attempt and every repair, because `repairLoop` pushes `clip.cost` after `attempt` has
  already charged it.

No provider was called and nothing was spent: the fal endpoint is stubbed throughout, and stubbed to
say the render finished, which is the only case this increment is about.

## Acceptance criteria

1. **A model that reaches the vendor carries the billed cost** on a local failure — both
   `DEFAULT_FAL_MODEL` and `veo3-fast`, with the record naming fal and the right frame count.
2. **A model that refuses before dispatch charges nothing**, by name, for both such models.
3. **The accounted path is handed it**: `generateAttempt` drains exactly one record into
   `onAttemptCost`, which is `chargeCost` in the worker.
4. **An untrusted clip URL is refused** — plain http, a foreign host, a port, a look-alike host, an
   unparseable string — with nothing written, and the billed cost still travelling with the refusal.
   A real `fal.media` host still gets through.
5. **An oversized clip is refused**, declared or streamed, and what was written is bounded.
6. **No `Bun.spawnSync` in this package runs without a timeout**, asserted over the source of all
   five files that use one.
7. Reverting the two source files makes criteria 1 and 3–6 fail; criterion 2 passes either way,
   which is its job.

- Tests: `packages/generator/test/fal-billed-failure.test.ts` (1–6).

## Known gaps this leaves

- **The sunk cost is attached, not reconciled.** A render fal billed and this studio could not use
  is now recorded as spent, which is true and is what the ledger is for. Whether the operator should
  then *ask fal for it back* is a vendor question and there is no reconciliation path for it, here
  or anywhere.
- **`stopped()` still does not name a local post-processing failure.** The router will try the next
  candidate after a billed render failed locally, which spends again — correctly recorded now, but
  spent. Whether a completed-and-billed render whose local half failed should stop the router rather
  than fail over is a spend decision and belongs with the operator, not in a build session.
- **The 256 MiB cap is a number, not a measurement.** No clip this studio asks for approaches it —
  ten seconds at 1080p — and nothing measured what fal's largest plausible response is.
- **The timeouts are bounds, not budgets.** Sixty seconds for a probe and a hundred and twenty for
  an encode are chosen to be far above any real clip and far below "forever". A film whose clip
  genuinely takes longer to normalise will now fail where it used to hang, which is the trade and is
  worth knowing.
- **`Bun.spawnSync` is still synchronous.** A timeout bounds how long the worker is unresponsive; it
  does not make it responsive. Routing these two through the asynchronous `command()` that
  `framing.ts` already has — which takes the `AbortSignal` the callers already hold — is the real
  fix and is a larger change to the adapter's shape.
