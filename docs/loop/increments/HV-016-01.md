# HV-016-01 — A Final Draft script, read into the studio's own screenplay

epic: HV-016
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0 — no provider is called and no dependency is added.

## Why

Release 2's slice of HV-016 is "FDX and PDF import; the crew suggests script revisions the writer
accepts line by line". Today the studio reads exactly one thing: Fountain text, pasted. There is no
importer of any kind — `parseFountain(text: string)` is the only ingest primitive, and an `.fdx`
posted to the screenplay route comes back `422 screenplay contains no parseable scenes`, because
Final Draft's XML contains no `INT.` lines.

Final Draft is the format most writers actually have. It is also the tractable half of the slice:
FULL-SCOPE scopes PDF as "OCR + structure recovery", which is a different problem and has no
precedent anywhere in this codebase, while FDX is a structured file that can be read the way the
retained caption reader is read — by hand, bounded at every step.

## What this increment does

- **`packages/parser/src/final-draft.ts`** — `importFinalDraft` converts a Final Draft script into
  the studio's Fountain, returning the text and **notes** saying what did not come across. Scene
  headings, action, character cues, speeches and transitions are carried; a heading Fountain would
  not recognise is forced with a leading `.` rather than lost; a wrapped action paragraph becomes one
  line.
- **`POST /api/projects/:id/script/import`** converts and shows the result back with the notes, the
  scene count and the parser's warnings. **It commits nothing.** The writer reads what was made of
  their script and saves it themselves through the route they already use, so the project's
  screenplay history still only ever contains text a person chose to save.
- **What cannot be represented is refused by name, or reported** — never skipped:
  - *Parentheticals are not imported.* The studio's screenplay has no parenthetical element, and one
    left inside a speech would be spoken by the voice vendor and burned into the captions. They are
    counted and reported.
  - The title page, and bold/italic/underline styling, are reported; the words are kept.
  - Dual dialogue becomes two speeches in sequence, and says so.
  - An unknown Final Draft element, a character cue the studio's screenplay cannot hold, a speech
    with no cue before it, dialogue before the first scene heading, and a script with no scene
    headings are each refused with a message naming the thing.
- **Written by hand and bounded**, in the shape of `edit-captions.ts`: 4 MiB of document, 20,000
  paragraphs, 20,000 characters per paragraph, 200,000 characters of resulting screenplay. Only the
  five XML names and numeric references to real code points resolve; any other entity, and any
  unescaped `&`, is refused. **A `<!DOCTYPE` or `<!ENTITY` declaration is refused before anything is
  read** — the one construct that can make a parser fetch or expand something the writer never wrote.
  No XML dependency is added, and none is wanted: a general parser would bring exactly that exposure
  to a file a stranger supplies.
- **`docs/SCRIPT-IMPORT.md`**, ending in what is not built.

## Acceptance criteria

1. **A Final Draft script becomes the screenplay the studio reads**, scene for scene and line for
   line: the converted text, parsed by `parseFountain`, yields the headings, action, cues, speeches
   and transitions of the original, with a lower-case cue upper-cased, an unrecognised heading
   forced, and a wrapped paragraph joined — and nothing unparseable left in it.
2. **What could not be carried across is reported**, with a note per kind and only for what the file
   actually contains, and the dropped parenthetical text does not appear in the screenplay.
3. **What cannot be represented is refused with a message naming it**: a document type or entity
   declaration, a non-script document, a file with no content, no scene headings, an unknown element,
   an impossible character cue, an orphan speech, dialogue before the first heading, an empty
   heading, and each of the four bounds.
4. **Only the five XML names and real code points resolve.** An unknown entity, an unescaped `&`, a
   surrogate and a control character are each refused.
5. **The route converts and commits nothing**: after an import the writer's own save is still the
   project's first screenplay version, and a second import writes nothing either.
6. **The route is the owner's**, takes a format it supports, and answers a refusal with its reason.
7. **Nothing else changes.** The parser and api suites pass unchanged, and the paste route, the
   version store and the safety gate are untouched.

- Tests: `packages/parser/test/final-draft.test.ts` with `packages/parser/test/fixtures/lighthouse.fdx`
  (1–4), `packages/api/test/script-import-route.test.ts` (5–6).

## Known gaps this leaves, stated rather than implied

- **PDF import is not built**, and is not a variation on this. FULL-SCOPE scopes it as OCR plus
  structure recovery; the only external-decoder precedent here is the sandboxed ffmpeg the reference
  normaliser uses, and an OCR path needs its own increment and its own honesty about accuracy.
- **Celtx, Highland and Markdown outlines are not imported**, and **no export exists** — the
  screenplay still leaves this studio as Fountain only, though FULL-SCOPE asks for FDX and PDF
  export too.
- **The crew's line-by-line revisions are the other half of this slice** and are untouched here.
- **The importer does not gate the screenplay against the content policy.** That gate runs where it
  always has, per shot at generation, over the combined heading, action and dialogue. Moving a copy
  of it to import time would be a growth of refusals, which is allowed — but it should be a
  deliberate increment with its own test, not a side effect of an importer.
