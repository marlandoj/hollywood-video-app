# HV-030-17 — The read-through sent a tone the plan step refuses to the paid crew model

epic: HV-030
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

The creator's tone goes into two crew prompts.

- **The plan route** reads it with `planInput`. That passes it through the prompt gate
  (`checkPrompt`) and refuses control characters, as for every other string the crew is given.
- **The read-through route**, the first one the creator reaches, read it with `readThroughInput`,
  which only checked that it was a string of 200 characters or fewer.

So a tone like "Like a Taylor Swift music video" went to the Anthropic model in the read-through and
was paid for. The stand-in crew echoed it back in its summary ("Played for …"). The file's own
header says every string passes the same prompt gate as any prompt. The creator found out only at
the next step, when the same tone was refused.

## What this increment does

- **`readThroughInput` refuses a tone that names a real person or falls outside the content
  policy, or that holds control characters,** with nothing sent: the same gate `planInput` applies.
- **Safety refusals only grow:** this adds a place where the gate is checked, not a rule.

## Acceptance criteria

1. **Same refusals as the plan step.** The read-through refuses every tone the plan step refuses
   (a named public figure, a control character). An ordinary tone, or none, is read as before.
2. **Refused before the model.** A refused tone is answered 400, and the crew model is asked nothing.
3. **Ordinary tones still work.** An ordinary tone still reaches the crew model.
4. Reverting `read-through.ts` fails criteria 1 and 2.

- Tests: `packages/api/test/crew-read-through-tone.test.ts`.

## Known gaps this leaves

- **The refusal doesn't say which part was refused.** Like the gate's other refusals, it gives no
  reason. The creator rewrites the tone in their own words.
