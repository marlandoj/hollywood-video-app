# HV-019-10 — The budget decision that read the ledger twice

epic: HV-019
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

`CostLedger.assertCanSpend` is the question the worker asks before every paid attempt: may this shot
spend this much. It answered out of two readings of the ledger file.

```ts
assertCanSpend(jobId, estimateUsd, shot?) {
  this.reload();                                     // reading one
  …
  if (shot && this.shotCapacity(jobId, …) …)         // shotCapacity reloads: reading two
  const r = this.state.reservations.find(…)          // …but this is still reading one
```

The shot's budget was checked against the file as it stood at one instant and the job's against the
file as it stood at another. A spend recorded by another worker between the two was counted by one
half of the decision and not by the other, so the answer the worker got was not an answer any single
state of the ledger justified. It is a JSON file shared between the API and worker processes; the
gap is real, not theoretical.

The cost is the corroboration rather than the point — the parse *is* the call. Measured on a ledger
at four sizes, with `/tmp/claude-0/ledger-probe.ts`:

| events | `record` | `assertCanSpend` (with a shot) | `shotCapacity` alone |
| --- | --- | --- | --- |
| 500 | 0.66 ms | 0.67 ms | 0.28 ms |
| 1,000 | 1.18 ms | 1.00 ms | 0.50 ms |
| 2,000 | 1.97 ms | 2.52 ms | 1.19 ms |
| 4,000 | 3.50 ms | **4.27 ms** | **1.90 ms** |

After:

| events | `record` | `assertCanSpend` (with a shot) | `shotCapacity` alone |
| --- | --- | --- | --- |
| 500 | 0.73 ms | 0.35 ms | 0.35 ms |
| 1,000 | 2.19 ms | 0.57 ms | 0.46 ms |
| 2,000 | 1.79 ms | 1.28 ms | 1.17 ms |
| 4,000 | 3.58 ms | **2.10 ms** | **2.02 ms** |

A decision with a shot now costs what reading the ledger once costs, which is what a decision
without a shot always cost. `worker.ts` asks it once per provider attempt per shot, on the JSON
ledger branch.

## What this increment does

- **A private `shotCapacityOf` computes the shot's remaining budget from the state already loaded.**
  `assertCanSpend` reloads once and calls it; both halves of the decision are then the same reading.
- **The public `shotCapacity` keeps its own reload and its own behaviour.** It is what the API calls
  to show a shot's remaining budget to a caller that has loaded nothing, and it is unchanged.
- **Nothing inside the ledger calls the public `shotCapacity` any more**, which is the shape of the
  defect rather than the one instance of it.

## Acceptance criteria

1. **One decision is one reading of the ledger**: `assertCanSpend` with a shot reads the file once —
   the same number of times as `assertCanSpend` without a shot, and as `shotCapacity` alone.
2. **Both halves are answered from that reading**: with another worker recording a spend against the
   same shot between what used to be the two reads, the decision is the one its own reading
   justifies, and the *next* decision sees the spend and refuses.
3. **Every refusal it made before it still makes, by name**: `invalid generation estimate`,
   `invalid shot budget`, `this shot reached its generation budget`, `this job reached its
   generation budget` — and every allowance too, including the free attempt that is checked against
   the shot but never against the job.
4. **No method in the ledger reaches the public `shotCapacity`**, `assertCanSpend` names `reload`
   once, and `shotCapacityOf` never reloads.
5. Reverting `packages/operator/src/index.ts` fails criteria 1, 2 and 4.

- Tests: `packages/operator/test/budget-single-read.test.ts`. Verified: reverting the source fails 3
  of the 4, and criterion 3 passes either way, which is what makes it the invariant.

## Known gaps this leaves

- **The decision is still not the spend.** `assertCanSpend` answers about the ledger as of the
  moment it is asked; the attempt it admits is recorded later, and `record` does not re-check the
  shot's cap. The shot cap can therefore be crossed by one attempt's estimate, exactly as before —
  this made the decision coherent, not atomic. Only the PostgreSQL ledger's `beginAttempt` closes
  that, and the worker uses it when there is a database.
- **`record` is still linear in the ledger's length**, so a run is quadratic in its own events: the
  4,000-event row above is 3.5 ms per recorded event, and the file is never pruned inside its 30-day
  window. That is the next thing in this file worth measuring, and it is a bigger number than this
  one was.
- **The PostgreSQL ledger does not have this shape, and does not have the shot check either.** Its
  `assertCanSpend(jobId, estimateUsd)` is one query and takes no shot; the worker passes it one
  anyway (`worker.ts:497`) and it is ignored, because on that branch the shot is bounded by
  `beginAttempt` instead. Nothing in the repo asserts that the two implementations refuse the same
  spends, and this increment did not add it.
- **The routing half is a reading of its own.** `RoutedGenerator`'s `availableUsd` callback calls
  `shotCapacity` while choosing a provider, and the worker then calls `assertCanSpend` before
  dispatching to it — two readings during one attempt, now from two call sites rather than from
  inside one method. Making *that* one reading is a larger change to the generator's contract.
