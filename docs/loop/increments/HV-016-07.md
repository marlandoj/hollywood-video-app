# HV-016-07 — A legal XML attribute ended the tag early

epic: HV-016
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

XML requires `<` and `&` to be escaped inside an attribute value. It leaves `>` alone: `a > b` is a
legal attribute value and any conformant writer may emit one. This importer found the end of a start
tag with `indexOf(">")` — three times over, in `element`, in `paragraphs`, and on the `<FinalDraft>`
root — so the tag ended inside the quotes and everything after it was read as content.

What that cost depended on where the character fell. Measured on this repo's own importer:

```
<Text AdornmentStyle="a > b">She waits.</Text>
  action: `b">She waits.`

<Paragraph Number="a > b" Type="Character"><Text>MAYA</Text></Paragraph>
  REFUSED: "This Final Draft script has a speech with no character before it."

<FinalDraft Title="A > B" DocumentType="Script" Version="5">
  REFUSED: "Choose a Final Draft script document. Other Final Draft document types are not imported."
```

The first is this package's own rule broken — *refuse rather than silently drop*. The writer's line
goes into the screenplay carrying stray markup, with no note and no refusal, and from the screenplay
it goes to the shot prompt, to the voice vendor to be spoken, and into the burnt-in captions.

The other two refuse a legal file and **name a cause that is not true of it**. A script whose
paragraph attributes happen to be in a different order is told it has a speech with no character
before it; a script whose root element carries a title before its document type is told it is not a
script. That is the diagnostic failure HV-016-05 was about one file over, where a dropped scene
heading made the parser blame a line that parsed perfectly.

The importer's own header already names the property this breaks: *"Every search here is a linear
`indexOf`, and the bound on the input is therefore also a bound on the work."* The searches were
linear. They were looking for the wrong thing.

This was recorded as an unbuilt finding at the end of HV-016-05 and is the whole of it.

## What this increment does

- **`tagEnd(source, open)`** returns the `>` that closes a start tag, with quoted attribute values
  skipped — both `"` and `'`, since single quotes are legal XML and may hold an unescaped double
  quote.
- **All three sites use it**: `element`, which is how every `<Text>` run and the `<Content>` element
  are read; `paragraphs`, which is how a paragraph's attributes are separated from its body; and the
  root `<FinalDraft>` check.
- **An attribute value that never closes its quote is named for what it is.** `tagEnd` reports it
  separately from "the file simply ran out", and a paragraph carrying one is refused with *"has a
  paragraph with an unterminated attribute value, so its element name cannot be read"*. Such a file
  is not valid XML, and the importer's rule is to refuse rather than guess where the tag ended.

  **This is the one existing message this increment changes.** `final-draft.test.ts` asserted the
  same file was refused with *"element name this importer cannot read"* — which was true only
  because the tag was being read as ending inside the quotes and the `Type` pattern then failed on
  what was left. The file is still refused; the message now describes the defect rather than its
  consequence, and that assertion is updated with the reason written beside it.
- **One forward-only cursor per tag.** The file's stated rule is that the bound on the input is a
  bound on the work, and a per-tag scan that could restart would be quadratic on a file of tags.

## Acceptance criteria

1. **A `>` in a `<Text>` run's attribute does not put markup into the writer's line** — the action
   is the writer's sentence and nothing else — including two in one run and one on the paragraph.
2. **A `>` before the `Type` attribute does not lose the paragraph's element name**: the cue and its
   speech import, and a paragraph reads identically with its attributes in either order. Attribute
   order is the writer's file's business.
3. **A `>` in the root element's attributes does not make a script a different document type**,
   including a single-quoted value holding an unescaped double quote.
4. **A document that really is not a script is still refused, by the same message** — and a
   `DocumentType="Script"` that appears only inside another attribute's escaped text does not
   satisfy the check. A DOCTYPE is still refused before anything is read.
5. **An attribute value that never closes its quote is refused and named for what it is** — "an
   unterminated attribute value" — rather than reported as a missing `>` or as an unreadable element
   name. The existing assertion in `final-draft.test.ts` moves with it, and nothing stops being
   refused.
6. **The whole document is still one pass** — eight times the document, at most twenty-four times
   the work, over three shapes including a paragraph of `>` characters.
7. Reverting `final-draft.ts` fails criteria 1, 2, 3 and 5.

- Test: `packages/parser/test/final-draft-attributes.test.ts`. One assertion in
  `packages/parser/test/final-draft.test.ts` moves to the more precise message, as criterion 5 says;
  the rest of that file is unchanged.

## Known gaps this leaves

- **This is not an XML parser and does not become one.** `tagEnd` knows about quotes; it does not
  know about comments (`<!-- ... >` ... `-->`), CDATA sections, or processing instructions, any of
  which can hold a `>` outside an attribute. None of those appear in a Final Draft export, and the
  DOCTYPE and entity refusal already stands in front of the file; a `<!--` holding `<Paragraph` is
  the shape that would still mislead this reader, and it is not handled.
- **The attribute values themselves are still read with patterns.** `Type` is matched with
  `/\bType\s*=\s*"([^"]{0,200})"/`, which reads a double-quoted value only: a conformant
  `Type='Action'` is not recognised, and falls through to the untyped default rather than being
  refused. That is a second defect of the same family, found while fixing this one, not fixed here.
- **`>` was the only character XML leaves unescaped in an attribute.** `<` and `&` must be escaped,
  so a file carrying them raw is malformed and is somebody else's refusal. Nothing here checks that
  they were.
- **This is the Final Draft importer.** The Fountain parser has its own reader and was not touched.
