# HV-027-10 — A deliverable that failed once could never be asked for again

epic: HV-027
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

`DeliveryApi` treats the same deliverable of the same sealed output as one job, whatever request key
asks for it. That rule exists so that two keys asking for one file don't render it twice and store
it twice:

```ts
const made=mine.find(job=>job.delivery?.idempotencyKey===plan.idempotencyKey);
if(made)return {status:202,body:{jobId:made.id}};
```

The check never asked what had become of that job. Take a 1:1 reframe that the worker refused for
disk headroom, or that ran out of retries, or was cancelled, or whose link had expired. It stayed
"the same job" for good. The creator freed space, asked again with a new request key, and got a
**202 with the failed job's id**. Nothing was queued, and the worker had nothing to pick up. The only
way to get that file was to render the whole film again, which is a paid step for a generated film.
The reproduction showed exactly this:

```
first job status: failed Not enough free disk for this deliverable.
retry returned jobId: e3da66ae-… same as failed job: true
worker picks up: nothing
```

## What this increment does

- **A job is reused only in two cases:** while it is still making the file (`queued` or `running`),
  or once it has made a file that can still be fetched (`done`, with an output the creator's view
  still offers).
- **A failed, cancelled or expired deliverable is admitted again as a new job.** The new job goes
  through the same permission and source checks at admission, and gets its own retained directory.

## Acceptance criteria

1. **A deliverable the worker refused is queued again when the creator asks again.** The new job has
   a different id and the same plan key, and the store then holds `failed` and `queued`.
2. **A deliverable still being made is still the one job, whatever key asks for it.** This holds
   while it is queued and while it is running, and only one delivery job exists.
3. Reverting `delivery-api.ts` fails criterion 1.

- Tests: `packages/api/test/delivery-retry.test.ts`, on the dub-studio fixture with a real picture
  render. The existing delivery route and admission tests pass unchanged.

## Known gaps this leaves

- **The failed job stays in the list**, beside the new one, with its reason. That record is useful,
  but a creator may see two rows for one kind.
- **Nothing retries automatically.** The creator asks again, and the reason the first job failed is
  still shown to them.
- `packages/queue/test/degraded-resume.test.ts` times out at 5 s in this container on main as well.
  This change does not touch it, and it passes in CI.
