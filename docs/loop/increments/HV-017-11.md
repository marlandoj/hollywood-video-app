# HV-017-11 — The one render the locked look did not reach

epic: HV-017
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

A critic pass over the planner's identity code, after HV-017-09 and HV-017-10.

HV-017-09 gave a character a **locked look**: one to four of its own images, in order, recorded on
the cast record, deciding what conditions every render of that character. The module says so in its
own words:

> A render's own reference set, locked or not: the one place that decides what conditions a shot.

`directCast` asks it. `characterSheetShots` did not. It read `character.references` directly, and
always had:

```ts
const referenceAssets=character.references ?? [];
```

So for a locked character the film's shots were conditioned on the locked set in the locked order,
and the character sheet was conditioned on **every image the character held, in upload order** —
including the images the owner had deliberately left out of the look. Exhibited on a character
holding three images and locked to the third and the first:

```
                 film's shot references    sheet's view references
unlocked         c, d, e                   c, d, e
locked [e, c]    e, c                      c, d, e      <- and "Reference image 3 depicts SPUD."
```

A sheet is not an incidental render. **Its views are what the studio adopts as the character's
reference images** — `POST /characters/:id/references` takes the sheet's frames, and HV-017-10 had
already had to teach that route about the lock, because "adopting sheet views over a locked look
failed anonymously through the snapshot validator". So the one render whose output becomes the next
reference set was the one render the lock did not reach, and a locked character's look drifted
through exactly the route that exists to pin it: generate a sheet on the unlocked set, adopt a view,
lock again, generate again on a now-wider unlocked set.

The reason it stayed invisible is the reason HV-029-06's fourteenth listing stayed invisible: two
call sites turned a character into a render's reference set, one of them was taught, and each looked
right on its own.

## What this increment does

- **`characterSheetShots` asks `renderReferences`**, the same function `directCast` asks. The
  numbered map the prompt hands the provider counts the locked set, exactly as the film's does.
- **A guard reads the whole planner.** Every `.references` read in every file under
  `packages/planner/src` is collected with the thing it is read off — comments stripped first,
  because a guard that counts the words in a comment about the defect passes when the defect returns
  — and the whole map is compared against a table naming each read's purpose. A new read in a new
  file fails the test rather than the review. A validation read costs one line and a reason; a
  render read has nowhere to go but `renderReferences`.
- **The film and the sheet are asserted over the pair**: for the same cast, both must equal
  `renderReferences(character)`, across four casts, rather than over one locked example. A third
  call site that answers differently fails here.

Nothing narrows for an unlocked character — `renderReferences` answers `character.references` for
it, which is what the sheet already used — and retained sheet *plans* are untouched, because
`createCharacterSheet`'s definition never named references and so no plan revision moves. What
changes is the reference set and prompt of a **locked** character's sheet views, which is the defect.

## Acceptance criteria

1. **A locked look conditions the character sheet**, in the lock's order, for all five sheet kinds,
   and the prompt's numbered map counts the locked set rather than everything held.
2. **An unlocked character's sheet is what it always was** — everything held, in upload order — and
   a character with no images still names none. This passes before and after, which is its job.
3. **Adopting another image into a locked character changes neither its next sheet nor its prompt**,
   which is the loop the lock exists to stop; unlocked, the same adoption still moves it.
4. **The film and the sheet agree**, asserted over the pair across four casts.
5. **`renderReferences` is the only thing in the planner that turns a character into a render's
   references**, asserted by collecting every `.references` read and its receiver across every file
   in the package and comparing the whole map.
6. Reverting `sheets.ts` makes 1, 3, 4 and 5 fail.

- Tests: `packages/planner/test/sheet-reference-lock.test.ts`.

## Known gaps this leaves

- **Sheets rendered before this increment are not re-rendered.** A locked character whose sheet was
  generated on the unlocked set has images in hand that were conditioned on the wrong set, and
  nothing tells its owner which. They are ordinary retained renders and regenerating is a click; a
  listing of a character's sheets against the lock in force when each was made would close it, and
  that is a view rather than a validator.
- **The guard is textual**, like HV-029-07's. It reads the source for `.references` and its
  receiver; a file that reached the field some other way, or aliased it, would pass. A type that
  made a character's raw image list unusable from a render path would be the real answer, and is a
  change to `CastCharacter` itself.
- **It is the planner only.** `packages/api/src` reads `character.references` in eight places — the
  upload, removal and share routes, and the catalog checks — and none of them builds a render's
  reference set. That was read one at a time while writing this, which is exactly the assurance
  HV-029-07 says is worth nothing on its own. The guard stops at the package boundary because
  `renderReferences` is a planner function and the api's reads are about storage, not conditioning.
- **The lock is still only the reference set.** FULL-SCOPE P2 asks for an embedding and an optional
  per-project fine-tune as well. Nothing here measures whether the pictures that come back resemble
  the images they were conditioned on, and `identityLocks` remains 0 for every adapter.
