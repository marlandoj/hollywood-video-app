# HV-032-04 — Provision a staging host from the repository, and cut staging over to it

epic: HV-032
release: 1 (build order step 4)
gate: G10-202609191100 (the operator's decision to move staging)
spend_usd: 0

## Goal

Private staging runs on the operator's desktop (`docs/STAGING-LOCAL.md`), built from the repository rather than copied from Zo, on PostgreSQL + S3 with three workers and observability.

## Why a script was needed

Zo's staging runtime was assembled by hand before the loop, and several of its parts existed nowhere in the repository:

- its supervisor;
- the startup wrappers `deploy-private-staging.py` reads as templates;
- `edge/edge.ts`;
- its mTLS CA and identities;
- its `secrets.env`.

A second host could only have been made by copying them from Zo. Zo was the thing being moved off.

## What this increment does

**`scripts/provision-staging-host.py`** turns an empty Debian host into a runtime of Zo's shape:

- a supervisord of its own, with XML-RPC on loopback, that exports `HV_SUPERVISOR_CONFIG` and `HV_SUPERVISOR_RPC_URL` to every program, plus a systemd unit to run it;
- the pinned Bun, refused unless it is a regular file reporting `1.4.0`;
- the data directories, and an empty project state;
- the edge, from **`infra/staging/edge.ts`**, which is Zo's file verbatim, now in the repository;
- the wrappers, which are exactly what `deploy-storage-staging.py`'s `wrappers()` writes at cutover;
- the mock-only runtime configuration, which is exactly what `deploy-private-staging.py` writes;
- a private CA, with a server identity for the API and a client identity for the edge;
- `secrets.env`, with a fresh token secret plus the operator's provider keys, copied by name;
- the four application programs.

Two rules hold throughout:

- **Every input is checked before anything is written.** A refusal leaves the host untouched.
- **It overwrites nothing, and prints no secret.**

**Portability defects found by running it:**

- `storage-runtime-launch.py` started the observability restore with `PATH=/usr/local/bin:/usr/bin:/bin` and nothing else. That had two effects:
  - Debian's `useradd` lives in `/usr/sbin`, so it couldn't be found.
  - The supervisor settings were dropped, so the child would have gone back to Zo's supervisor path.

  `host_config.child_environment()` now supplies the service `PATH`, with sbin, and passes through only the two supervisor settings.
- `observability-runtime.py` installs a copy of itself as the launcher `run-observability.py`. Since HV-032-03 it loads `host_config.py` from beside itself, but that module was never copied, so every launch failed on import.
  - This was latent on Zo too, where observability was already down (G9).
  - The module is now copied, and pinned in `runtime.json` as `hostConfigSha256`. The launcher's integrity check refuses it if it is changed or missing.

**The loop now points at the host.**

- `scripts/loop/loop.env` sets `LOOP_STAGING_ROOT=/srv/rough-cut/staging` and exports the supervisor settings.
- `scripts/loop/conveyor.sh` deploys with `deploy-storage-staging.py --release-sha`. The JSON-era `deploy-private-staging.py` refuses a PostgreSQL runtime, so the conveyor's deploy step could not have worked on Zo either since the storage cutover.

**Docs:** `docs/STAGING-LOCAL.md` records the cutover as it ran, and `CLAUDE.md` names the new host.

## What was done on the host (not in the diff)

`docs/STAGING-LOCAL.md`, "Build-session steps", in full. In short:

- **Pinned binaries.** Every binary was verified byte for byte against Zo's: PostgreSQL 15.19, RustFS 1.0.0-rc.5, Bun 1.4.0.
- **Provisioning and cutover.** The host was provisioned, `main` (`0e6ca3d`) was deployed on JSON, the storage platform was prepared with fresh credentials, and it was cut over to `hollywood_video_staging_desktop` / `rough-cut-staging-desktop`.
  - Nine programs are `RUNNING`, three of them workers.
  - A mock animatic job ran to `done`.
- **Observability.** It was installed and enabled, and after the fixes above, Jaeger, the collector and Prometheus all run.
- **Two empty destinations.** Two cutover attempts that stopped before activation, before `projects.json` was seeded, each left an empty, never-activated database and bucket. They are named in the doc and left in place: removing them is a staging deletion.
- **Zo.** Zo's staging was not touched.

## What this increment does not do

- **It does not re-record the Wave A or observability exit evidence.** That needs the host upgraded to a release carrying these fixes, then a collector run against it, and it is the next increment.
- **It does not publish the edge on the tailnet for reviewers.** That's an operator step, taken at the Release 1 review test.
- **It does not remove anything from Zo.**

## Acceptance criteria

1. **An empty host becomes a complete runtime.**
   - Every file and directory is present.
   - The edge equals `infra/staging/edge.ts`.
   - The secrets, wrappers, keys, CA key and supervisor config are private.
   - Each program is registered once.
   - The empty project state is seeded.
   - Tests: `scripts/test_storage_deployment.py`, `ProvisionTests`.
2. **Secrets.** They carry the operator's provider keys by name and a fresh 64-hex token secret. No secret value appears in the script's output.
3. **A second run creates nothing and changes no byte.**
4. **The identities chain to the CA.** The API certificate verifies for `sslserver` and the edge certificate for `sslclient`, but not the other way round.
5. **The configuration matches the rest of the repository.** The supervisor exports the two settings, with a URL `host_config` accepts. The runtime configuration is the one `deploy-private-staging.py` writes and is mock-only. The wrappers are the ones a cutover writes. The edge program stays on loopback.
6. **Refusals leave the host untouched:**
   - an operator file readable by others;
   - a value that isn't a single word;
   - a Bun that is a link or not 1.4.0;
   - a relative root.
7. **The observability restore gets the service `PATH` and only the two supervisor settings.** Tests: `scripts/test_storage_bootstrap.py`, `HostChildEnvironmentTests`.
8. **The launcher carries `host_config.py`, and its integrity check refuses it if changed or missing.** Tests: `scripts/test_observability_runtime.py`.
