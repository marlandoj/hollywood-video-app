# HV-023-03 — One appended edit replayed everything before it

epic: HV-023
release: 2 "Voice and crew depth"
gate: none new
spend_usd: 0

## Why

HV-023-01's own gap, built.

That increment memoized `editHistoryReplay` on the history's own **recomputed** revision, which made
the repeated replays of one save free: `validateEditLibrary` replays every sequence, twice, and
`appendEdit` replays the history it was handed. It could not make the last one free, because the
history `append` produces is content the cache has never seen:

```ts
const next=seal({...,events:[...structuredClone(history.events),{...data,revision:contentHash(data)}]});
editHistoryState(next);   // a full replay, from the root, of what this function just built
return next;
```

So every save still paid one complete replay. Measured on a 256-clip timeline, with the history it
is handed already replayed — which is what a route's own read leaves behind:

| events | a cold replay | `appendEdit` before | `appendEdit` after |
|---|---|---|---|
| 62 | 699 ms | 530 ms | **15 ms** |
| 125 | 1,033 ms | 1,045 ms | **14 ms** |
| 250 | 1,900 ms | 1,800 ms | **22 ms** |
| 500 | 3,811 ms | 4,389 ms | **23 ms** |
| 999 | 9,860 ms | 8,666 ms | **22 ms** |

The append *was* the replay, and grew with the history. Reaching n events takes n saves, so an
ordinary editing session was quadratic in itself: not a limit anyone reaches on purpose, just an
afternoon's work getting slower all afternoon, on a single-threaded server every other project is
also waiting on.

## What this increment does

What the replay of `next` establishes is two things: the prefix, and the one new event.

**The prefix is already established, in the same call.** `appendEdit` replays `history` before it
does anything else, and `next.root` and `next.events[0..n-1]` are `structuredClone`s of exactly
those bytes. That is established by content hash rather than by assumption — recomputing the
revision before consulting the cache is precisely what HV-023-01's first test is about.

So `append` extends that answer by the new event instead:

- **`extendReplay` applies the one event**, performing the loop's own checks for it in the loop's
  own order — the catalog and receipt conflict checks for a `source` operation, the sixteen-original
  ceiling, the non-source branch's `timeline.sources=parent.sources`, and then
  `timeline.revision !== event.timelineRevision`. The new node is the head and nothing points at it,
  so its children are none, and its parent is the old head.
- **It extends an `edit` event appended at the head, and nothing else.** A cursor event selects an
  existing node, and the timeline of a node that is not the head is in no replay's *answer* — only
  the head's is — so `moveEditCursor` still replays. That is the rarer path, and the one whose cost
  is not quadratic in the session. Retaining every node's timeline to cover it would be up to a
  thousand 256-clip timelines per cached history, which is the wrong trade.
- **The result seeds the cache** under `next`'s revision, recomputed like every other entry, so the
  library validation that follows the save is a hit rather than another replay.
- **The thousand-event ceiling is checked in `append`.** It used to be enforced by the replay that
  is no longer always run there, which is exactly the kind of thing removing a broad check loses.

The claim that this agrees with the full replay is not an argument. The test asserts the two answers
are **equal**, over six operation kinds at three history depths, over a source addition on top of a
source addition, and over an edit branching from a cursor move — by replaying the same content under
a different `id`, which is in the revision and in none of the answer, so the cache cannot serve it.

## Acceptance criteria

1. **An appended edit answers exactly what replaying it from the root answers**, for six operation
   kinds at three depths, compared whole.
2. **And so does a source addition on top of a source addition**, with the catalog sorted and both
   receipts held, which is the branch the catalog conflict check guards.
3. **And a cursor move, which still replays, still answers what it always did** — including an edit
   that branches from where the cursor is rather than from the last event.
4. **Appending costs the edit, not the history**: at 999 events, at most a fifth of what a cold
   replay of the same history costs on the same machine in the same test, with the replay's own
   figure asserted to be a real measurement rather than noise.
5. **The seeded answer is an answer about content**: a forged history naming the same revision is
   still refused, and what the cache hands out is still a copy.
6. **The thousand-event ceiling still fires** on the append that would exceed it.
7. Reverting `edit-history.ts` makes 4 fail. 1, 2, 3, 5 and 6 pass either way, which is their job:
   they are the assertion that this increment changed the cost and not the answer.

- Tests: `packages/planner/test/edit-append-cost.test.ts`, and
  `packages/planner/test/edit-history-replay.test.ts` unchanged.

## Known gaps this leaves

- **`moveEditCursor` still replays from the root**, so an undo or a redo at 999 events still costs
  seconds. Closing it means keeping every node's timeline, or keeping a per-node summary and
  re-deriving the target's timeline from the nearest ancestor that is cached — a real design, and a
  larger one than this.
- **The append is still linear in the history**, at about 22 ms at 999 events: `seal` hashes the
  whole history and `append` clones every event into the new one. No version of an append-only
  content-addressed history avoids that, and it is two orders of magnitude below what it replaces.
- **`extendReplay` repeats the loop's checks rather than sharing them.** Two pieces of code must
  agree about what an edit event means, which is the shape HV-031-06 was about. The equality tests
  are what stands between them; a loop factored so that one event's handling is one function, called
  by both, would be better and is a refactor of `replayEditHistory` itself.
- **`validateEditLibrary` still replays every sequence twice per save**, now from the cache. The
  hits are cheap, but the shape — every sequence validated because one changed — is untouched.
