## Traces and metrics

Set `HV_TELEMETRY_ENABLED=1` and `HV_OTLP_ENDPOINT` to a verified HTTPS or loopback HTTP OTLP base URL. Trace sampling defaults to 1; `HV_TRACE_SAMPLE_RATE` can reduce it. `HV_RELEASE_SHA` must be a 40-character hexadecimal commit identifier to appear in the resource. Unset or invalid telemetry configuration leaves rendering functional and disables export.

API actions create new root traces. Anonymous incoming trace headers are ignored. Admitted jobs store a validated W3C carrier, which workers use for job, provider, accounting, checkpoint, assembly, and publication spans. The carrier grants no access. Events, exception bodies, screenplay text, capability URLs, headers, filenames, provider credentials, and raw external errors are excluded. Operational identifiers are allowed in traces; metric labels exclude identifiers and use bounded operation, stage, provider category, outcome, failure code, method, route template, and HTTP status class. The failure code is set only on failed operations, so it multiplies error series alone. `hv.operations` and `hv.operation.duration` each carry a 256-series cardinality limit; the duration histogram uses explicit millisecond boundaries `5, 10, 25, 50, 100, 250, 500, 1000, 2500, 5000, 10000, 30000, 60000, 120000, 300000, 600000`, so a quantile reported at 600 s is a floor, not a measurement.

Export is asynchronous with bounded queues and deadlines. Failed and timed-out exports increment sanitized process counters. Those counters describe delivery attempts; they do not prove that stored traces, metrics, or other worker processes are queryable. Manual API/worker instrumentation is tested with pinned Bun 1.4.0 on Windows and Linux; this is not a claim of official OpenTelemetry support for every Bun API.

## Structured logs

Every line the API, the worker and the PostgreSQL retention sweeper write is one JSON object produced by `StudioLogger` (`packages/observability/src/logs.ts`). Two pre-existing, sanitized lines stay outside it: the sweeper's per-minute `sweptAt` status line, which `scripts/storage-wave-a-evidence.ts` parses and which is unchanged, and the fixed `telemetry.configuration_invalid` line `telemetryFromEnv` writes to stderr before any logger exists.

**Schema.** A line starts with the four fixed keys `ts` (ISO-8601), `level` (`debug|info|warn|error`), `service` (`api|worker|retention`) and `event`, followed only by allow-listed context keys that passed validation: `op`, `stage`, `outcome`, `code`, `traceId`, `spanId`, `durationMs`, `projectId`, `jobId`, `attemptId`, `provider`, `worker`, `method`, `route`, `status`, `jobStatus`, `leaseReason`, `costUsd`, `shots`, `files`, `retryInSeconds`, `port`, `tls`, `storage`, `release`, and `dropped`. A line is at most 2048 bytes. The logger accepts no `message`, `error`, `reason`, `url`, `path`, `headers` or other free-text key; `Error` objects are never serialized, and `failureCode(error)` is the only value derived from an exception.

**Allow-list and validators.** `safeLogFields` maps `projectId`, `jobId`, `attemptId`, `op`, `outcome`, `code`, `provider`, `method`, `route`, `status`, `costUsd`, `shots` and `files` onto the trace validators in `safeAttributes`, so a log can never carry a value a trace could not (`shots`/`files` must additionally be integers). Log-only keys have equally closed validators: `stage` ∈ the `JobStage` union; `jobStatus` ∈ `queued|running|done|failed|cancelled`; `leaseReason` ∈ `not_running|wrong_worker|lease_expired|fence_changed`; `worker` matches `^[A-Za-z0-9_.:-]{1,40}$`; `durationMs`, `retryInSeconds`, `shots` and `files` are integers in `[0, 1e9]`; `port` in `[1, 65535]`; `tls` boolean; `storage` ∈ `json|postgres|local|s3`; `release` 40 lowercase hex; `traceId` 32 non-zero hex; `spanId` 16 non-zero hex. Any other key, any value that fails its validator and any string longer than 128 characters is omitted and counted in `dropped` (absent when nothing was dropped; an `undefined` value means "not provided" and is not counted). An `event` outside the fixed `EVENTS` set produces one `log.dropped` line at `warn` instead of the requested line and never throws.

**Line guard.** After serialization, `guardLine` rejects any line containing `://`, a `Bearer` word, the signed-token wire shape (`[A-Za-z0-9_-]{16,}\.[A-Za-z0-9_-]{16,}`, see `packages/api/src/tokens.ts`) or a run of 64 or more base64 characters, or exceeding 2048 bytes. The rejected line is replaced by `{ts, level: "error", service, event: "log.suppressed", dropped: n}`, where `n` is the number of context keys withheld. Every allow-listed value is bounded, so a production line cannot reach the cap; the guard exists for the path nobody planned.

**Identifier rule (ADR-0018).** Lines may carry `projectId`, `jobId` and `attemptId` because they are random UUIDs minted by the service, scoped by capability tokens, bound to no account, device or person, and already present on traces (see "Operational identifiers are allowed in traces" above). The operator-assigned worker name (`HV_WORKER_ID`) may appear as `worker`; the worker accepts names up to 80 characters, but the log validator keeps only names of at most 40 characters (`^[A-Za-z0-9_.:-]{1,40}$`), so a longer `HV_WORKER_ID` is omitted from every worker line and counted in `dropped` (keep staging names at 40 or fewer). The per-incarnation `workerId`, the provider request id, tokens of every kind, client addresses, forwarded headers, user agents, cookies, URLs, filenames, screenplay text, error messages, provider bodies and credentials are outside the schema: the API logs only `routeTemplate(pathname)`, never the raw path, the `Authorization` header, a request or response body, or the client address computed for rate limiting; the worker never logs a job's `failureReason` or `cancelReason`.

**Trace correlation.** `traceId` and `spanId` are parsed from the active `SpanHandle.carrier()`: a line emitted inside `StudioTelemetry.run`/`http` joins that span, and an explicit `SpanHandle` argument wins over the ambient one. `StudioTelemetry.onOperation` (an optional field set by `loggerFromEnv(service, telemetry)`; the first logger attached to a telemetry keeps the hook, so a shared telemetry keeps one service name) receives every completed operation; the logger turns each completed `provider.attempt` into an `info` `op.finished` line and every other operation except `http.request` and `job.process` into a `debug` one, with the span's ids. When telemetry is disabled (`HV_TELEMETRY_ENABLED` unset) the logger still emits every line but without `traceId`/`spanId`; no substitute request or correlation id is generated, because that would be a new identifier.

**Level and sampling.** `HV_LOG_LEVEL` ∈ `error|warn|info|debug`, default `info`. `HV_LOG_SAMPLE` is a number in `[0, 1]`, default `1`, applied only to `debug` lines and to `api.request` lines with `status < 400`; `warn`/`error` lines and every `worker.*`, `retention.*` and `provider.attempt` line are never sampled out. The decision is trace-consistent: it derives from the last 8 hex digits of `traceId` when present (all lines of one trace are kept or dropped together) and from `Math.random()` otherwise. Unparseable or out-of-range values fall back to the defaults (out-of-range sample rates are clamped) and emit one `log.configuration_invalid` line at `warn`; that line and `log.dropped` bypass the level gate because they are the logger's own health signals; `HV_RELEASE_SHA` appears as `release` only when it is 40 lowercase hex. Below-level and unsampled lines cost one comparison, not a serialization.

**Streams.** `info`/`debug` lines go to stdout and `warn`/`error` lines to stderr, which the supervisor collects into its per-program files (`/dev/shm/<program>.log` and `/dev/shm/<program>_err.log` from `scripts/storage-runtime-launch.py`; rotation settings are unchanged). Nothing is shipped anywhere else, and there is no log query backend; those are later HV-038 increments.

**Event catalogue.**

- `api.started` (`port`, `tls`, `storage`) once the listener is bound; `api.request` per completed request (`method`, `route`, `status`, `durationMs`, `outcome`, `code` on a thrown error), emitted inside the `http.request` span.
- `worker.started` (`worker`, `storage`), `worker.stopped`, `worker.heartbeat_failed` (`warn`), `worker.job_started` (`projectId`, `jobId`, `stage`, `worker`) at the top of the `job.process` span, `worker.lease_lost` (`warn`, `leaseReason`) on both `LeaseError` branches, and `worker.job_finished` in the job's `finally` (`jobStatus`, `outcome`, `code`, `costUsd`, `shots`, `durationMs`; `info` for `done`, `warn` for `cancelled` and for any non-terminal outcome, `error` for `failed`). Callers of `processNextJob` that inject no `logger` are silent, mirroring the disabled default telemetry.
- `retention.failed`, `retention.cache_cleanup_failed`, `retention.incomplete_uploads_failed` (`error`, `retryInSeconds`).
- `op.finished` (`op`, `outcome`, `code`, `durationMs`, plus the operation's identifiers, `provider`, `stage`, `costUsd`, `shots` or `files`) from the telemetry hook.
- `log.dropped`, `log.suppressed`, `log.configuration_invalid` as described above.

**Evidence.** `packages/observability/test/logs.test.ts` covers the validators, the guard, the gates, env parsing, correlation, the hook, stream routing and the byte cap. `packages/observability/test/log-leakage.test.ts` runs the real API and `processNextJob` with canaries (screenplay text, the project token and signing secret, review and artifact tokens, a malformed body echoed by a 400, a throwing adapter whose message carries a sentinel and an `https://` URL, the worker incarnation id) and asserts that no line contains any of them, that every key is inside the schema, that `api.request` and `worker.job_*` lines carry the ids of exported spans and that `dropped` never appears. `docs/evidence/hv038-observability/structured-logs.json` (schema `hv-structured-logs/1`) records one real local run of that fixture and contains no canary value.

## Meaning of the readings

### Stored telemetry explorer

Expand **Stored traces and metrics** in the operator console. Runtime readings continue to refresh every 15 seconds while visible; stored telemetry loads on expansion, search, or **Refresh readings**, so an inspection does not lose keyboard focus or its span page to background polling.

- `GET /api/operator/traces` searches `rough-cut-worker` / `job.process` over the previous 24 hours, at most 20 results. An optional `jobId` must be a UUID. Entering a 32-character nonzero lowercase trace ID opens `GET /api/operator/traces/:traceId` directly. This direct lookup is useful outside the search window while the trace remains retained.
- Trace detail includes only approved operation/service names, trace/span IDs, same-trace parent references, timestamps, durations, job/stage correlation, and bounded outcome/failure categories. Raw tags, log events, exception messages, arbitrary operation names, process metadata and backend warnings are never returned. A detail view shows at most 500 of the stored approved spans, in pages of 50, and states when it is limited. Partial traces cannot establish a job's current or final state.
- `GET /api/operator/metrics` evaluates four fixed PromQL expressions, never a caller-supplied one: one range query over the previous 30 minutes at one-minute steps, and three instant queries evaluated at that range's minute-floored `end` with `timeout=1s` and row limits 30, 128 and 16. The range query returns 5-minute average completed API request and worker job rates per minute, split by success/error. Operator diagnostic routes are excluded from request activity. The four possible series do not include project, job, process, provider request, or URL labels. Missing series/samples remain missing; they are never filled with zero. The chart has an equivalent sample table. The three instant queries fill the additive `reliability` object (`evaluatedAt`, `windowSeconds: 300`, `ceilingMs`, `latency`, `failures`, `providers`). The three row limits are sized from the closed label sets. Latency sits at its ceiling (10 operations x 3 quantiles = 30); failures have headroom at 100 of 128; provider attempts are 6 kinds x 2 outcomes = 12 of 16 since HV-019-02. Widening `Operation`, `FailureCode` or the provider categories without widening the matching limit would make a complete result exceed its `limit` and the panel permanently `unavailable`. The provider headroom is not decoration: a `rate(...[5m])` window spanning a deploy reports the union of the labels the retired build emitted and the labels the new one emits, so a label that is *removed* from the set can still push a complete result over the limit for five minutes. `explorer.test.ts` asserts both the current bound and that every retired member is still a member. `packages/observability/test/explorer.test.ts` fails if a set outgrows its limit. The four run as one bundle under one pending slot, one two-second deadline and one cached reading, and they fail closed together: a hang, an unexpected label value, a duplicate row, a truncation warning or a row over the cap makes the whole reading `unavailable` rather than partial. The route schema stays `hv-operator-metrics/1` and any query parameter is still a 400.
- Query/evaluation timestamps establish when the backend was read, not worker liveness or fresh exporter delivery. The collector expires inactive metric series after two minutes; Prometheus lookback/rate windows can retain historical values longer. Continue to use runtime heartbeat checks for worker health. Sampling, dropped exports and retention can leave incomplete or empty traces.

All three endpoints require the same distinct, short-lived diagnostics token **before** initializing a query client. Project tokens are rejected. Caller-supplied PromQL, hosts, arbitrary filters, ranges and limits are rejected. The only query destinations are the managed loopback Jaeger and Prometheus ports. Redirects and credential forwarding are disabled. `HV_TELEMETRY_ENABLED=1` enables this managed-backend view; remote OTLP export alone does not imply a matching remote query backend.

Each backend allows one pending request, with a two-second response deadline, a 4 MiB decoded body limit and up to eight five-second cached readings. Concurrent identical queries share the pending request; a different query fails promptly while it is busy. Even a transport that ignores cancellation cannot create an accumulating queue. A late aborted reply cannot become a successful cached reading. Failed queries contain no prior value; the UI clearly labels any retained display as stale. Empty available results and an unconfigured backend are distinct states.

The Jaeger search contract follows its [pinned v2.20.0 query parser](https://github.com/jaegertracing/jaeger/blob/v2.20.0/cmd/jaeger/internal/extension/jaegerquery/internal/query_parser.go); metric range parsing follows the [Prometheus HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/). `scripts/telemetry-explorer-smoke.ts` runs only with explicit disposable Linux CI authorization and exercises the actual checksum-pinned Jaeger 2.20.0, Collector 0.160.0 and Prometheus 3.14.0 binaries. It emits synthetic API/worker operations, checks persisted parent correlation and job search, and requires all four positive rate series plus, from the same bundle, a non-null `job.process` p95 latency and a positive `job.process` `provider` failure rate; It also emits one `provider.attempt` per provider kind per outcome, rooted in its own trace so the correlated three-span trace is unchanged, and requires every kind to come back with both a positive success and a positive error rate — twelve rows returned complete under `limit=16`. It prints the observed `latencyOperations`, `failureCodes` and `providerKinds`. Because the bundle fails closed, that job is the only proof that Prometheus 3.14.0 accepts the three new expressions and the instant-query `limit` parameter against the collector's translated metric names. It uses no provider, storage, or deployment credentials and incurs no inference cost.

### Reliability panel

The **Reliability** section of the operator console is read-only; it contains no lever. Its four tables answer different questions from different sources, and each states its own state.

- **Operation latency** comes from the `hv.operation.duration` histogram: p50/p95/p99 per operation over a 5-minute window. A quantile at or above the 600 s top boundary is marked as at the ceiling — it is a floor, not a measurement, and only a wider boundary list would sharpen it. `NaN` and infinities are reported as no usable sample, never as zero.
- **Failure rates** come from the `hv.operations` counter, per operation and failure code, as a per-minute rate with the error share. The code `unknown` covers series exported before this release labelled failures, so it is expected during the roughly five-minute window in which old and new series overlap after a deploy; it is not a distinct failure mode.
- **Provider circuits** are each worker process's own breaker state, written into its existing five-second `hv_workers` heartbeat and read back by the API's isolated read-only diagnostics transaction. Only the latest incarnation of each worker name, with a heartbeat in the last 45 seconds and a state of `idle`, `busy` or `draining`, contributes; at most 64 workers and 24 pool entries each. A reading is therefore at most about 30 seconds old when fresh, and a stale or stopped incarnation contributes nothing. Every body that claims to carry circuits reaches the validator, including one whose `providers` is not an array: entries that fail validation are dropped and counted in `dropped`, never blanked and never filtered away before they can be counted. When more fresh workers report than the 64-row cap can show, the reading sets `truncated` and the console says the table is a subset; `truncated` and `dropped` are separate facts. On the JSON backend there is no worker registry, so this reading is `not_configured` and carries no value at all, which is distinct from `unavailable` — `unavailable` keeps the last verified rows and labels them stale, `not_configured` has no rows to keep. Observed latency is the same EWMA the router ranks on and stays null below three samples. An open circuit does not change the overall runtime status. The attempt rates beside each row come from the metrics bundle, not from the heartbeat. Since HV-019-02 the provider category distinguishes a billing lane from a free one: `rich-animatic` and `rich-animatic-paid` are the same adapter over the free local image renderer and over the paid one, and `anchor-storyboard` has its own label instead of folding into `other`. No registered adapter reaches `other` now, so a row labelled `other` means this build met an adapter it does not enumerate. The category still says nothing about *which* paid model a row used: a per-model label would be unbounded cardinality, which the metric allow-list refuses.
- **Cost by provider** uses the same `hv_cost_events` ledger admission counts against: trailing 24 hours, 7 days and 30 days in the same read-only transaction, at most 16 named providers with the remainder folded into `other`. The 30-day total covers the same window as the budget section's recorded spend and agrees with it to floating-point precision; it is a sum of per-provider sums, not the same arithmetic, so the two are compared with a tolerance rather than for exact equality. Beyond 64 distinct providers in 30 days the per-provider table is a subset and its totals are that subset's subtotal; the reading sets `truncated` and the console says so, exactly as the circuit reading does. `lastDayVsAverage` is the last day's spend divided by the 30-day total over 30; it is null when nothing has been recorded. Recorded costs remain unreconciled with provider invoices. Note that this table keys on the raw adapter name the ledger recorded, not on the bounded telemetry category the circuit table above uses: a rich animatic over the paid fal image model appears as `rich-animatic-paid` in circuits, as `rich-animatic` in the provider-attempt metrics, and as the wrapped image adapter's own name in costs. Reading a circuit row and a cost row as the same provider is therefore a mistake; unifying the three vocabularies would mean either putting an unbounded adapter name on a metric label or rewriting the ledger's recorded provider, and neither is proposed here.
- **Queue depth and running jobs** in this section are the existing database reading, restated next to the rest rather than measured again.

### Runtime and recovery

- Database observations include counts and financial aggregates only. The API still cannot read unscoped project/job bodies. A separate one-connection, read-only pool with statement and connection timeouts keeps monitoring away from admission connections.
- Worker readiness counts the latest incarnation of each worker name, with a heartbeat in the last 45 seconds. Busy workers count toward the expected fleet; draining or stopped processes do not. JSON fallback cannot independently observe worker liveness.
- Media storage performs an authenticated, one-key S3 list request. This proves connectivity and list permission, not every media checksum.
- Spending uses the same trailing 30-day window as admission. Reservations remain visible. A failed read retains the last verified figures and timestamp while marking current capacity unknown. Recorded prices have not been reconciled with provider invoices.
- Backup freshness uses the actual snapshot time, requires successful completion, and becomes stale after five minutes. A fresh snapshot can coexist with a failed retention cycle; that combination is degraded. The current scheduler writes same-host backups, so freshness does not establish off-host RPO or availability. An encrypted off-host transport and a fixtures-only recovery drill now exist and are tested (`docs/OFFHOST-RECOVERY.md`), but no off-host destination is configured, `readBackupStatus` still reports `localRepositoryOnly: true`, and backup freshness still does not establish off-host RPO. The exit evidence keeps the two apart in one place: `recovery.backup` carries the freshness facts (`state`, `lastSnapshotAt`, `lastCompletedAt`, `ageSeconds`, `freshWithin300s`, `failureStage`, `localRepositoryOnly: true`), `recovery.offHostDrill` carries the committed drill's measured packaging figure with its negatives (`provesOffHostRpo: false`, `provesHostLossRecovery: false`, `restoredIntoLiveDatabase: false`, its `independentDestination` string), and the section's own constants are `offHostDestinationConfigured: false` and `lastLiveRestoreAt: null`. `backupFresh` in `observabilityExit` is therefore a statement about a same-host snapshot and nothing else.

Each dependency has at most one pending probe. Concurrent page requests share a collection and short cache; a hung operation has a response deadline without spawning more requests. Failure responses contain fixed operational categories, not source error payloads.

## Exit evidence (loop)

`scripts/observability-exit-evidence.ts` is a read-only collector, modelled on `scripts/storage-wave-a-evidence.ts` and importing its helpers rather than copying them. Run on the private staging host, it writes `docs/evidence/hv038-observability/observability-exit.json` (schema `hv-observability-exit/1`) from what it observes there — the only HV-038 evidence that comes from live state rather than from a fixture. The sections below describe what one run records; the committed run is described in the increment's build notes, and its readings are quoted in the register where they bound a claim.

What it reads, section by section:

- `release` — the release sha, backend and expected worker count from the runtime manifest, through the imported `readDeployment`.
- `telemetryRuntime` — `observability.json` (enabled and root), `runtime.json` (the immutable `sourceSha`), `binaries.json` (the pinned Jaeger 2.20.0 / Collector 0.160.0 / Prometheus 3.14.0 releases), the supervisor state of `rough-cut-observability-collector`, `-metrics` and `-traces`, and the three loopback readiness endpoints `127.0.0.1:15333/`, `127.0.0.1:15686/api/services` and `127.0.0.1:15909/-/ready` (Prometheus redirects `/`, so `/-/ready` is the probe).
- `traces` — one `TelemetryExplorer.recentTraces()` call: window, trace count, the outcome counts, the newest start time, the minimum and maximum span counts, and the closed service set the search is restricted to. `withJobId` is an invariant of that reading rather than a measurement — the explorer keeps only job-correlated traces, so it always equals `traces`, and the block is rejected if it does not. The search itself is pinned to `service=rough-cut-worker`, `operation=job.process` over the previous 24 hours, so a trace that never reached a worker — an API-only request — is invisible to this reading, and a zero here means "no job traces in the window", not "no traces". No trace id, span id, job id, project id or stage value is written.
- `metrics` — one `TelemetryExplorer.metrics()` call: how many of the four series came back and how many carry a sample, plus the reliability bundle's `evaluatedAt`, window, ceiling, and the operation, failure-code and provider **labels** it returned. Because the bundle fails closed, a `recorded` `metrics` section is live proof on the host of what only the disposable `telemetry-contract` CI job proves today: that Prometheus accepts `LATENCY_QUERY`, `FAILURES_QUERY`, `PROVIDER_ATTEMPTS_QUERY` and the instant-query `limit` against the collector's translated metric names. Each method is called once and the explorer is closed, so the one-pending/one-deadline/five-second-cache rule is never raced.
- `logs` — `supervisorctl … tail -65536 <program> stdout|stderr` for `rough-cut-staging-api`, `-worker` and `-sweeper`. A tail that came back at its full 65536-byte budget may have begun mid-line, so its first line is dropped; a shorter tail reached the start of the stream's retained bytes and keeps it. A trailing partial line is always dropped. Every discard is counted in `partialLinesDiscarded`, because a dropped line is a line nobody classified: if the only `guardLine` violation in a stream sat on it, `guardViolations` cannot see it, and the file says how many lines that could be. Each remaining line is classified with `EVENTS`, `LOG_KEYS`, `LOG_LINE_MAX_BYTES` and `guardLine` from `packages/observability/src/logs.ts`, and only counts are recorded: `lines`, `parsed`, `conforming`, per-event and per-level counts, `traceCorrelated`, `unknownKeyLines`, `oversizeLines`, `guardViolations`, `droppedLines`, `suppressedLines`, `configurationInvalidLines`, `knownNonLoggerLines` and `partialLinesDiscarded`. `knownNonLoggerLines` counts exactly the two documented exceptions — the sweeper's per-minute `sweptAt` status line and `telemetryFromEnv`'s fixed `telemetry.configuration_invalid` stderr line — so neither is ever counted as a violation. No line, no key outside `LOG_KEYS` and no field value is copied out.
- `reliabilityPanel` — the same SQL shape `storageDiagnostics` uses (latest incarnation per worker name, heartbeat within 45 seconds, state `idle|busy|draining`, the 65-row over-fetch; the 30-day `hv_cost_events` rollup with its own 65-row over-fetch), run inside one imported read-only `hv_admin` transaction and passed through `providerHealthReadings` and `costReadings`. It records counts and closed labels only — no pool `id`, no project, job or attempt id — and states its vantage: `hv_admin read-only transaction on the host`, with `httpSurfaceRead: false`, because the console's own endpoints need an operator-minted token the collector will not open. The panel's `lastDayVsAverage` ratio is deliberately not copied: the section records `totals.dayUsd` and `dailyAverageUsd` and, as `lastDayVsAverage`, only which of the two is larger (`below`, `at`, `above`, or `null` when nothing is recorded).
- `recovery` — backup freshness through `readBackupStatus` and the committed `offhost-drill.json` re-validated, as described in "Runtime and recovery" above.
- `availability` — the SLI definition and one bounded loopback burst; see the next section.
- `waveA` — the committed `docs/evidence/hv040-storage/wave-a-exit.json` fed through **that** collector's own `validateDocument`, keeping only `recordedAt`, `releaseSha` and `satisfied`. Nothing `storage-wave-a-evidence.ts` records — the database, migrations, workers, object store, readiness, health or CI sections — is measured again here.

Every block is one of three states. `recorded` carries the observed fields. `pending` carries a fixed, whitelisted reason from `REASONS` and null fields; a reason is never raw error text, a URL or an identifier. `not_configured` is distinct and is used only when the host itself states the capability is off — `observability.json` absent, `enabled: false`, or the observability root missing — mirroring the console's own `not_configured` versus `unavailable` distinction. A capability that is on but unreadable is `pending`, never `not_configured`.

`observabilityExit` is derived from the blocks, never asserted, and `validateExitDocument` refuses a document whose booleans do not recompute from its own sections:

- `tracesQueryable` — the `traces` section is `recorded`; stored traces were queryable through the console's own code path. An empty window is a successful reading.
- `metricsQueryable` — the `metrics` section is `recorded`; all four expressions were accepted and every label passed its closed set.
- `reliabilityPanelReadable` — the `reliabilityPanel` section is `recorded`; the circuits and cost readings came back through the panel's own validators.
- `structuredLogsConforming` — every log program is `recorded` with `conforming === parsed` and `guardViolations === 0`, and the three programs together produced at least one logger line. The "at least one" is deliberately a property of the set, not of each program: the retention sweeper writes only its per-minute `sweptAt` status line in normal operation and reaches `StudioLogger` on failure alone, so a healthy sweeper has `parsed === 0`, and a per-program rule would have measured "did every program happen to log during the window" rather than "do the logs conform". A program that said nothing through the logger, with no violation, is conforming; a program nobody could read is not, and pends.
- `backupFresh` — the backup block is `recorded`, its state is `running` or `healthy`, and the five-minute rule holds. Same-host only.
- `instrumented` — the conjunction of those five, and nothing more. Read it as "every reading the console depends on came back through its own code path on the host", not as "telemetry has been observed". The two come apart, and in the committed run they do: the stack answered every query while `traces` was 0, every metrics reliability row was empty, `traceCorrelated` was 0 on all three log programs and all nine provider circuits were `unknown`. A queryable backend with nothing in it satisfies `instrumented`; see "Telemetry produced by the deployed services" in the register.
- `sloClaimed` and `availabilityMeasuredExternally` — structural constants, always `false`.

## Availability SLI and the 99.9 % target

FULL-SCOPE §P15 states a 99.9 % control-plane target. This repository can define that target's indicator precisely; it cannot measure it. Both halves of that sentence are recorded in the evidence file, and **no availability figure is claimed or computed anywhere in this repository** — the exit file contains counts and durations only, and a test fails the build if a percentage or the string `99.9` ever appears in it.

The service level indicator, recorded verbatim in `availability.sli`:

- **Operation** — `GET {edge}/health`.
- **Success predicate** — HTTP 200 within 2000 ms, a JSON body, `service === "hollywood-video-private-staging"`, and `queueDepth`, `runningJobs` and `monthSpendUsd` all present and finite.
- **Excluded from the predicate** — the body's `status` field. `packages/api/src/server.ts` hard-codes it to `"healthy"` on every reply, so it distinguishes nothing and a predicate that consulted it would be measuring a constant.
- **Vantage** — an external prober outside the staging host and its network path.
- **Window** — rolling 30 days, at least one sample per 60 s, announced maintenance windows excluded.
- **Error budget** — a three-nines control-plane target allows 43 m 12 s of failing samples in 30 days; at one sample per 60 s that budget resolves to about 43 samples. The arithmetic is 30 × 24 × 60 × 60 s × 0.001 = 2592 s = 43 m 12 s.

The deeper signal — `GET /api/operator/status`, which knows about workers, budget, object store and backup — cannot serve as the indicator today: it requires a distinct diagnostics credential that an operator mints for 15 minutes at a time, and a long-lived credential held by a prober is exactly what the operator-access design forbids. `/health` needs no credential, which is why it is the operation, and also why the indicator is shallow.

What the collector actually records is one bounded instrument check of that predicate from the host's own loopback: `--availability-samples` requests (default 10, maximum 60), one at a time, one per second, each with a 2000 ms deadline, recorded as `attempts`, `successes`, `predicateFailures`, `p50LatencyMs`, `maxLatencyMs`, `startedAt`, `endedAt` and the vantage `loopback on the staging host`. That burst establishes that the predicate is computable and that the edge answered it during those seconds. It establishes nothing about availability: a loopback sample shares the host's fate, ten samples are not a window, and the section carries `establishesSlo: false`, `measuredExternally: false`, `windowDays: null` and a `blockedBy` list naming the missing external vantage (G3), the credential the deep signal would need (G3), the absence of any declared operating window, and the fact that publishing an endpoint for an external prober to probe is itself fail-closed under ADR-0020 and gate G7.

## Private runtime and restart behavior

The checksum-pinned installer provides Jaeger 2.20.0, OpenTelemetry Collector Contrib 0.160.0, and Prometheus 3.14.0 from their official GitHub release assets. Configuration is copied from an immutable source commit and checked by each binary's own validator. The dedicated `hv-observability` identity runs the three services; their process environments contain only PATH, the observability root, and the Go memory limit. PostgreSQL, S3, signing, and provider credentials are absent.

All nine listeners bind to IPv4 loopback. Application OTLP uses port 15418, Jaeger storage ingestion 15419, Jaeger query 15686/15685, Prometheus query 15909, and local scrape/health endpoints 15464/15888/15889/15333. Collector queues and application exports are bounded. Jaeger retains traces for 48 hours; Prometheus uses two-day and 2 GB retention settings. Heap targets are not hard process or filesystem quotas.

`scripts/observability-canary.ts` emits synthetic telemetry under a separate canary service identity. A live canary's two spans and matching metrics were queried successfully. After restarting Jaeger and Prometheus, both the trace and metrics evaluated at the pre-restart timestamp remained queryable. This verifies service restart persistence, not redundant storage or host-loss recovery.

Zo restarted during installation and discarded the newly created observability directory, while the existing PostgreSQL/S3 deployment and repaired backup scheduler recovered. The pinned installer restored the missing directory. Managed API startup can prepare and restore the optional observability services from the active immutable release in a detached process. Storage readiness and worker progress do not wait for that process. Missing or invalid optional settings disable export; enabling settings takes effect on the next managed process start. A fresh installation cannot reconstruct telemetry data that the host discarded.

Use `scripts/configure-observability.py --runtime RUNTIME --enable` (or `--disable`) to stage the owned settings and separate API diagnostics key, then apply the normal managed release/start workflow. This command does not restart a running job. Startup restoration is separate from ongoing dependency monitoring.

## Deferred from HV-038 (with reason)

HV-038 delivered instrumentation, a read-only operator surface, structured logs, an encrypted off-host transport and the exit evidence above. It did not deliver the following. Each item states what is missing, why it is not here, who or which gate owns it, and what is true today.

- **The 99.9 % control-plane availability SLO claim.** The SLI is defined exactly in this document and in `availability.sli`; nothing measures it. A claim needs a prober outside the host and its network path and a declared operating window — the prober is a vendor or a second machine (G3), and giving it a public target to probe is fail-closed under ADR-0020 and G7. What the exit evidence carries instead: one bounded loopback burst of the predicate, recorded as counts, with `establishesSlo: false`.
- **Multi-region deployment and regional placement.** One host, one region, no replica. A second region needs an account and a provider (G3); the CDN and edge placement it would sit behind are owned by HV-032. Today: nothing regional exists to observe.
- **A real independent off-host destination, a persistent operator identity, a live restore and a five-minute off-host recovery point.** The destination and the long-lived `age` identity need a vendor and a secret (G3); restoring into the live database is an irreversible staging operation (G8). HV-038-03 landed the encrypted transport and a fixtures-only drill, which prove packaging and refusal behaviour and neither of those things. Today: `readBackupStatus` reports `localRepositoryOnly: true` and the exit evidence records `recovery.offHostDestinationConfigured: false`.
- **Continuous replication: WAL shipping, log-shipped standbys and point-in-time recovery.** A destination is not the last thing between today and a short off-host recovery point. Today: `offhost-drill.json` records `continuousReplication: false`, and the exit evidence carries that negative forward in `recovery.offHostDrill.continuousReplication`.
- **The host-loss disaster-recovery drill.** The observability canary proves service-restart persistence only.
