# Managed private storage deployment

The pinned `RUNTIME/bin/bun` must be a regular executable in the runtime, not a symlink into a package cache. Install the verified merged release with `deploy-private-staging.py` while staging still uses JSON. Then run `deploy-storage-staging.py --root RUNTIME --repo CHECKOUT --platform STORAGE_RUNTIME --database hollywood_video_staging --bucket rough-cut-staging` on Zo. Subsequent cutovers require fresh dedicated staging names; evaluation databases and buckets are refused. No source database, source directory or old backup is deleted.

The workflow closes admission, drains jobs, stops services, saves the current JSON source, imports state and every completed/checkpoint media file into fresh private PostgreSQL/S3 destinations, compares record and cost totals, and takes a consistent backup before activating the new backend. Failure before activation restarts the old application. Failure after activation keeps the new database authoritative because new work may already exist.

API startup restores the existing private PostgreSQL and object services plus three worker slots and the backup scheduler. An authenticated database/bucket readiness check releases a gate bound to the current kernel boot and immutable release configuration. Worker and backup service shutdown signals the parent first, giving active work time to finish before a process-group kill fallback. The gate coordinates startup; it is not a continuous availability monitor.

Bucket preparation (`scripts/prepare-object-bucket.py`, run by `prepare-object-storage.py` and the CI storage lane) creates the bucket, applies and verifies the public-access block, and then declares one bucket lifecycle rule, `AbortIncompleteMultipartUpload` with `DaysAfterInitiation: 1`, matching the sweeper's 24-hour application grace so the object store enforces the same policy on its own. The script reads the configuration back and prints `"bucketLifecycle": "declared"`; a store that answers `NotImplemented`, `MalformedXML` or an equivalent unsupported-operation error yields `"bucketLifecycle": "unsupported"` with a successful exit and the public-access block still verified, while any other error or a read-back that differs from the declared rule fails the preparation. The declaration never removes or relaxes the public-access block. Whether a given store reports `declared` or `unsupported` is recorded in `docs/evidence/hv040-storage/object-lifecycle.json` for the store version actually exercised. Bucket preparation runs only at cutover; `deploy-storage-staging.py --release-sha` upgrades never run `prepare-object-bucket.py`, so the live staging bucket carries the rule only after an explicit, operator-approved one-time `prepare-object-bucket.py` run against that bucket (a live object-store configuration change, gate G8 by analogy). Until then the collector below records `lifecycle: "absent"` for it and the application sweeper alone enforces the 24-hour grace.

Private role files keep the API on `hv_api`, workers and retention on `hv_worker`, and backups on `hv_admin`. The API does not inherit the inference key; workers do not inherit capability signing keys; backups and retention do not inherit Zo connector credentials. Database traffic uses client certificates and verified TLS. The bucket blocks public access. Media still passes through the capability-authorized API. The URL shape, token lifetimes, expiry boundary, path rule and revocation levers of that media path are stated in `docs/STORAGE-DELIVERY.md`.

Schema migrations reach the staging database only through `--release-sha`, after admission is closed, the API and edge are stopped, active jobs are drained, the worker and sweeper are stopped and a consistent backup exists; `scripts/migrate-storage.ts` then runs as `hv_admin` and the services restart on the new release. Migration `0015_accounting_capabilities` uses that ordering: it revokes `UPDATE, DELETE` on `hv_reservations` and `DELETE` on `hv_budget_accounts` from `hv_api`, enables and forces row-level security on `hv_budget_accounts`, `hv_reservations`, `hv_cost_events`, `hv_workers` and `hv_operator_reviews`, and adds the per-role, per-command policies the running code needs, so no live API session ever observes a half-applied grant and the unscoped readiness probe (`hv_api` reading the operator cap) passes on restart. The complete privilege and policy matrix, the scope contract and the guard test are in `docs/STORAGE-CAPABILITIES.md`.

To roll back, run `deploy-storage-staging.py --root RUNTIME --repo CHECKOUT --rollback`. It closes admission and drains jobs, exports **current** PostgreSQL state and all media into new directories, validates the export, creates a separate writable JSON copy without the immutable snapshot manifest, removes the extra worker/backup registrations and switches JSON configuration only after every export succeeds. Unresolved provider attempts, reservations or damaged media refuse the switch. New charges are never overwritten by an older ledger. The PostgreSQL database, bucket, source directories and private operation journals remain available.

For another PostgreSQL cutover after rollback, choose a new staging database and bucket. The next import uses the current JSON pointer, including work created during rollback, rather than the original source. The older JSON deployment tool refuses to operate while the PostgreSQL marker or an exported JSON pointer is active. To install a verified merged release while retaining either backend, use `deploy-storage-staging.py --root RUNTIME --repo CHECKOUT --release-sha MERGED_SHA`. This stages immutable files first, drains work, saves current data (a consistent backup for PostgreSQL), applies PostgreSQL migrations when applicable, and updates the release without resetting the active JSON paths. Failed upgrades retain current storage and a private recovery journal; never substitute an older ledger.

Backups run sequentially every 120 seconds with bounded retention and private status records. These are full consistent database snapshots with deduplicated object copies on the same host. They do not provide continuous WAL recovery or off-host disaster recovery. Production RPO and availability targets remain unproven until independent recovery storage and operational evidence exist.

All generated cutover checks use mock providers with the existing $500 monthly and $5 per-shot/animatic caps. Recorded provider cost is not invoice reconciliation.

## Wave A exit verification (loop)

The FULL-SCOPE §9 Wave A exit ("Staging runs on PostgreSQL + S3 with the existing E2E passing; fleet of ≥3 workers") is re-verified by a committed, read-only collector, `scripts/storage-wave-a-evidence.ts`, run on the private staging host against the live runtime. It writes `docs/evidence/hv040-storage/wave-a-exit.json` (schema `hv-wave-a-exit/1`) from what it observes; nothing in that file is typed in by hand. Invocation on the host, from the checkout of the release under test:

```
set -a; source RUNTIME/storage-backup.env; set +a
bun scripts/storage-wave-a-evidence.ts --runtime RUNTIME --repo "$PWD" --output docs/evidence/hv040-storage/wave-a-exit.json
```

`RUNTIME` is the private runtime root (for example `/home/workspace/.runtime/rough-cut-staging-6d439a3`). The `hv_admin` connection and the object credentials come only from the sourced backup role file; the script never opens `secrets.env`, never prints a URL, key or password, and refuses to start if `HV_PG_ADMIN_URL` names a user other than `hv_admin`. `--ci-run ID` pins the CI run instead of listing by sha, `--timeout-ms` (default 120000) bounds every probe, and `--require-satisfied` makes the exit code non-zero when the derived exit is not met; otherwise the exit code is 0 whatever was observed.

What it reads, section by section. `release`: `storage-deployment.json` (the same shape checks as `storage-runtime-launch.py:deployment()`), `active-release.txt` and the release's `.deployed-sha`, which must agree with the manifest. `database`: PostgreSQL `version()`, the number of `hv_*` tables and how many force row security, and the row counts of `hv_projects`, `hv_jobs`, `hv_artifacts` plus `hv_queue_counts()` — no ids, no bodies. `migrations`: rows in `drizzle.__drizzle_migrations` against `infra/drizzle/meta/_journal.json`; `head` is the journal tag whose `when` equals `max(created_at)`, and `inSync` requires `applied === journalEntries` and `head` equal to the last journal tag. `workers`: the latest `hv_workers` row per `body->>'name'` (`distinct on … order by heartbeat_at desc, id desc`, the operator console's rule) whose heartbeat is within 45 seconds and whose state is `idle`, `busy` or `draining`, the expected count from the manifest, the names only, and the `supervisorctl status` state of `rough-cut-staging-worker`, `-2` and `-3`; stale incarnations never count. `objectStore`: a signed `GET /{bucket}?lifecycle` classified as `declared` (200 with `DaysAfterInitiation`), `absent` (404 `NoSuchLifecycleConfiguration`), `unsupported` (501 or an unsupported-operation code) or `pending`; a signed `GET /{bucket}?uploads&max-uploads=1` classified as `supported`, `unsupported` or `pending`; and `sweeper.incompleteUploads` from the last complete JSON status line of the sweeper's stdout (`supervisorctl tail`). `readiness`: `scripts/storage-readiness.ts` run exactly as the launcher runs it, under `storage-api.env` (the `hv_api` role) with the pinned `bin/bun`; the admin connection never reaches that process. `health`: `GET http://127.0.0.1:8081/health` recorded as `serviceStatus`, `queueDepth`, `runningJobs`, `monthSpendUsd`. `backup`: `state`, `lastCompletedAt`, `objects`, `localRepositoryOnly` through `readBackupStatus` on the manifest's backup repository. `ci`: `gh run list --workflow ci --branch main --commit <release sha>` then `gh run view` for the `quality` job's steps `unit + integration`, `three-worker PostgreSQL and S3 flow` and `private staging smoke`.

All database reads run inside a `set transaction read only` block with a `set local statement_timeout`; the only object-store calls are the two signed GETs above; the only child processes are `storage-readiness.ts`, `supervisorctl … status`/`tail` and `gh run list`/`view`. The collector performs no write, `DELETE`, `PUT`, lifecycle declaration, restart or migration against staging.

Fail-closed rule: every section is `recorded` or `pending`. A `pending` section carries a fixed, whitelisted `reason` (never raw error text) and null data fields; a missing or unauthenticated `gh`, a CI run still `in_progress`, a run whose `headSha` differs from the live release sha, a readiness timeout, an unreachable edge, or a manifest that fails the launcher's shape checks each pend that section and only that section. `waveAExit` is derived from the sections, never asserted: `postgresBackend` (release backend `postgres` and the database section recorded), `s3Backend` (object store recorded over HTTPS with the lifecycle and the multipart listing both classified, i.e. authenticated bucket-level answers), `workersRegistered`/`workersExpected` (numbers, or null while pending), `fleetAtLeastThree` (`registered >= 3`, `registered >= expected`, all three supervisor programs `RUNNING`), `migrationsInSync`, `readinessPassed` (`ready`, role `hv_api`, private objects authenticated), `existingE2ePassing` (all three named steps `success` on the exact release sha) and `satisfied`, the conjunction of the six booleans. `health` and `backup` are recorded as context and do not enter the conjunction.

"Existing E2E passing" means, concretely: the CI `quality` job step `unit + integration` (`bun test packages test`, which contains `test/e2e-12shot.test.ts` and the storage lane's `pgtest`/`s3test` cases), the step `three-worker PostgreSQL and S3 flow` (`scripts/storage-fleet-smoke.ts`, the PostgreSQL + S3 + three-process flow against a per-run database and the empty fleet-test bucket) and the step `private staging smoke` (`bun run smoke:runtime`, the offline JSON runtime smoke — it does not touch PostgreSQL or S3). The three-process PostgreSQL/S3 flow is the fleet step, not the staging smoke. Evidence pointer: `docs/evidence/hv040-storage/wave-a-exit.json`; `packages/storage/test/wave-a-evidence.test.ts` re-validates the committed file on every run and recomputes `satisfied` from its sections.

## Deferred from HV-040 (with reason)

HV-040 delivers PostgreSQL as the system of record, S3-compatible private media, row-level capability checks, the archive schemas and the three managed worker slots on the private staging host. It does not deliver the items below; each names the epic or gate that owns it so the G6 acknowledgement of HV-040 is of a bounded, stated scope.

- **CDN delivery and regional placement.** Media is served through the capability-authorized API from one host; there is no edge/CDN vendor, no regional bucket and no cache tier. Adding a vendor is gate G3; the work is owned by HV-032.
- **Off-host replication, a 5-minute RPO, multi-region and disaster-recovery drills.** Backups are same-host snapshots every 120 seconds with `localRepositoryOnly: true`; no independent recovery storage exists and no restore drill from another host has been run. Owned by HV-038 (draft PR #19). Until then production RPO and availability targets remain unproven, as stated above.
- **Public publication of the archive schemas.** HV-040-04 fixed in-repo `urn:` identifiers only; publishing them is HV-033 behind gate G7 and ADR-0020 (no public surface before launch).
- **Per-review-link artifact revocation.** Media access is revoked per project (takedown, retention, secret rotation), not per review link; a per-link lever needs a versioned token payload (`docs/STORAGE-DELIVERY.md`). Future HV-040-0N or HV-029.
- **The `coalesce(current_setting('hv.project_id', true), '') <> ''` guard on the 0001 `*_capability` policies.** Migration 0015 adds that guard to the accounting policies; the 0001 project-scoped policies compare `project_id = current_setting('hv.project_id', true)` without it. That is safe today because `''` never equals a project id (the guard test in `packages/storage/test/capability-coverage.test.ts` proves the `''` refusal), but uniformity needs an additive `ALTER POLICY` migration; the hashed 0001 file is never edited.
- **The bucket-level `AbortIncompleteMultipartUpload` rule on the live staging bucket.** `--release-sha` upgrades never run `prepare-object-bucket.py`, so the live bucket answers `NoSuchLifecycleConfiguration` (a signed `GET ?lifecycle` on 2026-09-14 did; the evidence file records `objectStore.lifecycle` as the collector sees it on each run) and the application sweeper alone enforces the 24-hour grace. Declaring it is a one-time, operator-approved `prepare-object-bucket.py` run against the live bucket — a live object-store configuration change, gate G8 by analogy — and is not done by the loop.
- **`docs/evidence/hv040-storage/object-lifecycle.json` stays `pending`** unless the drill in `packages/storage/test/incomplete-uploads.test.ts` is re-run on the host's native PostgreSQL/RustFS with a per-run database and the dedicated empty fleet-test bucket; likewise `worker-fleet.json` keeps its 2026-09-05 recording unless `scripts/storage-fleet-smoke.ts` is re-run on the same services. Neither is a staging write, and neither is required for the Wave A exit.
