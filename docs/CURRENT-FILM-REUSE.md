# Canonical film reuse contracts

The version-three plan represents each target slot as either fresh generation or a selected successful original take. It retains each source binding once in a bounded catalog. The choice includes the original receipt, slot, input and render-record revisions, together with a recomputed execution review. Changing the source, target or review invalidates the plan; an unavailable selection never falls back to generation implicitly.

The reuse review compares the actual captured provider emission, including prompt, both seed channels, scalar parameters, reference order and digests, anchor positions, pinned provider policy, repair choice and native speech inputs. It retains the original successful attempt rather than predicting a new stochastic result. Native speech comparison follows the selected provider's recorded runtime, line performances and sample timing. Source and target must also share the checked physical document and shot lineage. Moving an unchanged scene can preserve its media while changing its target input revision. Different camera, duration, seed, spoken performance or provider policy prevents adoption.

An adoption record specifies the exact original, carrier and new owned path for each media role. It does not rewrite the original shot record or execution capture. The original evidence stays in the plan's source catalog; the wrapper binds that evidence to the new target and physical correspondence. Its deterministic copy specification does not itself prove that files exist, that the carrier is held by the service, or that current permissions allow access.

The selected-role media helper uses an authenticated carrier reader, exclusive destination creation and bounded asynchronous copying. It checks current access and cancellation throughout the operation, verifies every published role's size and digest, and reuses the original native PCM and decoded-frame verifier in a private scratch namespace. Failed copies remove only directories created by that invocation. Restored verification uses the owned roles without requiring the original or carrier directory. These selected copies do not yet retain the complete original film inventory required for restoring a future mixed job.

The mixed authority check requires the exact current target, current source permissions and the actual carrier snapshots supplied under the service's admission or worker fence. It rechecks expiry and permissions even after successful historical validation. Successful immutable plan replay uses a bounded full-content digest cache; descriptors, capacity and the entire content remain checked on every call. The cache contains no permission or media-verification result.

Version-three checkpoint rows distinguish generated records with their actual captures from reused adoption records. Both bind their exact ordered target slot and measured frame count. A generated capture must match the held new job's route journal. Original source routes cannot be imported into that journal. Advancing a checkpoint preserves every previously recorded row and rejects changed counts, replaced takes and missing historical progress. Metadata validation remains separate from verification of copied media and current authority.

These modules currently define and test planning, authority and progress contracts. They do not activate version-three admission, worker processing, output, source inspection or archive restoration. Version-two runtime discriminators remain strict. The next integration must resolve authenticated carriers and live permissions under the held job, verify owned media before checkpointing, assemble and index adopted media without changing original captures, and prove resume and independent database/bucket restoration with the actual mixed worker. Independent restoration also requires a complete retained inventory for each original source; selected shot roles alone do not satisfy the existing source receipt's full media inventory.

Tests use real no-cost version-two worker output, including repeated physical dialogue lines, scene insertion and a subsequently reordered scene. A separate all-fresh render verifies the reordered dispatch and resulting still/native audio bytes against the original. Checkpoint tests combine authentic fresh target-owned records with adoption metadata. These are evidence for the contracts, not a claim that a version-three render has avoided provider calls or completed the structural owner workflow.
